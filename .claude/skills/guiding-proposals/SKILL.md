# Proposal 规范指南

## Interview 模式

当用户表达想法但信息不完整时，**使用 `AskUserQuestion` 工具主动采访用户**收集必要信息，而非假设。

### ⚠️ 强制规则

1. **必须完成 3 轮采访**，不得跳过或提前结束
2. **采访结果用于填充模板**，禁止直接拷贝模板占位符
3. 每轮必须等待用户回答后，才能进入下一轮

### 触发条件

- 用户说"有个想法"、"想做个功能"但未提供完整信息
- `/propose` 参数不完整或缺失
- 用户不确定功能应归属哪个终端

### 采访流程（3 轮 6 维度）

使用 `AskUserQuestion` 工具，**options 根据上下文动态生成**：

```
Round 1 (What): 做什么？在哪？
    ├─ Q1: 终端（根据描述推断 2-3 个选项）
    └─ Q2: 问题/痛点（根据终端特性提供常见痛点）
           ↓
Round 2 (Why): 为什么？给谁？
    ├─ Q3: 业务价值（解决后能带来什么？）
    └─ Q4: 目标用户（根据终端推断）
           ↓
Round 3 (How): 怎么做？
    └─ Q5: 期望方案（根据问题推断可能方向）
           ↓
自动推断: 影响范围、技术复杂度、User Story
```

| Round | 问题     | options 策略                                  | 对应模板章节        |
| ----- | -------- | --------------------------------------------- | ------------------- |
| 1     | 终端     | 根据功能描述推断最可能的 2-3 个               | 影响范围-涉及终端   |
| 1     | 问题     | 根据终端特性提供常见痛点                      | 背景和动机-问题描述 |
| 2     | 业务价值 | 效率提升/成本降低/体验改善/合规需求           | 背景和动机-业务价值 |
| 2     | 目标用户 | **必须从 [rules.md](rules.md#终端用户映射) 映射表选择** | 背景和动机-目标用户 |
| 3     | 期望方案 | 根据问题推断可能的方案方向                    | 解决方案概述        |
| 推断  | 影响范围 | 根据方案自动推断涉及模块                      | 影响范围-涉及模块   |

**示例：用户说"结账时想快速选择支付方式"**

```yaml
Round 1: AskUserQuestion
  question: |
    关于这个功能，请回答：
    1. 主要在哪个终端使用？
    2. 目前遇到什么问题？
  options:
    终端:
      - pos: 收银端结账流程
      - assistant: 助手端辅助收银
    问题:
      - 支付方式太多，选择慢
      - 常用支付没有快捷入口
      - 其他（请描述）

Round 2: AskUserQuestion
  question: |
    1. 解决这个问题能带来什么价值？
    2. 这个功能主要服务谁？
  options:
    价值:
      - 提升结账效率
      - 减少顾客等待
      - 降低操作错误
    用户:  # 从 rules.md 终端→用户映射表选择，pos 对应：
      - 收银员（主要）
      - 店长（次要）

Round 3: AskUserQuestion
  question: "你期望怎么解决？"
  options:
    - 添加快捷支付按钮
    - 记住上次支付方式
    - 自定义支付方式排序
    - 其他
```

**原则：减少用户输入，提供智能推断的选项**

### 采访完成后

**只有完成 3 轮采访后，才能生成提案文件。**

1. **生成命名**: `{app}-{feature-name}`，feature-name 从用户描述中提炼英文 kebab-case
2. **填充模板**: 用采访结果填充 [template.md](template.md)，**禁止保留占位符**
3. **创建文件**: `docs/team/proposals/{YYYY-MM}/{name}.md`

### 采访结果 → 模板映射

| 采访维度 | 填充到模板章节        | 填充内容                         |
| -------- | --------------------- | -------------------------------- |
| Q1 终端  | 影响范围-涉及终端     | 勾选对应终端                     |
| Q2 问题  | 🎯 背景和动机-问题描述 | 用户描述的痛点                   |
| Q3 价值  | 🎯 背景和动机-业务价值 | 效率/成本/体验/合规              |
| Q4 用户  | 🎯 背景和动机-目标用户 | 勾选对应用户                     |
| Q5 方案  | 💡 解决方案概述        | 方案描述 + 核心功能点            |
| 推断     | 影响范围-涉及模块     | 根据方案推断                     |
| 推断     | 📊 初步评估-技术复杂度 | 根据方案推断复杂度               |
| 推断     | 📝 附录-User Story     | 作为{用户},我想{方案},以便{价值} |

**示例填充：**
```markdown
## 🎯 背景和动机
### 问题描述
<!-- ❌ 错误：保留占位符 -->
[当前存在什么问题？]

<!-- ✅ 正确：用采访结果填充 -->
目前 POS 端结账时，支付方式列表较长，收银员需要滚动查找常用支付方式，影响结账效率。

### 业务价值
- 提升结账效率约 30%
- 减少顾客等待时间
```

## 命名规则

**格式:** `{app}-{feature-name}`

- **app**: pos | shop | kds | qds | assistant | tablet | mobile | menu | member | kiosk | all
- **feature-name**: 英文 kebab-case，2-4 个单词

**示例:** `pos-quick-payment`, `shop-report-export`, `all-dark-mode`

## 目录结构

```
docs/team/proposals/
├── README.md        # 提案索引
└── {YYYY-MM}/       # 按月归档
    └── {app}-{feature}.md
```

## 创建提案

```bash
/proposal:create pos-quick-payment
```

## 状态流转

```
待评审 → ✅ 已批准 → 创建 Spec
       → ❌ 已拒绝
       → 🔄 需修改
```

## 评审通过后

1. 创建 Spec: `/spec:create story-{app}-{feature}`
2. 更新提案状态为 `✅ 已批准`
3. 填写 `关联 Spec` 字段
