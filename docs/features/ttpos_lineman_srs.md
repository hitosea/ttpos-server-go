# ttpos 与 LINE MAN 集成需求规格说明书 (SRS)

## 1. 引言

### 1.1 目的

本文档旨在详细说明 ttpos 后端系统与 LINE MAN 外部平台进行集成所需的所有软件功能和非功能需求。本 SRS 将作为项目开发、测试和验收阶段的正式依据，确保所有相关方对系统功能和性能要求达成一致。

### 1.2 范围

本 SRS 详细阐述了 ttpos 系统与 LINE MAN 平台之间的集成范围，涵盖以下核心领域：
*   **用户认证：** ttpos 与 LINE MAN 之间的 API 访问认证机制。
*   **菜单数据同步：** ttpos 向 LINE MAN 推送菜单信息，并响应 LINE MAN 的菜单同步请求。
*   **订单实时处理：** LINE MAN 向 ttpos 推送新订单详情，以及订单状态和编辑更新通知。
*   **门店营业状态控制：** ttpos 控制门店在 LINE MAN 平台上的开店/关店状态。

不属于本 SRS 范围的功能包括：ttpos 内部业务逻辑、LINE MAN 平台内部功能（除非与集成直接相关）、非上述明确集成点之外的任何第三方系统集成。

### 1.3 定义、缩略语和缩写

*   **ttpos:** 本地收银系统（Point of Sale）。
*   **LINE MAN:** 泰国领先的按需服务平台。
*   **SRS:** 软件需求规格说明书 (Software Requirements Specification)。
*   **API:** 应用程序编程接口 (Application Programming Interface)。
*   **OAuth 2.0:** 开放授权 2.0，一种行业标准的授权协议。
*   **Client Credentials Grant:** OAuth 2.0 授权模式之一，用于客户端（非用户）获取访问令牌。
*   **HTTPS:** 超文本传输安全协议，用于在计算机网络上进行安全通信。
*   **UUID:** 通用唯一标识符 (Universally Unique Identifier)。

## 2. 总体描述

### 2.1 产品透视

ttpos 系统是一个独立的本地餐饮收银管理系统。本次集成项目旨在将 ttpos 系统与 LINE MAN 平台连接，实现线上订单的无缝处理和菜单数据的自动化管理，以扩展商家的线上运营能力。在此集成中，ttpos 系统作为核心业务管理系统，LINE MAN 平台作为外部销售渠道和订单来源。双方通过定义好的 API 接口进行数据交换和业务协同。

### 2.2 产品功能

ttpos 系统与 LINE MAN 集成后将具备以下主要功能：

*   **认证管理：** ttpos 能够通过 OAuth 2.0 Client Credentials 模式获取和刷新 LINE MAN API 的访问令牌。
*   **菜单同步：** ttpos 能够向 LINE MAN 推送完整的菜单快照，确保线上菜单与本地 POS 菜单一致。同时，ttpos 能够响应 LINE MAN 发起的菜单重新同步请求。
*   **菜单状态更新（可选）：** ttpos 能够实时更新单个菜单项（或其选项）在 LINE MAN 平台上的可售状态。
*   **新订单接收：** ttpos 能够接收 LINE MAN 平台推送的新订单详细信息，并自动录入到 ttpos 系统进行处理。
*   **订单状态更新通知（可选）：** ttpos 能够接收 LINE MAN 平台推送的订单状态变更通知（如订单完成、取消）。
*   **订单编辑更新通知（可选）：** ttpos 能够接收 LINE MAN 平台推送的订单编辑后的最新详情。
*   **门店营业状态控制（可选）：** ttpos 能够控制门店在 LINE MAN 平台上的营业状态（开店/关店）。

### 2.3 用户特征

主要用户为**商家操作员** (ttpos 后台用户)。他们需要：
*   在 ttpos 系统中方便地管理和更新菜单，并确保其同步到 LINE MAN 平台。
*   查看并处理来自 LINE MAN 的订单。
*   在需要时通过 ttpos 系统控制门店在 LINE MAN 上的营业状态。
*   清晰地了解菜单同步和订单处理的反馈信息，例如同步结果、错误提示。

### 2.4 限制

*   **认证协议：** 必须严格遵循 OAuth 2.0 Client Credentials 授权模式。
*   **通信协议：** 所有 API 调用必须通过 HTTPS 进行安全传输。
*   **菜单同步模式：** 目前仅支持 ttpos 向 LINE MAN 推送完整菜单快照的模式，不支持 LINE MAN 主动拉取或增量同步。
*   **API 响应时间：** 本地服务间的 API 响应时间要求在 200ms 以内。
*   **可选功能：** 某些功能（如菜单状态更新、订单状态/编辑更新、门店开关控制）是可选的，需根据具体业务需求决定是否实现。
*   **IP 白名单：** LINE MAN 平台可能强制要求 IP 白名单，ttpos 部署环境需能满足此要求。

### 2.5 假设和依赖

*   **LINE MAN API 稳定性：** 假设 LINE MAN 平台提供的 API 接口稳定、可靠，且文档准确。
*   **网络连接：** 假设 ttpos 系统与 LINE MAN 平台之间存在稳定可靠的网络连接。
*   **ttpos 基础功能：** 假设 ttpos 系统已具备完善的订单管理、菜单管理和门店管理的基础功能。
*   **数据一致性：** 假设 ttpos 系统具备处理数据一致性冲突的能力，尤其是在菜单和订单同步时。
*   **消息队列/事件总线：** 假设 ttpos 内部已建立有效的消息队列或事件总线机制来处理异步通知和触发。

## 3. 特定需求

### 3.1 功能需求

本节详细描述 ttpos 与 LINE MAN 集成所需的所有功能需求。

#### 3.1.1 认证模块

*   **FR-AUTH-1 ttpos 获取访问令牌**
    *   **描述：** ttpos 系统应能够通过 HTTP POST 请求向 LINE MAN 的 OAuth 2.0 认证端点发送 Client Credentials（Client ID 和 Client Secret），以获取用于后续 API 调用的访问令牌 (Access Token)。
    *   **输入：** `client_id` (STRING), `client_secret` (STRING), `grant_type="client_credentials"`。
    *   **输出：** JSON 格式的 Access Token, Token Type (Bearer), Expires In (秒)。
    *   **错误处理：** 当认证凭据无效、LINE MAN 认证服务不可用或返回其他错误时，ttpos 应记录详细错误日志，并具备重试机制或触发警报通知管理员。
*   **FR-AUTH-2 LINE MAN 验证 ttpos API 请求**
    *   **描述：** LINE MAN 系统应能够验证所有来自 ttpos 的 API 请求头中包含的访问令牌的有效性（包括但不限于令牌格式、有效期、签名）。
    *   **输入：** API 请求头中的 `Authorization: Bearer <Access Token>`。
    *   **输出：** 验证成功（允许请求继续处理）或验证失败（返回 401 Unauthorized）。
    *   **错误处理：** 当访问令牌无效、过期或缺失时，LINE MAN 应返回标准的 401 Unauthorized HTTP 状态码及错误信息。
    *   **可选需求：** 如果 LINE MAN 启用 IP 白名单，LINE MAN 系统应额外验证 ttpos 请求的源 IP 地址是否在预配置的白名单列表中。如果不在白名单，应拒绝请求并返回适当的错误码。

#### 3.1.2 菜单同步模块

*   **FR-MENU-1 ttpos 推送完整菜单快照至 LINE MAN**
    *   **描述：** ttpos 系统应能够将当前门店的完整菜单数据（包括所有菜品、类别、选项、价格、图片URL、可售状态等）作为一个快照，通过 HTTP POST 请求推送到 LINE MAN 的菜单同步 API。
    *   **触发条件：**
        *   ttpos 后台菜单数据发生任何增删改变化时，自动触发菜单同步。
        *   商家操作员在 ttpos 后台手动触发菜单同步。
    *   **输入：** 完整的菜单数据结构（JSON格式），包含所有必要的菜单属性。
    *   **输出：** LINE MAN 菜单同步 API 的响应（例如，成功、失败、处理ID）。
    *   **可选需求：** ttpos 应能够接收 LINE MAN 通过 "Menu sync notification" API 回调的菜单同步结果通知（成功或失败），并据此更新 ttpos 内部的菜单同步状态。
    *   **错误处理：** 当网络请求失败、LINE MAN API 返回错误或处理超时时，ttpos 应记录详细错误日志、触发警报，并实施合理的重试策略。
*   **FR-MENU-2 LINE MAN 请求 ttpos 重新同步菜单**
    *   **描述：** ttpos 系统应能够接收 LINE MAN 通过回调机制发送的“触发菜单同步”请求，并立即响应，执行一次完整的菜单快照推送（即调用 FR-MENU-1）。
    *   **触发条件：** LINE MAN 系统调用 ttpos 的 "Trigger sync menu" 回调 API。
    *   **输入：** LINE MAN 的触发请求（可能包含门店ID等）。
    *   **输出：** ttpos 再次调用 LINE MAN 的 "Menu sync" API 的结果。
    *   **错误处理：** 如果 ttpos 无法响应 LINE MAN 的触发请求或在重新同步过程中发生错误，应记录日志并触发警报。
*   **FR-MENU-3 ttpos 更新单个菜单项状态至 LINE MAN (可选)**
    *   **描述：** ttpos 系统应能够向 LINE MAN 的“更新菜单项状态”API 发送请求，以实时更新单个菜品或菜单选项的可售状态。
    *   **触发条件：** 商家操作员在 ttpos 后台修改某个菜单项（或其选项）的销售状态（例如，标记为售罄、恢复可售、暂停销售）。
    *   **输入：** 菜单项（或选项）的唯一标识符（UUID），以及目标销售状态（AVAILABLE, SOLD_OUT_TODAY, SUSPENDED）。
    *   **输出：** LINE MAN 状态更新 API 的响应。
    *   **错误处理：** 当 API 调用失败、LINE MAN 返回错误（例如，未找到对应菜单项）时，ttpos 应记录错误日志并触发警报。

#### 3.1.3 订单处理模块

*   **FR-ORDER-1 LINE MAN 推送新订单详情至 ttpos**
    *   **描述：** ttpos 系统应能够作为一个 HTTPS 回调服务，接收 LINE MAN 通过 "Place order notification" API 推送的新订单详细信息。接收到订单后，ttpos 需进行数据验证、保存至本地数据库，并启动内部订单处理流程（如通知厨房）。
    *   **触发条件：** 顾客在 LINE MAN 平台成功提交订单。
    *   **输入：** 完整的订单详情 JSON 对象，包括订单 ID、商品列表（含数量、单价、选项、备注）、订单总价、配送信息、支付状态、顾客信息等。
    *   **输出：** HTTP 200 OK 响应（表示成功接收），或 HTTP 4xx/5xx 错误响应（表示接收失败）。
    *   **处理流程：**
        1.  接收 LINE MAN 的订单通知。
        2.  验证请求的签名和数据的完整性。
        3.  解析订单数据。
        4.  将订单数据保存到 ttpos 数据库，并生成内部订单号。
        5.  更新相关库存信息。
        6.  触发内部事件，通知厨房出餐或备餐系统。
        7.  返回成功响应给 LINE MAN。
    *   **错误处理：** 当接收失败（网络问题）、数据格式错误、缺少关键信息或内部处理失败时，ttpos 应返回相应的 HTTP 错误状态码和错误描述，并记录详细错误日志。
*   **FR-ORDER-2 LINE MAN 推送订单状态更新通知至 ttpos (可选)**
    *   **描述：** ttpos 系统应能够作为一个 HTTPS 回调服务，接收 LINE MAN 通过 "Status update notification" API 推送的订单状态更新通知。接收后，ttpos 需更新本地数据库中对应订单的状态。
    *   **触发条件：** LINE MAN 平台上的订单状态发生变化（例如，骑手已取餐、订单已送达、顾客取消订单、商家取消订单）。
    *   **输入：** 订单 ID，最新的订单状态（如 `COMPLETED`, `CANCELLED`），以及可能的更新时间。
    *   **输出：** HTTP 200 OK 响应，或 HTTP 4xx/5xx 错误响应。
    *   **处理流程：**
        1.  接收 LINE MAN 的状态更新通知。
        2.  验证请求和数据的合法性。
        3.  根据订单 ID 查找本地订单。
        4.  更新本地订单状态，并触发后续业务逻辑（如财务结算、库存回滚）。
        5.  返回成功响应。
    *   **错误处理：** 当接收失败、订单 ID 不存在或状态与本地业务逻辑冲突时，ttpos 应返回错误响应并记录日志。
*   **FR-ORDER-3 LINE MAN 推送订单编辑更新通知至 ttpos (可选)**
    *   **描述：** ttpos 系统应能够作为一个 HTTPS 回调服务，接收 LINE MAN 通过 "Order update notification" API 推送的订单编辑后的最新详情。接收后，ttpos 需更新本地数据库中对应订单的详细信息。
    *   **触发条件：** LINE MAN 平台上的订单被顾客或客服编辑并成功保存（例如，修改菜品数量、移除菜品、修改配送地址）。
    *   **输入：** 更新后的完整订单详情 JSON 对象或明确的变更部分。
    *   **输出：** HTTP 200 OK 响应，或 HTTP 4xx/5xx 错误响应。
    *   **处理流程：**
        1.  接收 LINE MAN 的订单编辑更新通知。
        2.  验证请求和数据的合法性。
        3.  根据订单 ID 查找本地订单。
        4.  更新本地订单的详细信息（如菜品列表、价格、配送地址）。
        5.  触发重新计算订单总价、重新通知厨房等必要的业务逻辑。
        6.  返回成功响应。
    *   **错误处理：** 当接收失败、订单 ID 不存在或更新数据与本地业务逻辑冲突时，ttpos 应返回错误响应并记录日志。

#### 3.1.4 门店状态控制模块

*   **FR-RESTAURANT-1 ttpos 控制 LINE MAN 门店营业状态 (可选)**
    *   **描述：** ttpos 系统应能够向 LINE MAN 的“强制开店/关店”API 发送请求，以控制门店在 LINE MAN 平台上的营业状态（开店或关店）。
    *   **触发条件：** 商家操作员在 ttpos 后台修改门店的营业状态。
    *   **输入：** 门店唯一标识符（ID），以及目标营业状态（例如，`OPEN`, `CLOSE`）。
    *   **输出：** LINE MAN API 的响应（例如，成功、失败）。
    *   **错误处理：** 当 API 调用失败、LINE MAN 返回错误（例如，未找到对应门店）时，ttpos 应记录错误日志并触发警报。

### 3.2 非功能需求

本节描述 ttpos 与 LINE MAN 集成所需的非功能需求。

#### 3.2.1 性能

*   **API 响应时间：** ttpos 调用 LINE MAN API 和 LINE MAN 调用 ttpos API 的本地响应时间应在 200ms 以内，以确保用户体验和系统实时性。
*   **菜单同步速度：** 完整的菜单快照推送，在正常网络条件下，应在 5 秒内完成，对于大型菜单（例如，超过 1000 个 SKU），应在 30 秒内完成。
*   **订单处理吞吐量：** ttpos 系统应能处理 LINE MAN 平台高峰期每秒至少 10 个订单的推送量，且平均处理延迟不超过 500ms。

#### 3.2.2 安全性

*   **数据传输安全：** ttpos 与 LINE MAN 之间所有通过 API 进行的数据传输必须使用 HTTPS 协议进行加密，防止数据窃听和篡改。
*   **认证安全：** 严格遵循 OAuth 2.0 Client Credentials 规范，Client ID 和 Client Secret 必须安全存储，不得硬编码，并定期轮换。Access Token 必须在传输和存储过程中保持安全，并及时刷新。
*   **访问控制：** ttpos 暴露给 LINE MAN 的回调 API 必须有严格的认证和授权机制。如果 LINE MAN 提供 IP 白名单功能，ttpos 应启用并配置有效的白名单 IP。
*   **日志安全：** 敏感数据（如 Client Secret）不得以明文形式记录在日志中。

#### 3.2.3 可用性

*   **系统正常运行时间：** ttpos 与 LINE MAN 集成服务应具备高可用性，目标年正常运行时间达到 99.9% 以上。
*   **错误恢复：** 系统应具备自动错误检测和恢复能力。对于可恢复的 API 调用失败（如网络瞬时故障），应实施幂等性设计和合理的重试机制（例如，指数退避策略）。
*   **降级机制：** 当 LINE MAN 平台或集成服务出现重大故障时，ttpos 应具备降级处理机制，例如，暂时切换到人工处理或通知商家。

#### 3.2.4 可维护性

*   **代码质量：** 集成模块的代码应遵循 Go 开发规范与最佳实践，具有良好的可读性、可测试性和可维护性。
*   **日志记录：** 系统应有完善的日志记录机制，包括请求/响应日志、错误日志、业务日志，方便故障排查、性能监控和业务审计。日志应包含足够的上下文信息。
*   **配置管理：** 所有与 LINE MAN 集成相关的配置参数（例如，API 端点、Client ID/Secret、超时设置）应通过配置文件或环境变量进行集中管理，方便更新和部署。
*   **监控与告警：** 应对集成服务的关键指标（如 API 调用成功率、响应时间、错误率、队列长度）进行实时监控，并配置相应的告警机制。

#### 3.2.5 可扩展性

*   **水平扩展：** 当集成门店数量或业务量增加时，ttpos 集成服务应能通过增加部署实例的方式进行水平扩展，以支持更大的并发请求和数据处理量。
*   **模块化设计：** 集成模块应采用模块化设计，方便未来添加新的 LINE MAN API 或与其他第三方平台集成。

#### 3.2.6 国际化

*   **错误消息：** ttpos 系统返回给 LINE MAN 的错误消息（如果需要）以及 ttpos 内部的错误提示应支持国际化，以便在不同地区使用。
*   **文本内容：** 所有用户可见的与集成相关的文本内容（如后台配置项、状态显示）应支持国际化。
