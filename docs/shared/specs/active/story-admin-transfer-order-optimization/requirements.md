## 📋 概述

在调拨单管理界面增加"我发出/我接收/我审核"三种角色视角的筛选功能，让门店用户能够快速定位与自己相关的调拨单，提升操作效率和用户体验。

当前调拨单界面缺少角色区分，门店管理员需要逐个查看单据才能确认是调出、调入还是需要审核，效率低下。优化后，用户可以按自己的角色快速筛选单据，特别是"我审核"视图能够明确显示需要本店处理的待审核单据，避免审核遗漏。

## 🎯 产品对齐

本功能支持以下产品目标：
- **提升用户效率**：减少用户查找目标单据的时间，提高门店运营效率
- **优化用户体验**：以用户视角展示数据，符合用户心智模型
- **降低培训成本**：界面更贴合业务场景，减少用户学习成本
- **减少业务风险**：明确显示待审核单据，避免审核延误导致的业务问题

## 📝 用户故事

**作为** 门店管理员

**以便于** 快速定位需要我处理的调拨单，提高工作效率

## 功能需求

### Requirement 1: 类型筛选器

**用户故事**: 作为门店管理员，我想在调拨单列表页看到"我发出/我接收/我审核"三种类型筛选器，以便于快速切换不同视角查看单据。

#### 验收标准

1. **WHEN** 用户进入调拨单管理页面 **THEN** 系统 **SHALL** 在列表上方显示三个筛选按钮："我发出"、"我接收"、"我审核"
2. **WHEN** 页面初始加载时 **THEN** 系统 **SHALL** 默认选中"我接收"筛选器，并显示本店作为调入方的调拨单
3. **WHEN** 用户点击某个筛选器 **THEN** 系统 **SHALL** 选中该筛选器，取消其他筛选器的选中状态，并更新列表数据
4. **WHEN** 用户点击已选中的筛选器 **THEN** 系统 **SHALL** 取消选择，显示所有调拨单（不区分角色）
5. **WHEN** 筛选器状态变化 **THEN** 系统 **SHALL** 同步更新状态筛选器的可选项

#### 具体要求

- [x] 1.1 筛选器组件支持单选模式（同时只能选择一种类型）
- [x] 1.2 筛选器组件支持取消选择（再次点击已选中项）
- [x] 1.3 筛选器状态变化时，重置分页为第 1 页
- [x] 1.4 筛选器状态保存在 URL 参数中，刷新页面后保持选中状态
- [x] 1.5 UI 设计：选中状态有明显的视觉区分（如高亮、边框等）

---

### Requirement 2: 我发出视图

**用户故事**: 作为调出方门店管理员，我想查看本店调出的所有调拨单，以便于跟踪调出单据的状态。

#### 验收标准

1. **WHEN** 用户点击"我发出"筛选器 **THEN** 系统 **SHALL** 显示本店作为调出方（transfer_out_shop_uuid == 本店UUID）的所有调拨单
2. **WHEN** 显示"我发出"视图 **THEN** 系统 **SHALL** 提供以下状态筛选项：全部、待提交、待审核、已驳回、待收货、已完成
3. **WHEN** 列表为空 **THEN** 系统 **SHALL** 显示提示："暂无调出单据"
4. **WHEN** 用户切换状态筛选 **THEN** 系统 **SHALL** 根据状态过滤列表数据
5. **WHEN** 单据状态更新 **THEN** 系统 **SHALL** 实时刷新列表（如单据被审核通过、驳回等）

#### 具体要求

- [x] 2.1 查询条件：`transfer_out_shop_uuid = 当前门店UUID`
- [x] 2.2 支持按状态筛选：待提交(status=1)、待审核(status=2)、已驳回(status=3)、待收货(status=4)、已完成(status=5)
- [x] 2.3 列表显示字段：单据编号、调入门店、商品信息、数量、状态、创建时间、操作按钮
- [x] 2.4 支持分页，每页默认 20 条
- [x] 2.5 支持按单据编号、调入门店名称搜索

### Requirement 4: 我审核视图

**用户故事**: 作为审核人员，我想查看当前需要本店审核的调拨单，以便于及时处理待审核单据。

#### 验收标准

1. **WHEN** 用户点击"我审核"筛选器 **THEN** 系统 **SHALL** 显示当前审核节点等于本店UUID的所有调拨单
2. **WHEN** 显示"我审核"视图 **THEN** 系统 **SHALL** 仅提供"待审核"状态筛选（固定状态）
3. **WHEN** 判断是否需要本店审核 **THEN** 系统 **SHALL** 根据以下四种场景判断：
   - 场景1：本店是调出方 AND 当前审核节点 == "发出方审核" AND 审核节点门店UUID == 本店UUID
   - 场景2：本店是调入方 AND 当前审核节点 == "接收店审核" AND 审核节点门店UUID == 本店UUID
   - 场景3：本店是调出方的上级门店 AND 当前审核节点 == "发出方上级门店审核" AND 审核节点门店UUID == 本店UUID
   - 场景4：本店是调入方的上级门店 AND 当前审核节点 == "接收方上级门店审核" AND 审核节点门店UUID == 本店UUID
4. **WHEN** 列表为空 **THEN** 系统 **SHALL** 显示提示："当前无待审核单据"
5. **WHEN** 单据审核通过后 **THEN** 系统 **SHALL** 从"我审核"列表中移除该单据

#### 具体要求

- [x] 4.1 查询条件：`current_approval_node_shop_uuid = 当前门店UUID AND status = 2（待审核）`
- [x] 4.2 审核节点判断逻辑：根据调拨单的审核流程配置，判断当前节点是否为本店
- [x] 4.3 列表显示字段：单据编号、调出门店、调入门店、商品信息、数量、当前审核节点、创建时间、操作按钮
- [x] 4.4 支持分页，每页默认 20 条
- [x] 4.5 支持按单据编号、门店名称搜索
- [x] 4.6 列表中显示"审核"按钮，点击进入审核详情页

### Requirement 5: 状态筛选器联动

**用户故事**: 作为门店管理员，我想在切换角色视角时，状态筛选器自动更新可选项，以便于快速筛选目标单据。

#### 验收标准

1. **WHEN** 选择"我发出"或"我接收" **THEN** 系统 **SHALL** 提供完整的状态筛选项（全部、待提交、待审核、已驳回、待收货、已完成）
2. **WHEN** 选择"我审核" **THEN** 系统 **SHALL** 仅提供"待审核"状态筛选项（其他状态禁用或隐藏）
3. **WHEN** 取消角色筛选（显示全部） **THEN** 系统 **SHALL** 提供完整的状态筛选项
4. **WHEN** 角色筛选切换 **THEN** 系统 **SHALL** 重置状态筛选为"全部"（如果"我审核"则为"待审核"）

#### 具体要求

- [x] 5.1 状态筛选器根据角色筛选动态调整可选项
- [x] 5.2 切换角色筛选时，自动重置状态筛选
- [x] 5.3 状态筛选器的 UI 状态与角色筛选联动（如禁用、隐藏等）

---

### Requirement 6: 边界场景处理

**用户故事**: 作为系统，我需要正确处理各种边界场景，确保功能稳定可靠。

#### 验收标准

1. **WHEN** 门店没有上级门店 **THEN** 系统 **SHALL** 不显示"场景3"和"场景4"的审核单据（避免查询出错）
2. **WHEN** 调拨单审核流程配置变更 **THEN** 系统 **SHALL** 根据最新配置判断审核节点
3. **WHEN** 单据在审核过程中被撤回 **THEN** 系统 **SHALL** 从"我审核"列表中移除
4. **WHEN** 用户同时是调出方和审核方 **THEN** 系统 **SHALL** 在"我发出"和"我审核"视图中都显示该单据（不重复计数）
5. **WHEN** 数据加载失败 **THEN** 系统 **SHALL** 显示错误提示并提供重试按钮

#### 具体要求

- [x] 6.1 审核节点判断逻辑需要处理门店层级关系（上级门店查询）
- [x] 6.2 单据状态变更时，清除相关缓存，确保数据一致性
- [x] 6.3 列表查询增加错误处理，网络异常时优雅降级
- [x] 6.4 审核流程配置变更时，提供数据迁移方案（如有）

## 风险和缓解

### 风险 1: 审核节点判断逻辑复杂，可能遗漏边界情况

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 详细梳理现有审核流程，与产品确认所有审核场景
- 编写完整的单元测试覆盖所有审核场景（包括边界情况）
- 代码审查时重点关注审核节点判断逻辑
- 与现有调拨单审核功能对照，确保逻辑一致

### 风险 2: 查询性能问题，筛选逻辑可能导致慢查询

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 增加数据库索引以优化查询性能
- 使用 Redis 缓存列表查询结果（缓存时间 60 秒）
- 对查询逻辑进行性能测试，评估慢查询风险
- 如性能不达标，考虑使用异步加载或分页优化

### 风险 3: 前后端联调可能遇到接口不一致问题

**影响**: 低  
**概率**: 中  
**缓解措施**:

- 前后端开发前明确接口定义（参数、响应格式）
- 后端先完成接口开发和测试，前端再进行联调
- 使用 Swagger 或 Postman 文档化接口
- 联调前进行接口 Mock 测试
