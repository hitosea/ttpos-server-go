## 📋 概述

BMP Nacos 多实例支持优化旨在解决当前各子模块仅支持单个 Nacos 实例配置的问题，通过支持多实例配置、实现故障转移和负载均衡，提升系统的高可用性和扩展性。

本功能主要涉及 Nacos 客户端配置格式优化、客户端初始化逻辑改造、故障转移机制实现等。

## 🎯 产品对齐

该功能支持公司 2025 年 Q4 的核心目标：

- **提升系统可用性**: 支持多实例配置，实现故障自动转移，降低单点故障风险
- **支持集群部署**: 支持 Nacos 集群模式，提升系统扩展性
- **提高运维灵活性**: 运维人员可以配置多个 Nacos 实例，实现负载均衡
- **符合生产环境最佳实践**: 满足高可用架构要求

## 功能需求

### Requirement 1: 多实例配置支持

**用户故事**: 作为运维人员，我想配置多个 Nacos 实例地址，以便于实现高可用部署

#### 验收标准

1. **WHEN** 配置多个 Nacos 实例地址（逗号分隔） **THEN** 系统 **SHALL** 能够解析并连接到所有配置的实例
2. **WHEN** 使用单实例配置格式（ip + port） **THEN** 系统 **SHALL** 保持向后兼容，正常工作
3. **IF** 配置格式错误（如地址格式不正确） **THEN** 系统 **SHALL** 返回清晰的错误提示
4. **WHEN** 配置多个实例地址 **THEN** 系统 **SHALL** 支持环境变量和配置文件两种方式

#### 具体要求

- [ ] 1.1 支持逗号分隔的多实例地址配置格式：`host1:port1,host2:port2,host3:port3`
- [ ] 1.2 保持单实例配置格式（`nacos.server.ip` + `nacos.server.port`）的向后兼容
- [ ] 1.3 配置解析优先级：优先使用 `addresses` 配置，不存在时使用 `ip` + `port`
- [ ] 1.4 统一各子模块的配置格式（ttpos-erp、ttpos-message、ttpos-websocket 等）

---

### Requirement 2: 故障转移机制

**用户故事**: 作为开发人员，我想系统能够自动检测 Nacos 实例故障并切换到备用实例，以便于提高系统可用性

#### 验收标准

1. **IF** 主 Nacos 实例故障 **THEN** 系统 **SHALL** 自动切换到备用实例
2. **WHEN** 主实例恢复 **THEN** 系统 **SHALL** 能够自动切换回主实例（可选）
3. **WHEN** 所有 Nacos 实例都不可用 **THEN** 系统 **SHALL** 记录错误日志并降级处理
4. **WHEN** 实例故障切换时 **THEN** 系统 **SHALL** 记录切换日志，便于运维排查

#### 具体要求

- [ ] 2.1 实现健康检查机制，定期检测 Nacos 实例可用性（心跳检测）
- [ ] 2.2 实现故障检测逻辑，当主实例不可用时自动切换
- [ ] 2.3 实现故障恢复检测，当主实例恢复时可选切换回主实例
- [ ] 2.4 记录详细的故障和切换日志

---

### Requirement 3: 负载均衡

**用户故事**: 作为运维人员，我想多个可用 Nacos 实例之间能够负载均衡，以便于提高系统性能和可用性

#### 验收标准

1. **WHEN** 配置多个可用 Nacos 实例 **THEN** 系统 **SHALL** 在多个实例之间进行负载均衡
2. **WHEN** 执行服务注册/发现操作 **THEN** 系统 **SHALL** 选择合适的实例进行连接
3. **IF** 某个实例负载较高 **THEN** 系统 **SHALL** 优先选择负载较低的实例

#### 具体要求

- [ ] 3.1 实现连接池管理，管理多个 Nacos 客户端连接
- [ ] 3.2 实现负载均衡算法（轮询、随机、最少连接等）
- [ ] 3.3 实现实例选择逻辑，根据负载情况选择合适的实例

---

### Requirement 4: 配置统一管理

**用户故事**: 作为开发人员，我想各子模块的 Nacos 配置格式统一，以便于维护和管理

#### 验收标准

1. **WHEN** 查看各子模块的配置文件 **THEN** 系统 **SHALL** 使用统一的配置格式
2. **WHEN** 修改 Nacos 配置解析逻辑 **THEN** 系统 **SHALL** 统一在 `internal/pkg/nacos` 中实现
3. **IF** 新增子模块需要对接 Nacos **THEN** 系统 **SHALL** 复用统一的配置解析逻辑

#### 具体要求

- [ ] 4.1 统一各子模块的配置文件格式（`config.tpl.yaml`）
- [ ] 4.2 在 `internal/pkg/nacos/service` 中实现统一的配置解析函数
- [ ] 4.3 各子模块复用统一的配置解析和初始化逻辑

## 非功能需求

### NFR 1: 性能要求

- **配置解析时间**: < 100ms
- **故障检测响应时间**: < 5 秒
- **故障切换时间**: < 10 秒

### NFR 2: 可维护性

- **代码结构清晰**: 配置解析、客户端初始化、故障转移逻辑分离
- **易于测试**: 支持模拟 Nacos 故障场景进行测试
- **文档完善**: 更新相关文档，说明配置格式和使用方法

### NFR 3: 兼容性

- **向后兼容**: 保持现有单实例配置格式完全兼容
- **GoFrame 兼容**: 确保与 GoFrame Nacos 客户端兼容
- **多子模块兼容**: 所有子模块都能正常使用新配置格式

### NFR 4: 可观测性

- **日志记录**: 记录配置解析、实例连接、故障切换等关键操作
- **监控指标**: 记录实例连接数、故障次数、切换次数等指标
- **错误处理**: 提供清晰的错误信息和处理建议

## 验收标准总结

### 功能验收

- [ ] ✅ 配置多个 Nacos 实例地址时，系统能够解析并连接到所有实例
- [ ] ✅ 使用单实例配置格式时，系统保持向后兼容，正常工作
- [ ] ✅ 主实例故障时，系统自动切换到备用实例
- [ ] ✅ 所有实例都不可用时，系统记录错误日志并降级处理
- [ ] ✅ 多个可用实例之间能够进行负载均衡

### 非功能验收

- [ ] ✅ 代码通过 `go fmt` 和 `go vet` 检查
- [ ] ✅ 配置解析和故障转移逻辑正确，无回归问题
- [ ] ✅ 各子模块配置文件格式统一
- [ ] ✅ 相关文档已更新（配置说明、使用指南等）
