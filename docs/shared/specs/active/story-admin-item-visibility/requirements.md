## 📋 概述

在物品管理模块中增加"允许子店可见"设置开关，总部管理员可以根据业务需要，控制物品是否在子店的相关业务模块中显示。当子店进行物品同步操作后，可见性设置才会生效。该功能主要用于管理特殊库存（如电子设备），避免子店误操作或查看不应该看到的物品。

## 🎯 产品对齐

提升库存管理精细化程度，满足多层级组织架构的权限控制需求，提高数据安全性和业务规范性。

## 📝 用户故事

**作为** 总部管理员  
**我想** 控制物品在子店的可见性  
**以便于** 管理特殊库存（如电子设备），避免子店误操作或查看不应该看到的物品

## 功能需求

### Requirement 1: 物品可见性设置

**用户故事**: 作为总部管理员，我想在物品管理中设置"允许子店可见"开关，以便于控制物品在子店的可见性

#### 验收标准

1. **WHEN** 总部在物品管理中设置"允许子店可见"为开启 **THEN** 系统 **SHALL** 默认该状态为开启，所有子店可见该物品
2. **WHEN** 总部将物品设置为允许子店可见（开启） **THEN** 子店同步后 **SHALL** 在相关业务模块中正常显示该物品
3. **WHEN** 总部将物品设置为不允许子店可见（关闭） **THEN** 子店同步后 **SHALL** 在物品列表、成本卡、采购申请、采购收货、品牌采购、品采收货、盘点单、调拨单、库存查询、出入库明细表中均不可见该物品

#### 具体要求

- [ ] 1.1 在 `ttpos_material` 表中增加 `allow_substore_visible` 字段（tinyint，默认值 1，表示允许子店可见）
- [ ] 1.2 创建数据库迁移文件，添加该字段
- [ ] 1.3 更新 Go Model `main/app/model/material.go`，添加 `AllowSubstoreVisible` 字段
- [ ] 1.4 更新 PHP Model `admin/app/common/model/product/Material.php`，添加对应字段
- [ ] 1.5 在物品管理界面（总店）添加"允许子店可见"开关控件
- [ ] 1.6 开关默认处于开启状态（值为 1）
- [ ] 1.7 仅总店有此设置权限，子店不可见该设置项

---

### Requirement 2: 同步机制

**用户故事**: 作为总部管理员，我想通过物品同步操作使可见性设置生效，以便于控制子店物品显示

#### 验收标准

1. **WHEN** 总部开启/关闭可见性 **THEN** 系统 **SHALL** 仅对新数据生效（采购订单、调拨、盘点已有物品则不进行隐藏）
2. **WHEN** 子店进行物品同步操作 **THEN** 系统 **SHALL** 根据总部的可见性设置更新子店物品显示状态

#### 具体要求

- [ ] 2.1 修改物品同步逻辑，同步 `allow_substore_visible` 字段
- [ ] 2.2 同步时仅对新数据生效，已有采购订单、调拨、盘点中的物品不受影响
- [ ] 2.3 子店同步后，根据 `allow_substore_visible` 字段控制物品显示

---

### Requirement 3: 业务模块可见性控制

**用户故事**: 作为子店管理员，我想在相关业务模块中只看到允许可见的物品，以便于正常业务操作

#### 验收标准

1. **WHEN** 物品设置为不允许子店可见（关闭） **THEN** 子店在以下业务模块中均不可见该物品：
   - 物品列表
   - 成本卡
   - 采购申请
   - 采购收货
   - 品牌采购
   - 品采收货
   - 盘点单
   - 调拨单
   - 库存查询
   - 出入库明细表

#### 具体要求

- [ ] 3.1 修改物品列表查询接口，子店查询时过滤 `allow_substore_visible = 1` 的物品
- [ ] 3.2 修改成本卡相关接口，子店查询时过滤不可见物品
- [ ] 3.3 修改采购申请相关接口，子店查询时过滤不可见物品
- [ ] 3.4 修改采购收货相关接口，子店查询时过滤不可见物品
- [ ] 3.5 修改品牌采购相关接口，子店查询时过滤不可见物品
- [ ] 3.6 修改品采收货相关接口，子店查询时过滤不可见物品
- [ ] 3.7 修改盘点单相关接口，子店查询时过滤不可见物品
- [ ] 3.8 修改调拨单相关接口，子店查询时过滤不可见物品
- [ ] 3.9 修改库存查询相关接口，子店查询时过滤不可见物品
- [ ] 3.10 修改出入库明细表相关接口，子店查询时过滤不可见物品

---

### Requirement 4: 批量操作

**用户故事**: 作为总部管理员，我想批量设置物品可见性，以便于提高操作效率

#### 验收标准

1. **WHEN** 总部进行批量设置 **THEN** 系统 **SHALL** 支持批量设置可见与不可见（同批量停用/开启逻辑一致）以及可批量筛选可见与不可见物品

#### 具体要求

- [ ] 4.1 在物品列表页面添加批量操作功能（批量设置可见/不可见）
- [ ] 4.2 批量操作逻辑与批量停用/开启保持一致
- [ ] 4.3 添加筛选功能，可按"允许子店可见"和"不允许子店可见"筛选物品
- [ ] 4.4 批量操作时显示确认提示

---

### Requirement 5: 操作提示

**用户故事**: 作为总部管理员，我想在操作时看到明确的提示信息，以便于了解操作影响范围

#### 验收标准

1. **WHEN** 总部关闭"允许子店可见" **THEN** 系统 **SHALL** 弹窗提示：关闭后，门店在同步前仍可见该物品，但子店完成同步操作后，物品列表、成本卡、采购申请、采购收货、品牌采购、品采收货、盘点单、调拨单、库存查询、出入库明细表均不可见该物品。确定要关闭吗？
2. **WHEN** 总部开启"允许子店可见" **THEN** 系统 **SHALL** 弹窗提示：开启后，门店在同步前仍不可见该物品，但子店完成同步操作后，物品列表、成本卡、采购申请、采购收货、品牌采购、品采收货、盘点单、调拨单、库存查询、出入库明细表均可见该物品。确定要开启吗？

#### 具体要求

- [ ] 5.1 关闭可见性时，显示确认弹窗，提示影响范围
- [ ] 5.2 开启可见性时，显示确认弹窗，提示影响范围
- [ ] 5.3 弹窗内容明确告知同步前后状态差异

---

### Requirement 6: 业务逻辑保持

**用户故事**: 作为系统，我想保持原有业务流程不受影响，以便于系统稳定性

#### 验收标准

1. **WHEN** 总部开启/关闭可见性 **THEN** 系统 **SHALL** 仅为可见/不可见（非不可用），保持原有的业务流程

#### 具体要求

- [ ] 6.1 可见性控制不影响原有业务流程
- [ ] 6.2 仅控制显示，不控制可用性
- [ ] 6.3 已有数据（采购订单、调拨、盘点）中的物品不受影响

## 验收标准

### 功能验收

1. **物品可见性设置**: 总店可以设置物品的"允许子店可见"开关，默认开启
2. **同步机制**: 可见性设置通过物品同步操作生效，仅对新数据生效
3. **业务模块控制**: 子店在 10 个业务模块中只能看到允许可见的物品
4. **批量操作**: 支持批量设置可见/不可见，支持批量筛选
5. **操作提示**: 开启/关闭时显示确认弹窗，明确告知影响范围
6. **业务逻辑保持**: 可见性控制不影响原有业务流程

### 测试验收

1. **单元测试**: 覆盖率达标（Service ≥ 70%, Repository ≥ 80%）
2. **API 测试**: 所有接口测试通过
3. **集成测试**: 端到端流程测试通过
4. **手动测试**: 浏览器兼容性测试通过

### 文档验收

1. **技术文档**: design.md 完整且准确
2. **API 文档**: API 接口文档完整（如有）
3. **数据库文档**: 迁移脚本和表结构文档完整
4. **测试文档**: tasks.md 中的测试任务完成

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error

#### PHP 模块

- 必须使用 ThinkPHP 6.0
- 遵循 MVC 分层
- Controller 不写业务逻辑
- 使用验证器验证参数
- 使用软删除

#### Vue 模块

- 必须使用 Vue 3 + TypeScript + Vite
- 使用 Element Plus 组件库
- 遵循 `.cursor/rules/vue.mdc`

### 业务约束

- 可见性设置仅总店有权限
- 可见性控制仅对新数据生效，已有数据不受影响
- 可见性控制不影响原有业务流程，仅控制显示

### 资源约束

- 开发时间: 5-7 天
- Story Point: 5 SP (必须 ≤ 5)

## 风险和缓解

### 风险 1: 同步机制可能影响现有业务流程

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 明确同步机制：仅对新数据生效，已有数据不受影响
- 充分测试各种业务场景，确保不影响现有流程

### 风险 2: 已有数据（采购订单、调拨、盘点）的处理逻辑需要明确

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 明确业务规则：已有数据不受影响
- 在代码中明确注释说明

### 风险 3: 批量操作可能影响大量数据，需要性能优化

**影响**: 低  
**概率**: 低  
**缓解措施**:

- 批量操作增加确认提示
- 考虑分批处理大量数据
