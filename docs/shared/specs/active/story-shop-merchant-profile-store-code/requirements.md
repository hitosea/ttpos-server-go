## 📋 概述

当前商家档案配置中缺少店铺编码字段，导致发票打印时无法准确显示店铺编号信息，不利于商家进行多门店管理和财务对账。本需求在 Shop 端商家档案的税号下方新增"店铺编码"配置项，支持最大 100 字符，用于发票打印中的"店铺编号 (SHOP:)"字段显示。

## 🎯 产品对齐

- 为多门店商家提供统一的店铺编码管理能力
- 支持发票打印中显示店铺编号，便于财务对账和门店识别
- 提升商家管理的规范性和便捷性
- 增强系统的多门店管理能力

## 📝 用户故事

**作为** 商户管理员  
**我想** 在商家档案中配置店铺编码  
**以便于** 在发票打印时显示准确的店铺编号，方便财务对账和多门店管理

## 功能需求

### Requirement 1: 商家档案页面新增店铺编码字段

**用户故事**: 作为商户管理员，我想在商家档案配置页面输入和保存店铺编码。

#### 验收标准

1. **WHEN** 打开商家档案配置页面 **THEN** 在税号字段下方显示"店铺编码"输入框。
2. **WHEN** 输入店铺编码 **AND** 长度不超过 100 字符 **THEN** 保存成功。
3. **WHEN** 输入店铺编码 **AND** 长度超过 100 字符 **THEN** 显示错误提示"店铺编码不能超过100个字符"。
4. **WHEN** 店铺编码为空 **THEN** 允许保存（店铺编码为可选字段）。
5. **WHEN** 保存成功后 **THEN** 页面刷新时能正确显示已保存的店铺编码。

#### 具体要求

- [ ] 在商家档案页面的税号字段下方新增"店铺编码"输入框
- [ ] 输入框采用右对齐样式，与税号字段保持一致
- [ ] 字段标签为"店铺编码"，使用系统默认标签样式
- [ ] 最大长度限制为 100 字符，支持中英文、数字和特殊字符
- [ ] 店铺编码为可选字段，可以为空
- [ ] 输入验证：超长时前端实时提示

---

### Requirement 2: API 支持店铺编码的保存和读取

**用户故事**: 作为前端开发者，我需要通过 API 保存和读取店铺编码。

#### 验收标准

1. **WHEN** 调用获取商家档案 API **THEN** 响应中包含 `store_code` 字段。
2. **WHEN** 调用更新商家档案 API **AND** 请求中包含 `store_code` 字段 **THEN** 成功保存到数据库。
3. **WHEN** `store_code` 长度超过 100 字符 **THEN** 返回参数校验错误，不执行保存。
4. **WHEN** `store_code` 为空字符串或 null **THEN** 允许保存（清空店铺编码）。
5. **WHEN** 保存成功后 **THEN** 下次查询时能正确返回保存的值。

#### 具体要求

- [ ] 在 `UpdateStoreSetting` 请求结构中新增 `StoreCode` 字段，类型 `string`，验证规则 `max=100`
- [ ] 在 `ShopProfile` 响应结构中新增 `StoreCode` 字段，类型 `string`
- [ ] 在 `setting.Store` 配置结构中新增 `StoreCode` 字段
- [ ] 更新 `EditStoreSetting` 方法，支持保存 `store_code` 到 `store_setting`
- [ ] 更新 `GetStoreSetting` 方法，确保能正确读取 `store_code`
- [ ] 保持现有 API 结构不变，向后兼容

---

### Requirement 3: 发票打印支持显示店铺编码

**用户故事**: 作为商户，我想在发票打印时看到店铺编号，以便区分不同门店的发票。

#### 验收标准

1. **WHEN** 打印发票 **AND** 已配置店铺编码 **THEN** 发票上显示"SHOP: {店铺编码}"。
2. **WHEN** 打印发票 **AND** 未配置店铺编码 **THEN** 不显示"SHOP:"字段。
3. **WHEN** 店铺编码包含中英文、数字和特殊字符 **THEN** 发票上能正确显示所有字符。
4. **WHEN** 店铺编码超过 100 字符（数据异常） **THEN** 发票打印时自动截断到 100 字符。

#### 具体要求

- [ ] 在打印发票时，从 `store_setting` 中读取 `store_code`
- [ ] 如果 `store_code` 不为空，在发票模板中添加"SHOP: {store_code}"
- [ ] 显示位置：在公司信息区域，税号附近（具体位置根据打印模板确定）
- [ ] 支持多语言环境下的正确显示
- [ ] 确保打印布局不受影响（如换行、对齐等）

---

### Requirement 4: 数据迁移与兼容性

**用户故事**: 作为系统管理员，我需要确保新增字段不影响现有数据和功能。

#### 验收标准

1. **WHEN** 系统升级后 **THEN** 现有商家的店铺编码字段默认为空。
2. **WHEN** 旧版本客户端访问 API **THEN** 不报错，正常运行（向后兼容）。
3. **WHEN** 新版本客户端访问旧数据 **THEN** 店铺编码字段显示为空，允许填写。
4. **WHEN** 数据库迁移执行 **THEN** 不影响现有数据的完整性。

#### 具体要求

- [ ] 创建数据库迁移脚本，新增 `store_code` 字段到相关配置
- [ ] 默认值为空字符串或 NULL
- [ ] 迁移脚本支持幂等操作（重复执行不报错）
- [ ] 确保向后兼容，旧版本客户端不受影响

## 非功能需求

### 性能要求

- 店铺编码的读取和保存不应影响商家档案页面的加载性能
- API 响应时间保持在 200ms 以内（正常网络环境）

### 安全要求

- 店铺编码仅允许当前商家的管理员修改
- 输入需进行 XSS 防护，过滤危险字符
- API 请求需要管理员权限验证

### 兼容性要求

- 支持 Flutter 新管理端（优先）
- 保持与现有 API 结构的向后兼容
- 支持多语言环境
