## 📋 概述

在 Shop 商家管理端，移除套餐商品的添加、修改、删除、同步操作中对ERP接口的调用，使套餐管理功能独立运行，不再依赖ERP系统。套餐数据仅在TTPOS系统内部管理，不再同步到ERP。通过移除ERP集成，提升操作性能、提高系统稳定性、简化系统架构，改善用户体验。

## 🎯 产品对齐

该功能支持产品在套餐管理上的独立性和稳定性需求，减少外部依赖，降低因ERP服务问题导致的业务中断风险，提升套餐操作的响应速度和可靠性。

## 📝 用户故事

**作为** 商户管理员  
**我想** 在Shop商家管理端添加、修改、删除、同步套餐时不再调用ERP接口  
**以便于** 提升操作性能、提高系统稳定性，减少因ERP服务问题导致的业务中断

## 功能需求

### Requirement 1: 移除添加套餐的ERP调用

**用户故事**: 作为商户管理员，我想在添加套餐时不再调用ERP接口，以便于提升操作性能和系统稳定性

#### 验收标准

1. **WHEN** 商户管理员在Shop商家管理端添加套餐 **THEN** 系统 **SHALL** 直接保存到TTPOS数据库，不调用 `erpSrv.AddPackage()` 接口
2. **WHEN** 添加套餐操作完成 **THEN** 系统 **SHALL** 返回成功响应，不等待ERP接口响应
3. **WHEN** ERP服务不可用时 **THEN** 系统 **SHALL** 仍能正常添加套餐，不受ERP服务状态影响

#### 具体要求

- [ ] 1.1 在 `main/app/service/product.go` 的套餐添加逻辑中，移除 `erpSrv.AddPackage()` 调用
- [ ] 1.2 保留本地数据库操作，确保套餐数据正常保存
- [ ] 1.3 移除添加套餐时的ERP相关错误处理和日志记录
- [ ] 1.4 验证添加套餐功能正常工作，数据正确保存到数据库

---

### Requirement 2: 移除修改套餐的ERP调用

**用户故事**: 作为商户管理员，我想在修改套餐时不再调用ERP接口，以便于提升操作性能和系统稳定性

#### 验收标准

1. **WHEN** 商户管理员在Shop商家管理端修改套餐信息 **THEN** 系统 **SHALL** 直接更新到TTPOS数据库，不调用 `erpSrv.UpdateProduct()` 接口
2. **WHEN** 修改套餐单位时 **THEN** 系统 **SHALL** 不调用ERP接口同步单位信息
3. **WHEN** 修改套餐操作完成 **THEN** 系统 **SHALL** 返回成功响应，不等待ERP接口响应

#### 具体要求

- [ ] 2.1 在套餐修改逻辑中，移除 `erpSrv.UpdateProduct()` 调用
- [ ] 2.2 移除套餐单位更新时的ERP同步逻辑（`product.go` 中的单位更新ERP调用）
- [ ] 2.3 保留本地数据库更新操作，确保套餐数据正确更新
- [ ] 2.4 移除修改套餐时的ERP相关错误处理和日志记录
- [ ] 2.5 验证修改套餐功能正常工作，数据正确更新到数据库

---

### Requirement 3: 移除删除套餐的ERP调用

**用户故事**: 作为商户管理员，我想在删除套餐时不再调用ERP接口，以便于提升操作性能和系统稳定性

#### 验收标准

1. **WHEN** 商户管理员在Shop商家管理端删除套餐 **THEN** 系统 **SHALL** 直接软删除到TTPOS数据库，不调用 `erpSrv.DeleteProduct()` 接口
2. **WHEN** 删除套餐操作完成 **THEN** 系统 **SHALL** 返回成功响应，不等待ERP接口响应
3. **WHEN** ERP服务不可用时 **THEN** 系统 **SHALL** 仍能正常删除套餐，不受ERP服务状态影响

#### 具体要求

- [ ] 3.1 在 `main/app/service/product.go` 的 `DeleteProductShop` 方法中，移除套餐删除时的 `erpSrv.DeleteProduct()` 调用（约 1414-1432 行）
- [ ] 3.2 保留本地数据库软删除操作，确保套餐数据正常删除
- [ ] 3.3 移除删除套餐时的ERP相关错误处理和日志记录
- [ ] 3.4 验证删除套餐功能正常工作，数据正确软删除到数据库
- [ ] 3.5 验证普通商品删除时的ERP调用不受影响（普通商品删除仍调用ERP接口）

---

### Requirement 4: 移除同步套餐的ERP调用

**用户故事**: 作为系统管理员，我想在同步套餐时不再调用ERP接口，以便于简化同步流程和提高系统稳定性

#### 验收标准

1. **WHEN** 系统执行套餐同步操作 **THEN** 系统 **SHALL** 不调用ERP接口进行套餐数据同步
2. **WHEN** 同步普通商品（非套餐）时 **THEN** 系统 **SHALL** 普通商品的ERP同步功能正常工作，不受套餐ERP移除影响
3. **WHEN** 执行套餐同步 **THEN** 系统 **SHALL** 跳过套餐相关的ERP同步逻辑

#### 具体要求

- [ ] 4.1 在 `main/app/service/sync_product_to_erp.go` 中，移除套餐相关的ERP同步逻辑
- [ ] 4.2 保留普通商品的ERP同步功能（如需要）
- [ ] 4.3 添加套餐类型判断，跳过套餐的ERP同步
- [ ] 4.4 验证普通商品ERP同步功能不受影响

---

1. **WHEN** 代码审查时 **THEN** 系统 **SHALL** 移除不再使用的ERP相关代码

#### 具体要求

- [ ] 5.4 代码审查确保无遗留的ERP调用逻辑

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [ ] URL 使用 snake_case 命名（如：`/api/v1/order_info`）
- [ ] data 字段必须是对象，不能是 null 或数组
- [ ] 分页信息统一放在 meta 中
- [ ] 响应格式：`{code, message, data{}}`
- [ ] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 数据库设计要求

- [ ] 必须包含: `id`, `uuid`, `create_time`, `update_time`, `delete_time`
- [ ] 时间字段使用 int 类型，\_time 结尾，默认值 0
- [ ] 金额字段使用 decimal(20,8)
- [ ] UUID 字段使用 bigint unsigned
- [ ] 表名使用 ttpos\_ 前缀
- [ ] 字段名使用 snake_case
- [ ] 参考: `.cursor/rules/database.mdc` - 数据库开发规范

### 性能要求

- [ ] 套餐操作响应时间 < 200ms（移除ERP调用后应明显提升）
- [ ] 数据库查询优化（使用索引）
- [ ] 缓存策略（Redis）
- [ ] 并发处理（使用 UUID 锁）

### 浏览器兼容性（管理后台）

- [ ] Chrome 90+
- [ ] Safari 14+
- [ ] Firefox 88+
- [ ] Edge 90+

### 测试要求

- [ ] Service 层测试覆盖率 ≥ 70%
- [ ] Repository 层测试覆盖率 ≥ 80%
- [ ] 集成测试覆盖核心流程（添加、修改、删除、同步套餐）
- [ ] API 测试覆盖所有接口
- [ ] 验证普通商品ERP同步功能不受影响
- [ ] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 国际化要求

- [ ] 支持 10 种语言（中文、英文、日语、韩语等）
- [ ] 所有文案使用多语言实现
- [ ] 参考: `main/i18n/` - 国际化配置

### 安全要求

- [ ] 所有 API 需要身份验证
- [ ] 敏感数据加密存储
- [ ] SQL 注入防护（使用参数化查询）
- [ ] XSS 防护（前端输入校验）
- [ ] CSRF 防护（Token 验证）
- [ ] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [ ] 网络异常时优雅降级（不再依赖ERP，无需处理ERP网络异常）
- [ ] 事务管理（保证数据一致性）
- [ ] 错误日志记录（使用 Logger）
- [ ] 故障恢复机制

## 验收标准

### 功能验收

1. **添加套餐不再调用ERP**: 添加套餐时，系统直接保存到TTPOS数据库，不调用ERP接口，操作成功
2. **修改套餐不再调用ERP**: 修改套餐时，系统直接更新到TTPOS数据库，不调用ERP接口，操作成功
3. **删除套餐不再调用ERP**: 删除套餐时，系统直接软删除到TTPOS数据库，不调用ERP接口，操作成功
4. **同步套餐不再调用ERP**: 同步套餐时，系统跳过ERP同步逻辑，不调用ERP接口
5. **普通商品ERP同步不受影响**: 普通商品的ERP同步功能正常工作，不受套餐ERP移除影响
6. **套餐操作性能提升**: 套餐操作响应时间明显缩短（不包含ERP接口调用耗时）

### 测试验收

1. **单元测试**: 覆盖率达标
2. **API 测试**: 所有接口测试通过
3. **集成测试**: 端到端流程测试通过（添加、修改、删除、同步套餐）
4. **回归测试**: 验证普通商品ERP同步功能不受影响

### 文档验收

1. **技术文档**: design.md 完整且准确（待创建）
2. **API 文档**: API 接口文档完整（如有）
3. **代码注释**: 更新相关代码注释，说明已移除ERP集成
4. **测试文档**: tasks.md 中的测试任务完成（待创建）

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error

### 业务约束

- 套餐数据仅在TTPOS系统内部管理，不再同步到ERP
- 普通商品的ERP同步功能必须保持正常工作
- 移除ERP集成后，需要确保没有其他业务模块依赖ERP中的套餐数据

### 资源约束

- 开发时间: 2-3 天
- Story Point: 3-5 SP (必须 ≤ 5)

## 风险和缓解

### 风险 1: 数据一致性风险

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 确认业务场景中是否真的需要ERP中的套餐数据
- 如果不需要，可以安全移除；如果需要，考虑其他同步方案
- 与业务方确认移除ERP集成的影响范围

### 风险 2: 业务依赖风险

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 全面梳理套餐数据的使用场景，确认是否有其他模块依赖ERP数据
- 与业务方确认移除ERP集成的影响范围
- 进行充分的回归测试

### 风险 3: 回滚风险

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 保留ERP接口调用代码的注释或文档，便于后续恢复
- 使用特性开关（Feature Flag）控制是否调用ERP，便于灰度发布和回滚
- 代码审查确保移除逻辑正确

### 风险 4: 普通商品ERP同步受影响

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 仔细审查代码，确保只移除套餐相关的ERP调用
- 添加套餐类型判断，明确区分套餐和普通商品
- 进行充分的回归测试，验证普通商品ERP同步功能
