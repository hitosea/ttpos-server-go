## 📋 概述

本功能为新管理端（桌面端）的票据样式设置页面新增外卖订单票据预览功能，包括"外卖顾客联"和"外卖商家联"两种票据类型。通过预览功能，商户管理员可以：

- 提前查看外卖订单票据的打印效果
- 对比商家联（店内商品名）和顾客联（平台商品名）的差异
- 验证 Grab、LINE MAN 等外卖平台的票据打印格式

预览功能为只读模式，不提供样式编辑功能，确保票据格式的一致性和稳定性。

## 🎯 产品对齐

本功能支持以下产品目标：

1. **完善外卖业务体验**：为接入 Grab、LINE MAN 等外卖平台提供完整的票据管理能力
2. **降低配置成本**：通过预览功能减少票据配置错误，降低客服支持成本
3. **提升商户满意度**：让商户管理员能够直观了解外卖票据的打印效果，增强信心

## 📝 用户故事

**作为** 商户管理员  
**我想** 在票据样式设置页面预览外卖商家联和顾客联  
**以便于** 提前确认票据打印效果，确保外卖订单票据符合业务要求

## 功能需求

### Requirement 1: 票据预览入口

**用户故事**: 作为商户管理员，我想在票据样式设置页面看到外卖票据预览入口，以便于快速访问预览功能

#### 验收标准

1. **WHEN** 商户管理员进入票据样式设置页面 **THEN** 系统 **SHALL** 在现有票据类型列表中显示"外卖顾客联"和"外卖商家联"两个预览入口
2. **IF** 用户没有票据样式设置权限 **THEN** 系统 **SHALL** 不显示外卖票据预览入口
3. **WHEN** 页面加载完成 **THEN** 系统 **SHALL** 将外卖票据入口放置在其他票据类型（如堂食小票、厨房单）附近的明显位置

#### 具体要求

- [ ] 1.1 在票据样式设置页面的票据类型列表中新增"外卖顾客联"预览入口
- [ ] 1.2 在票据样式设置页面的票据类型列表中新增"外卖商家联"预览入口
- [ ] 1.3 入口名称清晰明确，使用"外卖顾客联"和"外卖商家联"命名
- [ ] 1.4 入口图标或样式与现有票据类型保持一致
- [ ] 1.5 权限检查：前端和后端都需要检查用户是否有票据样式设置权限

---

### Requirement 2: 外卖顾客联预览

**用户故事**: 作为商户管理员，我想预览外卖顾客联的打印效果，以便于确认顾客收到的票据格式

#### 验收标准

1. **WHEN** 点击"外卖顾客联"预览入口 **THEN** 系统 **SHALL** 打开预览弹窗或页面，显示外卖顾客联的打印预览
2. **WHEN** 显示商品列表 **THEN** 系统 **SHALL** 使用外卖平台商品名称（如 Grab 商品名称、LINE MAN 商品名称）
3. **WHEN** 预览加载完成 **THEN** 系统 **SHALL** 显示完整的票据内容，包括订单信息、商品列表、金额信息、备注等
4. **IF** 商品没有外卖平台商品名称映射 **THEN** 系统 **SHALL** 降级使用店内商品名称并在预览中标注提示

#### 具体要求

- [ ] 2.1 预览使用外卖订单的真实数据或示例数据
- [ ] 2.2 商品名称使用 `takeout_platform_name` 字段（外卖平台商品名）
- [ ] 2.3 预览格式与实际打印效果保持一致
- [ ] 2.4 支持多语言显示（根据当前管理端语言设置）
- [ ] 2.5 预览窗口提供关闭按钮，方便用户退出预览

---

### Requirement 3: 外卖商家联预览

**用户故事**: 作为商户管理员，我想预览外卖商家联的打印效果，以便于确认商家内部使用的票据格式

#### 验收标准

1. **WHEN** 点击"外卖商家联"预览入口 **THEN** 系统 **SHALL** 打开预览弹窗或页面，显示外卖商家联的打印预览
2. **WHEN** 显示商品列表 **THEN** 系统 **SHALL** 使用店内商品名称（商家内部使用的商品名称）
3. **WHEN** 预览加载完成 **THEN** 系统 **SHALL** 显示完整的票据内容，包括订单信息、商品列表、金额信息、备注等
4. **IF** 商品名称包含规格信息 **THEN** 系统 **SHALL** 完整显示商品名称和规格

#### 具体要求

- [ ] 3.1 预览使用外卖订单的真实数据或示例数据
- [ ] 3.2 商品名称使用店内商品名称（`product.name` 字段）
- [ ] 3.3 预览格式与实际打印效果保持一致
- [ ] 3.4 支持多语言显示（根据当前管理端语言设置）
- [ ] 3.5 预览窗口提供关闭按钮，方便用户退出预览

---

### Requirement 4: 预览数据源

**用户故事**: 作为商户管理员，我想预览功能使用真实的订单数据，以便于更准确地了解票据效果

#### 验收标准

1. **WHEN** 用户请求预览 **THEN** 系统 **SHALL** 优先使用最近的外卖订单数据
2. **IF** 没有外卖订单数据 **THEN** 系统 **SHALL** 使用预设的示例数据
3. **WHEN** 使用示例数据 **THEN** 系统 **SHALL** 在预览页面明确标注"示例数据"

#### 具体要求

- [ ] 4.1 后端 API 查询最近 1 条已完成或进行中的外卖订单
- [ ] 4.2 如果没有外卖订单，使用预设的示例数据（包含完整的订单信息和商品列表）
- [ ] 4.3 示例数据包含多种商品类型（带规格、带加料、带备注等）
- [ ] 4.4 预览数据包含必要的商户信息（店名、地址、电话等）

---

### Requirement 5: 只读预览模式

**用户故事**: 作为商户管理员，我只需要查看预览效果，不需要编辑票据样式

#### 验收标准

1. **WHEN** 打开预览页面 **THEN** 系统 **SHALL** 仅提供预览功能，不提供编辑功能
2. **WHEN** 用户尝试修改预览内容 **THEN** 系统 **SHALL** 不响应修改操作
3. **WHEN** 预览窗口显示 **THEN** 系统 **SHALL** 不显示"编辑"、"保存"等编辑相关按钮

#### 具体要求

- [ ] 5.1 预览页面不提供任何编辑功能（不可输入、不可点击修改）
- [ ] 5.2 预览页面不显示编辑相关的按钮或控件
- [ ] 5.3 预览页面明确标注"预览模式"或"仅供查看"
- [ ] 5.4 用户可以关闭预览窗口返回票据样式设置页面

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/go-printer.mdc` - 打印模块开发规范
  - `.cursor/rules/vue.mdc` - Vue 前端规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [ ] URL 使用 snake_case 命名（如：`/api/v1/shop/takeout_receipt_preview`）
- [ ] data 字段必须是对象，不能是 null 或数组
- [ ] 响应格式：`{code, message, data{}}`
- [ ] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 数据库设计要求

本功能主要涉及查询现有数据，不需要新增表或字段。

- [ ] 查询外卖订单时使用现有的索引（如 `shop_id`, `order_type`, `create_time`）
- [ ] 查询商品名称映射时使用现有的 `product` 表和 `takeout_platform_product` 表

### 性能要求

- [ ] 预览数据查询响应时间 < 200ms
- [ ] 预览页面渲染时间 < 500ms
- [ ] 使用 Redis 缓存示例数据（如果没有真实订单数据）
- [ ] 数据库查询优化（使用索引，限制查询数量）

### 浏览器兼容性（管理后台）

- [ ] Chrome 90+
- [ ] Safari 14+
- [ ] Firefox 88+
- [ ] Edge 90+

### 测试要求

- [ ] Service 层测试覆盖率 ≥ 70%
- [ ] Repository 层测试覆盖率 ≥ 80%
- [ ] 集成测试覆盖核心流程
- [ ] API 测试覆盖所有接口
- [ ] 前端单元测试覆盖预览组件
- [ ] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 国际化要求

- [ ] 支持 10 种语言（中文、英文、日语、韩语、泰语等）
- [ ] 所有文案使用多语言实现
- [ ] 参考: `main/i18n/` - 国际化配置

### 安全要求

- [ ] 所有 API 需要身份验证（商户管理员权限）
- [ ] 权限检查：前端和后端都需要检查票据样式设置权限
- [ ] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [ ] 网络异常时优雅降级（显示友好错误提示）
- [ ] 错误日志记录（使用 Logger）
- [ ] 如果查询订单失败，降级使用示例数据

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error
- 遵循 `.cursor/rules/go-printer.mdc` 打印模块开发规范

#### Vue 模块

- 必须使用 Vue 3 + TypeScript + Vite
- 使用 Element Plus 组件库
- 遵循 `.cursor/rules/vue.mdc`

### 业务约束

- 外卖顾客联商品名称必须使用外卖平台商品名称（如 Grab 商品名称）
- 外卖商家联商品名称必须使用店内商品名称
- 预览功能为只读模式，不提供编辑功能
- 权限控制：只有有票据样式设置权限的用户才能看到预览入口

### 资源约束

- 开发时间: 3-5 天
- Story Point: 3-5 (必须 ≤ 5)

## 风险和缓解

### 风险 1: 商品名称映射不准确

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 在开发前与外卖平台对接团队确认商品名称映射逻辑
- 如果商品没有外卖平台名称映射，降级使用店内商品名称并标注提示
- 在预览页面提供"商品名称映射说明"，帮助管理员理解名称差异

### 风险 2: 票据样式兼容性

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 复用现有的票据打印模板和渲染逻辑
- 在测试阶段使用真实订单数据进行测试，确保预览效果与实际打印一致
- 如果发现样式差异，及时调整预览渲染逻辑

### 风险 3: 权限控制遗漏

**影响**: 高  
**概率**: 低  
**缓解措施**:

- 严格遵循权限控制规范，在前端和后端都进行权限检查
- 在代码审查阶段重点检查权限控制逻辑
- 在测试阶段专门测试权限控制场景
