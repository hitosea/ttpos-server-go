- **所属模块**: 商品管理（Product）
- **关联任务**: DooTask #38678
- **创建日期**: 2026-01-12
- **当前状态**: 待开发

---

## 需求背景

### 问题描述

当前系统存在以下问题：

1. **打印档口编辑限制**：总部来源的商品，子店无法编辑打印档口，导致无法打印送厨小票
2. **接口功能单一**：现有的修改商品状态接口（`POST /shop/product/status`）仅支持修改上下架状态，无法同时修改打印档口
3. **操作效率低**：如果需要同时修改状态和打印档口，需要调用两个接口（修改状态 + 完整编辑商品），操作繁琐

### 业务场景

**场景1：子店调整打印档口**
- 角色：子店店长
- 操作：总部推送了一批商品到子店，但子店的厨房布局与总部不同，需要修改打印档口
- 期望：能够直接修改打印档口，不需要修改其他商品信息

**场景2：批量调整商品状态和打印档口**
- 角色：店长
- 操作：新增了一个厨房档口，需要将多个商品快速调整状态并分配到新档口
- 期望：一次操作完成状态和打印档口的修改

---

## 用户故事

**作为** 子店店长/运营人员  
**我想** 能够编辑总部来源商品的打印档口，并快速调整商品的上下架状态  
**以便于** 确保商品在本店能够正常打印送厨小票，并提高商品管理效率

---

## 功能需求

### FR-1: 新增修改总部商品接口

**优先级**: P0（必须）

**需求描述**：
- 新增一个API接口"修改总部商品上下架和打印档口"，支持子店修改总部来源商品的上下架状态和打印档口
- 接口应支持以下操作：
  - 修改上下架状态（必须提供）
  - 修改打印档口（可选）
  - 同时修改上下架状态和打印档口

**输入参数**：
- `uuid`（必填）：商品UUID
- `status`（必填）：商品状态（0-下架 1-上架）
- `product_printer_uuids`（可选）：打印档口UUID列表

**输出结果**：
- 成功：返回成功消息
- 失败：返回错误信息（如商品不存在、打印档口不存在等）

**验收标准**：
- ✅ 必须传入 `status` 修改上下架状态
- ✅ 可以选择性传入 `product_printer_uuids` 修改打印档口
- ✅ 可以同时传入 `status` 和 `product_printer_uuids` 同时修改
- ✅ 子店可以修改总部来源商品的打印档口
- ✅ 修改后的数据能够正确保存到数据库
- ✅ 修改后的商品详情接口能返回最新的状态和打印档口信息
- ✅ 只同步修改子店自己创建的商品到 ERP（不同步总部商品到 ERP）

---

### FR-2: 保留原有状态接口

**优先级**: P0（必须）

**需求描述**：
- 保留现有的修改商品状态接口（`POST /shop/product/status`）
- 该接口继续只负责修改上下架状态，不涉及打印档口

**验收标准**：
- ✅ 原有接口功能不受影响
- ✅ 原有接口的调用方不需要修改代码

---

### FR-3: 权限控制

**优先级**: P1（重要）

**需求描述**：
- 子店可以修改总部来源商品的打印档口
- 子店可以修改总部来源商品的上下架状态（如果已有此权限）

**验收标准**：
- ✅ 子店店长/运营人员可以调用新接口
- ✅ 修改总部来源商品的打印档口时不会报错

---

## 非功能需求

### NFR-1: 性能要求

- 接口响应时间 < 500ms（正常情况）
- 支持并发修改不同商品

### NFR-2: 数据一致性

- 修改操作必须在事务中执行
- 失败时需要回滚所有修改
- 修改后需要清除相关缓存（如果有）

### NFR-3: 兼容性

- 新接口不影响现有接口的功能
- 前端可以根据需要选择使用新接口或原有接口

## 接口设计概要

### 新接口

```
POST /shop/product/update_headquarters_product
```

**请求体示例**：

```json
{
  "uuid": 123456,
  "status": 1,
  "product_printer_uuids": [1001, 1002]
}
```

**响应示例**：

```json
{
  "code": 0,
  "msg": "更新成功"
}
```

---

## 约束与限制

1. **参数约束**：`status` 为必填参数，`product_printer_uuids` 为可选参数
2. **数据验证**：
   - 商品UUID必须存在
   - 状态值必须为 0 或 1
   - 打印档口UUID必须存在且属于当前门店（如果提供）
3. **业务规则**：
   - 如果商品被其他套餐引用，下架时需要同时下架相关套餐（与现有逻辑一致）
   - 只同步修改子店自己创建的商品到 ERP，不同步总部商品
   - 同步功能会保留子店已修改的商品状态，不会被总部状态覆盖

## 测试要点

### 功能测试

1. 仅修改状态（不提供打印档口）
2. 同时修改状态和打印档口
3. 修改不存在的商品（预期失败）
4. 修改不存在的打印档口（预期失败）
5. 子店修改总部来源商品的打印档口（预期成功）
6. 修改被套餐引用的商品状态
7. 修改总部商品不同步到 ERP（预期成功）
8. 修改子店自己的商品同步到 ERP（预期成功）

### 边界测试

1. 打印档口列表为空数组或 null
2. 状态值为非法值（非0/1）
3. 商品UUID为0或负数
4. 缺少 status 参数（预期失败）

### 性能测试

1. 并发修改同一商品
2. 短时间内连续修改同一商品

## 风险评估

| 风险项 | 风险等级 | 应对措施 |
|---|---|---|
| 并发修改导致数据不一致 | 中 | 使用数据库事务，添加乐观锁或悲观锁 |

| 影响现有功能 | 低 | 充分测试现有修改状态接口 |
