## 📋 概述

设计并实现一套针对 TTPOS 高并发场景优化的缓存框架。该框架将请求合并（Singleflight）与多级缓存（Local Memory + Redis）深度集成，旨在保护下游数据库和外部 API 免受瞬间高并发冲击，同时降低系统响应延迟。

## 🎯 产品对齐

该功能支持 TTPOS 从 50 商户扩展到 500 商户的业务目标，通过提升单机处理能力和系统稳定性，确保在餐饮高峰期提供流畅的服务体验。

## 📝 用户故事

**作为** 后端开发人员

**以便于** 彻底解决高并发下的缓存击穿和请求重复执行问题。

## 功能需求

### Requirement 1: Singleflight 请求合并引擎

**用户故事**: 作为 [后端开发人员]，我想 [自动合并针对同一资源的并发请求]，以便于 [减少无效负载]

#### 验收标准

1. **WHEN** 多个协程同时请求同一个 `Hash` **THEN** 系统 **SHALL** 仅触发一次 `Exec()` 调用。
2. **IF** `Exec()` 正在执行 **THEN** 后续进入的协程 **SHALL** 阻塞直到 `Exec()` 完成并获取相同结果。
3. **WHEN** `Exec()` 执行完成 **THEN** 系统 **SHALL** 立即清理 `Hash` 以便后续新请求进入。

#### 具体要求

- [ ] 1.1 实现泛型接口 `Run[T Task](t T) T`。
- [ ] 1.2 支持自定义 `Hash()` 算法以区分不同资源。
- [ ] 1.3 确保并发安全，在高竞争下无死锁。

---

### Requirement 2: 多级缓存透明集成 (L1 + L2)

**用户故事**: 作为 [后端开发人员]，我想 [透明地使用本地和分布式缓存]，以便于 [在毫秒级内返回热点数据]

#### 验收标准

1. **IF** 数据存在于 L1 (内存) **THEN** 系统 **SHALL** 直接返回结果，不请求 Redis。
2. **IF** L1 不中但 L2 (Redis) 命中 **THEN** 系统 **SHALL** 返回结果并回填 L1。
3. **WHEN** 缓存均不中 **THEN** 系统 **SHALL** 触发 Singleflight 加载并在成功后填充 L1 和 L2。

#### 具体要求

- [ ] 2.1 封装 `Read-Through` 模式，开发者仅需提供 `Loader` 函数。
- [ ] 2.2 支持针对不同业务配置不同的过期时间（TTL）。
- [ ] 2.3 支持空结果缓存（Negative Caching），防止针对不存在 Key 的穿透。

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### 性能要求

- [x] 本地缓存响应时间 < 1ms
- [x] Redis 缓存响应时间 < 20ms
- [x] 并发合并成功率 > 99%

### 测试要求

- [x] Singleflight 并发竞争测试（Race Detection）
- [x] 缓存回写一致性测试
- [x] 单元测试覆盖率 ≥ 90%

## 验收标准

### 功能验收

1. **并发合并**: 100 并发下业务函数仅执行 1 次。
2. **多级流转**: L1 -> L2 -> DB 的流转逻辑符合预期。
3. **降级保护**: 第三方 API 超时时，Singleflight 能正确处理超时并广播错误。

### 测试验收

1. **并发测试**: 使用 `go test -race` 运行高并发模拟。
2. **内存分析**: 验证 Local Cache 不会导致 OOM。
