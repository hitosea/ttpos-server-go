## 📋 概述

收银机分批送厨前置关联模式功能旨在优化收银员操作流程，允许在选购商品时就关联分批类型，减少操作步骤，提升操作效率和准确性。

本功能主要涉及：

- 收银机基础信息接口调整（增加分批送厨模式字段）
- 购物车商品签名计算优化（包含 batch_tag_uuid）
- 加购接口调整（支持前置模式下的 batch_tag_uuid 参数）
- 分批送厨弹窗增强（支持更换类型功能）
- 更换类型接口开发

## 🎯 产品对齐

该功能支持公司 v2.10.0 版本的核心目标：

- **提升操作效率**：减少操作步骤，在选购商品时即可关联分批类型
- **降低操作错误率**：购物车中直观显示分批类型，减少选错概率
- **提升用户体验**：收银员可以提前规划分批策略，操作更流畅
- **支持复杂场景**：支持同一商品选择不同分批类型，满足多样化需求

## 📝 用户故事

**作为** 收银员  
**我想** 在选购商品时就关联分批类型  
**以便于** 提前规划分批送厨策略，减少操作步骤和错误率

## 功能需求

### Requirement 1: 业务设置接口调整

**用户故事**: 作为收银机客户端，我想获取商户的分批送厨模式（前置/后置），以便于前端展示相应的 UI 和交互

#### 验收标准

1. **WHEN** 调用 `/cashier/base` 接口 **THEN** 系统 **SHALL** 返回分批送厨模式字段
2. **IF** 商户未配置分批送厨模式 **THEN** 系统 **SHALL** 默认返回后置模式
3. **WHEN** 商户切换分批送厨模式 **THEN** 系统 **SHALL** 立即生效

#### 具体要求

- [ ] 1.1 在 `CashierBase` 响应结构中增加 `batch_cooking_mode` 字段（string: "pre" 前置 / "post" 后置）
- [ ] 1.2 在 `Business` 业务设置中增加 `batch_cooking_mode` 字段
- [ ] 1.3 从业务设置中读取分批送厨模式并返回给前端
- [ ] 1.4 默认值为 "post"（后置模式，保持向后兼容）

---

### Requirement 2: 购物车签名计算优化

**用户故事**: 作为系统，我想在购物车商品签名中包含分批类型 UUID，以便于区分相同商品但不同分批类型的商品

#### 验收标准

1. **WHEN** 前置模式下加购商品 **THEN** 系统 **SHALL** 在商品签名计算中包含 `batch_tag_uuid`
2. **IF** 相同商品但不同分批类型 **THEN** 系统 **SHALL** 在购物车中分开显示为两条数据
3. **IF** 相同商品且相同分批类型 **THEN** 系统 **SHALL** 合并为一条数据，数量累加

#### 具体要求

- [ ] 2.1 修改商品签名计算函数，当前置模式时包含 `batch_tag_uuid` 参数
- [ ] 2.2 确保签名计算逻辑正确，相同商品不同分批类型能正确分开
- [ ] 2.3 购物车商品合并逻辑支持基于签名合并
- [ ] 2.4 参考商品退菜逻辑，下单两份退一份后分开展示

---

### Requirement 3: 加购接口调整

**用户故事**: 作为收银机客户端，我想在加购商品时传入分批类型 UUID，以便于商品自动关联分批类型

#### 验收标准

1. **WHEN** 前置模式下调用加购接口 **THEN** 系统 **SHALL** 接受 `batch_tag_uuid` 参数
2. **IF** 未传入 `batch_tag_uuid` **THEN** 系统 **SHALL** 使用默认分批类型（排序第一的类型）
3. **WHEN** 加购商品成功 **THEN** 系统 **SHALL** 将商品与分批类型关联
4. **IF** 签名相同的商品 **THEN** 系统 **SHALL** 合并数量而非新增记录

#### 具体要求

- [ ] 3.1 在 `OrderCartProductAddReq` 中增加 `batch_tag_uuid` 字段（可选）
- [ ] 3.2 在 `InstantOrderCartProductAdd` 方法中处理 `batch_tag_uuid` 参数
- [ ] 3.3 当前置模式时，使用 `batch_tag_uuid` 计算商品签名
- [ ] 3.4 如果签名相同的商品要合并在一起
- [ ] 3.5 验证 `batch_tag_uuid` 的有效性（必须存在于分批类型列表中）

---

### Requirement 4: 分批送厨弹窗增强

**用户故事**: 作为收银员，我想在分批送厨弹窗中看到商品关联的类型，并支持更换类型，以便于灵活调整分批策略

#### 验收标准

1. **WHEN** 前置模式下点击送厨 **THEN** 系统 **SHALL** 弹出分批送厨弹窗
2. **WHEN** 弹窗显示 **THEN** 系统 **SHALL** 显示所有分批送厨商品及其关联类型
3. **WHEN** 商品已关联类型 **THEN** 系统 **SHALL** 在商品边框显示类型颜色
4. **WHEN** 点击"更换"图标 **THEN** 系统 **SHALL** 允许更换未送厨商品的分批类型
5. **WHEN** 点击类型按钮 **THEN** 系统 **SHALL** 将已关联该类型的未送厨商品进行送厨

#### 具体要求

- [ ] 4.1 修改 `GetOrderCartProductBatchCookingList` 接口，分批类型列表按 sort 排序，优先级高的在前
- [ ] 4.2 分批送厨弹窗中显示商品关联的类型边框（使用类型颜色）
- [ ] 4.3 未送厨商品支持显示"更换"图标
- [ ] 4.4 点击类型按钮，只送该类型关联的商品
- [ ] 4.5 已送厨的商品不能修改分批类型

---

### Requirement 5: 更换类型接口

**用户故事**: 作为收银机客户端，我想提供接口更换未送厨商品的分批类型，以便于收银员灵活调整

#### 验收标准

1. **WHEN** 调用更换类型接口 **THEN** 系统 **SHALL** 更新商品的分批类型关联
2. **IF** 商品已送厨 **THEN** 系统 **SHALL** 返回错误，不允许修改
3. **WHEN** 更换成功 **THEN** 系统 **SHALL** 同步更新到点餐助手端
4. **WHEN** 更换成功 **THEN** 系统 **SHALL** 更新购物车显示

#### 具体要求

- [ ] 5.1 创建新的更换类型接口 `/cashier/desk/order/cart/batch/change_tag`
- [ ] 5.2 接口接收 `sale_order_product_uuids` 和 `batch_tag_uuid` 参数
- [ ] 5.3 验证商品是否已送厨，已送厨则不允许修改
- [ ] 5.4 更新商品的分批类型关联
- [ ] 5.5 同步更新到点餐助手端（如果订单有关联的助手端）
- [ ] 5.6 返回更新后的购物车信息

---

### Requirement 6: 分批类型列表接口

**用户故事**: 作为收银机客户端，我想获取分批类型列表，以便于显示类型选择器

#### 验收标准

1. **WHEN** 调用分批类型列表接口 **THEN** 系统 **SHALL** 返回所有分批类型
2. **WHEN** 返回列表 **THEN** 系统 **SHALL** 按 sort 排序，优先级高的在前
3. **WHEN** 返回类型 **THEN** 系统 **SHALL** 包含类型名称（多语言）、颜色、缩写等信息

#### 具体要求

- [ ] 6.1 创建或修改分批类型列表接口，支持按 sort 排序
- [ ] 6.2 返回类型包含：uuid、locale_name（多语言）、color、sort、abbreviation（缩写）
- [ ] 6.3 接口仅在前置模式时使用，或始终可用但前端根据模式决定是否显示

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 分批送厨相关逻辑集中在 OrderService 中
- **模块化设计**: 前置模式和后置模式的逻辑隔离，通过配置控制
- **依赖管理**: Service 依赖 Repository 接口
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/api.mdc` - API 设计规范
  - `.cursor/rules/database.mdc` - 数据库开发规范

### API 设计要求

- [x] URL 使用 snake_case 命名：`/cashier/desk/order/cart/batch/change_tag`
- [x] data 字段必须是对象：`{"data": {"sale_bill_uuid": 123, "batch_tag_uuid": 456}}`
- [x] 响应格式：`{code: 1, message: "success", data: {}}`
- [x] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 性能要求

- [x] 加购接口响应时间 < 500ms（P0）
- [x] 购物车签名计算使用高效算法
- [x] 分批类型列表接口支持缓存（可选）

### 测试要求

- [x] OrderService 相关方法测试覆盖率 ≥ 70%
- [x] **购物车签名计算测试覆盖率 100%**（高风险，P0）
- [x] Repository 层测试覆盖率 ≥ 80%
- [x] 集成测试覆盖完整加购和送厨流程
- [x] 并发测试：多商品同时加购，确保签名计算正确
- [x] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 安全要求

- [x] 所有接口需要身份验证（JWT Token）
- [x] 订单 UUID 验证：订单必须属于当前商户
- [x] 分批类型 UUID 验证：必须存在于商户的分批类型列表中
- [x] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [x] 加购失败时事务回滚，保证数据一致性
- [x] 更换类型失败时不影响原有数据
- [x] 记录详细错误日志（Logger）
- [x] 异常时返回明确的错误信息

## 验收标准

### 功能验收

1. **前置关联模式基础功能**: 点餐/开桌时显示分批类型选择器，默认选择排序第一的类型，可切换
2. **商品关联类型**: 加购商品时自动关联当前选中的分批类型，购物车中显示类型标识
3. **同一商品不同类型分开显示**: 相同商品选择不同分批类型时，购物车中分开显示
4. **分批送厨弹窗**: 显示商品关联类型，支持更换类型，支持按类型送厨
5. **更换类型功能**: 未送厨商品可以更换分批类型，已送厨商品不允许修改

### 测试验收

1. **单元测试**: Service 和 Repository 覆盖率达标
2. **API 测试**: 所有接口测试通过，包含异常场景
3. **集成测试**: 端到端加购和送厨流程测试通过
4. **兼容性测试**: 后置关联模式不受影响，两种模式可以平滑切换

### 文档验收

1. **技术文档**: design.md 包含完整的 API 设计、数据模型设计
2. **API 文档**: docs/shared/api/ 已更新
3. **代码注释**: 关键逻辑有中文注释说明

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- Service 接口以 `I` 开头：`IOrderSrv`
- Service 依赖 Repository 接口（不直接依赖 db）
- Repository 只持有 db 实例
- 不使用 panic，所有错误返回 error

### 业务约束

- 前置模式和后置模式互斥，通过业务设置控制
- 已送厨的商品不能修改分批类型
- 不需要分批送厨的商品不受类型影响
- 更换类型操作需要同步到点餐助手端

### 资源约束

- 开发时间: 4-6 天
- Story Point: 6-11 SP

## 风险和缓解

### 风险 1: 购物车签名计算复杂度

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 充分测试各种场景，确保相同商品不同分批类型能正确分开
- 参考商品退菜逻辑的实现方式
- 使用单元测试覆盖所有边界情况

### 风险 2: 数据一致性

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 更换类型接口需要同步到点餐助手端
- 使用事务管理保证数据一致性
- 记录操作日志便于排查问题

### 风险 3: 兼容性

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 通过业务设置区分模式，确保两种模式的逻辑互不干扰
- 默认使用后置模式，保持向后兼容
- 充分测试两种模式的切换场景
