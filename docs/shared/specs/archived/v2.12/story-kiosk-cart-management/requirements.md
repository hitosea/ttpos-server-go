## 📋 概述

实现 Kiosk 自助点餐机购物车管理模块，提供完整的购物车管理功能，包括购物车信息查询、商品/套餐添加、数量修改、商品删除、商品选购详情查看等核心能力。购物车管理是用户点餐流程的核心环节，确保顾客能够顺畅地管理已选商品，为后续的订单确认和支付流程提供基础。

**实现范围**：实现后端 API 接口，参考 POS 端即时点餐模块和点餐助手端的购物车管理接口实现，确保功能一致性和用户体验的统一性。

## 🎯 产品对齐

- **用户体验**：提供实时、直观的购物车管理功能，提升顾客点餐体验
- **操作灵活性**：支持商品数量调整和删除，减少误操作导致的订单错误
- **价格透明**：实时计算和展示订单价格，帮助顾客快速决策
- **复杂场景支持**：支持套餐添加和商品选购详情查看，满足多样化点餐需求
- **运营效率**：减少因购物车操作不当导致的订单异常和客服咨询

## 功能需求

### Requirement 1: 购物车信息查询

**用户故事**: 作为 顾客，我想 在自助点餐机上查看购物车中的商品和订单总价，以便于 了解已选商品信息，做出后续购买决策

#### 验收标准

1. **WHEN** 顾客查看购物车 **THEN** 系统 **SHALL** 显示购物车中的商品列表、数量、单价、小计和订单总价
2. **WHEN** 购物车为空 **THEN** 系统 **SHALL** 显示空购物车提示，引导顾客添加商品
3. **WHEN** 购物车价格发生变化 **THEN** 系统 **SHALL** 实时更新显示的价格信息，确保价格准确性

#### 具体要求

- [ ] 1.1 实现 `/api/v1/kiosk/order/cart/info` 接口，参考 `/cashier/instant/order/cart/info` 的实现方式
- [ ] 1.2 返回购物车中的商品列表，包含商品基本信息（名称、图片、价格等）
- [ ] 1.3 返回每个商品的数量、单价、小计等信息
- [ ] 1.4 实时计算订单总价（原价、现价、折扣），确保价格准确性
- [ ] 1.5 当购物车为空时，返回空列表和空购物车提示信息
- [ ] 1.6 支持订单状态查询，确保购物车数据与订单状态一致

---

### Requirement 2: 商品添加功能

**用户故事**: 作为 顾客，我想 在自助点餐机上添加商品到购物车，以便于 快速选择需要的商品，无需重复操作

#### 验收标准

1. **WHEN** 顾客添加商品到购物车 **THEN** 系统 **SHALL** 将商品添加到购物车，若没有订单则自动创建订单，并更新购物车信息
2. **WHEN** 添加的商品已存在于购物车中 **THEN** 系统 **SHALL** 增加商品数量或创建新的购物车项（根据业务规则）
3. **WHEN** 添加商品失败（如商品下架、库存不足等） **THEN** 系统 **SHALL** 返回友好错误提示

#### 具体要求

- [ ] 2.1 实现 `/api/v1/kiosk/order/cart/product/add` 接口，参考 `/cashier/instant/order/cart/product/add` 的实现方式
- [ ] 2.2 支持添加单个商品到购物车，包含商品规格、属性、加料等选项
- [ ] 2.3 若没有订单则自动创建订单（SaleBill 和 SaleOrder）
- [ ] 2.4 添加成功后返回更新后的购物车信息
- [ ] 2.5 验证商品状态（是否上架、是否可售等）
- [ ] 2.6 验证商品库存（如需要）
- [ ] 2.7 处理商品价格计算（原价、折扣价等）

---

### Requirement 3: 套餐添加功能

**用户故事**: 作为 顾客，我想 在自助点餐机上添加套餐到购物车，以便于 选择套餐商品，享受套餐优惠

#### 验收标准

1. **WHEN** 顾客添加套餐到购物车 **THEN** 系统 **SHALL** 将套餐添加到购物车，支持配置套餐内各分组菜品
2. **WHEN** 套餐配置不完整（如必选分组未选择） **THEN** 系统 **SHALL** 返回错误提示，要求完成配置
3. **WHEN** 添加套餐成功 **THEN** 系统 **SHALL** 更新购物车信息，显示套餐商品和总价

#### 具体要求

- [ ] 3.1 实现 `/api/v1/kiosk/order/cart/product_package/add` 接口，参考 `/cashier/instant/order/cart/product_package/add` 的实现方式
- [ ] 3.2 支持添加套餐到购物车，包含套餐内各分组菜品的配置
- [ ] 3.3 验证套餐配置完整性（必选分组、可选分组等）
- [ ] 3.4 计算套餐价格（套餐原价、折扣价等）
- [ ] 3.5 添加成功后返回更新后的购物车信息

---

### Requirement 4: 商品数量修改功能

**用户故事**: 作为 顾客，我想 在自助点餐机上修改商品数量或删除商品，以便于 灵活调整订单内容，避免误操作

#### 验收标准

1. **WHEN** 顾客修改商品数量 **THEN** 系统 **SHALL** 更新商品数量，并实时重新计算订单总价
2. **WHEN** 商品数量修改为 0 或负数 **THEN** 系统 **SHALL** 返回错误提示或自动删除该商品（根据业务规则）
3. **WHEN** 修改数量后价格发生变化 **THEN** 系统 **SHALL** 实时更新显示的价格信息

#### 具体要求

- [ ] 4.1 实现 `/api/v1/kiosk/order/cart/product/num` 接口，参考 `/cashier/instant/order/cart/product/num` 的实现方式
- [ ] 4.2 支持增加或减少商品数量
- [ ] 4.3 验证数量范围（最小值、最大值等）
- [ ] 4.4 实时更新订单总价
- [ ] 4.5 修改成功后返回更新后的购物车信息

---

### Requirement 5: 商品选购详情查看功能

**用户故事**: 作为 顾客，我想 在自助点餐机上查看已选购商品的详细信息，以便于 确认商品的规格、属性等配置是否正确

#### 验收标准

1. **WHEN** 顾客查看商品选购详情 **THEN** 系统 **SHALL** 显示已选购商品的详细信息，包括规格、属性等配置
2. **WHEN** 商品不存在于购物车中 **THEN** 系统 **SHALL** 返回错误提示
3. **WHEN** 查询成功 **THEN** 系统 **SHALL** 返回完整的商品选购信息列表

#### 具体要求

- [ ] 5.1 实现 `/api/v1/kiosk/order/product/package/detail` 接口，参考 `/assistant/order/product/package/detail` 的实现方式
- [ ] 5.2 支持查询已选购商品的详细信息，包括规格、属性等配置
- [ ] 5.3 返回商品选购详情列表，包含每个商品的完整配置信息
- [ ] 5.4 验证商品是否存在于购物车中

---

### Requirement 6: 商品删除功能

**用户故事**: 作为 顾客，我想 在自助点餐机上修改商品数量或删除商品，以便于 灵活调整订单内容，避免误操作

#### 验收标准

1. **WHEN** 顾客删除购物车中的商品 **THEN** 系统 **SHALL** 从购物车中移除该商品，并实时更新订单总价
2. **WHEN** 删除最后一个商品后购物车为空 **THEN** 系统 **SHALL** 更新购物车状态，显示空购物车提示
3. **WHEN** 删除商品失败（如商品不存在） **THEN** 系统 **SHALL** 返回友好错误提示

#### 具体要求

- [ ] 6.1 实现 `/api/v1/kiosk/order/cart/product/delete` 接口，参考 `/cashier/instant/order/product/delete` 的实现方式
- [ ] 6.2 支持删除购物车中的商品（通过 SaleOrderProduct UUID）
- [ ] 6.3 删除后实时更新订单总价
- [ ] 6.4 验证商品是否存在于购物车中
- [ ] 6.5 删除成功后返回更新后的购物车信息

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [ ] URL 使用 snake_case 命名（如：`/api/v1/kiosk/order/cart/info`）
- [ ] data 字段必须是对象，不能是 null 或数组
- [ ] 分页信息统一放在 meta 中
- [ ] 响应格式：`{code, message, data{}}`
- [ ] 参考: `.cursor/rules/api.mdc` - API 设计规范
- [ ] 参考现有接口实现：POS 端即时点餐模块和点餐助手端的购物车管理接口

### 数据库设计要求

- [ ] 复用现有订单相关表结构（SaleBill、SaleOrder、SaleOrderProduct 等）
- [ ] 不新增数据库表，使用现有表结构
- [ ] 参考: `.cursor/rules/database.mdc` - 数据库开发规范

### 性能要求

- [ ] 本地响应时间 < 200ms
- [ ] 数据库查询优化（使用索引）
- [ ] 缓存策略（Redis）- 购物车信息可考虑缓存
- [ ] 并发处理（使用 UUID 锁）- 防止并发修改购物车

### 测试要求

- [ ] Service 层测试覆盖率 ≥ 70%
- [ ] Repository 层测试覆盖率 ≥ 80%
- [ ] **Order 相关模块测试覆盖率 100%**（高风险）
- [ ] 集成测试覆盖核心流程（添加商品、修改数量、删除商品等）
- [ ] API 测试覆盖所有接口
- [ ] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 国际化要求

- [ ] 支持多语言（中文、英文、日语、韩语等）
- [ ] 所有错误提示使用多语言实现
- [ ] 商品名称、描述等多语言显示
- [ ] 参考: `main/i18n/` - 国际化配置

### 安全要求

- [ ] 所有 API 需要身份验证（JWT Token）
- [ ] 验证用户权限（确保只能操作自己的订单）
- [ ] SQL 注入防护（使用参数化查询）
- [ ] 输入验证（商品数量、UUID 格式等）
- [ ] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [ ] 网络异常时优雅降级
- [ ] 事务管理（保证数据一致性）- 购物车操作需要事务保证
- [ ] 错误日志记录（使用 Logger）
- [ ] 故障恢复机制（订单状态修复）

## 验收标准

### 功能验收

1. **购物车信息查询**: 能够正确查询购物车信息，返回商品列表和订单总价

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error
- 参考现有购物车管理接口实现（POS 端、助手端）

### 业务约束

- 购物车操作需要与订单状态保持一致
- 价格计算需要遵循现有业务规则
- 套餐添加需要验证套餐配置完整性
- 商品删除需要考虑订单状态（如已支付则不允许删除）

### 资源约束

- 开发时间: 5-7 天
- Story Point: 8-13 (必须 ≤ 5，需要拆分)

## 风险和缓解

### 风险 1: 价格计算错误

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 参考 POS 端和助手端的成熟实现，复用价格计算逻辑
- 增加价格计算的单元测试，确保计算准确性
- 实现价格计算的日志记录，便于问题排查

### 风险 2: 数据同步问题

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 实现购物车数据的实时查询和更新机制，确保数据一致性
- 使用事务管理，保证购物车操作的原子性
- 增加数据一致性检查，及时发现和修复问题

### 风险 3: 套餐处理复杂

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 参考现有套餐添加接口的实现，确保逻辑一致性
- 增加套餐配置验证，确保配置完整性
- 增加套餐相关的单元测试和集成测试

### 风险 4: 用户体验问题

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 参考其他终端的购物车交互设计，针对大屏触摸优化交互体验
- 进行用户测试，收集反馈优化
- 提供友好的错误提示和操作引导
