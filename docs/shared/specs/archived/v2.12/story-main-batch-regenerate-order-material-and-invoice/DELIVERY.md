# 批量重新生成订单材料消耗和POS发票 - 交付文档

> 本文档用于交付批量重新生成工具，说明工具功能、使用方法和处理流程。

## 📋 工具概述

**命令名称**: `batch-regenerate-order-material-and-invoice`

**功能描述**: 批量重新生成指定公司和日期范围内的所有订单的材料消耗和POS发票数据。

**使用场景**:
- 成本卡配置变更后，需要批量更新历史订单的材料消耗
- 材料统计逻辑变更后，需要重新计算历史订单的材料用量
- 批量修复订单数据，确保材料消耗和POS发票数据的一致性

## 🎯 每个订单的处理流程

对于每个订单，工具会依次执行以下3个步骤：

### 步骤1: 重新生成订单材料消耗 (`regenerate-order-material`)

**功能**: 重新计算并保存订单的材料消耗记录

**具体操作**:
1. **软删除旧记录**：软删除订单的旧材料消耗记录（更新 `delete_time` 字段）
2. 根据订单的商品明细和当前的成本卡配置，重新计算每种材料的用量
3. **插入新记录**：插入新计算的材料消耗记录

**数据影响**: 
- 更新 `sale_order_material` 表（软删除旧记录，插入新记录）

**幂等性说明**: 
- ✅ **可视为幂等操作**：重复执行该步骤，最终结果一致（都是最新的计算结果）
- 重复执行仅会多出一些软删除的记录（`delete_time != 0`），不影响业务逻辑
- 每次执行会先查询并软删除未删除的记录（`delete_time = 0`），然后插入新记录

### 步骤2: 重新生成订单材料出库 (`regenerate-sale-order-material-outbound`)

**功能**: 重新生成订单的材料出库记录

**具体操作**:
1. 查询订单关联的材料出库记录（`warehouse_out_form_item` 表）
2. **退回库存**：将原记录中的材料数量退回到对应的仓库中（`warehouse_uuid`），更新 `warehouse_item` 表的库存数量
3. **软删除原记录**：软删除订单的现有材料出库记录（`scene = 0 AND revoke_time = 0 AND material_uuid != 0`）
4. 根据订单的商品明细和材料消耗记录，重新计算材料出库数据
5. **创建新记录**：根据重新计算的结果创建新的材料出库记录，并关联到原有的 `warehouse_out_form_uuid`
6. **扣减库存**：按新记录中的材料数量在对应的仓库中扣减库存，更新 `warehouse_item` 表的库存数量，并更新 `reduce_stock = 1`

**数据影响**: 
- 更新 `warehouse_out_form_item` 表（软删除旧记录，创建新记录）
- 更新 `warehouse_item` 表（退回库存时增加库存数量，扣减库存时减少库存数量）

**幂等性说明**: 
- ✅ **可视为幂等操作**：重复执行该步骤，最终结果一致（都是最新的计算结果）
- 重复执行仅会多出一些软删除的记录（`delete_time != 0`），不影响业务逻辑
- 每次执行会先查询并处理未删除的记录（`delete_time = 0`），退回库存后软删除，然后创建新记录并扣减库存
- 库存操作是成对的（退回和扣减），重复执行后最终库存数量保持一致

### 步骤3: 重新生成订单POS发票 (`regenerate-order-pos-invoice`)

**功能**: 重新生成订单的POS发票数据

**具体操作**:
1. 根据订单的商品明细、材料消耗和出库记录，重新计算POS发票数据
2. **新建POS发票**：调用ERP系统接口创建新的POS发票
3. 更新订单的发票信息字段（`ErpProductsInvoiceName`、`ErpMaterialInvoiceName`）

**数据影响**: 
- 在ERP系统中创建新的POS发票
- 更新订单表中的发票信息字段（`ErpProductsInvoiceName`、`ErpMaterialInvoiceName`）

**重要说明**: 
- ⚠️ **非幂等性操作**：该步骤每调用一次，就会为这个订单创建一次新的发票。重复调用会导致同一订单产生多张发票。
- 旧的发票由ERP系统自己去删除或作废，本工具不处理旧发票的清理
- 建议在批量处理前确认订单是否需要重新生成发票，避免重复创建

## 📅 日期级别处理

**执行时机**: 当某个日期的所有订单的3个步骤都完成后，执行日期级别的汇总步骤

**步骤**: 重新生成销售出库汇总 (`regenerate-sales-outbound`)

**功能**: 重新生成该日期的销售出库汇总数据

**具体操作**:
1. 汇总该日期所有订单的材料消耗和出库数据
2. **软删除旧记录**：软删除该日期在 `warehouse_in_out_log` 表中的旧销售出库汇总记录
3. **创建新记录**：根据汇总结果创建新的销售出库汇总记录到 `warehouse_in_out_log` 表
4. **更新统计状态**：更新 `sale_order_material` 表中相关记录的 `is_summarized` 字段

**数据影响**: 
- 更新 `warehouse_in_out_log` 表（软删除旧记录，创建新记录）
- 更新 `sale_order_material` 表（更新 `is_summarized` 字段，标记为已统计）

**幂等性说明**: 
- ✅ **可视为幂等操作**：重复执行该步骤，最终结果一致（都是最新的汇总结果）
- 重复执行仅会多出一些软删除的记录（`delete_time != 0`），不影响业务逻辑
- 每次执行会先查询并软删除未删除的记录（`delete_time = 0`），然后根据最新的订单数据创建新的汇总记录
- `is_summarized` 字段的更新也是幂等的（设置为1），重复执行不会产生副作用

## 🔄 执行顺序

工具按照以下顺序执行：

```
公司1
  └─ 日期1 (2025-12-15)
      ├─ 订单1
      │   ├─ 步骤1: 重新生成订单材料消耗
      │   ├─ 步骤2: 重新生成订单材料出库
      │   └─ 步骤3: 重新生成订单POS发票
      ├─ 订单2
      │   ├─ 步骤1: 重新生成订单材料消耗
      │   ├─ 步骤2: 重新生成订单材料出库
      │   └─ 步骤3: 重新生成订单POS发票
      └─ ...
      └─ 日期级别步骤: 重新生成销售出库汇总 (2025-12-15)
  └─ 日期2 (2025-12-16)
      └─ ...
```

**重要**: 日期级别的汇总步骤只有在该日期所有订单的所有步骤都完成后才会执行。

## 📝 使用方法

### 基本用法

```bash
./ttpos-server-go batch-regenerate-order-material-and-invoice \
  --company-uuids "7709131161600000" \
  --start-date "2025-12-15" \
  --open-pos-entry-name "POS-ENTRY-001"
```

### 参数说明

| 参数 | 必填 | 说明 | 示例 |
|------|------|------|------|
| `--company-uuids` | ✅ | 公司UUID列表，逗号分隔 | `"7709131161600000,7709131161600001"` |
| `--start-date` | ✅ | 起始日期，格式：YYYY-MM-DD | `"2025-12-15"` |
| `--open-pos-entry-name` | ✅ | OpenPosEntryName（用于生成POS发票） | `"POS-ENTRY-001"` |
| `--task-file` | ❌ | 任务清单文件路径（可选，默认自动生成） | `"./my-task.json"` |
| `--resume` | ❌ | 从现有任务清单继续执行 | - |
| `--dry-run` | ❌ | 预览模式，仅生成任务清单不执行 | - |
| `--show-progress` | ❌ | 显示详细进度信息（实时刷新） | - |
| `--progress-interval` | ❌ | 进度信息刷新间隔（秒数，默认5秒） | `10` |

### 常用场景

#### 1. 批量处理单个公司

```bash
./ttpos-server-go batch-regenerate-order-material-and-invoice \
  --company-uuids "7709131161600000" \
  --start-date "2025-12-15" \
  --open-pos-entry-name "POS-ENTRY-001" \
  --show-progress
```

#### 2. 批量处理多个公司

```bash
./ttpos-server-go batch-regenerate-order-material-and-invoice \
  --company-uuids "7709131161600000,7709131161600001" \
  --start-date "2025-12-15" \
  --open-pos-entry-name "POS-ENTRY-001" \
  --show-progress
```

#### 3. 预览任务清单（不执行）

```bash
./ttpos-server-go batch-regenerate-order-material-and-invoice \
  --company-uuids "7709131161600000" \
  --start-date "2025-12-15" \
  --open-pos-entry-name "POS-ENTRY-001" \
  --dry-run
```

#### 4. 断点续传

如果执行过程中断，可以使用 `--resume` 参数继续执行：

```bash
./ttpos-server-go batch-regenerate-order-material-and-invoice \
  --task-file "./batch-regenerate-task-1765886177.json" \
  --open-pos-entry-name "POS-ENTRY-001" \
  --resume \
  --show-progress
```

## 🔒 安全机制

1. **文件锁**: 使用分布式锁防止多个实例同时操作同一任务清单文件
2. **断点续传**: 支持程序中断后从断点继续，自动跳过已完成的步骤
3. **错误记录**: 每个步骤的错误信息都会记录到任务清单文件中，便于排查问题

## 📁 任务清单文件

工具会生成一个JSON格式的任务清单文件，包含：

- **任务结构**: 公司 → 日期 → 订单 → 步骤（四层结构）
- **执行状态**: 每个步骤的状态（pending/running/completed/failed）
- **执行时间**: 每个步骤的开始时间和结束时间
- **错误信息**: 失败步骤的错误详情

**文件位置**: 默认在当前目录生成，文件名格式：`batch-regenerate-task-{timestamp}.json`

## ⚠️ 注意事项

1. **时区处理**: 订单按公司配置的时区进行日期分组
2. **执行时间**: 每个订单的每个步骤执行完成后，会等待1秒再执行下一个订单（避免数据库压力过大）
3. **锁机制**: 如果任务清单文件被其他进程占用，需要等待最多15分钟后重试，或手动清理Redis锁,或重命名任务清单文件
4. **数据备份**: 建议在执行批量操作前备份相关数据

## 🐛 故障排查

### 问题1: 任务清单正在被其他进程使用

**原因**: 之前的执行异常退出，锁残留在Redis中

**解决方案**:
- 等待最多15分钟后重试（锁会自动过期）
- 或手动清理Redis锁（key格式：`batch_regenerate_task:{task_file_path}`）
- 或使用新的任务文件名（不指定 `--task-file` 参数）

### 问题2: 步骤执行失败

**查看方式**: 检查任务清单文件中的 `error` 字段

**处理方式**:
- 查看错误信息，修复问题后使用 `--resume` 参数继续执行
- 工具会自动跳过已完成的步骤，只重新执行失败的步骤
