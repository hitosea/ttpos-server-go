# 员工密码加密升级 - 需求文档

**文档编号**: SPEC-2025-12-001  
**创建日期**: 2025-12-16  
**创建人**: 曾振华  
**文档状态**: 📝 草稿  
**Story 级别**: Story  
**模块**: Security / Auth  
**关联提案**: `docs/team/proposals/2025-12/password-bcrypt-upgrade.md`

## 📋 需求概述

将系统员工密码加密方式从 **MD5 双重哈希 + 固定盐值** 升级为 **bcrypt 自适应哈希**，提升系统安全性，符合现代密码存储标准。

### 核心目标

1. 提升密码存储安全性
2. 防止暴力破解和彩虹表攻击
3. 满足安全合规要求
4. 不影响现有用户登录

---

## 🎯 功能需求

### FR-1: 密码双验证机制

**优先级**: P0（必须）

**需求描述**:  
系统需要支持 MD5 和 bcrypt 两种密码格式的验证，根据密码前缀自动识别：
- 如果密码以 `$2` 开头（bcrypt），使用 bcrypt 验证
- 否则使用旧的 MD5 验证

**验收标准**:
- ✅ MD5 格式密码可以正常登录
- ✅ bcrypt 格式密码可以正常登录
- ✅ 错误密码无法登录
- ✅ 验证逻辑自动识别，无需额外参数

### FR-2: 密码自动升级

**优先级**: P0（必须）

**需求描述**:  
当用户使用 MD5 格式密码成功登录后，系统自动在后台将密码升级为 bcrypt 格式。

**验收标准**:
- ✅ MD5 密码验证成功后，异步升级为 bcrypt
- ✅ 升级过程不影响登录响应时间
- ✅ 升级失败不影响登录成功
- ✅ 下次登录使用 bcrypt 验证

### FR-3: 新增员工使用 bcrypt

**优先级**: P0（必须）

**需求描述**:  
所有新增或修改密码的操作，直接使用 bcrypt 加密存储。

**适用场景**:
- 管理员添加新员工
- 员工修改密码
- 管理员重置员工密码
- 员工修改权限密码

**验收标准**:
- ✅ 新增员工的密码为 bcrypt 格式
- ✅ 修改密码后为 bcrypt 格式
- ✅ 权限密码也使用 bcrypt 格式

### FR-4: 修改密码验证旧密码

**优先级**: P0（必须）

**需求描述**:  
员工修改密码时，验证旧密码需要支持双格式验证。

**验收标准**:
- ✅ 旧密码为 MD5 格式时可以验证通过
- ✅ 旧密码为 bcrypt 格式时可以验证通过
- ✅ 新密码使用 bcrypt 加密

### FR-5: 权限密码验证

**优先级**: P0（必须）

**需求描述**:  
取消订单、退款等敏感操作验证权限密码时，支持双格式验证。

**适用场景**:
- 取消订单验证权限密码
- 其他需要权限密码的敏感操作

**验收标准**:
- ✅ MD5 格式权限密码可以验证通过
- ✅ bcrypt 格式权限密码可以验证通过
- ✅ 验证成功后自动升级（可选）

## 🚫 非功能需求

### NFR-1: 性能要求

**需求描述**:
- 登录响应时间不超过 300ms（P95）
- bcrypt 验证时间不超过 100ms
- 密码升级异步执行，不阻塞主流程

### NFR-2: 安全要求

**需求描述**:
- bcrypt 成本因子设置为 10
- 密码不得以明文形式记录到日志
- 升级过程不得泄露密码信息

### NFR-3: 兼容性要求

**需求描述**:
- 支持 Go 1.23+
- 支持 PHP 8.0+
- 不破坏现有 API 接口
- 不影响前端客户端

### NFR-4: 可维护性要求

**需求描述**:
- 密码验证逻辑封装为独立函数
- 提供明确的错误信息和日志
- 代码注释清晰

## 🗄️ 数据变更

### 不需要新增字段

采用原地升级方案，通过密码前缀自动识别格式：
- **MD5**: `5f4dcc3b5aa765d61d8327deb882cf99`（32位小写十六进制）
- **bcrypt**: `$2y$10$xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`（60位）

### 涉及的表和字段

| 数据库 | 表名 | 字段 | 当前格式 | 目标格式 | 优先级 | 说明 |
|--------|------|------|----------|----------|--------|------|
| saas | ttpos_admin_user | password | MD5 | bcrypt | P0 | 超管密码 |
| saas | ttpos_staff | password | MD5 | bcrypt | P0 | 统一账号员工密码 |
| shop_* | ttpos_staff | password | MD5 | bcrypt | P0 | 门店员工、供应商、收银员密码 |
| shop_* | ttpos_staff | permission_password | MD5 | bcrypt | P0 | 权限密码 |

## 🧪 测试场景

### 场景 1: MD5 密码登录并自动升级

**前置条件**: 员工密码为 MD5 格式
**操作步骤**:
1. 使用正确的账号密码登录
2. 登录成功后查看数据库密码字段

**预期结果**:
- 登录成功
- 数据库密码字段变为 bcrypt 格式（以 `$2` 开头）

### 场景 2: bcrypt 密码登录

**前置条件**: 员工密码为 bcrypt 格式
**操作步骤**:
1. 使用正确的账号密码登录

**预期结果**:
- 登录成功
- 数据库密码字段保持不变

### 场景 3: 错误密码登录

**前置条件**: 员工存在
**操作步骤**:
1. 使用错误密码登录

**预期结果**:
- 登录失败，提示"账号或密码错误"
- 数据库密码字段保持不变

### 场景 4: 修改密码（旧密码 MD5）

**前置条件**: 员工密码为 MD5 格式
**操作步骤**:
1. 提交旧密码（正确）+ 新密码
2. 查看数据库

**预期结果**:
- 修改成功
- 新密码为 bcrypt 格式

### 场景 5: 修改密码（旧密码 bcrypt）

**前置条件**: 员工密码为 bcrypt 格式
**操作步骤**:
1. 提交旧密码（正确）+ 新密码
2. 查看数据库

**预期结果**:
- 修改成功
- 新密码仍为 bcrypt 格式

## ✅ 已确认问题

1. **token 生成策略** ✅ 已确认
   - **最终方案**：统一使用 `md5($user->password)` 生成 token 标识
   - **原因**：保持与原有逻辑的兼容性，避免破坏现有 token 验证机制
   - **说明**：bcrypt 密码哈希存储在数据库中，md5 后的值保持一致
   - **后续优化**：可考虑使用不可变字段（如 `uuid`）或引入 `token_salt` 字段

2. **迁移完成标准** ✅ 已确认
   - **标准**：90% 活跃用户完成迁移
   - **策略**：长期未登录用户保留双验证逻辑
   - **监控**：通过 SQL 查询定期检查迁移进度

3. **是否需要强制密码重置** ✅ 已确认
   - **决定**：不强制，采用自然升级方式
   - **原因**：避免影响用户体验，降低运维成本

4. **是否需要通知用户** ✅ 已确认
   - **决定**：无需通知，后台静默升级
   - **原因**：对用户透明，不影响正常使用

5. **password_change_time 字段处理** ✅ 已确认
   - **创建员工**：设置为 `0`（表示从未修改）
   - **更新密码**：**不再更新此字段**（保持原有值或不设置）
   - **原因**：该字段仅用于密码修改次数统计，不影响密码验证和 token 生成

6. **主键字段差异** ✅ 已确认
   - **超管表**（`ttpos_admin_user`）：使用 `admin_user_id`
   - **员工表**（`ttpos_staff`）：使用 `uuid`
   - **影响**：密码升级函数调用时需使用正确的字段名
