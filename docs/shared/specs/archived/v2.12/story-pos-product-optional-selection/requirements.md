# 商品选择-可选属性/加料/套餐分组 需求文档

## 基本信息

- **Spec ID**: `story-pos-product-optional-selection`
- **DooTask 任务**: [#37618](https://task.example.com/37618)
- **创建时间**: 2025-12-23
- **影响版本**: v2.12.0
- **优先级**: 高
- **Story Point**: 待评估

## 需求背景

当前系统中，套餐分组、商品属性、商品加料的选择都采用"必选"或"固定数量"的方式。在实际业务中，商家需要更灵活的配置，允许顾客可以不选择某些分组/属性/加料，或者在一定范围内自由选择数量。

## 涉及终端

| 终端 | 服务对象 | 影响范围 | 优先级 |
|------|----------|---------|--------|
| **pos** | 前台收银员、店长 | 点餐时商品选择 | 高 |
| **assistant** | 店员、收银辅助人员 | 辅助点单时商品选择 | 高 |

| **mobile** | 顾客 | 扫码点餐时商品选择 | 高 |
| **member** | 会员顾客 | 会员端点餐时商品选择 | 中 |

## 用户故事

### 故事 1: 套餐可选分组

**背景**：商家提供套餐时，希望某些分组是可选的，顾客可以选择 0 到 N 个商品。

**用户故事**：
- 作为 **收银员/顾客**
- 我想 **在选择套餐时，某些分组可以不选择或选择任意数量的商品**
- 以便于 **满足不同顾客的个性化需求，提升点餐体验**

### 故事 2: 商品属性可选

**背景**：商家提供商品时，某些属性不是必选的，顾客可以根据需要选择或不选。

**用户故事**：
- 作为 **收银员/顾客**
- 我想 **在选择商品时，某些属性可以不选择**
- 以便于 **快速完成点餐，避免不必要的选择**

### 故事 3: 商品加料可选

**背景**：商家提供加料服务时，某些加料不是必选的，顾客可以选择 0 到 N 个加料。

**用户故事**：
- 作为 **收银员/顾客**
- 我想 **在选择商品时，可以自由选择加料的数量**
- 以便于 **满足不同口味需求**

## 验收标准 (AC)

### AC1: 套餐可选分组

**Given** 套餐中存在可选分组（后台配置允许可选范围 0-N）

**When** 用户在前端选择套餐商品时

**Then** 
- 可选分组的最小选择数量为 `optional_min_count`，最大选择数量为 `optional_count`
- 当 `optional_min_count = 0` 时，用户可以不选择该分组中的任何商品
- 当用户选择的商品数量 < `optional_min_count` 时，系统提示：
  ```
  【分组名称】最少选择 X 份
  ```
- 当用户选择的商品数量 = `optional_count` 时，不允许再选择更多，提示：
  ```
  当前已选满，请取消其他项再试
  ```

### AC2: 商品属性可选

**Given** 商品中存在可选属性（后台配置 `min_selection = 0`）

**When** 用户在前端选择商品时

**Then** 
- 属性组的最小选择数量为 `min_selection`，最大选择数量为 `max_selection`
- 当 `min_selection = 0` 时，用户可以不选择该属性组中的任何属性
- 当用户选择的属性数量 < `min_selection` 时，系统逐一提示：
  ```
  【属性组名称】最少选择 X 份
  ```
- 当用户选择的属性数量 = `max_selection` 时，不允许再选择更多，提示：
  ```
  当前已选满，请取消其他项再试
  ```

### AC3: 商品加料可选

**Given** 商品中存在可选加料（后台配置 `sauce_min_selection = 0`）

**When** 用户在前端选择商品时

**Then** 
- 加料的最小选择数量为 `sauce_min_selection`，最大选择数量为 `sauce_max_selection`
- 当 `sauce_min_selection = 0` 时，用户可以不选择任何加料
- 当用户选择的加料数量 < `sauce_min_selection` 时，系统提示：
  ```
  加料最少选择 X 份
  ```
- 当用户选择的加料数量 = `sauce_max_selection` 时，不允许再选择更多，提示：
  ```
  当前已选满，请取消其他项再试
  ```

### AC4: 套餐内商品属性可选

**Given** 套餐中的商品包含可选属性

**When** 用户在前端选择套餐内商品时

**Then** 
- 应用与 AC2 相同的验证规则
- 提示信息格式相同

### AC5: 提交订单验证

**Given** 用户选择了商品并准备提交订单

**When** 用户点击提交订单按钮时

**Then** 
- 后端验证所有可选项是否满足最小选择数量要求
- 如果不满足，返回错误信息并阻止订单提交

## 业务规则

1. **兼容性规则**：
   - 旧版本使用 `is_must = 1` 表示必选，新版本统一使用 `min_selection >= 1`
   - 后端需要支持旧数据的自动转换：当 `min_selection = 0` 且 `is_must = 1` 时，自动设置 `min_selection = 1`

2. **验证规则**：
   - `min_selection` 必须 >= 0
   - `max_selection` 必须 >= `min_selection`
   - 当 `max_selection = 0` 时，表示不限制最大选择数量

3. **套餐分组规则**：
   - 固定分组（`group_type = 0`）：`is_required = 1`，`is_default = 1`，用户无法修改
   - 可选分组（`group_type = 1`）：根据 `optional_min_count` 和 `optional_count` 控制选择范围

4. **前端交互规则**：
   - 当用户选择数量达到 `max_selection` 时，未选择的项应该置灰或禁用
   - 当用户尝试提交订单时，如果选择数量 < `min_selection`，应该高亮显示未满足的分组/属性/加料

## 非功能性需求

1. **性能要求**：
   - 商品数据查询响应时间 < 500ms
   - 订单提交验证响应时间 < 300ms

2. **兼容性要求**：
   - 后端必须兼容旧版本的 `is_must` 字段
   - 前端必须能够正确处理 `min_selection = 0` 的情况

3. **数据一致性**：
   - 商品配置修改后，前端缓存需要及时更新
   - 订单提交时的验证规则必须与后台配置完全一致

## 约束和限制

1. **技术约束**：
   - 数据库表结构已经支持 `min_selection`、`max_selection`、`optional_min_count`、`optional_count` 字段
   - 不需要修改数据库表结构，只需要调整逻辑

2. **业务约束**：
   - 不影响已有订单的数据
   - 不影响已有商品的配置（向下兼容）
