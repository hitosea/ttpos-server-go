## 📋 概述

总店在审核的时候，发现品牌采购中的订单编号不是唯一性，导致用户在搜索单据及操作单据时容易出错。本需求通过优化单据编号生成规则，将时间戳从日期级别（yyyyMMdd）提升到秒级别（yyyyMMddHHmmss），确保集团内品牌采购单据编号全局唯一，提升用户体验和操作准确性。

## 🎯 产品对齐

- **业务目标**: 提升单据编号唯一性，降低操作风险，提升审核效率
- **用户价值**: 方便用户快速查找、修改、审批单据，防止误操作
- **技术目标**: 优化编号生成逻辑，确保并发安全，保持历史数据兼容

## 📝 用户故事

**作为** 总店审核人员  
**我想** 品牌采购单据编号具有唯一性  
**以便于** 准确搜索、识别和操作目标单据，避免误操作

## 功能需求

### Requirement 1: 优化单据编号时间戳格式

**用户故事**: 作为 总店审核人员，我想 单据编号使用秒级时间戳，以便于 确保编号在集团内全局唯一

#### 验收标准

1. **WHEN** 系统生成新的单据编号 **THEN** 时间戳部分使用 `yyyyMMddHHmmss` 格式（14位） **SHALL** 替代原有的 `yyyyMMdd` 格式（8位）
2. **IF** 同一秒内生成多个单据 **THEN** 系统 **SHALL** 通过序列号递增确保编号唯一性
3. **WHEN** 历史单据使用旧格式编号 **THEN** 系统 **SHALL** 能正确识别和展示，新旧格式可以共存

#### 具体要求

- [ ] 1.1 修改采购申请（外部）编号生成逻辑：`PR` + `yyyyMMddHHmmss` + `序列号`
- [ ] 1.2 修改采购收货（外部）编号生成逻辑：`PRC` + `yyyyMMddHHmmss` + `序列号`
- [ ] 1.3 修改品牌采购（内部）编号生成逻辑：`TPHY` + `yyyyMMddHHmmss` + `序列号`
- [ ] 1.4 修改品采收货（内部）编号生成逻辑：`TPHY` + `yyyyMMddHHmmss` + `序列号`
- [ ] 1.5 修改盘点单编号生成逻辑：`ST` + `yyyyMMddHHmmss` + `序列号`
- [ ] 1.6 修改调拨单编号生成逻辑：`TR` + `yyyyMMddHHmmss` + `序列号`
- [ ] 1.7 确保历史数据不受影响，不修改已存在的单据编号
- [ ] 1.8 确保并发场景下编号生成的唯一性和安全性

---

### Requirement 2: 统一业务前缀标准

**用户故事**: 作为 系统管理员，我想 单据编号前缀使用标准英文缩写，以便于 统一管理和识别

#### 验收标准

1. **WHEN** 创建采购申请（外部） **THEN** 系统 **SHALL** 使用前缀 `PR`
2. **WHEN** 创建采购收货（外部） **THEN** 系统 **SHALL** 使用前缀 `PRC`
3. **WHEN** 创建品牌采购（内部） **THEN** 系统 **SHALL** 使用前缀 `TPHY`
4. **WHEN** 创建品采收货（内部） **THEN** 系统 **SHALL** 使用前缀 `TPHY`
5. **WHEN** 创建盘点单 **THEN** 系统 **SHALL** 使用前缀 `ST`
6. **WHEN** 创建调拨单 **THEN** 系统 **SHALL** 使用前缀 `TR`

#### 具体要求

- [ ] 2.1 采购申请（外部）前缀统一为 `PR`（Purchase Request）
- [ ] 2.2 采购收货（外部）前缀统一为 `PRC`（Purchase Receipt）
- [ ] 2.3 品牌采购（内部）前缀保持 `TPHY`（TTPOS Purchase）
- [ ] 2.4 品采收货（内部）前缀保持 `TPHY`
- [ ] 2.5 盘点单前缀保持 `ST`（Stock Take）
- [ ] 2.6 调拨单前缀保持 `TR`（Transfer）
- [ ] 2.7 历史数据的前缀不做修改，保持向后兼容

---

### Requirement 3: 确保编号唯一性和并发安全

**用户故事**: 作为 系统，我想 在并发场景下生成唯一编号，以便于 避免编号冲突和数据错误

#### 验收标准

1. **IF** 同一秒内多个用户同时创建单据 **THEN** 系统 **SHALL** 通过序列号递增或分布式锁确保编号唯一
2. **WHEN** 系统生成编号失败 **THEN** 系统 **SHALL** 返回明确的错误信息，不生成重复编号
3. **IF** Redis 服务不可用 **THEN** 系统 **SHALL** 有降级方案确保编号生成不中断

#### 具体要求

- [ ] 3.1 使用数据库事务或分布式锁保护编号生成逻辑
- [ ] 3.2 序列号生成使用 Redis 自增或数据库序列确保唯一性
- [ ] 3.3 实现 Redis 不可用时的降级方案（如使用时间戳+随机数）
- [ ] 3.4 添加编号唯一性校验，防止重复编号入库
- [ ] 3.5 记录编号生成失败的日志，便于排查问题

---

### Requirement 4: 前端展示和搜索兼容

**用户故事**: 作为 用户，我想 搜索和查看新旧格式的单据编号，以便于 正常使用系统功能

#### 验收标准

1. **WHEN** 用户搜索单据编号 **THEN** 系统 **SHALL** 支持新旧两种格式的搜索
2. **WHEN** 前端展示单据编号 **THEN** 系统 **SHALL** 确保长编号能正常显示，不被截断
3. **IF** 用户输入旧格式编号搜索 **THEN** 系统 **SHALL** 能正确匹配历史单据

#### 具体要求

- [ ] 4.1 前端列表页支持显示完整单据编号（最长约 20 位）
- [ ] 4.2 搜索功能支持模糊匹配，兼容新旧格式
- [ ] 4.3 单据详情页正常展示新旧格式编号
- [ ] 4.4 导出功能包含完整单据编号
- [ ] 4.5 前端输入框宽度适配新编号长度

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 编号生成逻辑封装在 Helper 或 Service 中
- **模块化设计**: 各单据类型的编号生成逻辑独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [ ] URL 使用 snake_case 命名（如：`/api/v1/shop/purchase_order`）
- [ ] data 字段必须是对象，不能是 null 或数组
- [ ] 响应格式：`{code, message, data{}}`
- [ ] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 数据库设计要求

- [ ] 单据编号字段长度需支持新格式（建议 varchar(50)）
- [ ] 在单据编号字段上建立索引，提升查询性能
- [ ] 参考: `.cursor/rules/database.mdc` - 数据库开发规范

### 性能要求

- [ ] 编号生成响应时间 < 50ms
- [ ] 并发场景下编号生成不阻塞业务
- [ ] 使用 Redis 缓存序列号，减少数据库查询

### 测试要求

- [ ] Service 层测试覆盖率 ≥ 70%
- [ ] 编号生成逻辑单元测试覆盖率 100%
- [ ] 并发测试：验证同一秒内生成多个编号的唯一性
- [ ] 集成测试覆盖所有单据类型的编号生成
- [ ] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 安全要求

- [ ] 编号生成逻辑防止 SQL 注入（使用参数化查询）
- [ ] 并发场景下使用分布式锁防止重复生成
- [ ] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [ ] 编号生成失败时返回明确错误信息
- [ ] 事务管理（保证编号生成和单据创建的一致性）
- [ ] 错误日志记录（使用 Logger）
- [ ] Redis 不可用时的降级方案

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error

### 业务约束

- **历史数据兼容**: 不修改已存在的单据编号，保持向后兼容
- **编号长度**: 新编号最长约 20 位（前缀 2-4 位 + 时间戳 14 位 + 序列号 4 位）
- **序列号范围**: 序列号从 0001 开始，每天重置（或使用全局序列）

### 资源约束

- 开发时间: 3-5 天
- Story Point: 5 SP (必须 ≤ 5)

## 风险和缓解

### 风险 1: 并发场景下编号重复

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 使用数据库事务或分布式锁保护编号生成
- 使用 Redis 自增序列号确保唯一性
- 添加唯一性校验，防止重复编号入库

### 风险 2: 历史数据兼容性问题

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 明确不修改历史数据，只对新生成的单据应用新规则
- 搜索功能支持模糊匹配，兼容新旧格式
- 前端展示逻辑兼容新旧格式

### 风险 3: 前端展示受影响

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 检查并调整前端展示，确保长编号能正常显示
- 列表页和详情页适配新编号长度
- 导出功能包含完整单据编号

### 风险 4: Redis 服务不可用

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 实现 Redis 不可用时的降级方案（使用时间戳+随机数）
- 记录降级日志，便于监控和排查
- 确保降级方案不影响业务连续性
