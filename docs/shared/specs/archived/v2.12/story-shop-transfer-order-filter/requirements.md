## 📋 概述

当前新管理端的调拨单列表将本店提交和其他门店提交的调拨单混合展示，导致区分与定位困难。通过新增“提交方”筛选（全部/本店提交/他店提交），让店长与仓管能快速按来源查看并减少误操作。

## 🎯 产品对齐

- 提升列表可用性与清晰度，贴合门店日常调拨的关注方式（发出 vs 收到）。
- 降低误处理风险，帮助快速定位需要处理的调拨单。
- 支撑后续统计与运营（发出/收到的调拨量区分）。

## 📝 用户故事

**作为** 商户管理员或仓管人员  
**我想** 在调拨单列表中按提交方快速筛选（全部/本店提交/他店提交）  
**以便于** 分别管理发出的调拨和收到的调拨，提升管理效率并减少误操作

## 功能需求

### Requirement 1: 提交方筛选按钮组

**用户故事**: 作为店长/仓管，我想通过“提交方”按钮组查看特定来源的调拨单。

#### 验收标准

1. **WHEN** 页面加载 **THEN** 默认选中“全部”，展示与本店相关的所有调拨单（本店发出 + 本店收到）。
2. **WHEN** 选择“本店提交” **THEN** 仅展示本店作为调出方的调拨单。
3. **WHEN** 选择“他店提交” **THEN** 仅展示其他门店发起、本店作为调入方的调拨单。
4. **WHEN** 切换筛选条件 **AND** 组合其他现有筛选（日期、状态等） **THEN** 列表结果实时更新且条件互不冲突。
5. **IF** 筛选结果为空 **THEN** 显示友好的空状态提示和返回全部的快捷操作。

#### 具体要求

- [ ] 在列表顶部新增“提交方”按钮组，包含：全部（默认）/ 本店提交 / 他店提交。
- [ ] 选中状态需高亮且与现有筛选样式一致。
- [ ] 筛选条件写入 URL 或前端持久化，页面刷新或返回时保持最近一次选择。
- [ ] 与分页、排序、日期、状态等筛选联动，参数组合需一致、可复用。

---

### Requirement 2: API 查询支持提交方筛选

**用户故事**: 作为前端调用方，我想通过查询参数指定提交方来源，使列表数据精准返回。

#### 验收标准

1. **WHEN** 请求参数 `submit_side` 缺省或为 `all` **THEN** 返回与本店相关的全部调拨单。
2. **WHEN** `submit_side=self` **THEN** 仅返回本店作为调出方的调拨单。
3. **WHEN** `submit_side=other` **THEN** 仅返回其他门店发起、本店作为调入方的调拨单。
4. **IF** `submit_side` 值非法 **THEN** 返回参数校验错误，不执行查询。

#### 具体要求

- [ ] 新增查询参数：`submit_side` ∈ {`all`,`self`,`other`}，默认 `all`。
- [ ] 使用当前登录门店 ID 进行过滤：`self` 按 `from_store_id = current_store_id`，`other` 按 `to_store_id = current_store_id` 且 `from_store_id != current_store_id`。
- [ ] 保持现有响应结构与分页字段不变，新增参数需在 API 文档中说明。
- [ ] 确认调拨单表的 `from_store_id`、`to_store_id` 具备合适索引，避免筛选性能退化。

---

### Requirement 3: 状态保持与交互反馈

**用户故事**: 作为使用者，我希望筛选状态可被记住，并在交互中获得清晰反馈。

#### 验收标准

1. **WHEN** 页面刷新或返回列表 **THEN** 仍保留上次选择的提交方筛选。
2. **WHEN** 正在加载筛选结果 **THEN** 展示加载状态，避免误认为卡顿。
3. **WHEN** 列表无数据 **THEN** 展示空状态与“查看全部”或“重置筛选”入口。

#### 具体要求

- [ ] 筛选状态可通过 URL 参数或本地缓存持久化，并在进入页面时恢复。
- [ ] 需有加载态与错误提示，错误时保留上次成功的列表数据。
- [ ] QA 需覆盖三种筛选值与与现有筛选组合的回归用例。

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层。
- **单一职责原则**: 每个文件聚焦一类逻辑，避免耦合 UI 与查询组装。
- **模块化设计**: 筛选参数组装与 API 调用封装成可复用方法。
- **依赖管理**: 前端仅通过 API 封装层调用，后端 Service 不直接暴露查询实现。
- **遵循规范**:
  - `.cursor/rules/go-main.mdc`
  - `.cursor/rules/api.mdc`
  - `.cursor/rules/database.mdc`
  - `.cursor/rules/structs.mdc`

### API 设计要求

- [x] URL 使用 snake_case，`submit_side` 作为查询参数。
- [x] data 字段为对象，分页信息放在 meta。
- [x] 响应格式 `{code, message, data{}}`。
- [x] 在 API 文档中标注默认值与可选值，并说明与其他筛选的组合。

### 数据库设计要求

- [x] 复用现有表结构，不新增字段。
- [x] 确认 `from_store_id`、`to_store_id` 索引存在且可用于筛选。
- [x] 金额、时间等字段沿用现有规范，不修改字段含义。

### 性能要求

- [x] 本地响应时间 < 200ms；列表查询使用索引避免全表扫描。
- [x] 支持分页，避免一次性返回过大数据集。
- [ ] 需根据实际压测结果补充缓存策略（若必要）。

### 测试要求

- [x] 前后端联调覆盖三种提交方筛选值及与日期/状态的组合。
- [x] API 单元/集成测试验证 `submit_side` 参数取值与错误处理。
- [x] 空数据、异常数据、切换筛选快速点击等交互用例。
- [ ] 支付/订单高风险专项：若复用订单模块公用方法需补充覆盖率。

### 国际化要求

- [x] 新增/复用筛选按钮文案需接入多语言。

### 安全要求

- [x] API 需鉴权，使用当前登录门店信息进行过滤。
- [x] 参数校验防止 SQL 注入；使用 ORM 参数化。

### 可靠性要求

- [x] 查询异常时返回明确错误码与提示，不抛 panic。
- [x] 日志记录筛选参数，便于排查。

## 验收标准

### 功能验收

1. **提交方筛选**: 三种筛选值均返回符合预期的数据集。
2. **组合筛选**: 与日期、状态等条件组合后结果正确且分页正常。
3. **状态保持**: 刷新或返回列表后，筛选状态保持且结果与状态一致。

### 测试验收

1. **单元测试**: API 参数校验与查询逻辑覆盖。
2. **API 测试**: 三种筛选值及异常值用例通过。
3. **集成测试**: 前后端联调流程、空状态、快速切换场景通过。

### 文档验收

1. **技术文档**: design.md 补充接口参数与查询逻辑。
2. **API 文档**: 说明 `submit_side` 取值、默认值、组合规则。
3. **测试文档**: tasks.md 中的测试用例执行并记录结果。

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin；不使用 panic，返回 error。
- Service 仅依赖接口，Repository 不持有 DBManager。

#### Flutter 前端模块

- 前端实现在 `ttpos-flutter` 仓库，不在本后端 Spec 范围。
- 后端需提供符合规范的 API，确保 Flutter 端可正常调用。

### 业务约束

- 不改变调拨单原有状态流转与权限模型，仅新增筛选能力。

### 资源约束

- 开发时间: 2 天（含前后端联调）
- Story Point: 3（≤5）

## 风险和缓解

### 风险 1: 数据量大导致查询变慢

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 确认并补充 `from_store_id`、`to_store_id` 索引。
- 如需要，限制单次分页大小并监控慢查询。

### 风险 2: 与现有筛选组合出现逻辑冲突

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 设计与 QA 覆盖筛选组合用例。
- 保持查询参数组装的单测与接口契约文档。
