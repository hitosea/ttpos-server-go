# story-ttpos-erp-payment-mode-save / SaveModeOfPayment 需求说明

> 基于 DooTask #37499（ERPNext对接-支付方式），规范 TTPOS 与 ERP 支付方式的创建、命名和双向同步。

## 1. 概要

| 字段 | 说明 |
| --- | --- |

| 主要角色 | ERP/TTPOS 集成维护者、商户管理员 |

## 2. 背景与目标

- 现状：支付方式命名缺少统一规则，ERP↔TTPOS 双向同步易出现重名、不可读或冲突；缺少标准化保存接口。
- 目标：新增 `SaveModeOfPayment` 接口，强制执行“渠道+支付方式+4位序号+商户简称”命名规则，确保命名可读且唯一；支持 ERP 与 TTPOS 双向同步，保留存量数据不回写。

## 3. 业务/功能需求

1. 支付方式保存
   - 输入：`company_abbr`（必填）、`branch`（必填）、`channel`（必填，来自 TTPOS 渠道，如 `LianLianPay`）、`pay_type`（必填，TTPOS 支付类型）。
   - 生成名称：`{channel}-{pay_type}-{4位序号} - {company_abbr}`。
   - 序号：按 `channel + pay_type` 维度递增；系统/默认占用 `0000`，自建从 `0001` 起；冲突时顺延。
   - 返回：规范化名称、唯一标识/ID（若有）、状态。
2. 校验与错误
   - 缺少必填字段或非法字符时返回校验错误，不落库。
   - 并发下需避免重复序号；失败应返回明确错误码并可重试。
3. 同步规则
   - TTPOS 新增/更新支付方式 → 同步到 ERP，使用规范化名称。
   - ERP 新增/更新支付方式 → 同步回 TTPOS；旧数据保持原名，不强制重算。
4. 数据兼容
   - 存量支付方式只读，不改名；新建遵循新规则。
   - 状态字段沿用现有 TTpos/ERP 状态映射。

## 4. 约束与假设

- 渠道枚举来自 TTPOS 侧输入；未识别渠道按“通用”处理，仍按规则命名。
- 4 位序号足够当前规模；若溢出需告警并阻断创建。
- ERP/TTPOS 已具备基础支付方式实体与状态字段，对接仅新增保存与同步逻辑。

## 5. 验收标准（AC）

1. 当传入 `channel=LianLianPay, pay_type=Alipay, company_abbr=No.21` 时，返回名称 `LianLianPay-Alipay-0000 - No.21`，落库并同步成功。
2. 当同一组合再次自建支付方式时，序号从 `0001` 起递增（如 `LianLianPay-Alipay-0001 - No.21`），不与 `0000` 冲突。
3. 当缺失 `company_abbr` 或 `pay_type` 时，接口返回校验错误，不写入。
4. 当 TTPOS 创建/更新支付方式时，可在 ERP 看到对应记录且名称一致；ERP 侧更新后 TTPOS 侧同步成功。
5. 并发创建同一组合时，最终落库名称唯一且符合递增规则，无重复。

## 6. 不在范围

- 既有支付方式批量重命名。
- UI 交互与前端管理界面改造。
- 支付渠道接入能力本身（仅处理命名与保存/同步）。
