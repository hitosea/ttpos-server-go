## 📋 概述

实现 Kiosk 自助点餐机首页功能模块，提供统一的首页入口，包含轮播广告展示、用餐方式选择、多语言切换、呼叫服务员等核心功能。首页作为用户登录后的第一个界面，需要提供清晰的信息展示和操作引导。

**实现范围**：实现后端 API 接口，参考收银机（Cashier）、平板端（Tablet）、助手端（Assistant）等终端的 base 接口和呼叫服务员接口实现。

## 🎯 产品对齐

- **用户体验**：提供清晰的首页入口，引导用户快速进入点餐流程
- **多场景支持**：通过用餐方式选择，支持堂食和外带两种业务场景
- **国际化支持**：通过多语言切换，满足不同地区用户的语言需求
- **营销推广**：通过轮播广告展示，提升商家营销效果
- **服务支持**：通过呼叫服务员功能，提供人工服务支持

## 功能需求

### Requirement 1: 获取首页基本信息

**用户故事**: 作为 顾客，我想 在首页看到商家信息、设备信息、语言列表和轮播广告配置，以便于 了解商家信息和功能配置

#### 验收标准

1. **WHEN** 用户登录成功并请求首页信息 **THEN** 系统 **SHALL** 返回商家基本信息（名称、Logo等）、设备信息（设备ID、设备备注等）、语言列表配置、轮播广告配置
2. **WHEN** 商家在后台配置轮播广告和语言列表 **THEN** 系统 **SHALL** 在首页接口返回最新配置
3. **WHEN** 网络异常或配置获取失败 **THEN** 系统 **SHALL** 返回友好错误提示，支持使用默认配置

#### 具体要求

- [ ] 1.1 实现 `/api/v1/kiosk/base` 接口，参考 `/api/v1/cashier/base`、`/api/v1/tablet/base`、`/api/v1/assistant/base` 的实现方式
- [ ] 1.2 返回商家基本信息（名称、Logo等），从 `company` 表获取
- [ ] 1.3 返回设备信息（设备ID、设备备注等），从 `device` 表获取
- [ ] 1.4 返回语言列表配置，从商家后台自助点餐机设置中获取（参考 `/api/v1/shop/setting/kiosk` 接口的 `language_list` 字段）
- [ ] 1.5 返回轮播广告配置，从商家后台自助点餐机设置中获取
- [ ] 1.6 实现配置缓存机制，定期刷新配置数据，提升性能
- [ ] 1.7 增加配置变更通知机制，支持实时更新

---

### Requirement 2: 轮播广告展示

**用户故事**: 作为 顾客，我想 在首页看到轮播广告，以便于 了解商家信息和最新活动

#### 验收标准

1. **WHEN** 用户进入首页 **THEN** 系统 **SHALL** 从商家后台获取轮播广告配置，支持图片和视频轮播
2. **WHEN** 商家在后台配置轮播广告 **THEN** 系统 **SHALL** 在首页展示最新配置
3. **WHEN** 轮播广告配置为空或不存在 **THEN** 系统 **SHALL** 显示默认占位图或隐藏轮播区域

#### 具体要求

- [ ] 2.1 轮播广告配置从商家后台自助点餐机设置中获取（通过 `/api/v1/kiosk/base` 接口返回）
- [ ] 2.2 支持图片和视频两种类型的轮播内容
- [ ] 2.3 支持自动播放和手动切换功能（前端实现）
- [ ] 2.4 支持点击广告跳转到指定页面（可选，前端实现）
- [ ] 2.5 轮播广告数据格式参考商家后台自助点餐机设置的数据结构

---

### Requirement 3: 用餐方式选择

**用户故事**: 作为 顾客，我想 在首页选择用餐方式（堂食/外带），以便于 根据我的需求快速进入点餐流程

#### 验收标准

1. **WHEN** 用户在首页选择用餐方式（堂食/外带） **THEN** 系统 **SHALL** 保存选择，影响后续订单的取餐方式
2. **WHEN** 用户在订单确认页面修改用餐方式 **THEN** 系统 **SHALL** 更新订单的取餐方式
3. **WHEN** 用户未选择用餐方式 **THEN** 系统 **SHALL** 使用默认值（堂食）或提示用户选择

#### 具体要求

- [ ] 3.1 用餐方式选择在前端实现，选择后保存到本地存储或状态管理
- [ ] 3.2 用餐方式影响后续订单的取餐方式字段（`takeout_type` 或类似字段）
- [ ] 3.3 支持在订单确认页面修改用餐方式
- [ ] 3.4 用餐方式选项：堂食（dine_in）、外带（takeout）

---

### Requirement 4: 多语言切换

**用户故事**: 作为 顾客，我想 在首页切换界面语言，以便于 使用我熟悉的语言进行点餐

#### 验收标准

1. **WHEN** 用户在首页切换语言 **THEN** 系统 **SHALL** 更新界面文字、商品名称、描述等，支持简体中文、繁体中文、英文等多种语言
2. **WHEN** 用户切换语言后浏览商品 **THEN** 系统 **SHALL** 显示对应语言的商品名称和描述
3. **WHEN** 商品缺少某种语言的翻译 **THEN** 系统 **SHALL** 显示默认语言（简体中文）或降级方案

#### 具体要求

- [ ] 4.1 语言列表从商家后台自助点餐机设置中获取（通过 `/api/v1/kiosk/base` 接口返回 `language_list` 字段）
- [ ] 4.2 支持简体中文、繁体中文、英文等多种语言
- [ ] 4.3 语言切换在前端实现，切换后保存到本地存储或状态管理
- [ ] 4.4 语言切换影响界面文字、商品名称、描述等的显示
- [ ] 4.5 支持默认语言设置，从商家后台配置获取
- [ ] 4.6 提供多语言数据缺失时的降级方案（显示默认语言）

---

### Requirement 5: 呼叫服务员功能

**用户故事**: 作为 顾客，我想 在首页呼叫服务员，以便于 在需要帮助时快速获得人工服务

#### 验收标准

1. **WHEN** 用户点击呼叫服务员按钮 **THEN** 系统 **SHALL** 发送呼叫通知到相关终端（KDS、Assistant等），显示呼叫成功提示
2. **WHEN** 呼叫服务员成功 **THEN** 系统 **SHALL** 返回成功提示信息
3. **WHEN** 呼叫服务员失败 **THEN** 系统 **SHALL** 返回友好错误提示，支持重试
4. **WHEN** 用户取消呼叫 **THEN** 系统 **SHALL** 取消呼叫通知（如支持）

#### 具体要求

- [ ] 5.1 实现 `/api/v1/kiosk/call` 接口，参考 `/api/v1/tablet/call`、`/api/v1/h5/call` 的实现方式
- [ ] 5.2 呼叫服务员服务通知相关终端（KDS、Assistant等），复用现有的呼叫服务逻辑
- [ ] 5.3 返回呼叫成功提示信息
- [ ] 5.4 实现呼叫服务的重试机制和状态查询
- [ ] 5.5 增加呼叫日志记录，便于问题排查
- [ ] 5.6 支持取消呼叫功能（如需要，前端实现）

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [x] URL 使用 snake_case 命名（如：`/api/v1/kiosk/base`）
- [x] data 字段必须是对象，不能是 null 或数组
- [x] 分页信息统一放在 meta 中
- [x] 响应格式：`{code, message, data{}}`
- [x] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 数据库设计要求

- [x] 复用现有的 `store_setting` 表存储自助点餐机设置（key = "kiosk"）

- [x] 复用现有的 `company` 表存储商家信息
- [x] 参考: `.cursor/rules/database.mdc` - 数据库开发规范

### 性能要求

- [ ] 本地响应时间 < 200ms

- [ ] API 测试覆盖所有接口
- [ ] 集成测试覆盖核心流程（首页信息获取、呼叫服务员）
- [ ] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 国际化要求

- [x] 支持多种语言（简体中文、繁体中文、英文等）
- [x] 语言列表从商家后台配置获取
- [x] 所有文案使用多语言实现
- [x] 参考: `main/i18n/` - 国际化配置

- [ ] 错误日志记录（使用 Logger）
- [ ] 故障恢复机制（配置缓存失效时重新获取）

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error

### 业务约束

- 首页功能模块是 Kiosk 自助点餐机终端的一部分，需要与登录认证功能配合使用
- 轮播广告和语言列表配置依赖商家后台的自助点餐机设置功能
- 呼叫服务员功能依赖现有的呼叫服务基础设施

### 资源约束

- 开发时间: 3-4 天
- Story Point: 5-8（待技术评审确认，必须 ≤ 5）

## 风险和缓解

### 风险 1: 配置数据同步风险

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 实现配置缓存机制，定期刷新配置数据
- 增加配置变更通知机制，支持实时更新
- 配置获取失败时使用默认配置，保证系统可用性

### 风险 2: 呼叫服务员通知风险

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 实现呼叫服务的重试机制和状态查询
- 增加呼叫日志记录，便于问题排查
- 呼叫失败时返回友好错误提示，支持重试

### 风险 3: 多语言数据完整性风险

**影响**: 低  
**概率**: 中  
**缓解措施**:

- 建立多语言数据管理流程，确保数据完整性
- 提供多语言数据缺失时的降级方案（显示默认语言）
- 在商品服务中确保多语言数据完整性

### 风险 4: 大屏适配风险

**影响**: 低  
**概率**: 中  
**缓解措施**:

- 在多种设备上进行测试，建立设备兼容性清单
- 使用响应式布局，支持不同分辨率适配
- 前端实现时考虑大屏触摸交互特点
