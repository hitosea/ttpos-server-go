## 📋 概述

在点餐时（收银机/点餐助手/H5/平板）为菜品添加备注时，可以直接从商户后台已设置的预设选项中选择，无需手动输入。支持为不同菜品显示不同的备注选项，提高操作效率。

**业务价值**：
- 提升点餐效率，减少重复输入时间
- 降低操作错误率，提高服务质量
- 缩短顾客等待时间，提升满意度
- 支持快速选择常用备注，提升用户体验

**前置条件**：
- ✅ 商户后台的备注预设管理功能已实现
- ✅ 商户可以为菜品关联备注预设
- ✅ 备注预设数据已存储在数据库中

## 🎯 产品对齐

该功能支持提升点餐效率和用户体验的产品目标，通过预设备注选项减少重复操作，提高收银员和点餐员的工作效率，同时保证服务质量的一致性。

## 📝 用户故事

**作为** 收银员/点餐员  
**我想** 从预设的备注选项中选择菜品备注  
**以便于** 快速完成点餐，减少重复输入时间

## 功能需求

### Requirement 1: 获取菜品备注预设列表

**用户故事**: 作为收银员/点餐员，我想在点餐时看到菜品的预设备注选项，以便于快速选择

#### 验收标准

1. **WHEN** 用户为菜品添加备注 **THEN** 系统 **SHALL** 调用 API 获取该菜品的备注预设列表
2. **IF** 菜品有关联的备注预设 **THEN** 系统 **SHALL** 返回菜品专属的备注预设列表（按排序顺序）
3. **IF** 菜品无关联备注预设 **THEN** 系统 **SHALL** 返回全局备注预设列表（如有）
4. **WHEN** 备注预设被禁用 **THEN** 系统 **SHALL** 不返回该预设
5. **WHEN** API 调用失败 **THEN** 系统 **SHALL** 优雅降级，允许手动输入备注

#### 具体要求

- [ ] 1.1 提供 API 接口获取菜品的备注预设列表
- [ ] 1.2 API 接口需要身份验证
- [ ] 1.3 返回的备注预设按排序顺序排列
- [ ] 1.4 只返回启用状态的备注预设
- [ ] 1.5 支持缓存备注预设列表（Redis），减少数据库查询
- [ ] 1.6 API 响应时间 < 200ms

---

### Requirement 2: 点餐端显示备注选择界面

**用户故事**: 作为收银员/点餐员，我想在点餐时看到备注选择界面，以便于快速选择备注

#### 验收标准

1. **WHEN** 用户点击为菜品添加备注 **THEN** 系统 **SHALL** 显示备注选择界面
2. **WHEN** 备注预设列表加载完成 **THEN** 系统 **SHALL** 显示预设选项列表
3. **WHEN** 备注预设列表为空 **THEN** 系统 **SHALL** 显示手动输入框
4. **WHEN** 备注预设加载失败 **THEN** 系统 **SHALL** 显示手动输入框（优雅降级）
5. **IF** 备注预设数量较多 **THEN** 系统 **SHALL** 支持搜索功能

#### 具体要求

- [ ] 2.1 在 POS 收银端支持显示备注选择界面
- [ ] 2.2 在 Assistant 助手端支持显示备注选择界面
- [ ] 2.3 在 Tablet 平板端支持显示备注选择界面
- [ ] 2.4 在 Mobile/H5 扫码端支持显示备注选择界面
- [ ] 2.5 备注选择界面按预设的排序顺序显示
- [ ] 2.6 备注选择界面适配不同终端屏幕尺寸
- [ ] 2.7 支持搜索备注预设（备注内容较多时）
- [ ] 2.8 备注选择界面支持单选或多选（根据业务需求）
- [ ] 2.9 备注选择界面显示加载状态

---

### Requirement 3: 快速选择预设备注

**用户故事**: 作为收银员/点餐员，我想点击预设选项快速选择备注，以便于快速完成点餐

#### 验收标准

1. **WHEN** 用户点击预设备注选项 **THEN** 系统 **SHALL** 自动填充备注内容到订单项
2. **WHEN** 用户选择多个预设备注 **THEN** 系统 **SHALL** 将多个备注内容合并（用逗号分隔）
3. **WHEN** 用户取消选择预设备注 **THEN** 系统 **SHALL** 移除对应的备注内容
4. **WHEN** 用户选择预设备注后提交订单 **THEN** 系统 **SHALL** 保存备注内容到订单项

#### 具体要求

- [ ] 3.1 支持点击选择预设备注
- [ ] 3.2 支持多选预设备注（如需要）
- [ ] 3.3 多个备注内容自动合并（用逗号分隔）
- [ ] 3.4 备注内容实时显示在订单项中
- [ ] 3.5 支持取消已选择的备注
- [ ] 3.6 订单提交时保存备注内容到订单项

---

### Requirement 4: 自定义备注输入

**用户故事**: 作为收银员/点餐员，我想在需要时手动输入自定义备注，以便于满足特殊需求

#### 验收标准

1. **WHEN** 用户需要输入自定义备注 **THEN** 系统 **SHALL** 提供手动输入框
2. **WHEN** 用户同时选择预设备注和输入自定义备注 **THEN** 系统 **SHALL** 将两者合并保存
3. **WHEN** 用户只输入自定义备注 **THEN** 系统 **SHALL** 保存自定义备注内容
4. **WHEN** 订单提交时 **THEN** 系统 **SHALL** 保存备注内容（预设或自定义）到订单项

#### 具体要求

- [ ] 4.1 保留手动输入备注功能
- [ ] 4.2 支持预设备注和自定义备注同时使用
- [ ] 4.3 自定义备注内容长度限制：最多 200 个字符
- [ ] 4.4 备注内容保存到订单项，支持查看历史订单备注

---

### Requirement 5: 备注数据兼容性

**用户故事**: 作为系统用户，我想查看历史订单的备注信息，以便于追溯订单详情

#### 验收标准

1. **WHEN** 用户查看历史订单 **THEN** 系统 **SHALL** 显示订单项的备注内容（无论预设或自定义）
2. **IF** 备注预设被删除 **THEN** 系统 **SHALL** 仍能显示历史订单中的备注内容
3. **WHEN** 订单备注内容被修改 **THEN** 系统 **SHALL** 记录修改历史（如需要）

#### 具体要求

- [ ] 5.1 订单项备注字段存储实际备注内容（文本），不存储预设 ID
- [ ] 5.2 历史订单备注内容独立存储，不受预设删除影响
- [ ] 5.3 支持查看历史订单的备注内容

- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error

### 业务约束

- 备注预设数据由商户后台管理（已实现）
- 订单项备注字段存储实际备注内容（文本），不存储预设 ID
- 自定义备注内容长度限制：最多 200 个字符
- 备注预设列表需要缓存，提高性能

### 资源约束

- 开发时间: 3-4 天
- Story Point: 3 (必须 ≤ 5)

## 风险和缓解

### 风险 1: 不同终端（H5/平板）的交互方式需要统一设计

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 统一设计备注选择组件，适配不同终端
- 使用响应式设计，适配不同屏幕尺寸
- 在多个终端进行充分测试

### 风险 2: API 性能问题（备注预设列表查询）

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 使用 Redis 缓存备注预设列表
- 优化数据库查询（使用索引）
- 设置合理的缓存失效策略

### 风险 3: 网络异常时的用户体验

**影响**: 低  
**概率**: 中  
**缓解措施**:

- 实现优雅降级，API 失败时允许手动输入备注
- 显示友好的错误提示
- 支持离线模式（如需要）
