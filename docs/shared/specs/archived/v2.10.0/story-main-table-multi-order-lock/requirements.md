## 📋 概述

统一并台、转台和转菜操作的锁机制，使用订单级别的锁（`SaleBillUuid`），当操作涉及多个订单时，需要获取所有相关订单的锁，并按照统一的顺序获取锁以避免死锁。

本功能主要解决当前并台、转台、转菜操作中锁粒度不一致的问题，提高并发性能，同时保证数据一致性。

## 🎯 产品对齐

该功能支持系统并发性能优化目标：

- **提高并发性能**：使用订单级别的锁，不同订单的操作可以并发执行，提高系统吞吐量
- **保证数据一致性**：当操作涉及多个订单时，锁定所有相关订单，避免数据竞争
- **避免死锁**：通过统一的锁获取顺序（按订单 UUID 排序），避免死锁风险
- **符合业务逻辑**：并台、转台、转菜操作本质上是订单级别的操作，使用订单锁更符合业务语义

## 功能需求

### Requirement 1: 并台操作多订单锁

**用户故事**: 作为系统，我想在并台操作时锁定所有涉及的订单，以便于避免数据竞争和死锁

#### 验收标准

1. **WHEN** 执行并台操作 **THEN** 系统 **SHALL** 锁定主订单和所有被合并的订单（按 UUID 排序）
2. **IF** 并台操作涉及多个订单 **THEN** 系统 **SHALL** 按订单 UUID 升序依次获取锁
3. **WHEN** 锁获取失败 **THEN** 系统 **SHALL** 返回适当的错误提示
4. **WHEN** 操作完成 **THEN** 系统 **SHALL** 按相反顺序释放所有锁

#### 具体要求

- [ ] 1.1 修改并台操作（`MergeDesk`）的锁机制，移除 `companyUuid` 锁
- [ ] 1.2 收集所有需要锁定的订单 UUID（主订单 + 所有被合并的订单）
- [ ] 1.3 按订单 UUID 排序后依次获取锁
- [ ] 1.4 按相反顺序释放锁
- [ ] 1.5 确保锁的获取和释放顺序正确
- [ ] 1.6 保持现有业务逻辑不变，仅调整锁的粒度

---

### Requirement 2: 转台操作多资源锁

**用户故事**: 作为系统，我想在转台操作时锁定源订单和目标桌台，以便于避免与开台操作并发冲突

#### 验收标准

1. **WHEN** 执行转台操作 **THEN** 系统 **SHALL** 锁定源订单和目标桌台（按 UUID 排序）
2. **IF** 转台操作和开台操作同时涉及同一桌台 **THEN** 系统 **SHALL** 串行执行，避免并发冲突
3. **WHEN** 锁获取失败 **THEN** 系统 **SHALL** 返回适当的错误提示
4. **WHEN** 操作完成 **THEN** 系统 **SHALL** 按相反顺序释放所有锁

#### 具体要求

- [ ] 2.1 修改转台操作（`ChangeDesk`）的锁机制，增加目标桌台的锁
- [ ] 2.2 收集需要锁定的资源：源订单 UUID + 目标桌台 UUID
- [ ] 2.3 按 UUID 排序后依次获取锁
- [ ] 2.4 按相反顺序释放锁
- [ ] 2.5 确保转台操作与开台操作使用相同的桌台锁，避免并发冲突
- [ ] 2.6 保持现有业务逻辑不变，仅调整锁的粒度

---

### Requirement 3: 转菜操作多订单锁

**用户故事**: 作为系统，我想在转菜操作时锁定源订单和目标订单，以便于避免数据不一致

#### 验收标准

1. **WHEN** 执行转菜操作 **THEN** 系统 **SHALL** 锁定源订单和目标订单（按 UUID 排序）
2. **IF** 转菜操作涉及两个订单 **THEN** 系统 **SHALL** 按订单 UUID 升序依次获取锁
3. **WHEN** 锁获取失败 **THEN** 系统 **SHALL** 返回适当的错误提示
4. **WHEN** 操作完成 **THEN** 系统 **SHALL** 按相反顺序释放所有锁

#### 具体要求

- [ ] 3.1 修改转菜操作（`InstantOrderCartProductChangeDesk`）的锁机制，增加目标订单的锁
- [ ] 3.2 获取目标订单 UUID（通过目标桌台 UUID 查询）
- [ ] 3.3 按订单 UUID 排序后依次获取锁
- [ ] 3.4 按相反顺序释放锁
- [ ] 3.5 保持现有业务逻辑不变，仅调整锁的粒度

---

### Requirement 4: 统一的锁管理工具

**用户故事**: 作为开发者，我想使用统一的锁管理工具函数，以便于简化代码并确保锁获取顺序一致

#### 验收标准

1. **WHEN** 需要锁定多个订单 **THEN** 系统 **SHALL** 提供统一的工具函数
2. **IF** 工具函数处理多个 UUID **THEN** 系统 **SHALL** 自动去重并排序
3. **WHEN** 使用工具函数 **THEN** 系统 **SHALL** 确保所有操作都使用相同的排序规则

#### 具体要求

- [ ] 4.1 实现 `LockMultipleOrders` 函数，支持锁定多个订单（按 UUID 排序）
- [ ] 4.2 实现 `UnlockMultipleOrders` 函数，支持释放多个订单锁（按相反顺序）
- [ ] 4.3 工具函数自动去重（避免重复锁定同一订单）
- [ ] 4.4 工具函数自动过滤无效 UUID（0 值）
- [ ] 4.5 在并台、转台、转菜操作中使用统一的工具函数

## 验收标准

### 功能验收

1. **并台操作锁机制**: 锁定主订单和所有被合并的订单（按 UUID 排序），操作完成后按相反顺序释放
2. **转台操作锁机制**: 锁定源订单和目标桌台（按 UUID 排序），避免与开台操作并发冲突
3. **转菜操作锁机制**: 锁定源订单和目标订单（按 UUID 排序），操作完成后按相反顺序释放
4. **锁管理工具**: 提供统一的锁管理工具函数，自动去重和排序

### 测试验收

1. **单元测试**: Service 和 Repository 覆盖率达标
2. **并发测试**: 并台、转台、转菜操作的并发场景测试通过
   - 重点测试：转台操作与开台操作同时操作同一桌台的并发场景
3. **死锁测试**: 验证所有操作都按订单 UUID 排序获取锁，避免死锁
4. **集成测试**: 端到端流程测试通过

### 文档验收

1. **技术文档**: design.md 包含完整的锁机制设计
2. **代码注释**: 锁获取和释放逻辑有清晰的注释说明

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 使用现有的锁机制（`main/pkg/lock/lock_redsync.go`）
- Service 层使用锁管理工具函数
- 不使用 panic，返回 error
- 锁的获取和释放必须在同一个函数中，使用 defer 确保释放

### 业务约束

- 并台操作涉及多个订单（主订单 + 所有被合并的订单）
- 转台操作涉及源订单和目标桌台
- 转菜操作涉及源订单和目标订单
- 所有操作必须按订单 UUID 排序获取锁，避免死锁

## 风险和缓解

### 风险 1: 死锁风险

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 统一按订单 UUID 排序后获取锁，确保所有操作都按相同顺序获取锁
- 实现统一的锁获取工具函数，确保所有操作都使用相同的排序规则
- 代码审查：确保所有操作都使用统一的锁获取顺序

### 风险 2: 锁获取顺序错误

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 实现统一的锁管理工具函数，确保所有操作都使用相同的排序规则
- 代码审查：确保所有操作都使用统一的锁获取顺序
- 单元测试：测试多订单锁的获取和释放逻辑

### 风险 3: 性能影响

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 并台操作相对较少，性能影响可接受
- 不同订单的操作可以并发执行，提高系统吞吐量
- 性能测试：在高并发场景下测试锁的性能影响

### 风险 4: 代码复杂度增加

**影响**: 低  
**概率**: 中  
**缓解措施**:

- 封装锁管理工具函数，简化代码
- 代码审查：确保代码清晰易懂
- 单元测试：测试多订单锁的获取和释放逻辑

### 风险 5: 转台操作与开台操作的并发冲突

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 转台操作需要锁定目标桌台（`DeskUuid`），与开台操作使用相同的锁，确保串行执行
- 集成测试：测试转台操作与开台操作同时操作同一桌台的并发场景
- 验证转台操作锁定目标桌台后，开台操作会被正确阻塞
- 锁顺序验证：确保转台操作锁定源订单和目标桌台时，按 UUID 排序获取锁
