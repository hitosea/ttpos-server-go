## 📋 概述

在旧管理端（PHP Admin 模块）的商品管理模块中，创建或编辑套餐时，套餐组的"可选数量"字段目前允许输入 0，这会导致业务逻辑错误。本需求要求在**后端 API 接口**中添加数据校验，确保套餐组的可选数量至少为 1，防止创建无效的套餐配置。

**注意**：本需求仅修改 PHP 后端 API，不涉及前端页面修改。

## 🎯 产品对齐

- **防止数据错误**：避免创建无效的套餐配置，确保套餐业务逻辑的正确性
- **提升数据质量**：通过后端校验保证数据完整性，即使前端绕过验证也能拦截
- **减少业务异常**：避免因数据错误导致的套餐展示、下单等后续问题

## 📝 用户故事

**作为** 商户管理员  
**我想** 在创建或编辑套餐时，系统自动校验套餐组的可选数量不能为 0  
**以便于** 确保套餐配置的有效性，避免创建无效的套餐

## 功能需求

### Requirement 1: 后端 API 数据校验

**用户故事**: 作为商户管理员，我想在保存套餐时系统自动校验套餐组可选数量，以便于确保数据有效性

#### 验收标准

1. **WHEN** 用户通过 API 提交套餐数据，套餐组可选数量为 0 **THEN** 系统 **SHALL** 返回错误响应，拒绝保存，并提示"套餐组可选数量不能小于 1"
2. **WHEN** 用户通过 API 提交套餐数据，套餐组可选数量为负数 **THEN** 系统 **SHALL** 返回错误响应，拒绝保存，并提示"套餐组可选数量不能小于 1"
3. **WHEN** 用户通过 API 提交套餐数据，套餐组可选数量为空或 null **THEN** 系统 **SHALL** 返回错误响应，拒绝保存，并提示"套餐组可选数量不能为空"
4. **WHEN** 用户通过 API 提交套餐数据，套餐组可选数量为 1 或更大的正整数 **THEN** 系统 **SHALL** 允许保存并返回成功响应
5. **WHEN** 用户通过 API 提交套餐数据，包含多个套餐组 **THEN** 系统 **SHALL** 校验所有套餐组的可选数量，任一不满足条件则拒绝保存

#### 具体要求

- [ ] 1.1 在套餐保存接口（创建/更新）中添加套餐组可选数量校验逻辑
- [ ] 1.2 校验规则：可选数量必须为大于等于 1 的正整数
- [ ] 1.3 错误提示信息清晰明确，便于前端展示给用户
- [ ] 1.4 校验失败时返回标准的错误响应格式（code, message, data）
- [ ] 1.5 校验应在数据保存到数据库之前执行，避免产生脏数据

## 非功能需求

- **分层设计**: 严格遵循 Controller → Service → Repository 分层

- **模块化设计**: 校验逻辑应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:

## 验收标准

### 功能验收

1. **后端校验生效**: 通过 API 提交可选数量为 0 的数据时，接口返回错误，数据未保存
2. **错误提示清晰**: 错误响应中包含明确的错误信息，便于前端展示
3. **正常数据通过**: 可选数量为 1 或更大的正整数时，接口正常保存数据
4. **多套餐组校验**: 包含多个套餐组时，所有套餐组都进行校验

### 测试验收

1. **单元测试**: 校验逻辑测试覆盖率 100%
2. **API 测试**: 所有校验场景测试通过（0、负数、空值、正常值、多套餐组）
3. **集成测试**: 端到端流程测试通过
4. **边界测试**: 测试边界值（1、最大值等）

### 文档验收

1. **技术文档**: design.md 完整且准确（如需要）
2. **API 文档**: 接口错误响应文档更新（如有）
3. **代码注释**: 校验逻辑代码注释清晰

## 风险和缓解

### 风险 1: 现有数据中存在可选数量为 0 的套餐组

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 开发前先检查现有数据情况
- 如有异常数据，需要先进行数据修复（单独处理）
- 本需求仅添加校验，不处理历史数据

### 风险 2: 校验逻辑可能影响其他相关功能

**影响**: 低  
**概率**: 低  
**缓解措施**:

- 与相关功能负责人确认影响范围
- 充分测试，确保不影响现有正常功能
- 如有问题，及时回滚
