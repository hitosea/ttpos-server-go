## 📋 概述

在收银机和点餐助手端实现敏感操作（折扣/退款/免单）的权限验证功能。当普通员工进行折扣、退款或免单操作时，系统判断当前员工是否为授权验证人：

- **如果是授权员工**：无需输入密码，直接进行下一步操作
- **如果不是授权员工**：弹出授权验证弹窗，要求输入授权员工账号（邮箱或手机号）和权限密码

**前置依赖**：

- ✅ 商家后台业务设置中的"敏感操作设置"功能（DooTask #36940 / `story-shop-sensitive-operation-settings`）
- ✅ 权限密码配置功能（DooTask #36940）

## 🎯 产品对齐

该功能支持门店管理需求：

- **增强权限控制**：普通员工进行折扣/退款/免单操作时，需要授权员工验证
- **降低财务风险**：敏感操作必须经过授权验证，防止误操作和滥用
- **操作可追溯**：订单操作记录中记录授权员工信息，便于审计
- **灵活授权机制**：授权员工即使本身无"优惠折扣/退款设置"权限，也可作为验证节点

## 📝 用户故事

**作为** 普通员工（收银员）  
**我想** 在进行折扣/退款/免单操作时，通过授权员工验证后完成操作  
**以便于** 确保敏感操作经过授权，降低财务风险

**作为** 门店经理/店长（授权验证人）  
**我想** 通过输入权限密码验证普通员工的折扣/退款/免单操作  
**以便于** 控制敏感操作的权限，保护门店财务安全

## 功能需求

### Requirement 1: 检查授权接口

**用户故事**: 作为收银员，我想在点击折扣/退款按钮时，系统自动检查我是否有权限操作，以便于决定是否需要弹出授权弹窗

#### 验收标准

1. **WHEN** 调用检查授权接口，通过 token 识别员工 **THEN** 系统 **SHALL** 判断当前操作人是否在授权人名单中
2. **IF** 当前操作人在授权名单中 **THEN** 系统 **SHALL** 返回有权限，无需弹出授权弹窗
3. **IF** 当前操作人不在授权名单中 **THEN** 系统 **SHALL** 返回没有权限，需要弹出授权弹框
4. **WHEN** 系统设置中未开启密码验证 **THEN** 系统 **SHALL** 返回有权限，无需弹出授权弹窗

#### 具体要求

- [ ] 1.1 在 Go API（`main/app/api/v1/cashier/cashier_order.go` 或新建文件）中创建检查授权接口
- [ ] 1.2 接口路径：`/cashier/order/check_authorization`（POST）
- [ ] 1.3 请求参数：无
- [ ] 1.4 响应参数：是否有权限（`has_permission`: `true` 或 `false`）
- [ ] 1.5 在 Go Service（`main/app/service/order_manage.go` 或新建文件）中实现权限检查逻辑
- [ ] 1.6 从业务设置中读取授权员工列表和密码验证开关
- [ ] 1.7 判断当前员工是否在授权名单中

### Requirement 2: 密码验证接口

**用户故事**: 作为收银员，我想在授权弹窗中输入授权员工账号和密码后，系统验证密码是否正确，以便于确认授权

#### 验收标准

1. **WHEN** 调用密码验证接口，传入授权员工账号（邮箱或手机号）和密码 **THEN** 系统 **SHALL** 验证账号是否为权限员工且密码是否正确
2. **IF** 账号是权限员工且密码正确 **THEN** 系统 **SHALL** 返回验证成功
3. **IF** 账号不是权限员工 **THEN** 系统 **SHALL** 返回错误："不是权限员工，请确认信息"
4. **IF** 账号是权限员工但密码错误 **THEN** 系统 **SHALL** 返回错误："密码错误"
5. **WHEN** 输入的账号格式不正确（既不是邮箱也不是手机号） **THEN** 系统 **SHALL** 返回参数验证错误

#### 具体要求

- [ ] 2.1 在 Go API（`main/app/api/v1/cashier/cashier_order.go` 或新建文件）中创建密码验证接口
- [ ] 2.2 接口路径：`/cashier/order/verify_password`（POST）
- [ ] 2.3 请求参数：授权员工账号（`authorized_staff_account`：邮箱或手机号）、权限密码（`password`）
- [ ] 2.4 响应参数：验证结果（`verified`: `true` 或 `false`）
- [ ] 2.5 在 Go Service 中实现密码验证逻辑
- [ ] 2.6 根据账号（邮箱或手机号）查找员工
- [ ] 2.7 验证员工是否在授权名单中
- [ ] 2.8 验证密码是否正确（从 staff 表中读取权限密码 permission_password）

### Requirement 5: 授权验证弹窗（前端）

**用户故事**: 作为收银员，我想在需要授权时看到授权验证弹窗，输入授权员工账号和密码，以便于完成敏感操作

#### 验收标准

1. **WHEN** 点击整单改价/打折/抹零、退款或免单按钮，系统检查授权后返回需要授权 **THEN** 系统 **SHALL** 弹出授权验证弹窗
2. **WHEN** 授权验证弹窗显示 **THEN** 系统 **SHALL** 显示以下内容：
   - 授权员工账号输入框（支持邮箱或手机号）
   - 权限密码输入框
   - 确认按钮和取消按钮
3. **WHEN** 未输入授权员工账号或权限密码，点击确认 **THEN** 系统 **SHALL** 在输入框下方提示：请选择授权员工/请输入权限密码
4. **WHEN** 输入授权员工账号和密码后，点击确认 **THEN** 系统 **SHALL** 调用密码验证接口
5. **IF** 密码验证成功 **THEN** 系统 **SHALL** 关闭弹窗，记录授权员工信息，继续执行折扣/退款/免单操作
6. **IF** 密码验证失败（密码错误） **THEN** 系统 **SHALL** toast 提示"密码错误"
7. **IF** 密码验证失败（账号不是权限员工） **THEN** 系统 **SHALL** toast 提示"不是权限员工，请确认信息"
8. **WHEN** 每次进行退款/整单改价/打折/抹零/免单操作 **THEN** 系统 **SHALL** 都需要弹出授权弹窗（即使之前已输入过）

#### 具体要求

- [ ] 5.1 在 POS 前端创建授权验证弹窗组件
- [ ] 5.2 在 Assistant 前端创建授权验证弹窗组件（可复用）
- [ ] 5.3 弹窗包含：授权员工账号输入框、权限密码输入框、确认/取消按钮
- [ ] 5.4 实现表单验证：账号和密码必填
- [ ] 5.5 实现密码验证接口调用
- [ ] 5.6 实现错误提示（toast）
- [ ] 5.7 验证成功后，记录授权员工信息，用于后续接口调用

## 风险和缓解

### 风险 1: 授权验证弹窗需要在多个场景下复用（整单退款、部分退款、折扣），需要统一交互逻辑

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 设计统一的授权验证组件，在 POS 和 Assistant 端复用
- 统一弹窗交互逻辑和错误处理

### 风险 2: 密码验证逻辑需要与商家后台的权限密码配置保持一致

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 与商家后台的权限密码配置功能对接，确保数据一致性
- 使用相同的密码验证逻辑

### 风险 3: 操作记录需要准确记录授权员工信息，需要考虑边界情况（如授权员工被删除）

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 在操作记录中存储授权员工 ID、姓名和邮箱，即使员工被删除也能追溯
- 在记录时保存快照信息

### 风险 4: 已输入授权员工、权限密码后，后台修改权限密码，需要正确处理（二次验证）

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 在提交操作时再次验证密码（二次验证），确保密码未被后台修改
- 如果密码验证失败，返回明确错误提示

### 风险 5: 版本兼容性风险

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 版本判断逻辑：如果无法识别版本或版本 < v2.10.0，默认不进行权限验证（向后兼容）
- 版本号格式统一：使用语义化版本号（如 `2.10.0`），便于解析和比较
- 版本信息传递：通过请求头 `Client-Version` 传递，格式为 `v2.10.0` 或 `2.10.0`
- 默认行为：未传递版本信息时，视为旧版本，不进行权限验证
- 版本解析错误处理：如果版本号无法解析，视为旧版本，不进行权限验证
