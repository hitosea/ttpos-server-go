## 📋 概述

在收银端和点餐助手的结账页面增加【活动】选项，支持选择满减/每满减营销活动。系统自动计算活动抵扣金额，并在结账时进行验证和核销。活动信息会显示在结账单、预结账单和发票中。该功能旨在提升商家营销能力，通过满减活动吸引顾客消费，提高客单价和营业额。

## 🎯 产品对齐

该功能支持产品愿景中的"提升商家营销能力"和"增加顾客消费意愿"目标，通过灵活的满减规则设置，帮助商家制定有效的营销策略，提升营业额。

## 📝 用户故事

**作为** 收银员  
**我想** 在结账时选择满减营销活动  
**以便于** 自动计算活动抵扣金额，提高收银效率和准确性

**作为** 商户管理员  
**我想** 在收银端使用满减营销活动  
**以便于** 通过灵活的营销手段吸引顾客消费，提高客单价

## 功能需求

### Requirement 1: 活动列表展示

**用户故事**: 作为收银员，我想在结账页面看到可用的满减活动列表，以便于选择合适的活动

#### 验收标准

1. **WHEN** 进入结账页面 **THEN** 系统 **SHALL** 显示有效日期内的满减活动列表
2. **IF** 活动不在适用时段内 **THEN** 系统 **SHALL** 置灰显示，不可选择
3. **IF** 订单金额未达到满减条件 **THEN** 系统 **SHALL** 置灰显示，不可选择
4. **WHEN** 系统显示活动列表 **THEN** 活动 **SHALL** 按照可用时间范围排序，可用时间范围内的活动显示在前，不在可用时间范围内的活动显示在后

#### 具体要求

- [ ] 1.1 在结账页面信息接口中增加满减活动列表
- [ ] 1.2 活动列表只显示有效日期内的活动（不显示已结束和已失效的活动）
- [ ] 1.3 不在适用时段内的活动显示但置灰
- [ ] 1.4 未达到满减金额的活动置灰显示
- [ ] 1.5 活动排序：可用时间范围内显示在前，不在可用时间范围内的活动在后
- [ ] 1.6 每个活动显示：活动多语言名称、满减类型、开始日期、结束日期、适用时段、满减规则

---

### Requirement 2: 活动选择与验证

**用户故事**: 作为收银员，我想选择满减活动并验证其有效性，以便于确保活动可用

#### 验收标准

1. **IF** 已选择一个活动 **THEN** 系统 **SHALL** 将其他活动置灰，不可同时选择多个
2. **IF** 活动信息发生变更 **THEN** 系统 **SHALL** 提示"活动信息已经变更，请重新确认"
3. **IF** 选择活动后变更会员折扣/积分抵扣 **THEN** 系统 **SHALL** 提示活动规则已失效，取消活动选择
4. **IF** 订单已部分支付 **THEN** 系统 **SHALL** 所有活动不可点击（置灰）
5. **IF** 积分抵扣后最终应收为0 **THEN** 系统 **SHALL** 不可选择满减活动

#### 具体要求

- [ ] 2.1 单笔订单只能使用一个营销活动
- [ ] 2.2 选择活动后，其他活动置灰不可选
- [ ] 2.3 实时验证活动有效性（有效期、时段、满减条件）
- [ ] 2.4 活动信息变更时提示重新确认
- [ ] 2.5 结账完成时进行二次确认活动有效性和是否满足活动要求
- [ ] 2.6 更换会员后自动取消满减活动选择
- [ ] 2.7 订单已部分支付时，所有活动不可选择

---

### Requirement 3: 金额计算与互斥规则

**用户故事**: 作为收银员，我想系统自动计算活动抵扣金额，并正确处理与其他优惠的互斥关系

#### 验收标准

1. **IF** 活动抵扣金额大于订单金额 **THEN** 系统 **SHALL** 最终应收金额为0，不显示负数
2. **IF** 选择活动后变更会员折扣/积分抵扣 **THEN** 系统 **SHALL** 提示活动规则已失效，取消活动选择
3. **IF** 使用活动抵扣 **THEN** 系统 **SHALL** 可以在会员折扣、积分抵扣后进行满减，但选择满减之后积分不再自动抵扣
4. **IF** 使用活动抵扣 **THEN** 系统 **SHALL** 可以在满减之后进行结账抹零

#### 具体要求

- [ ] 3.1 自动计算活动抵扣金额（满减/每满减）
- [ ] 3.2 活动抵扣金额不能超过订单金额（负数时显示为0）
- [ ] 3.3 与会员折扣、积分抵扣的互斥处理：可以在会员折扣、积分抵扣后进行满减，但选择满减之后积分不再自动抵扣
- [ ] 3.4 更换会员后自动取消满减活动选择
- [ ] 3.5 与抹零规则的兼容处理：可以在满减之后进行结账抹零
- [ ] 3.6 活动与优惠券只能二选一

---

### Requirement 4: 活动核销与记录

**用户故事**: 作为系统，我想在结账时核销活动并记录活动信息，以便于统计和追溯

#### 验收标准

1. **IF** 使用活动抵扣并结账完成 **THEN** 系统 **SHALL** 在结账单、预结账单、发票中显示活动抵扣金额
2. **IF** 使用活动抵扣并结账完成 **THEN** 系统 **SHALL** 活动抵扣金额不计入会员累计消费金额
3. **IF** 使用活动抵扣 **THEN** 系统 **SHALL** 在订单操作日志中记录活动名称和抵扣金额
4. **IF** 反结账 **THEN** 系统 **SHALL** 清空活动相关字段

#### 具体要求

- [ ] 4.1 结账时验证活动有效性
- [ ] 4.2 记录活动抵扣金额到订单表（activity_amount）
- [ ] 4.3 记录活动UUID到订单表（full_reduction_activity_uuid）
- [ ] 4.4 记录活动规则信息到订单表（full_reduction_activity_message）
- [ ] 4.5 活动抵扣金额不计入会员累计消费
- [ ] 4.6 订单操作日志记录活动使用信息
- [ ] 4.7 在结账单、预结账单、发票中显示活动抵扣金额
- [ ] 4.8 反结账时清空活动相关字段

---

### Requirement 5: 拆单和免单场景

**用户故事**: 作为收银员，我想在拆单和免单场景下正确处理活动，以便于保证业务逻辑正确

#### 验收标准

1. **IF** 拆单1使用满减活动 **THEN** 系统 **SHALL** 拆单2和3可再继续使用满减活动
2. **IF** 已选择活动但未结账，进行免单并结账操作 **THEN** 系统 **SHALL** 正常免单结账完成（此时订单未使用活动）

#### 具体要求

- [ ] 5.1 拆单场景：每个拆单可以独立使用满减活动
- [ ] 5.2 免单场景：免单时清空活动选择，正常完成免单结账

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [ ] URL 使用 snake_case 命名（如：`/api/v1/cashier/desk/order/payment/activity`）
- [ ] data 字段必须是对象，不能是 null 或数组
- [ ] 分页信息统一放在 meta 中
- [ ] 响应格式：`{code, message, data{}}`
- [ ] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 数据库设计要求

- [ ] 必须包含: `id`, `uuid`, `create_time`, `update_time`, `delete_time`
- [ ] 时间字段使用 int 类型，\_time 结尾，默认值 0
- [ ] 金额字段使用 decimal(20,8)
- [ ] UUID 字段使用 bigint unsigned
- [ ] 表名使用 ttpos\_ 前缀
- [ ] 字段名使用 snake_case
- [ ] 参考: `.cursor/rules/database.mdc` - 数据库开发规范

### 性能要求

- [ ] 本地响应时间 < 200ms
- [ ] 数据库查询优化（使用索引）
- [ ] 缓存策略（Redis）- 活动列表缓存
- [ ] 并发处理（使用 UUID 锁）

### 测试要求

- [ ] Service 层测试覆盖率 ≥ 70%
- [ ] Repository 层测试覆盖率 ≥ 80%
- [ ] **Payment/Order 相关模块测试覆盖率 100%**（高风险）
- [ ] 集成测试覆盖核心流程
- [ ] API 测试覆盖所有接口
- [ ] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 国际化要求

- [ ] 支持 10 种语言（中文、英文、日语、韩语等）
- [ ] 所有文案使用多语言实现
- [ ] 参考: `main/i18n/` - 国际化配置

### 安全要求

- [ ] 所有 API 需要身份验证
- [ ] 敏感数据加密存储
- [ ] SQL 注入防护（使用参数化查询）
- [ ] XSS 防护（前端输入校验）
- [ ] CSRF 防护（Token 验证）
- [ ] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [ ] 网络异常时优雅降级
- [ ] 事务管理（保证数据一致性）
- [ ] 错误日志记录（使用 Logger）
- [ ] 故障恢复机制

5. **活动核销**: 结账时正确核销活动，记录活动信息
6. **拆单场景**: 拆单场景下活动使用正确

## 约束条件

### 技术约束

#### Go Main 模块

- 必须使用 Gin 框架
- 接口以 `I` 开头，实现以 `Impl` 结尾
- Service 只能依赖其他 Service 接口
- Repository 只能持有 db 实例，不能持有 DBManager
- 不使用 panic，返回 error

### 业务约束

- 活动与优惠券只能二选一
- 活动可以在会员折扣、积分抵扣后进行，但选择活动后积分不再自动抵扣
- 更换会员后自动取消活动选择
- 订单已部分支付时，所有活动不可选择
- 拆单场景下，每个拆单可以独立使用活动

### 资源约束

- 开发时间: 10-15 天
- Story Point: 8-13 SP（待技术评审确认）

## 风险和缓解

### 风险 1: 活动规则复杂度

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 建立完善的测试用例，覆盖各种满减场景
- 参考商家端满减营销功能的实现逻辑

### 风险 2: 并发控制

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 使用分布式锁和数据库事务保证数据一致性
- 在结账完成时重新验证活动有效性

### 风险 3: 数据一致性

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 在结账完成时重新验证活动有效性，变更则提示用户
- 活动信息变更时，已选择活动的订单如何处理

### 风险 4: 性能影响

**影响**: 中  
**概率**: 低  
**缓解措施**:

- 使用缓存优化活动列表查询
- 异步处理非关键验证
