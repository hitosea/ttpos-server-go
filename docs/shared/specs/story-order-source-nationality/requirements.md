## 📋 概述

基于 Proposal「点餐方式增加订单来源-国籍选择」和华莱士客户需求，在收银系统中增加订单来源（店内/外卖平台）和顾客国籍的记录能力，通过后台开关灵活控制功能显隐，并在订单详情中展示相关信息，为商户渠道管理和数据分析提供支持。

## 🎯 产品对齐

- 支持商户区分店内和外卖平台订单，提升多渠道运营管理能力。
- 记录顾客国籍信息，为精准营销和服务优化提供数据基础。
- 通过后台开关按商家需求灵活启用功能，避免不必要的操作复杂度。
- 支持自定义外卖平台和国籍选项，满足不同商户的个性化需求。

## 📝 用户故事

**作为** 收银员  
**我想** 在点餐时选择订单来源（店内/外卖平台）和顾客国籍  
**以便于** 商户能够准确区分不同渠道的订单，并记录顾客国籍信息用于数据分析

**作为** 商户管理员  
**我想** 在后台配置外卖来源和国籍选项，并控制功能开关  
**以便于** 根据实际业务需求灵活启用或关闭相关功能

**作为** 店长  
**我想** 在订单详情中查看订单来源和顾客国籍  
**以便于** 分析不同渠道和不同国籍顾客的消费习惯

## 功能需求

### Requirement 1: 新管理端-业务设置-外卖来源管理（对应任务 36914）

**用户故事**: 作为 商户管理员，我想在新管理端业务设置中配置外卖来源，以便收银端可以选择订单来源。

**技术实现**: 新管理端（Flutter）调用 Main 模块（Go）的配置管理 API。

#### 验收标准

1. **WHEN** 管理员进入「业务设置」页面 **THEN** 系统展示「外卖管理」配置模块，包含功能开关和外卖来源列表。
2. **IF** 外卖功能开关默认为「关闭」状态 **THEN** 收银端不显示外卖选项。
3. **WHEN** 管理员开启外卖功能开关并保存 **THEN** 收银端点餐界面显示「外卖」按钮。
4. **WHEN** 系统初始化外卖来源列表 **THEN** 默认包含：Grab、Line Man、悟空外卖、Foodpanda。
5. **WHEN** 管理员新增自定义外卖来源 **THEN** 系统支持保存并在收银端选择列表中显示。
6. **WHEN** 管理员编辑或删除外卖来源 **THEN** 系统更新数据并同步到收银端。

#### 具体要求

- [ ] 1.1 外卖功能开关默认关闭，开启后收银端才显示外卖选项。
- [ ] 1.2 外卖来源支持增删改查，包含名称和多语言支持。
- [ ] 1.3 系统预置 4 个外卖平台：Grab、Line Man、悟空外卖、Foodpanda。
- [ ] 1.4 删除外卖来源时，需校验是否有订单使用该来源，有则不允许删除（可软删除）。
- [ ] 1.5 外卖来源列表支持排序，影响收银端显示顺序。

### Requirement 2: 新管理端-业务设置-国籍管理（对应任务 36914）

**用户故事**: 作为 商户管理员，我想在新管理端业务设置中配置国籍选项，以便收银端可以记录顾客国籍。

**技术实现**: 新管理端（Flutter）调用 Main 模块（Go）的配置管理 API。

#### 验收标准

1. **WHEN** 管理员进入「业务设置」页面 **THEN** 系统展示「国籍管理」配置模块，包含功能开关和国籍列表。
2. **IF** 国籍功能开关默认为「关闭」状态 **THEN** 收银端不显示国籍选项。
3. **WHEN** 管理员开启国籍功能开关并保存 **THEN** 收银端点餐/桌台界面显示「国籍」选择控件。
4. **WHEN** 系统初始化国籍列表 **THEN** 默认包含：泰国、中国、美国、日本、韩国、英国、法国、俄罗斯。
5. **WHEN** 管理员新增自定义国籍 **THEN** 系统支持保存并在收银端选择列表中显示。
6. **WHEN** 管理员编辑或删除国籍 **THEN** 系统更新数据并同步到收银端。
7. **WHEN** 系统显示国籍名称 **THEN** 自动根据当前语言环境显示对应翻译。

#### 具体要求

- [ ] 2.1 国籍功能开关默认关闭，开启后收银端和点餐助手才显示国籍选项。
- [ ] 2.2 国籍支持增删改查，包含名称和多语言支持（自动翻译）。
- [ ] 2.3 系统预置 8 个国家：泰国、中国、美国、日本、韩国、英国、法国、俄罗斯。
- [ ] 2.4 删除国籍时，需校验是否有订单使用该国籍，有则不允许删除（可软删除）。
- [ ] 2.5 国籍列表支持排序，影响收银端显示顺序。
- [ ] 2.6 国籍名称走系统多语言翻译机制，不需要手动配置多语言。

### Requirement 3: 收银端-点餐方式-外卖选项（对应任务 36931）

**用户故事**: 作为 收银员，我想在收银机点餐时选择外卖来源，以便标记订单是外卖还是店内。

#### 验收标准

1. **IF** 后台未开启外卖功能 **THEN** 收银机点餐界面不显示「外卖」按钮。
2. **WHEN** 后台开启外卖功能且有外卖来源配置 **THEN** 收银机点餐界面显示「外卖」按钮。
3. **WHEN** 收银员点击「外卖」按钮 **THEN** 弹出外卖来源选择列表，显示后台配置的所有外卖平台。
4. **WHEN** 收银员选择某个外卖来源 **THEN** 订单标记为该外卖平台订单。
5. **IF** 收银员不点击「外卖」按钮或不选择外卖来源 **THEN** 订单默认为店内来源（堂食/外带）。
6. **WHEN** 收银员创建订单 **THEN** 订单数据中记录订单来源信息（外卖平台 ID 或店内标识）。

#### 具体要求

- [ ] 3.1 「外卖」按钮与「堂食」「外带」等按钮并列显示。
- [ ] 3.2 外卖来源选择列表按后台配置顺序显示。
- [ ] 3.3 订单来源为可选字段，不选择时默认为店内。
- [ ] 3.4 不控制角色权限，所有收银员都可见。
- [ ] 3.5 外卖来源选择后，界面上需要有明确的标识（如高亮、图标等）。

### Requirement 4: 收银端/点餐助手-点餐/桌台-国籍选择（对应任务 36931）

**用户故事**: 作为 收银员/店员，我想在点餐或桌台管理时选择顾客国籍，以便记录顾客信息。

#### 验收标准

1. **IF** 后台未开启国籍功能 **THEN** 收银端/点餐助手不显示国籍选择控件。
2. **WHEN** 后台开启国籍功能且有国籍配置 **THEN** 收银端/点餐助手点餐和桌台界面显示「国籍」选择控件。
3. **WHEN** 收银员/店员点击国籍选择控件 **THEN** 弹出或展开国籍列表，显示后台配置的所有国籍选项。
4. **WHEN** 收银员/店员选择某个国籍 **THEN** 订单记录该国籍信息。
5. **IF** 收银员/店员不选择国籍 **THEN** 订单的国籍字段为空（可选字段）。
6. **WHEN** 系统显示国籍列表 **THEN** 按当前系统语言显示国籍名称。

#### 具体要求

- [ ] 4.1 国籍选择为可选字段，不强制填写。
- [ ] 4.2 国籍选择控件在点餐流程和桌台管理中都要显示。
- [ ] 4.3 收银端和点餐助手的交互保持一致。
- [ ] 4.4 不控制角色权限，所有收银员/店员都可见。
- [ ] 4.5 国籍选择支持搜索或快速定位（如按首字母）。
- [ ] 4.6 国籍列表按后台配置顺序显示。

---

### Requirement 5: 订单详情-显示订单来源和国籍（对应任务 36919）

**用户故事**: 作为 店长/收银员，我想在订单详情中查看订单来源和顾客国籍，以便了解订单渠道和顾客信息。

#### 验收标准

1. **WHEN** 查看订单详情（收银端/商家后台） **THEN** 显示「订单来源」字段。
2. **IF** 订单标记了外卖来源 **THEN** 显示具体外卖平台名称（如「Grab」）。
3. **IF** 订单未标记外卖来源 **THEN** 显示「店内」或「未记录」。
4. **WHEN** 查看订单详情（收银端/商家后台） **THEN** 显示「国籍」字段。
5. **IF** 订单记录了国籍 **THEN** 显示国籍名称（按当前语言显示）。
6. **IF** 订单未记录国籍 **THEN** 显示「未记录」或空白。
7. **IF** 订单对应的外卖来源或国籍已被删除 **THEN** 仍显示原名称（软删除或历史记录保护）。

#### 具体要求

- [ ] 5.1 订单详情页需新增「订单来源」和「国籍」两个显示字段。
- [ ] 5.2 显示位置与其他订单信息（如订单号、桌台、金额等）保持一致的布局风格。
- [ ] 5.3 历史订单（功能上线前创建的订单）显示「未记录」。
- [ ] 5.4 支持后续数据统计和报表分析（预留接口）。

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 每个文件应有单一、明确的目的
- **模块化设计**: Service 和 Repository 应独立且可复用
- **依赖管理**: Service 只能依赖其他 Service 接口，不能直接依赖 Repository
- **遵循规范**:
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/php.mdc` - PHP 开发规范
  - `.cursor/rules/vue.mdc` - Vue 前端规范
  - `.cursor/rules/structs.mdc` - 项目结构规范

### API 设计要求

- [ ] URL 使用 snake_case 命名（如：`/api/v1/order_source`）
- [ ] data 字段必须是对象，不能是 null 或数组
- [ ] 分页信息统一放在 meta 中
- [ ] 响应格式：`{code, message, data{}}`
- [ ] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 数据库设计要求

- [ ] 必须包含: `id`, `uuid`, `create_time`, `update_time`, `delete_time`
- [ ] 时间字段使用 int 类型，\_time 结尾，默认值 0
- [ ] UUID 字段使用 bigint unsigned
- [ ] 表名使用 ttpos\_ 前缀
- [ ] 字段名使用 snake_case
- [ ] 参考: `.cursor/rules/database.mdc` - 数据库开发规范

### 性能要求

- [ ] 本地响应时间 < 200ms
- [ ] 数据库查询优化（使用索引）
- [ ] 缓存策略（Redis）- 外卖来源和国籍配置可缓存
- [ ] 避免 N+1 查询问题

### 多语言要求

- [ ] 外卖来源名称支持多语言
- [ ] 国籍名称走系统多语言翻译机制
- [ ] 前端文案通过多语言资源管理

### 安全要求

- [ ] 所有 API 需要身份验证
- [ ] 参数校验防止 SQL 注入
- [ ] XSS 防护（前端输入校验）
- [ ] 配置修改需要管理员权限
- [ ] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [ ] 数据兼容性：历史订单没有订单来源和国籍字段，需处理空值
- [ ] 软删除：删除外卖来源或国籍时使用软删除，避免历史订单数据丢失
- [ ] 事务管理：配置修改需要事务保证数据一致性
- [ ] 错误日志记录（使用 Logger）

## 约束条件

### 技术约束

- Go Main 模块：遵循三层架构，Service 不直接依赖 DBManager
- PHP Admin 模块：Controller 只做参数获取/校验，业务逻辑放在 Service
- 前端：收银端和点餐助手使用 Flutter，管理后台使用 Vue 3
- 数据库：使用 MySQL 8.0+，遵循数据库设计规范

### 业务约束

- 外卖功能和国籍功能必须可独立开关，互不影响
- 历史订单数据必须兼容，不能因新功能导致旧数据显示异常
- 不控制角色权限，功能开关控制整个商家的显隐
- 删除外卖来源或国籍时，需校验是否有订单使用

### 资源约束

- 开发时间: 8-10 天
- Story Point: 5-8 SP (必须 ≤ 8，建议拆分为多个 SP ≤ 5 的子任务)

## 风险和缓解

### 风险 1: 数据兼容性问题

**影响**: 高  
**概率**: 中  
**缓解措施**:

- 订单表新增字段使用默认值，避免 NULL
- 历史订单显示「未记录」或默认值
- 充分测试历史订单在各终端的显示效果

### 风险 2: 多终端一致性问题

**影响**: 中  
**概率**: 中  
**缓解措施**:

- 收银端和点餐助手复用相同的 UI 组件和交互逻辑
- 统一 API 接口，避免多终端调用不同接口
- 充分联调测试，确保多终端体验一致

### 风险 3: 多语言翻译准确性

**影响**: 低  
**概率**: 低  
**缓解措施**:

- 使用成熟的翻译库或服务
- 支持后台手动修正翻译
- 提供常用国家的预置翻译
