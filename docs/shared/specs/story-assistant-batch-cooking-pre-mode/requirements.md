## 📋 概述

点餐助手端分批送厨前置模式功能旨在优化助手端操作流程，允许店员在选购商品时就关联分批类型，下单后自动按优先级送厨，减少操作步骤，提升操作效率和准确性。

本功能主要涉及：
- 助手端基础信息接口调整（增加分批送厨模式字段）
- 新增分批类型列表接口
- 购物车商品签名计算优化（包含 batch_tag_uuid）
- 加购接口调整（支持前置模式下的 batch_tag_uuid 参数）
- 智能送厨逻辑（下单后自动按优先级送厨）

## 🎯 产品对齐

该功能支持公司 v2.10.0 版本的核心目标：
- **提升操作效率**：在选购商品时即可关联分批类型，减少后续操作步骤
- **优化用户体验**：操作流程更符合实际业务场景，降低学习成本
- **提高准确性**：前置选择分批类型，减少送厨时的误操作
- **统一体验**：与收银端前置模式保持一致，降低多终端切换的学习成本

## 📝 用户故事

**作为** 点餐助手端用户（店员）  
**我想** 在选购商品时就选择并关联分批类型  
**以便于** 下单后系统能自动按类型分批送厨，减少操作步骤，提高效率

## 功能需求

### Requirement 1: 业务设置接口调整

**用户故事**: 作为助手端客户端，我想获取商户的分批送厨模式（前置/后置），以便于前端展示相应的UI和交互

#### 验收标准

1. **WHEN** 调用 `/assistant/base` 接口 **THEN** 系统 **SHALL** 返回分批送厨模式字段
2. **IF** 商户未配置分批送厨模式 **THEN** 系统 **SHALL** 默认返回后置模式
3. **WHEN** 商户切换分批送厨模式 **THEN** 系统 **SHALL** 立即生效

#### 具体要求

- [ ] 1.1 在 `AssistantBase` 响应结构中增加 `batch_cooking_mode` 字段（string: "pre" 前置 / "post" 后置）
- [ ] 1.2 在 `Business` 业务设置中增加 `batch_cooking_mode` 字段
- [ ] 1.3 从业务设置中读取分批送厨模式并返回给前端
- [ ] 1.4 默认值为 "post"（后置模式，保持向后兼容）

---

### Requirement 2: 分批类型列表接口

**用户故事**: 作为助手端客户端，我想获取分批类型列表，以便于显示类型选择器

#### 验收标准

1. **WHEN** 调用新增的分批类型列表接口 **THEN** 系统 **SHALL** 返回所有分批类型
2. **WHEN** 返回列表 **THEN** 系统 **SHALL** 按 sort 排序，优先级高的在前
3. **WHEN** 返回类型 **THEN** 系统 **SHALL** 包含类型名称（多语言）、颜色、缩写等信息

#### 具体要求

- [ ] 2.1 创建 `/assistant/batch_tag/list` 接口获取分批类型列表
- [ ] 2.2 返回类型包含：uuid、locale_name（多语言）、color、sort、abbreviation（缩写）
- [ ] 2.3 接口按 sort 排序，优先级高的在前
- [ ] 2.4 接口仅在前置模式时使用，或始终可用但前端根据模式决定是否显示

---

### Requirement 3: 购物车签名计算优化

**用户故事**: 作为系统，我想在购物车商品签名中包含分批类型UUID，以便于区分相同商品但不同分批类型的商品

#### 验收标准

1. **WHEN** 前置模式下加购商品 **THEN** 系统 **SHALL** 在商品签名计算中包含 `batch_tag_uuid`
2. **IF** 相同商品但不同分批类型 **THEN** 系统 **SHALL** 在购物车中分开显示为两条数据
3. **IF** 相同商品且相同分批类型 **THEN** 系统 **SHALL** 合并为一条数据，数量累加

#### 具体要求

- [ ] 3.1 修改商品签名计算函数，当前置模式时包含 `batch_tag_uuid` 参数
- [ ] 3.2 确保签名计算逻辑正确，相同商品不同分批类型能正确分开
- [ ] 3.3 购物车商品合并逻辑支持基于签名合并
- [ ] 3.4 参考商品退菜逻辑，下单两份退一份后分开展示

---

### Requirement 4: 加购接口调整

**用户故事**: 作为助手端客户端，我想在加购商品时传入分批类型UUID，以便于商品自动关联分批类型

#### 验收标准

1. **WHEN** 前置模式下调用加购接口 **THEN** 系统 **SHALL** 接受 `batch_tag_uuid` 参数
2. **IF** 未传入 `batch_tag_uuid` **THEN** 系统 **SHALL** 使用默认分批类型（排序第一的类型）
3. **WHEN** 加购商品成功 **THEN** 系统 **SHALL** 将商品与分批类型关联
4. **IF** 签名相同的商品 **THEN** 系统 **SHALL** 合并数量而非新增记录

#### 具体要求

- [ ] 4.1 在 `OrderCartProductAddReq` 中增加 `batch_tag_uuid` 字段（可选）
- [ ] 4.2 在 `InstantOrderCartProductAdd` 方法中处理 `batch_tag_uuid` 参数
- [ ] 4.3 当前置模式时，使用 `batch_tag_uuid` 计算商品签名
- [ ] 4.4 如果签名相同的商品要合并在一起
- [ ] 4.5 验证 `batch_tag_uuid` 的有效性（必须存在于分批类型列表中）
- [ ] 4.6 如果未提供 `batch_tag_uuid`，使用默认类型（sort 最小的类型）

---

### Requirement 5: 智能送厨逻辑

**用户故事**: 作为助手端客户端，我想在下单后自动按优先级送厨，以便于减少操作步骤

#### 验收标准

1. **WHEN** 点击下单按钮 **THEN** 系统 **SHALL** 将所有分批送厨商品变为预送厨状态
2. **WHEN** 存在多个分批类型的预送厨商品 **THEN** 系统 **SHALL** 自动送厨优先级最高的分批类型商品
3. **WHEN** 每次点击下单 **THEN** 系统 **SHALL** 重复此过程，直到没有可送厨商品
4. **IF** 没有可送厨商品 **THEN** 系统 **SHALL** 正常完成下单流程

#### 具体要求

- [ ] 5.1 修改下单逻辑，下单后分析所有预送厨商品
- [ ] 5.2 找出优先级最高的分批类型（sort 最小的类型）
- [ ] 5.3 自动送厨该类型的所有商品
- [ ] 5.4 每次点击下单都重复此过程，直到没有可送厨商品
- [ ] 5.5 确保送厨逻辑不影响正常下单流程

## 非功能需求

### 代码架构和模块化

- **分层设计**: 严格遵循 Controller → Service → Repository 分层
- **单一职责原则**: 分批送厨相关逻辑集中在 OrderService 中
- **模块化设计**: 前置模式和后置模式的逻辑隔离，通过配置控制
- **依赖管理**: Service 依赖 Repository 接口
- **遵循规范**: 
  - `.cursor/rules/go-main.mdc` - Go Main 开发规范
  - `.cursor/rules/api.mdc` - API 设计规范
  - `.cursor/rules/database.mdc` - 数据库开发规范

### API 设计要求

- [x] URL 使用 snake_case 命名：`/assistant/batch_tag/list`
- [x] data 字段必须是对象：`{"data": {"list": []}}`
- [x] 响应格式：`{code: 1, message: "success", data: {}}`
- [x] 参考: `.cursor/rules/api.mdc` - API 设计规范

### 性能要求

- [x] 加购接口响应时间 < 500ms（P0）
- [x] 购物车签名计算使用高效算法
- [x] 分批类型列表接口支持缓存（可选）
- [x] 智能送厨逻辑不影响下单性能

### 测试要求

- [x] OrderService 相关方法测试覆盖率 ≥ 70%
- [x] **购物车签名计算测试覆盖率 100%**（高风险，P0）
- [x] Repository 层测试覆盖率 ≥ 80%
- [x] 集成测试覆盖完整加购和送厨流程
- [x] 并发测试：多商品同时加购，确保签名计算正确
- [x] 智能送厨逻辑测试：验证按优先级正确送厨
- [x] 参考: `.cursor/rules/go-main.mdc` - 测试规范

### 安全要求

- [x] 所有接口需要身份验证（JWT Token）
- [x] 订单UUID验证：订单必须属于当前商户
- [x] 分批类型UUID验证：必须存在于商户的分批类型列表中
- [x] 参考: `.cursor/rules/security.mdc` - 安全开发规范

### 可靠性要求

- [x] 加购失败时事务回滚，保证数据一致性
- [x] 智能送厨失败时不影响原有数据
- [x] 记录详细错误日志（Logger）
- [x] 异常时返回明确的错误信息

## 验收标准

### 功能验收

1. **前置关联模式基础功能**: 开桌完成时显示分批类型选择弹窗，默认选择排序第一的类型，可切换
2. **商品关联类型**: 加购商品时自动关联当前选中的分批类型，购物车中显示类型标识
3. **同一商品不同类型分开显示**: 相同商品选择不同分批类型时，购物车中分开显示
4. **智能送厨功能**: 下单后自动按分批类型优先级送厨，每次送优先级最高的类型
5. **分批类型列表**: 接口返回按 sort 排序的分批类型列表

### 测试验收

1. **单元测试**: Service和Repository覆盖率达标
2. **API测试**: 所有接口测试通过，包含异常场景
3. **集成测试**: 端到端加购和送厨流程测试通过
4. **兼容性测试**: 后置关联模式不受影响，两种模式可以平滑切换

### 文档验收

1. **技术文档**: design.md 包含完整的API设计、数据模型设计
2. **API 文档**: docs/shared/api/ 已更新
3. **代码注释**: 关键逻辑有中文注释说明

## 约束条件

### 技术约束

#### Go Main 模块
- 必须使用 Gin 框架
- Service 接口以 `I` 开头：`IOrderSrv`
- Service 依赖 Repository 接口（不直接依赖 db）
- Repository 只持有 db 实例
- 不使用 panic，所有错误返回 error

### 业务约束

- 前置模式和后置模式互斥，通过业务设置控制
- 已送厨的商品不能修改分批类型
- 不需要分批送厨的商品不受类型影响
- 智能送厨逻辑只在前置模式下生效

### 资源约束

- 开发时间: 3-5 天
- Story Point: 5 SP（待技术评审确认）

## 风险和缓解

### 风险 1: 购物车签名计算复杂度

**影响**: 高  
**概率**: 中  
**缓解措施**:
- 充分测试各种场景，确保相同商品不同分批类型能正确分开
- 参考商品退菜逻辑的实现方式
- 使用单元测试覆盖所有边界情况

### 风险 2: 智能送厨逻辑复杂度

**影响**: 中  
**概率**: 中  
**缓解措施**:
- 充分测试按优先级送厨的逻辑
- 确保每次点击下单都正确送优先级最高的类型
- 使用单元测试覆盖所有场景

### 风险 3: 兼容性

**影响**: 中  
**概率**: 低  
**缓解措施**:
- 通过业务设置区分模式，确保两种模式的逻辑互不干扰
- 默认使用后置模式，保持向后兼容
- 充分测试两种模式的切换场景
