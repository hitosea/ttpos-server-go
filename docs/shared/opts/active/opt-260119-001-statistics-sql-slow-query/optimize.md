## 优化需求

### 当前问题

统计商品排行功能中的 SQL 查询存在严重的性能问题，导致全表扫描和临时表使用。

**问题 SQL**：
```sql
EXPLAIN SELECT
	sp.product_sale_price AS sale_price,
	sp.product_package_uuid AS product_package_uuid,
	SUM(sp.product_num) AS sale_num,
	SUM(IF(sp.free_num > 0 OR sp.give_num > 0, 0, sp.product_final_price * (sp.product_num - sp.refund_num))) AS sale_amount 
FROM
	ttpos_statistics_product AS sp 
WHERE
	sp.refund_time = 0 
GROUP BY
	`sp`.`product_package_uuid`;
```

**问题表现（优化前）**：
- **全表扫描（type: ALL）**：扫描了 520,002 行数据，没有使用任何索引
- **临时表（Using temporary）**：GROUP BY 操作需要创建临时表，消耗大量内存和磁盘 I/O
- **查询性能差**：在大数据量情况下，查询响应时间可能达到数秒甚至更久

**问题表现（创建联合索引后）**：
- **全索引扫描（type: index）**：虽然使用了联合索引 `idx_refund_time_product_package_uuid`，但仍然是全索引扫描，扫描了 520,002 行
- **索引选择性差**：`refund_time = 0` 的数据占比约 90%（filtered: 10.00 表示过滤后只保留 10%，即 90% 的数据满足条件）
- **临时表已消除**：不再使用临时表（Using temporary 已消失），这是好的改进
- **查询性能仍不理想**：虽然避免了临时表，但全索引扫描仍然需要扫描大量数据

**优化效果（创建覆盖索引后）**：
- ✅ **索引查找（type: ref）**：从全索引扫描优化为索引查找，性能显著提升
- ✅ **扫描行数减少**：从 520,002 行减少到 260,001 行（减少 50%）
- ✅ **覆盖索引（Using index）**：完全使用覆盖索引，避免回表操作，减少 I/O 开销
- ✅ **过滤效率提升**：`filtered: 100.00` 表示所有扫描的行都满足条件，过滤效率 100%
- ✅ **查询性能大幅提升**：预计查询时间从数秒降低到 < 1 秒

**问题根源**：
1. **数据分布问题**：`refund_time = 0` 的数据占比过高（约 90%），导致索引选择性差
2. **索引类型选择**：MySQL 选择了全索引扫描（type: index）而不是索引查找（type: ref），因为扫描整个索引可能比查找更高效
3. **缺少覆盖索引**：查询需要回表获取 `product_sale_price`、`product_num`、`free_num`、`give_num`、`product_final_price`、`refund_num` 等字段
4. **数据量大**：`ttpos_statistics_product` 表数据量达到 52 万行，且持续增长

## 初步分析

### 可能原因

1. **数据分布问题（主要原因）**
   - `refund_time = 0` 的数据占比约 90%（大部分订单未退款）
   - 索引选择性差，MySQL 选择全索引扫描而不是索引查找
   - 需要分析数据分布，考虑其他优化方案

2. **缺少覆盖索引**
   - 查询需要回表获取多个字段：`product_sale_price`、`product_num`、`free_num`、`give_num`、`product_final_price`、`refund_num`
   - 回表操作增加了 I/O 开销
   - 创建覆盖索引可以避免回表，提升性能

3. **索引类型选择**
   - MySQL 选择了全索引扫描（type: index）而不是索引查找（type: ref）
   - 因为 `refund_time = 0` 的数据占比太高，索引查找可能不如全索引扫描高效
   - 需要进一步优化索引结构或查询方式

### 优化方向

1. **方案一：创建覆盖索引（推荐）**
   - 创建索引：`idx_refund_time_product_package_uuid_covering (refund_time, product_package_uuid, product_sale_price, product_num, free_num, give_num, product_final_price, refund_num)`
   - 优点：
     - 完全覆盖查询所需字段，无需回表
     - 避免回表 I/O 开销
     - 性能提升明显（预计提升 50-80%）
   - 缺点：
     - 索引体积较大（约 8 个字段）
     - 维护成本稍高
     - 写入性能略有影响（但统计表主要是读操作）

2. **方案二：物化视图/汇总表**
   - 创建汇总表：`ttpos_statistics_product_summary`，按 `product_package_uuid` 预聚合数据
   - 定期更新汇总表（如每小时或每天）
   - 优点：
     - 查询性能最优（直接查询汇总表，无需 GROUP BY）
     - 可以大幅减少扫描行数
   - 缺点：
     - 需要额外的存储空间
     - 需要维护汇总逻辑
     - 数据实时性略差

3. **方案三：优化查询逻辑**
   - 如果查询有时间范围限制，添加时间条件减少扫描范围
   - 使用 `LIMIT` 限制返回结果数量
   - 优点：
     - 实现简单，无需修改表结构
   - 缺点：
     - 优化效果有限
     - 可能影响业务逻辑

4. **方案四：分区表优化**
   - 按 `refund_time` 或时间范围分区
   - 优点：
     - 可以大幅减少扫描范围
   - 缺点：
     - 改动较大，需要重构表结构
     - 可能影响其他查询

**推荐方案**：方案一（创建覆盖索引）
- 性能提升明显（避免回表操作）
- 实现相对简单，只需创建索引
- 对现有代码无影响
- 如果覆盖索引效果仍不理想，再考虑方案二（物化视图）

**已实现（联合索引）**：
- ✅ 消除临时表：不再使用临时表，减少内存和磁盘 I/O
