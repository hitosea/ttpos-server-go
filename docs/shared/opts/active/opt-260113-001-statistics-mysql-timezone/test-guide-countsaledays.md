# CountSaleDays 测试指南

## 测试目标

验证 CountSaleDays 方法修复后，能够正确使用业务时区进行日期分组，而不是依赖 MySQL 服务器的时区。

## 测试环境准备

### 1. 数据库时区设置

为了验证时区转换的正确性，建议：
- MySQL 服务器时区设置为 UTC 或其他时区（与业务时区不同）
- 商户时区设置为 `Asia/Shanghai`、`Asia/Tokyo` 等

### 2. 测试数据准备

创建测试订单，包含以下场景：
- 同一订单在不同时区的日期边界
- 跨日期边界的订单（如 23:00-01:00）
- 不同时区的订单

## 测试用例

### 测试用例 1: 基本时区转换测试

**目的**: 验证时区转换基本功能

**步骤**:
1. 设置商户时区为 `Asia/Shanghai`
2. 创建订单，完成时间为 `2025-01-13 12:00:00`（上海时区）
3. 调用 `CountSaleDays` 方法
4. 验证结果中日期为 `2025-01-13`

**预期结果**:
- 订单被正确归类到 `2025-01-13` 这一天
- 统计数据准确

### 测试用例 2: 跨日期边界测试（Asia/Shanghai）

**目的**: 验证跨日期边界的订单被正确分组

**步骤**:
1. 设置商户时区为 `Asia/Shanghai`
2. 创建以下订单：
   - 订单 A: 完成时间 `2025-01-13 23:30:00`（上海时区）
   - 订单 B: 完成时间 `2025-01-14 00:30:00`（上海时区）
   - 订单 C: 完成时间 `2025-01-14 01:00:00`（上海时区）
3. 调用 `CountSaleDays` 方法
4. 验证结果

**预期结果**:
- 订单 A 被归类到 `2025-01-13`
- 订单 B 被归类到 `2025-01-14`
- 订单 C 被归类到 `2025-01-14`

### 测试用例 3: 不同时区测试（Asia/Tokyo）

**目的**: 验证不同时区的日期分组正确性

**步骤**:
1. 设置商户时区为 `Asia/Tokyo`（UTC+9）
2. 创建订单，完成时间使用东京时区的时间
3. 调用 `CountSaleDays` 方法
4. 验证结果

**预期结果**:
- 订单被正确归类到东京时区的日期

### 测试用例 4: 时区差异对比测试

**目的**: 验证同一时间戳在不同时区下的日期分组差异

**步骤**:
1. 使用固定的时间戳（例如 `1735142400`，对应 UTC `2024-12-26 00:00:00`）
2. 分别设置商户时区为：
   - `Asia/Shanghai`（UTC+8，应该显示为 `2024-12-26 08:00:00`）
   - `Asia/Tokyo`（UTC+9，应该显示为 `2024-12-26 09:00:00`）
   - `Asia/Bangkok`（UTC+7，应该显示为 `2024-12-26 07:00:00`）
3. 调用 `CountSaleDays` 方法
4. 验证结果

**预期结果**:
- 上海时区：订单归类到 `2024-12-26`
- 东京时区：订单归类到 `2024-12-26`
- 曼谷时区：订单归类到 `2024-12-25`（如果时间戳是 UTC `2024-12-26 00:00:00`，对应曼谷时区是 `2024-12-25 17:00:00`）

### 测试用例 5: 统计数据准确性测试

**目的**: 验证修复后的统计数据与修复前的一致性（在时区一致的情况下）

**步骤**:
1. 创建测试数据
2. 使用修复前的代码（使用 MySQL FROM_UNIXTIME）统计
3. 使用修复后的代码（应用层时区转换）统计
4. 对比结果（在 MySQL 时区与业务时区一致的情况下，结果应该一致）

**预期结果**:
- 统计数据一致（在时区一致的情况下）
- 日期分组正确（使用业务时区）

### 测试用例 6: 性能测试

**目的**: 验证应用层分组对性能的影响

**步骤**:
1. 准备大量测试数据（例如 10000 条订单）
2. 使用修复后的代码执行 `CountSaleDays`
3. 记录执行时间
4. 与修复前的性能对比（可选）

**预期结果**:
- 性能影响在可接受范围内
- 响应时间合理

## 手动测试步骤

### 1. 准备测试环境

```sql
-- 查看 MySQL 时区
SELECT @@global.time_zone, @@session.time_zone;

-- 设置商户时区（在应用配置中）
-- timezone: Asia/Shanghai
```

### 2. 创建测试数据

```sql
-- 插入测试订单数据
INSERT INTO ttpos_statistics_sale (
    sale_bill_uuid, complete_time, product_price, payment_amount, 
    refund_amount, product_num, is_meger, is_special, is_takeout,
    desk_uuid, order_source_uuid, meal_num
) VALUES
-- 订单 1: 2025-01-13 12:00:00 (Asia/Shanghai)
(1001, UNIX_TIMESTAMP('2025-01-13 12:00:00'), 100.00, 100.00, 0, 1, 0, 0, 0, 0, 0, 0),
-- 订单 2: 2025-01-13 23:30:00 (Asia/Shanghai)
(1002, UNIX_TIMESTAMP('2025-01-13 23:30:00'), 200.00, 200.00, 0, 1, 0, 0, 0, 0, 0, 0),
-- 订单 3: 2025-01-14 00:30:00 (Asia/Shanghai)
(1003, UNIX_TIMESTAMP('2025-01-14 00:30:00'), 300.00, 300.00, 0, 1, 0, 0, 0, 0, 0, 0);
```

### 3. 调用 API 测试

```bash
# 调用统计接口
curl -X POST http://localhost:8080/api/v1/shop/statistics/sale-days \
  -H "Content-Type: application/json" \
  -d '{
    "time_type": 5,
    "timezone": "Asia/Shanghai"
  }'
```

### 4. 验证结果

检查返回结果中的日期分组是否正确：
- 订单 1 应该归类到 `2025-01-13`
- 订单 2 应该归类到 `2025-01-13`
- 订单 3 应该归类到 `2025-01-14`

## 注意事项

1. **时区数据**: 确保测试环境中的时区数据完整（IANA 时区数据库）
2. **时间戳格式**: `complete_time` 字段存储的是 Unix 时间戳（秒）
3. **日期格式**: 返回的日期格式为 `YYYY-MM-DD`
4. **时区一致性**: 测试时确保商户时区设置正确
