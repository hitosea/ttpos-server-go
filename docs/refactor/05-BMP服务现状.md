# 05 - BMP服务现状与优化建议

> **结论**：BMP-ERP当前架构合理，无需大规模重构
> 
> **核心认知**：进销存线强依赖ERPNext，销售线弱依赖ERPNext

---

## 一、BMP-ERP的正确定位

### 1.1 BMP-ERP是什么？

**BMP-ERP 是 TTPOS 与 ERPNext 的适配层**

```
TTPOS Main (餐饮业务系统)
    ↓ gRPC
BMP-ERP (适配层)
    ↓ HTTP REST API
ERPNext (开源ERP - 进销存/财务系统)
```

**提供的价值：**
1. **API封装**：简化ERPNext复杂的REST API调用
2. **数据转换**：TTPOS数据模型 ↔ ERPNext数据模型
3. **多站点管理**：不同商户路由到不同ERPNext实例（SiteCode）
4. **gRPC服务**：统一对外提供gRPC接口

### 1.2 ERPNext的作用

**ERPNext提供专业的进销存和财务能力：**

```
进销存管理：
• Item管理（物料档案、BOM配方）
• Purchase Order（采购单）
• Stock Entry（库存出入库）
• Material Transfer（物料调拨）
• Stock Reconciliation（库存盘点）
• Warehouse管理（仓库）

财务核算：
• Sales Invoice（销售单）
• 会计凭证
• 成本计算（移动加权平均）
• 财务报表
```

**TTPOS依赖ERPNext的原因：**
- ERPNext是成熟的开源ERP，提供专业的进销存能力
- TTPOS无需重复开发复杂的BOM、成本核算、多仓库等功能
- 开发成本低，维护成本低

## 二、两条业务线的调用模式

### 2.1 进销存管理线（强依赖ERPNext）

```
后台管理功能 → 必须同步调用ERPNext

TTPOS后台 → BMP-ERP → ERPNext

• 物品管理    → 同步，需要返回Item Code
• BOM配方     → 同步，用于成本核算
• 采购单      → 同步，需要返回采购单号
• 收货入库    → 同步，库存更新
• 调拨        → 同步，需要返回调拨单号
• 盘点        → 同步
• 基础数据    → 同步

特点：
✓ 操作频率低（每天几十次）
✓ 同步调用延迟（200-500ms）可接受
✓ ERPNext是核心系统，提供专业能力
✓ 架构合理，无需改动
```

### 2.2 销售业务线（弱依赖ERPNext）

```
前台收银功能 → 本地处理，异步同步

TTPOS前台 → 本地处理 → 异步同步到ERPNext

• 用户下单    → 本地处理，不调用ERP ✓
• 支付结算    → 本地处理，不调用ERP ✓
• 订单完成    → 本地处理，不调用ERP ✓
    ↓ 异步同步
• Sales Invoice → ERPNext（用于财务核算）

特点：
✓ 操作频率高（每天几千笔）
✓ 用户要求<200ms响应
✓ 当前已不调用ERP，性能良好
✓ 订单异步同步到ERPNext用于财务
```

## 三、当前架构评估

### ✅ 架构合理，无需改动

**1. 进销存依赖ERPNext是正确的**
```
优势：
• ERPNext提供专业的进销存能力
• 避免重复造轮子
• 同步调用虽有延迟，但低频操作可接受

评估：✓ 架构合理
建议：保持现状
```

**2. BMP-ERP适配层有价值**
```
价值：
• API封装：简化ERPNext REST API
• 数据转换：TTPOS ↔ ERPNext
• 多站点管理：支持多个ERPNext实例
• gRPC统一服务

评估：✓ 中间层有必要
建议：继续维护
```

**3. 销售前台不调用ERP**
```
现状：
• 用户下单不查询ERPNext
• 库存查询查本地数据
• 性能良好

评估：✓ 设计合理
建议：保持现状
```

## 四、可优化的部分（优先级P2）

### 4.1 销售订单异步同步到ERPNext

**当前可能的问题：**
- 订单数据是否实时同步到ERPNext？
- 如果实时同步，是否阻塞了某些流程？

**优化建议：**
```
订单创建流程：
1. TTPOS创建订单 → 本地保存 → 立即返回用户
2. 发布事件到消息队列（RabbitMQ）
3. BMP-ERP消费事件 → 批量同步到ERPNext
4. 用于财务核算，T+0或T+1可接受

优点：
• 用户下单不等待ERPNext
• 批量同步效率更高
• ERPNext故障不影响收银
```

**实施复杂度：** 中等  
**优先级：** P2（改进建议）  
**预期收益：** 提升健壮性，降低ERPNext故障影响

### 4.2 ERPNext性能监控

**潜在风险：**
- 随着业务增长，采购等操作频率可能增加
- ERPNext性能能否承受？

**建议：**
```
监控指标：
• BMP-ERP → ERPNext的调用延迟（P50/P95/P99）
• ERPNext各API的响应时间
• ERPNext的资源使用率（CPU、内存、数据库）

告警规则：
• 调用延迟 P95 > 1s → 告警
• ERPNext响应时间 P95 > 2s → 告警
• ERPNext CPU > 80% → 告警
```

**实施复杂度：** 低  
**优先级：** P2（改进建议）  
**预期收益：** 提前发现性能瓶颈

## 五、常见误区澄清

### ❌ 误区1：BMP-ERP增加了调用链路，应该去掉

**错误理解：**
- 三层调用（Main → BMP → ERP）增加延迟
- 应该让Main直接调用ERPNext

**正确理解：**
- BMP-ERP提供API封装、数据转换、多站点管理等价值
- 进销存是低频操作，延迟可接受
- 去掉BMP-ERP需要Main维护ERPNext对接逻辑，得不偿失

### ❌ 误区2：销售下单调用ERPNext导致延迟

**错误理解：**
- 用户下单需要等待ERPNext响应
- 导致用户体验差

**正确理解：**
- 当前销售下单已不调用ERPNext ✓
- 库存查询查本地数据 ✓
- 订单异步同步到ERPNext用于财务 ✓
- 性能良好，无需优化

### ❌ 误区3：TTPOS应该本地管理所有进销存

**错误理解：**
- TTPOS应该本地维护库存、BOM、成本核算
- ERPNext仅用于财务报表

**正确理解：**
- ERPNext是专业的进销存系统
- 提供成熟的BOM、成本核算、多仓库能力
- TTPOS重复开发成本高、风险大
- 当前架构合理，充分利用ERPNext能力

## 六、总结

### 核心结论

**BMP-ERP当前架构合理，无需大规模重构**

```
合理的部分（保持）：
✓ 进销存依赖ERPNext（提供专业能力）
✓ BMP-ERP适配层（封装、转换、路由）
✓ 销售前台不调用ERP（性能良好）

可优化的部分（P2）：
💡 销售订单异步同步到ERPNext
💡 ERPNext性能监控

不需要改动的：
✗ 去掉BMP-ERP中间层
✗ Main直接调用ERPNext
✗ TTPOS本地实现进销存
```

### 架构治理的重点

**本次架构治理应聚焦：**

1. **Main服务模块化重构**（P0）
   - 拆分超大文件（order.go 14K行）
   - 解决服务循环依赖
   - 应用DDD重构

2. **多租户数据库优化**（P0）
   - 解决500商户连接数爆炸问题
   - 共享表+TenantID模式

3. **基础设施完善**（P0）
   - 链路追踪（OpenTelemetry）
   - 监控告警（Prometheus + Grafana）
   - 消息队列（RabbitMQ）

4. **代码质量提升**（P1）
   - 提升测试覆盖率
   - 解决N+1查询
   - 统一错误处理

**而不是：**
- ✗ BMP-ERP重构/迁移
- ✗ 重复开发ERPNext的进销存能力

---

**结论**：BMP-ERP架构合理，保持现状即可。  
**优先级**：P2（可优化，但非核心问题）  
**建议**：聚焦Main服务重构和基础设施完善
