## 三、回滚预案

### 3.1 回滚触发条件

**立即回滚：**
```
• 错误率>5%
• 核心功能不可用
• 数据严重错误
• P99延迟>2秒
```

**评估后回滚：**
```
• 错误率1-5%
• 性能下降>30%
• 用户投诉增加
• 非核心功能异常
```

### 3.2 回滚步骤

**场景1：代码回滚**
```bash
# 1. 立即切换到上一版本
kubectl rollout undo deployment/ttpos-main

# 2. 验证回滚成功
kubectl rollout status deployment/ttpos-main

# 3. 通知团队
# 4. 分析原因

预计时间：5分钟
```

**场景2：数据库回滚**
```
灰度期（双写期间）：
1. 停止读新库 → 切回旧库
2. 停止写新库 → 只写旧库
3. 数据已同步，无丢失
预计时间：10分钟

全量期（新库期）：
1. 旧库保留1个月备份
2. 可恢复数据
3. 但需要重新双写迁移
预计时间：1天
```

**场景3：功能回滚**
```
通过配置中心动态开关：
1. Nacos关闭新功能开关
2. 自动切回旧逻辑
3. 无需重启服务
预计时间：1分钟
```

## 七、FAQ

### Q1: 为什么不一次性重构所有模块？
```
A: 风险太高！
• 一次性重构需要3-6个月
• 期间无法发版
• 出问题难以定位
• 难以回滚

分阶段重构：
• 每个模块2-4周
• 每个阶段可回滚
• 风险可控
• 经验可复用
```

### Q2: 为什么不直接拆微服务？
```
A: 不需要！
• 核心业务需要事务一致性
• 微服务带来网络开销
• 增加运维复杂度
• 当前规模不需要

模块化单体：
• 保留单体的优势
• 获得模块化的好处
• 未来可平滑拆分
```

### Q3: 6个月时间够吗？
```
A: 够！（如果优先级清晰）
• Month 1: 基础设施（必须）
• Month 2-3: 核心域重构（必须）
• Month 4: 数据库优化（必须）
• Month 5-6: 微服务拆分（可选）

如果人力不足：
• 前4个月必须完成
• 后2个月可延期
```

### Q4: 如何说服团队？
```
A: 用数据说话！
• 演示链路追踪效果
• 展示性能提升数据
• 分享重构成功案例
• 小范围试点验证

关键：
• 先做出成果
• 再推广经验
• 建立信心
```

### Q5: 如果进度延期怎么办？
```
A: 弹性调整！
• 优先完成P0任务
• P1任务延后
• P2任务砍掉

关键路径：
• 基础设施 → 必须
• 核心域重构 → 必须
• 数据库优化 → 必须
• 其他 → 可选
```
