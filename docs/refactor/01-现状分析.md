### 2.2 服务循环依赖问题（P0 - 严重）

#### 问题描述

通过分析服务构造函数，发现以下循环依赖：

**循环依赖 1：Material ↔ Warehouse**

```go
// MaterialSrv依赖WarehouseSrv
type materialSrv struct {
    warehouseSrv IWarehouseSrv  // 👈 依赖Warehouse
}

// WarehouseSrv依赖MaterialSrv
type warehouseSrv struct {
    materialSrv IMaterialSrv   // 👈 依赖Material
}

// 形成循环！
Material → Warehouse → Material
```

**循环依赖 2：Product ↔ Material**

```go
// ProductSrv需要查询Material库存
type productSrv struct {
    materialSrv IMaterialSrv   // 👈 依赖Material
}

// MaterialSrv需要关联Product信息
type materialSrv struct {
    productSrv IProductSrv     // 👈 依赖Product
}
```

#### 影响分析

```
1. 单元测试困难
   - 无法独立测试单个服务
   - Mock依赖复杂（需要Mock循环依赖链）
   - 测试用例难以编写

2. 代码理解困难
   - 调用链路混乱
   - 开发者难以理解服务边界
   - 容易引入新的依赖

3. 重构风险高
   - 修改一个服务影响多个服务
   - 难以拆分为独立模块
   - 无法独立部署

4. 性能隐患
   - 可能导致无限递归调用
   - 内存泄漏风险
```

## 💡 三、BMP 服务现状分析

### 3.1 BMP-ERP 的角色与定位

**BMP-ERP 是 TTPOS 与 ERPNext 的适配层：**

```
调用链路：
TTPOS Main (餐饮业务系统)
    ↓ gRPC
BMP-ERP (适配层)
    ↓ HTTP REST API
ERPNext (开源ERP - 进销存/财务系统)
```

**BMP 服务组成：**

```
ttpos-bmp/app/
├── ttpos-erp/          (ERPNext对接服务 - 核心)
│   ├── Buying          采购管理 → ERPNext Purchase Order
│   ├── Selling         销售管理 → ERPNext Sales Invoice
│   ├── Stock           库存管理 → ERPNext Stock Entry
│   ├── Item            商品/物料 → ERPNext Item
│   ├── Warehouse       仓库管理 → ERPNext Warehouse
│   ├── Material Transfer 物料调拨 → ERPNext Material Transfer
│   ├── Manufacturing   生产制造 → ERPNext BOM/Work Order
│   ├── Setup           基础设置
│   └── Company         公司/站点管理
│
├── ttpos-takeout/      (外卖平台对接)
│   └── Skootar/Grab/Lineman等平台API封装
│
├── ttpos-message/      (消息推送)
│
├── ttpos-manager/      ⚠️ 功能unclear
├── ttpos-shop/         ⚠️ 功能unclear
└── ttpos-publisher/    ⚠️ 功能unclear
```

**ERPNext 在 TTPOS 中的作用：**

```
ERPNext提供的专业能力：
1. 进销存管理
   - 物料管理（Item、BOM）
   - 采购管理（Purchase Order、Supplier）
   - 库存管理（Stock Entry、Stock Reconciliation）
   - 仓库管理（Warehouse、Bin）

2. 财务核算
   - 会计凭证
   - 成本计算（移动加权平均）
   - 财务报表（利润表、资产负债表）

3. 生产管理
   - 物料清单（BOM）
   - 生产计划（Work Order）

TTPOS使用场景：
• 后台进销存管理 → 依赖ERPNext能力
• 前台销售订单 → 异步同步到ERPNext用于财务
```

### 3.2 两条业务线的调用模式

**TTPOS 与 ERPNext 的集成分为两条业务线：**

```
【进销存管理线】- 强依赖ERPNext（后台管理功能）
TTPOS后台 → BMP-ERP → ERPNext
• 物品管理（Item）         → 必须同步，需要ERPNext返回Item Code
• BOM配方（BOM）           → 必须同步，用于成本核算
• 采购单（Purchase Order） → 必须同步，需要ERPNext返回采购单号
• 收货入库（Stock Entry）  → 必须同步，库存更新
• 调拨（Material Transfer）→ 必须同步，需要ERPNext返回调拨单号
• 盘点（Stock Reconciliation）→ 必须同步
• 基础数据（Warehouse/Supplier）→ 必须同步

特点：
✓ 操作频率低（每天几十次）
✓ 同步调用延迟（200-500ms）可接受
✓ ERPNext是这些业务的核心系统（提供专业进销存能力）
✓ 架构合理，无需改动

【销售业务线】- 弱依赖ERPNext（前台收银功能）
TTPOS前台销售 → 本地处理 → 异步同步到ERPNext
• 用户下单       → TTPOS本地处理（不调用ERP）✓
• 支付结算       → TTPOS本地处理（不调用ERP）✓
• 订单完成       → TTPOS本地处理（不调用ERP）✓
    ↓ 异步同步
• Sales Invoice  → ERPNext（用于财务核算）

特点：
✓ 操作频率高（每天几千笔）
✓ 用户要求<200ms响应
✓ 当前已不调用ERP，性能良好 ✓
✓ 可优化点：将订单异步同步到ERPNext（用于财务）
```

### 3.3 当前架构评估

#### ✅ 架构合理的部分

**1. 进销存管理依赖 ERPNext**

```
优势：
• ERPNext提供专业的进销存能力（BOM、成本核算、多仓库）
• TTPOS无需重复开发复杂的进销存逻辑
• 同步调用虽有延迟，但低频操作可接受

评估：✓ 架构合理，符合业务需求
建议：保持现状，无需改动
```

**2. BMP-ERP 作为适配层**

```
价值：
• API封装：简化ERPNext复杂的REST API调用
• 数据转换：TTPOS数据模型 ↔ ERPNext数据模型
• 多站点管理：支持不同商户路由到不同ERPNext实例
• gRPC接口：统一对外服务

评估：✓ 中间层有存在价值
建议：保留BMP-ERP，继续维护
```

**3. 销售前台不调用 ERP**

```
现状：
• 用户下单不查询ERPNext
• 库存查询查本地数据
• 性能良好

评估：✓ 设计合理
建议：保持现状
```

#### 💡 可优化的部分

**1. 销售订单异步同步到 ERPNext**

```
当前可能的问题：
• 订单数据是否实时同步到ERPNext？
• 如果是实时同步，是否阻塞了某些流程？

优化建议：
• 订单创建后，异步推送到消息队列
• BMP-ERP消费事件，批量同步到ERPNext
• 用于财务核算，T+0或T+1可接受

优先级：P2（改进建议）
```

**2. ERPNext 性能监控**

```
潜在风险：
• 随着业务增长，采购等操作频率增加
• ERPNext性能能否承受？

建议：
• 监控BMP-ERP → ERPNext的调用延迟
• 监控ERPNext的响应时间
• 提前发现性能瓶颈
```

## ⚠️ 四、基础设施问题分析

### 4.1 多租户数据库架构问题（P0 - 严重）

#### 当前方案

```go
// DBManager管理多个商户数据库
type DBManager struct {
    dbs map[uint64]*gorm.DB
}

// 初始化：为每个商户创建独立连接
func (m *DBManager) initDBs(conf) {
    // 1. 主库
    m.dbs[0] = connect("ttpos")

    // 2. 查询所有商户
    companies := queryCompanies()

    // 3. 为每个商户创建连接
    for _, company := range companies {
        db := connect(fmt.Sprintf("shop%d", company.Uuid))
        m.dbs[company.Uuid] = db
    }
}

当前状态（50商户）：
├── ttpos (主库)：1个连接池（MaxOpenConns=50）
├── shop1：1个连接池（MaxOpenConns=10）
├── shop2：1个连接池（MaxOpenConns=10）
├── ...
└── shop50：1个连接池（MaxOpenConns=10）

总连接数：50 + 50*10 = 550个连接
```

#### 扩展到 500 商户的问题

```
预测问题（500商户）：
├── 连接数爆炸：50 + 500*10 = 5050个连接
│   └── MySQL默认max_connections=151
│       → 需要修改到10000+ （风险极高）
│
├── 资源浪费
│   ├── 小商户（10订单/天）占用10个连接
│   ├── 大商户（1000订单/天）也只占用10个连接
│   └── 资源分配不合理
│
├── 运维成本高
│   ├── 备份500个数据库
│   ├── 监控500个数据库
│   └── 数据迁移需要逐个操作
│
└── 跨租户查询困难
    ├── 平台级统计需要遍历500个数据库
    ├── 全局商品搜索无法实现
    └── 数据分析困难
```

#### 性能瓶颈

```
1. 连接池瓶颈
   - 高峰期连接数不足
   - 连接等待时间长
   - 连接泄漏风险

2. 内存占用高
   - 每个连接约2-5MB内存
   - 5050个连接约10-25GB内存
   - 仅连接池就占用大量资源

3. 数据库压力大
   - 维护5050个连接消耗CPU
   - 上下文切换频繁
   - 查询缓存效率低
```

## 📊 六、性能瓶颈识别

### 6.1 数据库性能问题

#### 问题 1：N+1 查询

```go
// 发现位置：订单查询
func (s *orderSrv) GetOrderList() []Order {
    orders := repo.GetOrders()  // 1次查询

    for _, order := range orders {
        // N次查询！
        products := repo.GetOrderProducts(order.Id)

        for _, product := range products {
            // N*M次查询！
            detail := repo.GetProductDetail(product.Id)
        }
    }
}

性能影响：
• 查询100个订单
• 每个订单10个商品
• 总SQL数：1 + 100 + 1000 = 1101次！
• 耗时：~5秒（不可接受）

优化方案：
• 使用Preload
• 批量查询
• 预期耗时：~100ms
```

#### 问题 2：缺少索引

```sql
-- 高频查询（发现于订单列表）
SELECT * FROM ttpos_sale_order
WHERE company_uuid = 123
  AND status = 1
  AND create_time BETWEEN 1609459200 AND 1612137600
ORDER BY create_time DESC
LIMIT 20 OFFSET 0;

-- 当前索引
INDEX idx_uuid (uuid)
INDEX idx_company_uuid (company_uuid)

-- 问题：缺少组合索引
-- 查询需要扫描 company_uuid 所有行，然后过滤 status 和 create_time
-- 影响：100万行数据，扫描10万行，耗时500ms

-- 优化：添加组合索引
INDEX idx_company_status_time (company_uuid, status, create_time)
-- 预期：扫描1000行，耗时20ms
```

### 6.2 缓存策略问题

**当前状态：**

```go
// ❌ 热点数据未缓存
func (s *productSrv) GetProduct(id uint64) *Product {
    return db.Find(&product, id) // 每次查数据库
}

影响：
• 商品详情QPS：1000
• 数据库QPS：1000（压力大）
• P99延迟：50ms

✅ 应该实现多级缓存：
func (s *productSrv) GetProduct(id uint64) *Product {
    // L1: 本地缓存（5s TTL）
    if product := localCache.Get(id); product != nil {
        return product  // 耗时：<1ms
    }

    // L2: Redis缓存（5min TTL）
    if product := redis.Get(id); product != nil {
        localCache.Set(id, product)
        return product  // 耗时：~5ms
    }

    // L3: 数据库
    product := db.Find(&product, id)  // 耗时：~20ms
    redis.Set(id, product)
    localCache.Set(id, product)
    return product
}

优化效果：
• 缓存命中率90%
• 平均延迟：2ms（降低90%）
• 数据库QPS：100（降低90%）
```

```
4. 熔断器保护（避免雪崩）
```
