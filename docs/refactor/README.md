## 📊 核心数据

### 现状问题（P0级）

```
1. 超大文件：order.go (14,174行) 
2. 连接数爆炸：500商户将导致5000个DB连接
3. 无链路追踪：故障排查平均30分钟
4. 事件丢失风险：内存事件总线
5. 服务循环依赖：Material ↔ Warehouse
```

### 目标成果（6个月）

| 指标 | 当前 | 目标 | 提升 |
|------|------|------|------|
| QPS | ~500 | ~5000 | **10倍** |
| P99延迟 | ~800ms | <200ms | **75%↓** |
| DB连接数 | 550 | 250 | **固定** |
| 故障定位 | >30min | <5min | **83%↓** |
| 测试覆盖 | <5% | >70% | **14倍** |
| 代码行数 | 14K/文件 | <2K/文件 | **86%↓** |

## 💡 关键决策

### 架构定位

```
核心业务 → 模块化单体（Main）
├─ 商品域
├─ 订单域
├─ 库存域
├─ 收银域
├─ 桌台域
└─ 会员域

增值服务 → 独立微服务
├─ 鉴权服务
├─ 消息服务
├─ 统计服务
├─ 外卖服务
├─ 短信服务
└─ 结算服务
```

### 保持现状的决策 ✓

1. **BMP-ERP架构保持**
   - TTPOS定位："餐饮+ERP一体化"
   - ERPNext提供专业进销存能力
   - 架构合理，保持现状

2. **独立数据库方案保持**
   - 便于数据迁移（库对库copy）
   - 通过连接池优化控制连接数

3. **离线收银暂缓（P2）**
   - 客户暂无痛点，在规划中
   - 优先解决开发效率和扩展性

### 技术选型

| 决策点 | 方案 | 理由 |
|--------|------|------|
| Main重构 | DDD分层架构 | 清晰边界、可测试、提升开发效率 |
| 数据库 | 独立DB+连接池优化 | 保持隔离，控制连接数 |
| 链路追踪 | OpenTelemetry + Jaeger | CNCF标准、生态成熟 |
| 消息队列 | RabbitMQ | 可靠性高、运维成熟 |
| 监控 | Prometheus + Grafana | 业界标准 |
| API网关 | APISIX | 高性能、动态配置 |
