## 🎯 背景和动机

### 问题描述

当前 TTPOS 系统采用多租户架构，每个商家拥有独立的数据库和账号体系。一个账号（username）只能登录一个商家，这在实际业务场景中存在以下问题：

1. **区域经理管理多个门店**：区域经理需要频繁切换账号才能管理不同门店
2. **连锁企业总部员工**：总部员工需要访问多个分店，但当前只能绑定一个商家
3. **第三方服务商**：服务商需要同时管理多个客户商家，但需要维护多个账号
4. **员工跨商家工作**：员工在不同商家间切换工作时，需要记住多个账号密码

**用户痛点**：
- 需要维护多个账号和密码
- 切换商家需要重新登录，操作繁琐
- 账号管理复杂，容易混淆

### 业务价值

解决这个问题能带来以下业务价值：

- ✅ **提升用户体验**：一个账号管理多个商家，减少账号管理负担
- ✅ **提高工作效率**：支持快速切换商家，无需重新登录
- ✅ **降低管理成本**：减少账号维护成本，简化权限管理
- ✅ **增强系统灵活性**：支持更复杂的组织架构和业务场景
- ✅ **提升客户满意度**：满足连锁企业和区域管理的实际需求

## 💡 解决方案概述

### 方案描述

实现一个账号可以登录多个商家的功能，通过扩展 SaaS 数据库表结构，建立全局用户与商家的多对多关系。登录后可以查看可访问的商家列表，支持在已登录状态下切换商家，每个商家内的权限独立管理。

**核心思路**：
1. 在 SaaS 库中创建全局用户表（`ttpos_global_user`）
2. 创建用户-商家关联表（`ttpos_user_company`），建立多对多关系
3. 登录时返回可访问的商家列表
4. 支持切换商家功能，无需重新登录
5. 保持现有权限体系（RBAC）不变

### 核心功能点

1. **多商家账号绑定**：一个账号可以绑定多个商家
2. **商家列表展示**：登录后显示可访问的商家列表
3. **商家切换功能**：支持在已登录状态下切换商家
4. **权限隔离**：每个商家内的权限独立管理
5. **向后兼容**：通过数据迁移保持与现有系统的兼容

### 风险识别

**潜在风险**：

1. **数据迁移风险**：需要将现有 `company_staff` 数据迁移到新表结构
   - **缓解措施**：充分测试迁移脚本，准备回滚方案，分批迁移

2. **权限混乱风险**：用户可能访问错误的商家数据
   - **缓解措施**：严格验证权限，添加审计日志，确保权限隔离

3. **Token 兼容性问题**：现有 Token 可能失效
   - **缓解措施**：支持新旧 Token 格式，逐步迁移

4. **性能影响**：登录查询可能变慢
   - **缓解措施**：添加数据库索引，使用缓存优化

5. **用户体验变化**：用户可能不适应新流程
   - **缓解措施**：提供引导，保持界面一致性

### 第三方鉴权库推荐

技术方案文档中详细对比了以下方案：

1. **Logto**（团队考虑，最推荐）⭐⭐⭐⭐⭐
   - **开源**，支持多租户，集成简单，开发者友好
   - **技术栈匹配**：提供 Go SDK，与现有项目集成方便
   - **现代化体验**：UI 现代化，支持无密码认证
   - **成本低**：开源免费，可自托管
   - **标准协议**：遵循 OIDC/OAuth，便于未来扩展
   - 文档：https://docs.logto.io/
   - GitHub：https://github.com/logto-io/logto

2. **Casdoor**（团队考虑，次推荐）⭐⭐⭐⭐
   - **开源**，功能丰富，支持多种协议（OAuth/OIDC/SAML/CAS/LDAP）
   - **多租户支持**：内置多租户和身份代理
   - **技术栈匹配**：Go + React，与项目技术栈一致
   - **成本低**：开源免费，可自托管
   - ⚠️ **注意事项**：需关注安全配置，UI 可能需要自定义
   - 文档：https://casdoor.org/docs/overview
   - GitHub：https://github.com/casbin/casdoor

3. **Keycloak**（企业级推荐）
   - 开源，功能强大，支持 SSO、OAuth 2.0
   - 文档：https://www.keycloak.org/

4. **Clerk**（快速开发推荐）
   - 开箱即用，集成简单，支持多租户
   - ⚠️ 商业产品，有费用
   - 文档：https://clerk.com/docs

5. **Auth0**（企业级）
   - 功能全面，安全性高
   - ⚠️ 商业产品，费用较高
   - 文档：https://auth0.com/docs

6. **Ory Kratos**（自托管推荐）
   - 开源，可自托管，云原生架构
   - 文档：https://www.ory.sh/docs/kratos/

7. **自建方案**（当前推荐）
   - 基于现有架构扩展，改动最小，实施简单

**推荐结论**：
- **方案一（推荐）**：当前阶段不引入第三方库，采用自建方案（扩展表结构）
- **方案二（如果选择第三方库）**：
  - **优先考虑 Logto**：最适合 TTPOS 项目，集成简单，技术栈匹配
  - **次选 Casdoor**：功能丰富，支持多种协议，适合复杂场景

**作为** 区域经理  
**我想** 使用一个账号登录多个门店  
**以便于** 快速切换门店进行管理，无需记住多个账号密码

**作为** 连锁企业总部员工  
**我想** 访问多个分店的数据  
**以便于** 统一管理和分析各分店的经营情况

**作为** 第三方服务商  
**我想** 同时管理多个客户商家  
**以便于** 提供统一的服务支持，提高服务效率

### AC 验收标准（初稿）

1. **WHEN** 用户登录 **THEN** 系统 **SHALL** 返回可访问的商家列表
2. **IF** 用户有多个商家权限 **THEN** 系统 **SHALL** 显示商家选择界面
3. **WHEN** 用户切换商家 **THEN** 系统 **SHALL** 更新 Token 并切换到对应商家
4. **IF** 用户无权限访问商家 **THEN** 系统 **SHALL** 拒绝访问并提示错误
5. **WHEN** 用户在不同商家间切换 **THEN** 系统 **SHALL** 保持权限隔离，确保数据安全

### 推荐方案

**方案一：扩展 company_staff 表（方案 1.2：新增全局用户表）**

- SaaS 库：创建 `ttpos_global_user`（全局用户表）
