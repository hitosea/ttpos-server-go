## 🎯 背景和动机

### 问题描述

当前系统在创建订单时，虽然 `SaleBill` 表已有 `source` 字段用于记录订单来源，但在实际创建订单的业务逻辑中并未正确设置该字段值。同时，系统也缺少对客户端版本的记录，无法追踪订单来自哪个版本的客户端（如 2.10.0、2.9.0）。这导致无法准确追踪订单来源和客户端版本，影响后续的数据分析和问题排查。

**现状**：
- `SaleBill` 表已存在 `source` 字段（类型：`int(10)`，默认值：0）
- 字段注释已定义：`0-默认值、1-收银机、2-点餐助手、3-平板、4-H5、5-会员端`
- 但创建订单时，`source` 字段始终为默认值 0，未根据实际请求来源设置
- `SaleBill` 表缺少 `client_version` 字段，无法记录客户端版本信息
- 系统已具备从请求头获取客户端版本的能力（`ctx.GetVersion()` 从 `Client-Version` header 获取），但未在订单中记录

**痛点**：
- 无法区分订单来自收银机、点餐助手、平板还是 H5
- 无法追踪订单来自哪个版本的客户端（如 2.10.0、2.9.0）
- 影响订单来源统计和分析
- 无法针对不同来源的订单进行差异化处理
- 当订单出现问题时，无法快速定位是哪个版本的客户端导致的问题

### 业务价值

解决这个问题能带来以下业务价值：

- **数据统计准确性**：准确记录订单来源和客户端版本，支持按来源和版本维度进行数据分析
- **业务决策支持**：了解各客户端的订单占比和版本分布，优化产品策略和版本发布策略
- **问题排查能力**：当订单出现问题时，可快速定位来源客户端和版本，提高问题排查效率
- **运营分析**：支持按来源和版本分析订单转化率、客单价等关键指标
- **版本兼容性分析**：了解各版本的使用情况，评估版本升级进度和兼容性问题

## 💡 解决方案概述

### 方案描述

在创建订单的业务逻辑中，根据请求上下文自动设置 `SaleBill` 表的 `source` 和 `client_version` 字段值。系统已具备获取请求来源和客户端版本的能力（通过 JWT token 中的 source 信息和请求头中的 `Client-Version`），只需在创建 `SaleBill` 时映射并设置正确的值。

**实现要点**：
1. **数据库字段**：在 `SaleBill` 表中新增 `client_version` 字段（类型：`varchar(20)`，默认值：空字符串）
2. **定义 Source 常量映射**：将 JWT Source 值映射到 `source` 字段值（0-5）
3. **设置 source 字段**：在创建 `SaleBill` 的所有入口处，根据 `ctx.GetSource()` 设置 `source` 字段
4. **设置 client_version 字段**：在创建 `SaleBill` 的所有入口处，根据 `ctx.GetVersion()` 设置 `client_version` 字段
5. **确保向后兼容**：对于无法识别来源的请求，使用默认值 0；对于无法获取版本的请求，使用空字符串

### 核心功能点

1. **数据库迁移**
   - 创建迁移文件，在 `SaleBill` 表中新增 `client_version` 字段
   - 字段类型：`varchar(20)`，默认值：空字符串，注释：客户端版本号（如 2.10.0、2.9.0）

2. **定义 Source 映射常量**
   - 在 `constant` 包中定义 Source 到 source 字段值的映射关系
   - 支持：收银机(1)、点餐助手(2)、平板(3)、H5(4)、会员端(5)、默认值(0)

3. **修改订单创建逻辑**
   - 在 `CreateInstantOrder`（即时订单）中设置 source 和 client_version
   - 在 `CreateDeskOrder`（桌台订单）中设置 source 和 client_version
   - 在 `createMemberOrder`（会员端订单）中设置 source 和 client_version
   - 在其他创建 SaleBill 的地方统一设置 source 和 client_version

4. **确保数据一致性**
   - 所有创建 SaleBill 的代码路径都要设置 source 和 client_version
   - 添加单元测试验证 source 和 client_version 字段设置正确性

### 风险识别

**潜在风险**：
1. **遗漏创建入口**：可能存在其他创建 SaleBill 的代码路径未设置 source 和 client_version
2. **历史数据**：已有订单的 source 字段为 0，client_version 为空，无法追溯真实来源和版本
3. **JWT Source 值不完整**：某些客户端可能未正确设置 JWT 中的 source 信息
4. **客户端版本格式不一致**：不同客户端可能使用不同的版本号格式（如 2.10.0 vs 2.10 vs v2.10.0）
5. **请求头缺失**：某些客户端可能未在请求头中发送 `Client-Version`

**缓解措施**：
1. **代码审查**：全面搜索 `CreateSaleBill` 调用，确保所有路径都设置 source 和 client_version
2. **历史数据**：接受历史数据无法追溯的现实，从新版本开始记录
3. **默认值处理**：对于无法识别的来源，使用默认值 0；对于无法获取的版本，使用空字符串，并在日志中记录警告
4. **版本格式标准化**：在设置 client_version 时，统一处理版本号格式（去除前缀 v，统一为 x.y.z 格式）
5. **向后兼容**：对于未发送版本号的客户端，使用空字符串作为默认值，不影响现有功能

## 📝 附录

### User Story（初稿）

**作为** 商户管理员  
**我想** 在订单数据中看到订单来自哪个客户端和客户端版本  
**以便于** 分析各客户端的使用情况、订单转化率，以及排查特定版本的问题

**作为** 开发人员  
**我想** 在订单数据中看到订单来自哪个客户端和客户端版本  
**以便于** 快速定位问题订单的来源和版本，提高问题排查效率

### AC 验收标准（初稿）

**订单来源追踪**：
1. **WHEN** 通过收银机创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 source 字段记录为 1
2. **WHEN** 通过点餐助手创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 source 字段记录为 2
3. **WHEN** 通过平板创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 source 字段记录为 3
4. **WHEN** 通过 H5 创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 source 字段记录为 4
5. **WHEN** 通过会员端创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 source 字段记录为 5
6. **WHEN** 无法识别来源时 **THEN** 系统 **SHALL** 在 SaleBill 表的 source 字段记录为 0（默认值）

**客户端版本追踪**：
7. **WHEN** 客户端在请求头中发送 `Client-Version: 2.10.0` 创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 client_version 字段记录为 `2.10.0`
8. **WHEN** 客户端在请求头中发送 `Client-Version: 2.9.0` 创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 client_version 字段记录为 `2.9.0`
9. **WHEN** 客户端未发送 `Client-Version` 请求头创建订单 **THEN** 系统 **SHALL** 在 SaleBill 表的 client_version 字段记录为空字符串
10. **WHEN** 客户端发送的版本号格式为 `v2.10.0` **THEN** 系统 **SHALL** 自动去除前缀 `v`，记录为 `2.10.0`

**数据查询**：
11. **WHEN** 查询历史订单时 **THEN** 系统 **SHALL** 正确返回 source 和 client_version 字段值
12. **WHEN** 按客户端版本筛选订单时 **THEN** 系统 **SHALL** 能够正确过滤出指定版本的订单
