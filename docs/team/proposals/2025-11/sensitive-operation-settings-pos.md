## 🎯 背景和动机

### 问题描述

普通员工在进行折扣/退款/免单操作时，需要输入门店经理/店长权限密码进行二次验证。当前系统缺乏有效的权限验证机制，可能导致：

- 普通员工误操作或滥用权限
- 财务风险增加
- 门店经理/店长无法有效监管敏感操作

**用户故事**：

> 作为门店经理/店长，我想在收银机端对折扣/退款/免单操作进行权限验证，以便于控制普通员工进行敏感操作时的权限，降低财务风险。

### 业务价值

- ✅ **增强权限控制**：普通员工进行折扣/退款/免单操作时，需要授权员工验证
- ✅ **降低财务风险**：敏感操作必须经过授权验证，防止误操作和滥用
- ✅ **操作可追溯**：订单操作记录中记录授权员工信息，便于审计
- ✅ **灵活授权机制**：授权员工即使本身无"优惠折扣/退款设置"权限，也可作为验证节点

### 目标用户

- [x] 收银员（普通员工）
- [x] 门店经理/店长（授权验证人）
- [x] 点餐助手（Assistant 端）

## 💡 解决方案概述

### 方案描述

在收银机和点餐助手端实现敏感操作（折扣/退款/免单）的权限验证功能。当普通员工进行折扣、退款或免单操作时，系统判断当前员工是否为授权验证人：

- **如果是授权员工**：无需输入密码，直接进行下一步操作
- **如果不是授权员工**：弹出授权验证弹窗，要求选择授权员工并输入权限密码

**技术实现思路**：

1. 增加"检查授权"接口，判断当前操作人是否有权限操作（是否在授权人名单中）
2. 修改"整单/部分退款"接口，增加授权人账号和授权密码参数（可选参数）
3. 修改"优惠折扣"接口，增加授权人账号和授权密码参数（可选参数）
4. 修改"免单"接口，增加授权人账号和授权密码参数（可选参数）
5. 接口处理逻辑增加版本判断和权限判断：
   - 根据客户端版本判断是否需要权限验证
   - v2.10.0 之前的版本不进行权限验证（向后兼容）
   - v2.10.0 及之后的版本进行权限验证

### 核心功能点

1. **权限检查接口**

   - 判断当前操作人是否在授权人名单中
   - 如果在授权名单中，返回有权限，无需弹出授权弹窗
   - 如果不在授权名单中，返回没有权限，需要弹出授权弹框

2. **授权验证弹窗**

   - 输入授权人的邮箱(username)或手机号(phone)
   - 输入权限密码
   - 每次进行退款/折扣/免单都需要弹出（即使之前已输入过）

3. **退款/折扣/免单接口增强**

   - 增加授权人账号和授权密码参数（可选参数，用于向后兼容）
   - **版本判断逻辑**：
     - 如果客户端版本 < v2.10.0：不进行权限验证，直接允许操作（向后兼容）
     - 如果客户端版本 >= v2.10.0：进行权限验证
       - 接口调用人在授权名单中：直接允许操作
       - 接口调用人不在授权名单中：检查授权账号和授权密码是否正确且具有权限
   - 客户端版本通过请求头 `Client-Version`传递
   - **涉及接口**：
     - 整单退款接口：`/cashier/desk/order/refund`、`/assistant/desk/order/refund`
     - 部分退款接口：`/cashier/desk/order/refund/partial`、`/assistant/desk/order/refund/partial`
     - 折扣接口：`/cashier/desk/order/discount`、`/assistant/desk/order/discount`
     - 免单接口：`/cashier/desk/order/free`、`/cashier/instant/order/free`、`/assistant/desk/order/free`

4. **操作记录增强**

   - 订单操作记录中记录操作人：授权员工的姓名（邮箱）
   - 不另外增加操作记录类型,在原本的折扣和退款记录中增加授权员工信息,不需要显示到前端仅记录在数据库记录中

5. **密码验证逻辑**
   - 输入密码后，若密码正确，进行下一步的折扣、退款或免单操作
   - 若密码错误，toast 提示"密码错误"
   - 若输入的账号不是权限员工，则 toast 提示"不是权限员工，请确认信息"
   - 授权验证弹窗中进行一次密码验证,在优惠、退款和免单接口中又再一次进行密码验证(二次验证)

### 影响范围

**涉及终端**：

- [x] **POS 收银端**：折扣/退款/免单操作的权限验证

- [x] 业务逻辑（权限判断、密码验证）
- [x] 数据模型（操作记录表，记录授权员工信息）

### 风险识别

**潜在风险**：

1. 授权验证弹窗需要在多个场景下复用（整单退款、部分退款、折扣、免单），需要统一交互逻辑
2. 密码验证逻辑需要与商家后台的权限密码配置保持一致
3. 操作记录需要准确记录授权员工信息，需要考虑边界情况（如授权员工被删除）
4. 已输入授权员工、权限密码后，后台修改权限密码，需要正确处理（toast 提示：密码错误）
5. **版本兼容性风险**：
   - 需要准确识别客户端版本，避免版本判断错误导致的安全漏洞
   - 旧版本客户端可能无法传递版本信息，需要设置默认行为
   - 版本号格式需要统一规范，避免解析错误
6. **免单操作特殊性**：
   - 免单操作涉及多个接口（收银端桌台、点餐页面、助手端），需要统一处理逻辑
   - 免单操作在产品定义中属于折扣类型，需要与折扣接口保持一致的权限验证逻辑

**缓解措施**：

1. 设计统一的授权验证组件，在 POS 和 Assistant 端复用
2. 与商家后台的权限密码配置功能对接，确保数据一致性
3. 在操作记录中存储授权员工 ID 和姓名，即使员工被删除也能追溯
4. 在提交操作时再次验证密码，确保密码未被后台修改
5. **版本兼容性措施**：
   - 版本判断逻辑：如果无法识别版本或版本 < v2.10.0，默认不进行权限验证（向后兼容）
   - 版本号格式统一：使用语义化版本号（如 `2.10.0`），便于解析和比较
   - 版本信息传递：通过请求头 `Client-Version` 传递，格式为 `v2.10.0` 或 `2.10.0`
   - 默认行为：未传递版本信息时，视为旧版本，不进行权限验证

**以便于** 确保敏感操作经过授权，降低财务风险

**作为** 门店经理/店长（授权验证人）  
**我想** 通过输入权限密码验证普通员工的折扣/退款/免单操作  
**以便于** 控制敏感操作的权限，保护门店财务安全

### AC 验收标准（初稿）

基于任务 #36989 的验收标准：

1. **WHEN** 具有"优惠折扣/退款设置"权限且系统设置需密码验证时，在收银机或点餐助手界面点击"折扣"、"退款"或"免单"按钮 **THEN** 系统 **SHALL** 判断当前员工是否为"授权验证人"

2. **IF** 当前员工为授权员工 **THEN** 系统 **SHALL** 无需输入密码，直接进行下一步的折扣、退款或免单操作

3. **IF** 当前员工非授权员工 **THEN** 系统 **SHALL** 弹出授权员工选择弹窗：授权员工、权限密码（每一次进行退款/折扣/免单都需要弹出）

4. **WHEN** 输入密码后，若密码正确 **THEN** 系统 **SHALL** 进行下一步的折扣、退款或免单操作

5. **WHEN** 输入密码后，若密码错误 **THEN** 系统 **SHALL** toast 提示"密码错误"

6. **WHEN** 订单操作完成后 **THEN** 系统 **SHALL** 在订单操作记录中记录操作人：授权员工的姓名（邮箱）

7. **WHEN** 已输入授权员工、权限密码，此时后台修改权限密码，确定后 **THEN** 系统 **SHALL** toast 提示：密码错误

8. **WHEN** 未输入授权员工/权限密码、确定后 **THEN** 系统 **SHALL** 校验内容：输入框下方提示：请选择授权员工/请输入权限密码

9. **WHEN** 输入的账号不是权限员工 **THEN** 系统 **SHALL** toast 提示：不是权限员工，请确认信息

10. **WHEN** 客户端版本 < v2.10.0 **THEN** 系统 **SHALL** 不进行权限验证，直接允许折扣/退款/免单操作（向后兼容）

11. **WHEN** 客户端版本 >= v2.10.0 **THEN** 系统 **SHALL** 进行权限验证，按照上述规则执行

12. **WHEN** 客户端未传递版本信息或版本信息无法识别 **THEN** 系统 **SHALL** 视为旧版本，不进行权限验证（向后兼容）

13. **WHEN** 在收银端或助手端进行免单操作时 **THEN** 系统 **SHALL** 按照与折扣操作相同的权限验证逻辑执行

**特殊说明**：

- 员工 A 被选为授权验证人，即使其本身无"优惠折扣/退款设置"权限，也可作为验证节点
- **版本兼容性**：v2.10.0 之前的客户端版本不进行权限验证，确保旧版本客户端可以正常使用折扣/退款/免单功能
- **版本判断**：通过请求头 `Client-Version` 传递客户端版本号，格式为 `v2.10.0` 或 `2.10.0`
- **免单操作**：免单操作在产品定义中属于折扣类型（discount_type = 4），需要与折扣操作保持一致的权限验证逻辑

### 开发实现思路（来自任务 #36989）

#### 1. 增加"检查授权"接口

- 该接口判断当前操作人是否有权限操作（即是否在授权人名单中）
- 如果在授权人名单中，则返回有权限，不用弹出授权弹窗进行二次授权
- 如果不在授权人名单中，则返回没有权限，弹出授权弹框

#### 2. 增加"密码验证"接口

- 弹出授权弹框时,输入权限人的邮箱或密码并提交,该接口判断是不是权限员工和密码是否正确
- 方便密码验证通过后前端记录下账号密码用于在后续的优惠和退款接口中

#### 3. 修改"整单/部分退款"接口

- 增加授权人账号和授权密码参数（可选参数，用于向后兼容）
- **版本判断逻辑**：
  - 从请求头 `Client-Version` 获取客户端版本号
  - 如果版本号 < v2.10.0 或无法识别版本：不进行权限验证，直接允许退款（向后兼容）
  - 如果版本号 >= v2.10.0：进行权限验证
    - 如果接口调用人在授权名单中，则表示允许退款
    - 如果不在，则检查参数中的授权账号和授权密码是否正确且具有权限
    - 有权限才能退款

#### 4. 修改"优惠折扣"接口

- 增加授权人账号和授权密码参数（可选参数，用于向后兼容）
- **版本判断逻辑**：
  - 从请求头 `Client-Version` 获取客户端版本号
  - 如果版本号 < v2.10.0 或无法识别版本：不进行权限验证，直接允许折扣（向后兼容）
  - 如果版本号 >= v2.10.0：进行权限验证
    - 如果接口调用人在授权名单中，则表示允许折扣
    - 如果不在，则检查参数中的授权账号和授权密码是否正确且具有权限
    - 有权限才能折扣

#### 5. 修改"免单"接口

- 增加授权人账号和授权密码参数（可选参数，用于向后兼容）
- **涉及接口**：
  - `/cashier/desk/order/free` - 收银端桌台免单
  - `/cashier/instant/order/free` - 收银端点餐页面免单
  - `/assistant/desk/order/free` - 助手端桌台免单
- **版本判断逻辑**：
  - 从请求头 `Client-Version` 获取客户端版本号
  - 如果版本号 < v2.10.0 或无法识别版本：不进行权限验证，直接允许免单（向后兼容）
  - 如果版本号 >= v2.10.0：进行权限验证
    - 如果接口调用人在授权名单中，则表示允许免单
    - 如果不在，则检查参数中的授权账号和授权密码是否正确且具有权限
    - 有权限才能免单
- **业务逻辑**：
  - 免单操作在产品定义中属于折扣类型（discount_type = 4），需要与折扣操作保持一致的权限验证逻辑
  - 免单操作记录中需要记录授权员工信息，与折扣操作记录保持一致

#### 6. 业务步骤

**新版本客户端（v2.10.0+）**：
- 整单退款/部分退款，填好退款参数之后点击确认退款时弹出授权弹窗
- 点击确认退款时，先调用"检查授权"接口
- 如果弹出授权窗口，则输入授权人账号和授权密码
- 点击确认授权即调用退款接口（请求头中包含 `Client-Version: v2.10.0`）
- 折扣操作：填好折扣参数之后点击确认折扣时弹出授权弹窗，流程同上
- 免单操作：填好免单参数之后点击确认免单时弹出授权弹窗，流程同上

**旧版本客户端（< v2.10.0）**：
- 整单退款/部分退款，填好退款参数之后点击确认退款
- 直接调用退款接口（不传递版本信息或版本 < v2.10.0）
- 后端根据版本判断，不进行权限验证，直接允许退款
- 折扣操作：直接调用折扣接口，不进行权限验证
- 免单操作：直接调用免单接口，不进行权限验证

#### 7. 版本判断实现

**版本号格式**：
- 请求头：`Client-Version: v2.10.0` 或 `Client-Version: 2.10.0`
- 版本号解析：使用语义化版本号解析库，支持格式如 `v2.10.0`、`2.10.0`、`2.10.0.1` 等

**版本比较逻辑**：
```go
// 伪代码示例
func shouldRequireAuth(clientVersion string) bool {
    if clientVersion == "" {
        return false // 未传递版本，视为旧版本，不验证
    }
    
    version := parseVersion(clientVersion)
    if version == nil {
        return false // 无法解析版本，视为旧版本，不验证
    }
    
    targetVersion := parseVersion("2.10.0")
    return version.Compare(targetVersion) >= 0 // >= v2.10.0 才验证
}
```

**默认行为**：
- 如果请求头中未包含 `Client-Version`：视为旧版本，不进行权限验证
- 如果版本号无法解析：视为旧版本，不进行权限验证
- 如果版本号 < v2.10.0：不进行权限验证
