## 🎯 背景和动机

### 问题描述

当前 `UpdateMenuModifierReq` 协议只支持 Grab 平台的修饰符（Modifier/Property Values）更新逻辑，所有字段都按照 Grab 的规范设计。随着业务拓展到 Lineman 平台，需要支持不同平台的差异化处理：

1. **平台识别缺失**：无法区分当前更新请求是针对哪个平台
2. **状态枚举类型不一致**：
   - TTPOS 内部：`available_status` 为 `string` 类型（`"AVAILABLE"`, `"UNAVAILABLE"` 等）
   - Lineman API：`status` 为 `int` 类型（`1=AVAILABLE`, `2=SOLD_OUT_TODAY`, `3=SUSPENDED`）
3. **状态语义映射不同**：Grab 和 Lineman 的状态枚举语义不同
   - Grab: `AVAILABLE`, `UNAVAILABLE`
   - Lineman: `AVAILABLE(1)`, `SUSPENDED(3)`, `SOLD_OUT_TODAY(2)`（今日售罄，明天自动恢复）
4. **API 调用差异**：不同平台需要调用不同的第三方 API
   - Grab: Update Menu Modifier
   - Lineman: Update Menu Property Values Status

**示例**：
> 当商户在 TTPOS 后台将某个修饰符（如"加辣"）设置为"售罄"时，系统需要：
> - 对 Grab 平台：调用 Grab API，设置状态为 `UNAVAILABLE`
> - 对 Lineman 平台：调用 Lineman API，设置状态为 `SOLD_OUT_TODAY(2)`（明天自动恢复）

**关键技术挑战**：
- TTPOS `available_status` 是 `string`，但 Lineman API 要求 `int`，需要进行类型转换和枚举值映射

### 业务价值

- **平台扩展性**：为后续接入更多外卖平台（如 FoodPanda、ShopeeFood）奠定基础
- **状态一致性**：确保 TTPOS 与各平台的修饰符状态实时同步
- **用户体验**：商户在一个后台操作，自动同步到所有平台
- **降低错误率**：避免状态映射错误导致的修饰符上下架问题

### 目标用户

## 💡 解决方案概述

### 方案描述

在 `UpdateMenuModifierReq` 中增加 `provider_name` 字段用于标识平台，默认值为 `grab`（保持向后兼容）。当 `provider_name` 为 `lineman` 时，执行 Lineman 专用逻辑：

1. **平台识别**：通过 `provider_name` 字段区分平台
2. **类型转换**：将 TTPOS 的 `available_status` (string) 转换为 Lineman 的 `status` (int)
   - `"AVAILABLE"` → `1`
   - `"UNAVAILABLE"` → `3` (SUSPENDED)
   - `"SOLD_OUT_TODAY"` → `2` (今日售罄，明天自动恢复)
3. **API 调用**：调用 Lineman 的修饰符状态更新接口
   - `PUT /v1/partners/{partnerId}/stores/{storeId}/menu/property/values/status`

### 核心功能点

1. **增加 provider_name 字段**
   - 类型: `string`
   - 默认值: `grab`
   - 可选值: `grab`, `lineman`

2. **Lineman 状态映射（string → int）**
   - TTPOS `"AVAILABLE"` → Lineman `1` (AVAILABLE)
   - TTPOS `"UNAVAILABLE"` → Lineman `3` (SUSPENDED)
   - TTPOS `"SOLD_OUT_TODAY"` → Lineman `2` (SOLD_OUT_TODAY，明天自动恢复)

3. **Lineman 专用处理逻辑**
   - 将 `available_status` (string) 转换为 Lineman `status` (int)
   - 调用 Lineman API 进行状态更新
   - 处理 API 调用失败和重试逻辑

4. **向后兼容**
   - 未指定 `provider_name` 时，默认按 Grab 逻辑处理
   - 现有 Grab 调用方无需修改代码

**分解**：

### 风险识别

**潜在风险**：
1. **类型转换错误**：string → int 映射错误导致 Lineman API 调用失败
2. **Lineman API 调用失败**：网络问题、认证失败、限流
3. **状态映射错误**：导致修饰符错误上下架
4. **向后兼容问题**：现有 Grab 调用方受影响

**缓解措施**：
1. **严格枚举校验**：使用 map 进行 string → int 映射，未知状态返回错误
2. **重试机制**：API 调用失败时自动重试，记录失败日志
3. **单元测试**：覆盖所有状态映射场景（AVAILABLE, UNAVAILABLE, SOLD_OUT_TODAY）
4. **集成测试**：覆盖 Grab 和 Lineman 两种场景，确保互不影响

## 📝 附录

### User Story（初稿）

**作为** 商户管理员  
**我想** 在 TTPOS 后台统一管理修饰符状态，自动同步到 Grab 和 Lineman 平台  
**以便于** 无需在多个平台分别操作，提高管理效率，减少状态不一致

### AC 验收标准（初稿）

1. **WHEN** 调用 `UpdateMenuModifierReq` 且 `provider_name=lineman` **THEN** 系统 **SHALL** 将 `available_status` (string) 转换为 Lineman `status` (int) 并调用 Lineman API 更新修饰符状态
2. **WHEN** `available_status="UNAVAILABLE"` 且 `provider_name=lineman` **THEN** 系统 **SHALL** 映射为 Lineman 的 `status=3` (SUSPENDED)
3. **WHEN** `available_status="SOLD_OUT_TODAY"` 且 `provider_name=lineman` **THEN** 系统 **SHALL** 映射为 Lineman 的 `status=2` (SOLD_OUT_TODAY，明天自动恢复)
4. **WHEN** `available_status="AVAILABLE"` 且 `provider_name=lineman` **THEN** 系统 **SHALL** 映射为 Lineman 的 `status=1` (AVAILABLE)
5. **IF** 未指定 `provider_name` **THEN** 系统 **SHALL** 默认使用 `grab` 处理逻辑
6. **IF** `available_status` 值不在合法枚举范围内 **THEN** 系统 **SHALL** 返回错误提示

### 技术实现要点

#### 1. Protobuf 修改

```protobuf
// 更新菜单修饰符请求
message UpdateMenuModifierReq {
  string merchant_id = 1;                         // Grab MerchantID (必填)
  string modifier_id = 2;                         // 修饰符ID (partner modifier id, 必填)
  string modifier_name = 3;                       // 修饰符名称 (用于定位记录, 必填)
  optional int64 price = 4;                       // 价格 (minor unit，单位：分)
  optional string available_status = 5;           // 可用状态: AVAILABLE, UNAVAILABLE, SOLD_OUT_TODAY
  optional bool is_free = 6;                      // 是否免费
  repeated AdvancedPricing advanced_pricings = 7; // 高级定价配置
  string request_id = 8;                          // 请求 ID (可选，用于追踪)
  optional string provider_name = 9;              // 平台名称: grab (默认), lineman
}
```

#### 2. 状态映射表（string → int）

| TTPOS 状态 (string)    | Grab 状态         | Lineman 状态 (int) | Lineman 语义 |
|------------------------|-------------------|--------------------|--------------|
| `"AVAILABLE"`          | `AVAILABLE`       | `1`                | AVAILABLE    |
| `"UNAVAILABLE"`        | `UNAVAILABLE`     | `3`                | SUSPENDED    |
| `"SOLD_OUT_TODAY"`     | -（不支持）       | `2`                | SOLD_OUT_TODAY (明天自动恢复) |

#### 3. Lineman API 调用

**Endpoint**: `PUT /v1/partners/{partnerId}/stores/{storeId}/menu/property/values/status`

**Request Body**:
```json
{
  "propertyValues": [
    {
      "id": "partner-modifier-id",
      "status": 3  // 1=AVAILABLE, 2=SOLD_OUT_TODAY, 3=SUSPENDED
    }
  ]
}
```

**Response**:
```json
{
  "status": "ok",
  "code": "SUCCESS",
  "message": "Property values status updated"
}
```

#### 4. 类型转换实现（Go 示例）

```go
// 状态映射：TTPOS string → Lineman int
var linemanModifierStatusMap = map[string]int{
    "AVAILABLE":      1, // AVAILABLE
    "UNAVAILABLE":    3, // SUSPENDED
    "SOLD_OUT_TODAY": 2, // SOLD_OUT_TODAY
}

func convertToLinemanStatus(ttposStatus string) (int, error) {
    if status, ok := linemanModifierStatusMap[ttposStatus]; ok {
        return status, nil
    }
    return 0, fmt.Errorf("unsupported status: %s", ttposStatus)
}
```
