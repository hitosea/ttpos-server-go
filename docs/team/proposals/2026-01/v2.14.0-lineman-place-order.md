## 🎯 背景和动机

### 问题描述

LINE MAN 是泰国主流的外卖配送平台之一，目前 ttpos-takeout 模块已完成 LINE MAN 的菜单同步、OAuth 认证等基础功能，但**订单接收功能尚未实现**。

**当前状态**：
- LINE MAN PlaceOrder 接口定义已存在 (`api/lineman/v1/order.go`)
- Controller 层代码已生成但未实现 (`internal/controller/lineman/lineman_v1_place_order.go`)
- 缺少 Logic 层的订单数据转换和处理逻辑
- 缺少与 Main 模块的消息队列集成

**业务影响**：
- LINE MAN 平台的订单无法自动同步到 TTPOS 系统
- 商户需要在多个系统间手动录入订单，效率低下
- 无法支持 LINE MAN 平台的完整业务闭环

### 业务价值

- **完善外卖集成**：实现 LINE MAN 平台的完整订单流程，从菜单同步到订单接收
- **提升运营效率**：订单自动同步，减少人工操作，降低错误率
- **扩大市场覆盖**：支持泰国主流外卖平台，增强产品竞争力
- **复用现有架构**：参考 Grab 订单处理流程，降低开发和维护成本

### 目标用户

- [x] 商户管理员（配置 LINE MAN 集成）

- [x] 厨房人员（接收 LINE MAN 订单出餐）
- [ ] 顾客
- [ ] 其他: LINE MAN 平台（作为订单推送方）

## 💡 解决方案概述

### 方案描述

参考现有的 **Grab 订单处理架构**，实现 LINE MAN 的 PlaceOrder 订单接收功能：

1. **Logic 层实现**：在 `internal/logic/lineman/` 创建订单处理逻辑
2. **数据转换**：将 LINE MAN 订单数据转换为统一的订单数据模型，保存到 `ttpos_takeout_order` 和 `ttpos_takeout_order_item` 表
3. **消息队列通知**：复用现有的 `takeout_grab_order` topic，通知 Main 模块处理订单
4. **Controller 实现**：完成 `lineman_v1_place_order.go` 的业务逻辑调用
5. **错误处理**：参数验证、数据库事务、MQ 发送失败的容错处理

### 核心功能点

1. **订单数据接收**
   - 接收 LINE MAN 的 PlaceOrder Webhook 请求
   - 验证请求参数的完整性和有效性
   - 提取 `partnerId`、`storeId`、`orderId`、`items` 等核心字段

2. **数据模型转换**
   - LINE MAN 订单结构 → TTPOS 统一订单模型
   - 商品明细转换（items → order_items）
   - 价格计算（restaurantRevenue、unitPrice、discount）
   - 订单类型映射（DELIVERY/PICKUP → 外送/自取）

3. **订单数据持久化**
   - 保存订单主表（`ttpos_takeout_order`）
   - 保存订单明细（`ttpos_takeout_order_item`）
   - 保存原始请求数据（`raw_data` 字段，用于问题排查）
   - 事务保证数据一致性

4. **消息队列通知**
   - 复用 `takeout_grab_order` topic（支持多渠道订单）
   - 发送订单事件给 Main 模块
   - MQ 失败不影响主流程（订单已入库）

5. **错误处理和日志**
   - 参数验证失败返回标准错误响应
   - 数据库操作失败触发事务回滚
   - 完整的日志记录便于问题排查

## 📊 初步评估

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [x] **中**：需要前后端联调，基础业务逻辑
- [ ] **高**：涉及架构调整、第三方集成、复杂算法

**说明**：可以完全参考现有的 Grab 订单处理实现（`grab_order.go`），技术方案成熟，风险可控。主要工作是数据结构转换和逻辑复用。

### 工作量预估

[基于 Grab 订单处理实现的复用程度]

- **预计天数**：2-3 天
- **预估 SP**：5（待技术评审确认）

**工作量分解**：
- Logic 层订单处理实现（参考 grab_order）：4h
- 数据转换逻辑（LINE MAN → TTPOS）：3h
- Service 注册和 Controller 实现：2h
- 单元测试（订单转换、入库）：3h
- 集成测试（Webhook + MQ + Main 模块）：4h

### 风险识别

**潜在风险**：
1. LINE MAN 订单数据结构与 Grab 存在差异，可能需要调整数据库 schema
2. 订单金额字段（restaurantRevenue vs subtotal/totalAmount）的映射关系需要明确
3. 商品选项（properties）的结构与 Grab 的 modifiers 不同，需要特殊处理
4. MQ Topic 复用可能导致 Main 模块需要识别订单来源（lineman vs grab）

**缓解措施**：
1. 先对比 LINE MAN 和 Grab 的订单字段，评估是否需要数据库调整
2. 参考 LINE MAN 文档明确金额计算逻辑，与业务方确认
3. 将 properties 序列化为 JSON 存储，参考 Grab modifiers 的处理方式
4. 在 OrderEvent 中增加 `ProviderName` 字段区分订单来源（已支持）

## 📝 附录

### User Story（初稿）

**作为** 商户管理员  
**我想** LINE MAN 平台的订单能够自动同步到 TTPOS 系统  
**以便于** 厨房和收银人员能够及时处理订单，提升运营效率

**作为** LINE MAN 平台  
**我想** 通过 PlaceOrder Webhook 将新订单推送到 TTPOS  
**以便于** 商户能够在 TTPOS 系统中统一管理所有渠道的订单

### AC 验收标准（初稿）

1. **WHEN** LINE MAN 平台发送 PlaceOrder 请求（包含完整的订单数据）**THEN** 系统 **SHALL** 成功保存订单到数据库并返回 HTTP 200
2. **WHEN** 订单保存成功 **THEN** 系统 **SHALL** 发送消息队列事件通知 Main 模块
3. **IF** 请求参数缺失或格式错误 **THEN** 系统 **SHALL** 返回参数错误（HTTP 400）并记录日志
4. **IF** 数据库保存失败 **THEN** 系统 **SHALL** 回滚事务并返回服务器错误（HTTP 500）
5. **WHEN** MQ 发送失败 **THEN** 系统 **SHALL** 记录警告日志但不影响订单保存（订单已入库）
6. **WHEN** 查询订单 **THEN** 系统 **SHALL** 能够区分 LINE MAN 订单和 Grab 订单（通过 provider_name 字段）

### 技术要点

#### 数据转换映射

| LINE MAN 字段 | TTPOS 字段 | 说明 |
|--------------|-----------|------|
| orderId | provider_order_id | LINE MAN 订单 ID |
| orderShortCode | short_order_number | 短订单号（后4位） |
| storeId | provider_merchant_id | 门店 ID |
| restaurantRevenue | total_amount | 商户收入总额 |
| orderAcceptedTime | order_time | 订单接受时间 |
| customerType | order_type | DELIVERY/PICKUP |
| items | order_items | 订单明细（需遍历转换） |
| additionalItems | note | 附加项（序列化为文本） |

#### MQ 事件格式

```go
&grab.OrderEvent{
    Action:       "create",
    ProviderName: "lineman",  // 区分订单来源
    ShopUUID:     storeId,
    OrderUUID:    orderUUID,
    OrderID:      orderId,
    MerchantID:   storeId,
    Status:       "ACCEPTED",
    Timestamp:    time.Now().Unix(),
}
```
