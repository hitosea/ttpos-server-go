## 🎯 背景和动机

### 问题描述

当前 `ReturnPosInvoiceReq` 退票请求存在以下问题：

1. **缺少退票原因追踪**：退票时无法记录附注/备注信息，无法追溯退票原因
2. **外部系统无法感知**：外部 ERP 系统无法及时获知发票取消事件
3. **缺少业务上下文**：即使有消息通知，也缺少必要的业务信息（如订单号、发票名称、退票原因等）

### 业务价值

- **系统集成完整性**：让外部 ERP 系统能及时感知发票取消事件，保持数据同步
- **业务可追溯性**：退票原因有记录，便于审计和问题排查
- **运营效率提升**：减少人工核对和沟通成本，自动化信息传递

### 目标用户

- [x] 外部 ERP 系统（通过 MQ 消息订阅）
- [x] 开发/运维人员（排查问题时查看上下文信息）

## 💡 解决方案概述

### 方案描述

扩展现有 `ReturnPosInvoiceReq` 结构，增加可选的 `remark`（附注）字段。当后端消费逻辑处理完成后，发送 MQ 消息到 `erp-invoice-cancel` topic，消息内容包含退票的关键业务信息。

### 核心功能点

1. `ReturnPosInvoiceReq` 增加可选的 `remark` 字段（附注/备注）
2. 消费逻辑处理完成后，发送 MQ 消息到 `erp-invoice-cancel` topic
3. MQ 消息包含以下字段：
   - `remark`：附注信息
   - `order_no`：订单号
   - `invoice_name`：发票名称

## 📝 附录

### User Story（初稿）

**作为** 外部 ERP 系统
**我想** 订阅发票取消事件并获取附注信息
**以便于** 及时同步发票状态并了解取消原因

### AC 验收标准（初稿）

1. **WHEN** 调用 ReturnPosInvoiceReq 接口并传入 remark 字段 **THEN** 系统 **SHALL** 正确接收并处理该字段
2. **WHEN** 退票消费逻辑处理完成 **THEN** 系统 **SHALL** 发送 MQ 消息到 erp-invoice-cancel topic
3. **WHEN** MQ 消息发送 **THEN** 消息体 **SHALL** 包含 remark、order_no、invoice_name 字段

### MQ 消息格式（草案）

```json
{
  "order_no": "ORD20260129001",
  "invoice_name": "发票名称",
  "remark": "用户请求退票：商品质量问题"
}
```
