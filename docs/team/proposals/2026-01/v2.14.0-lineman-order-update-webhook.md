## 🎯 背景和动机

### 问题描述

LINE MAN 外卖平台在订单创建后，可能会因为以下情况需要更新订单信息：

- **顾客修改订单**：顾客在配送前修改订单内容（增加/减少商品、修改备注等）
- **平台促销调整**：LINE MAN 平台端调整促销折扣，导致订单金额变化
- **商品信息纠正**：发现订单商品信息有误需要修正

当前系统已经实现了订单创建（PlaceOrder）和订单状态更新（OrderStatusUpdate）接口，但 **缺少订单内容更新（OrderUpdate）接口**。

根据 [LINE MAN API 规范](https://docs.google.com/spreadsheets/d/1CKRl7tRLtp6dCAcXQqWhPvS_0M378-vdKpucR6ZtNbg/edit?gid=586287212#gid=586287212)，LINE MAN 会通过 `PUT /v1/partners/{partnerId}/stores/{storeId}/orders` Webhook 通知商户系统订单信息已更新，商户系统需要：

1. **接收更新通知**：接收 LINE MAN 发送的订单更新数据
2. **更新本地订单**：将更新后的订单信息同步到 TTPOS 数据库
3. **触发业务流程**：通过 MQ 事件通知下游系统（Main 模块）处理订单变更

**示例场景**：
> 顾客在 LINE MAN 下单后 5 分钟内修改订单，增加了 2 份饮料。LINE MAN 通过 OrderUpdate Webhook 通知 TTPOS 订单已更新，TTPOS 需要更新订单数据并通知 POS 端重新出单。

### 业务价值

- **订单数据准确性**：确保 TTPOS 系统中的订单信息与 LINE MAN 平台保持一致
- **业务流程完整性**：完善 LINE MAN 订单生命周期管理，支持订单修改场景
- **用户体验提升**：顾客修改订单后，商家能及时收到更新通知，避免备餐错误
- **运营效率提升**：减少因订单信息不一致导致的客诉和退款
- **消息可靠传递**：通过 RocketMQ 确保订单更新事件可靠传递到 Main 模块
- **消息可靠传递**：通过 RocketMQ 确保订单更新事件可靠传递到 Main 模块

## 💡 解决方案概述

### 方案描述

实现 LINE MAN 订单更新 Webhook 接口，参考现有的 Grab 订单处理逻辑：

1. **接收 Webhook 请求**
   - 端点：`PUT /v1/partners/{partnerId}/stores/{storeId}/orders`
   - 验证请求签名（复用 Lineman 认证中间件）
   - 校验请求参数（使用 GoFrame 的验证器）

2. **更新订单数据**
   - 查询现有订单（根据 `orderId` 查找）
   - 更新订单信息：
     - 商品列表（`items`）
     - 商品选项（`properties`）
     - 订单金额（`restaurantRevenue`）
     - 订单更新时间（`orderUpdatedTime`）
     - 附加信息（`additionalItems`）
   - 保存到 `takeout_order` 和相关表

3. **发送 RocketMQ 事件**
   - 构造 `grab.OrderEvent` 消息（复用 Grab 的事件结构）
   - 设置 `action` 为 `"update"`
   - 设置 `providerName` 为 `"lineman"`
   - 发送到 RocketMQ Topic（`takeout_grab_order` 或新建 Lineman Topic）
   - Main 模块监听 RocketMQ 并处理订单更新

4. **返回响应**
   - 成功返回 `200` 和 `{"status": "ok", "code": "SUCCESS"}`
   - 失败返回相应错误码（400/404/500）

参考代码路径：
- Grab 实现：`ttpos-bmp/app/ttpos-takeout/internal/logic/grab/grab_order.go`
- API 定义：`ttpos-bmp/app/ttpos-takeout/api/lineman/v1/order.go` （已定义 `OrderUpdateReq`）

### 核心功能点

1. **分层架构设计**
   - **Controller 层**（`controller/lineman/lineman_v1_order_update.go`）
     - 接收请求，调用 Service 层
     - 参数验证（GoFrame 自动验证 `OrderUpdateReq`）
     - 返回统一格式响应（`LinemanCommonResData`）
   
   - **Service 接口**（`service/lineman_order.go`）
     - 定义 `HandleOrderUpdate` 接口方法
   
   - **Logic 层**（`logic/lineman/lineman_order.go`）
     - 实现 `HandleOrderUpdate` 业务逻辑
     - 查询、更新订单数据
     - 发送 MQ 事件

2. **订单更新逻辑**（Logic 层）
   - 查询现有订单（`dao.Order.Where("provider_order_id = ?").One()`）
   - 幂等性处理（比较 LINE MAN 的 `orderUpdatedTime` 与数据库的 `updated_at`）
   - 更新订单记录（使用事务确保数据一致性）
     - 更新订单主表（金额、时间、`raw_data`、`updated_at`）
     - 删除旧订单明细
     - 插入新订单明细

3. **RocketMQ 事件发送**
   - 复用 `grab.OrderEvent` 结构体
   - Topic：`takeout_grab_order`（复用现有 Topic）
   - Action：`consts.OrderActionUpdate`
   - ProviderName：`consts.ProviderLineman`
   - 使用 `queue.PushWithContext()` 发送消息

4. **错误处理**
   - 订单不存在：Logic 层返回 error → Controller 返回 `fail` + `500`
   - 订单已处理（幂等性）：Logic 层返回 nil（静默跳过）
   - 数据库错误：Logic 层返回 error → Controller 返回 `fail` + `500`

### 风险识别

**潜在风险**：
1. **订单更新冲突**：如果同一订单在短时间内收到多次更新通知，可能导致数据不一致
2. **RocketMQ 消息丢失**：如果 RocketMQ 发送失败，Main 模块可能无法感知订单变更
3. **数据库事务死锁**：如果订单更新和订单状态更新同时发生，可能产生死锁
4. **幂等性实现**：需要正确处理重复的 Webhook 通知（LINE MAN 可能重试）

**缓解措施**：
1. **乐观锁**：使用 `orderUpdatedTime` 字段作为版本号，防止并发更新冲突
2. **RocketMQ 可靠性**：
   - 发送失败只记录日志，不影响主流程（订单已入库）
   - RocketMQ 自带重试机制，确保消息最终送达
3. **事务隔离级别**：使用合适的事务隔离级别（READ COMMITTED）避免死锁
4. **幂等性设计**：比较 LINE MAN 的 `orderUpdatedTime` 与数据库的 `updated_at` 字段，避免旧数据覆盖新数据

## 📝 附录

### User Story（初稿）

**作为** LINE MAN 外卖平台  
**我想** 通过 Webhook 通知 TTPOS 订单信息已更新  
**以便于** TTPOS 系统能够同步最新的订单数据并通知商家

**作为** 商家  
**我想** 在 POS/KDS 端看到顾客修改后的订单内容  
**以便于** 按照最新订单内容备餐，避免出错

### AC 验收标准（初稿）

1. **WHEN** LINE MAN 发送订单更新 Webhook **THEN** TTPOS **SHALL** 接收并验证请求签名
2. **WHEN** 订单存在且更新时间更新 **THEN** TTPOS **SHALL** 更新订单数据并返回 200
3. **WHEN** 订单不存在 **THEN** TTPOS **SHALL** 返回 404 错误
4. **WHEN** 收到重复的更新通知（相同 `orderUpdatedTime`）**THEN** TTPOS **SHALL** 返回 409 或 200（幂等性）
5. **WHEN** 订单更新成功 **THEN** TTPOS **SHALL** 发送 MQ 事件到 Main 模块
6. **IF** MQ 发送失败 **THEN** TTPOS **SHALL** 记录错误日志但仍返回 200（订单已入库）

### 技术实现要点

#### 0. 数据库设计

**无需新增字段**：复用现有的 `updated_at` 字段（int(10) 类型）存储订单最后更新时间。

**幂等性实现方案**：
- 比较 LINE MAN 请求的 `orderUpdatedTime` 与数据库的 `updated_at` 字段
- 如果请求时间 <= 数据库时间，则跳过更新（幂等）
- 更新时同步更新 `updated_at` 字段为当前时间戳

**优势**：
- ✅ 无需数据库迁移
- ✅ 无需修改表结构
- ✅ 使用标准的 `updated_at` 字段，符合 GoFrame 规范
- ✅ 实现简单，性能高（无需解析 JSON）

#### 1. 分层架构（参考 PlaceOrder 实现）

```go
// HandleOrderUpdate 处理 LINE MAN 订单更新 Webhook
func (s *sLinemanOrder) HandleOrderUpdate(ctx context.Context, req *v1.OrderUpdateReq) error {
    // 1. 查询现有订单
    existingOrder, err := dao.Order.Ctx(ctx).
        Where(dao.Order.Columns().ProviderName, ProviderNameLineman).
        Where(dao.Order.Columns().ProviderOrderId, req.OrderId).
        One()
    if err != nil || existingOrder.IsEmpty() {
        return gerror.New("订单不存在")
    }
    
    // 2. 幂等性检查（比较 LINE MAN 的 orderUpdatedTime 与数据库的 updated_at）
    dbUpdatedAt := existingOrder["updated_at"].Int64()
    if dbUpdatedAt > 0 {
        // 解析 LINE MAN 的 orderUpdatedTime
        newUpdatedTime, err := gtime.StrToTime(req.OrderUpdatedTime)
        if err == nil && newUpdatedTime != nil {
            // 如果 LINE MAN 的更新时间 <= 数据库记录时间，则跳过
            if newUpdatedTime.Unix() <= dbUpdatedAt {
                g.Log().Infof(ctx, "订单更新时间未变化，跳过: orderId=%s, db_updated_at=%d, lineman_updated_time=%s",
                    req.OrderId, dbUpdatedAt, req.OrderUpdatedTime)
                return nil
            }
        }
    }
    
    // 3. 更新订单（事务）
    orderUUID := existingOrder["uuid"].String()
    err = s.updateOrder(ctx, orderUUID, req)
    if err != nil {
        return err
    }
    
    // 4. 发送 RocketMQ 事件
    event := &grab.OrderEvent{
        Action:       string(consts.OrderActionUpdate),
        ProviderName: ProviderNameLineman,
        ShopUUID:     req.StoreId,
        OrderUUID:    orderUUID,
        OrderID:      req.OrderId,
        Status:       string(consts.OrderStatusAccepted),
        Timestamp:    gtime.Now().Unix(),
    }
    if err := queue.PushWithContext(ctx, TopicLinemanOrder, event); err != nil {
        // RocketMQ 发送失败只记录日志，不影响主流程（订单已入库）
        g.Log().Warningf(ctx, "发送订单更新 RocketMQ 事件失败 %s: %v", orderUUID, err)
    }
    
    g.Log().Infof(ctx, "成功更新 LINE MAN 订单: %s (UUID: %s)", req.OrderId, orderUUID)
    return nil
}

// updateOrder 更新订单到数据库（事务）
func (s *sLinemanOrder) updateOrder(ctx context.Context, orderUUID string, req *v1.OrderUpdateReq) error {
    return dao.Order.Transaction(ctx, func(ctx context.Context, tx gdb.TX) error {
        // 1. 更新订单主表（包括 raw_data）
        orderTime, _ := gtime.StrToTime(req.OrderAcceptedTime)
        rawDataJSON, _ := gjson.EncodeString(req)
        
        _, err := dao.Order.Ctx(ctx).Where("uuid", orderUUID).Update(&do.Order{
            TotalAmount: req.RestaurantRevenue,
            Subtotal:    req.RestaurantRevenue,
            OrderTime:   orderTime,
            RawData:     rawDataJSON,
            UpdatedAt:   gtime.Now().Unix(),
        })
        if err != nil {
            return gerror.Wrap(err, "更新订单失败")
        }
        
        // 2. 删除旧的订单明细
        _, err = dao.OrderItem.Ctx(ctx).Where("order_uuid", orderUUID).Delete()
        if err != nil {
            return gerror.Wrap(err, "删除旧订单明细失败")
        }
        
        // 3. 插入新的订单明细
        for _, item := range req.Items {
            propertiesJSON, _ := gjson.EncodeString(item.Properties)
            
            _, err := dao.OrderItem.Ctx(ctx).Data(&do.OrderItem{
                OrderUuid:      orderUUID,
                ProviderItemId: item.Id,
                ItemName:       item.Id,
                Quantity:       item.Quantity,
                Price:          item.UnitPrice,
                TotalPrice:     item.UnitPrice * float64(item.Quantity),
                Modifiers:      propertiesJSON,
                Note:           item.Memo,
            }).Insert()
            if err != nil {
                return gerror.Wrap(err, "插入新订单明细失败")
            }
        }
        
        return nil
    })
}
```

#### 2. MQ Topic 选择

**方案 A**：复用 Grab Topic
- Topic：`takeout_grab_order`
- `providerName` 字段区分 `"grab"` 和 `"lineman"`
- **优点**：无需修改 Main 模块的 MQ 监听逻辑
- **缺点**：Topic 名称不够通用

**方案 B**：新建通用 Topic
- Topic：`takeout_order` 或 `takeout_order_event`
- **优点**：更通用，支持未来其他平台（Foodpanda 等）
- **缺点**：需要修改 Main 模块，迁移 Grab 订单监听

**推荐**：方案 A（短期）→ 方案 B（长期重构）
