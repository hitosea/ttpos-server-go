## 🎯 背景和动机

### 问题描述

当前叫号系统显示屏上，订单完成后会一直显示在屏幕上，无法自动消失。这会导致：

- 显示屏上积累大量已完成的订单信息，影响用户查看当前需要处理的订单
- 已完成的订单占用显示空间，降低显示屏的可用性和可读性
- 无法根据业务需求灵活控制订单显示时长

### 业务价值

- **提升用户体验**：显示屏只显示需要关注的订单，信息更清晰
- **提高运营效率**：减少视觉干扰，帮助店员更快定位待处理订单
- **灵活配置**：支持按门店需求设置订单显示时长，满足不同业务场景

## 💡 解决方案概述

### 方案描述

为叫号系统添加订单完成后自动消失功能，使用现有的 `timeout_limit` 配置项。当订单完成后超过设定的时间，自动从叫号系统显示屏上移除该订单的显示内容。设置为 0 时表示订单完成后不自动消失。

**技术实现**：
- 使用现有的 `timeout_limit` 字段（单位：分钟），无需新增字段
- 订单完成时间从 `PreparedQueue` 的 score（Redis Sorted Set 的时间戳）获取
- 在 `/callboard/data` 接口中根据 `timeout_limit` 过滤 `PreparedQueue` 中的订单

### 核心功能点

1. **超时时间配置**：使用现有的 `timeout_limit` 配置项（单位：分钟），0 或 nil 表示不自动消失
2. **自动移除机制**：订单完成后，系统根据 `timeout_limit` 配置，自动从显示屏移除已完成的订单
3. **时间判断逻辑**：订单完成后未超过 `timeout_limit` 分钟，应继续显示在叫号显示屏上；超过 `timeout_limit` 分钟后，自动移除显示

### 风险识别

**潜在风险**：
1. 时间同步问题：不同设备时间可能不一致，导致移除时机不准确
2. 实时性要求：需要确保订单状态变更后能及时更新显示
3. 配置兼容性：现有设备配置需要兼容，`timeout_limit` 为 nil 或 0 时不进行过滤
4. 性能影响：过滤逻辑可能影响接口性能

**缓解措施**：
1. 使用服务器时间（`time.Now().Unix()`）而非客户端时间进行判断
2. 采用 WebSocket 或轮询机制确保状态实时同步
3. 使用现有的 `timeout_limit` 字段，无需数据库迁移，保持向后兼容
4. 在 Service 层高效实现过滤逻辑，考虑在 Redis 查询时直接过滤

## 📝 附录

### User Story（初稿）

**作为** 叫号系统操作人员  
**我想** 配置订单完成后的自动消失时间  
**以便于** 显示屏上只显示需要关注的订单，提高信息可读性和操作效率

### AC 验收标准（初稿）

1. **WHEN** 订单完成时间超过配置的 `timeout_limit`（分钟） **THEN** 系统 **SHALL** 自动从叫号显示屏移除该订单
2. **IF** 配置的 `timeout_limit` 为 0 或 nil **THEN** 系统 **SHALL** 不自动移除已完成的订单
3. **IF** 订单完成后未超过配置的 `timeout_limit` **THEN** 系统 **SHALL** 继续在叫号显示屏上显示该订单
4. **WHEN** 新增设备配置时 **THEN** 系统 **SHALL** 默认 `timeout_limit` 为 nil（不自动消失）
