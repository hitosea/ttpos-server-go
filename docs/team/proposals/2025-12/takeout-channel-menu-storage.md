## 🎯 背景和动机

### 问题描述

目前 TTPOS 系统正在接入 Grab 外卖平台，后续计划接入 Lineman 等其他渠道。不同外卖平台的菜单结构、价格策略、商品映射关系差异较大。目前系统缺乏一个统一且隔离的机制来保存发送给各渠道的特定菜单数据快照。如果直接复用主菜单数据，难以满足各渠道的差异化需求，且难以追溯发送给各渠道的历史菜单状态。

### 业务价值

- **支持多渠道差异化管理**：允许不同外卖渠道（Grab, Lineman 等）拥有独立的菜单配置。
- **兼容未来渠道**：设计通用的存储结构，能够适应 Grab, Lineman 以及未来可能接入的其他渠道的数据格式。
- **数据追溯与调试**：通过保存发送给渠道的菜单数据快照（Text/JSON），便于排查同步失败的问题，特别是当不同渠道的数据结构完全不同时。
- **解耦业务逻辑**：将渠道特定的菜单数据与 TTPOS 核心菜单数据解耦，避免相互影响。

## 💡 解决方案概述

### 方案描述

在数据库中新增通用存储结构，用于保存 TTPOS 商家针对不同外卖渠道的菜单数据。

核心设计：
1.  **统一渠道标识**：使用 `provider_name` (如 `grab`, `lineman`) 作为渠道标识，与现有系统（如 `menu_log`）保持一致。
2.  **通用存储字段**：使用 `text` (或 `longtext`) 类型的 `menu_data` 字段存储完整的菜单 JSON 结构。不预定义具体的 JSON Schema，以适应 Grab 和 Lineman 截然不同的数据结构。
3.  **联合索引**：使用 `shop_uuid` 和 `provider_name` 作为联合唯一索引（或主键），确保每个商户在每个渠道只有一份当前生效的菜单快照。

### 核心功能点

1.  **多渠道菜单存储**：支持按 `shop_uuid` + `provider_name` 维度存储菜单数据。
2.  **Schema-less 设计**：利用 JSON 文本存储，兼容 Grab 的层级结构和 Lineman 的扁平结构（或其他特定结构）。
3.  **读写接口**：提供内部 API 用于保存（覆盖/更新）和读取指定商户指定渠道的菜单数据。

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [x] **中**：需要前后端联调，基础业务逻辑 (主要是后端数据库变更和 DAO 层实现)
- [ ] **高**：涉及架构调整、第三方集成、复杂算法

### 工作量预估

- **预计天数**: 1-2 天
- **预估 SP**: 3（待技术评审确认）

### 风险识别

**潜在风险**：
1.  **数据结构差异大**：Grab 和 Lineman 的菜单结构可能完全不同，导致应用层解析逻辑复杂。
    *   *缓解*：存储层只负责存取 JSON 字符串，具体的解析和业务处理逻辑由各渠道的适配器（Adapter）层处理。
2.  **数据量增长**：菜单 JSON 数据可能较大（尤其是包含图片链接和多语言描述时）。
    *   *缓解*：使用 `LONGTEXT` 类型；如果仅用于快照/调试，可考虑只保留最新版本。
3.  **兼容性维护**：未来新增渠道可能引入新的字段需求。
    *   *缓解*：保持表结构简单（ShopID, Provider, Data），扩展属性也可放入 JSON 中。

## 📝 附录

### User Story（初稿）

**作为** 外卖运营/系统后台
**我想** 保存特定渠道（如 Grab, Lineman）的菜单数据快照
**以便于** 记录同步给外卖平台的菜单状态，并在需要时重新获取或进行调试。

### AC 验收标准（初稿）

1.  **WHEN** 调用保存接口传入 `shop_uuid`, `provider_name` (e.g., "grab", "lineman") 和菜单 JSON **THEN** 系统应成功保存数据，如果已存在则更新。
2.  **WHEN** 调用读取接口传入 `shop_uuid`, `provider_name` **THEN** 系统应返回对应的菜单 JSON 数据。
3.  **IF** 传入不存在的 `shop_uuid` 或 `provider_name` **THEN** 读取接口应返回空或错误提示。
4.  **兼容性验证**：必须能够分别存储 Grab 格式和 Lineman 格式的 JSON 数据，互不干扰且无报错。
