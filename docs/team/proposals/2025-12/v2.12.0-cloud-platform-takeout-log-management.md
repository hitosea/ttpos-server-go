## 🎯 背景和动机

### 问题描述

当前云平台缺少对外卖相关业务（Grab、LINE MAN 等）的日志管理功能，导致：

1. **问题排查困难**：当外卖订单同步出现问题时，无法快速查看同步日志，难以定位失败原因
2. **数据追溯缺失**：无法追溯外卖订单的完整同步历史，包括推送时间、状态变更、失败原因等
3. **运维效率低**：技术支持人员需要登录服务器查看日志文件，效率低下且不便于非技术人员使用
4. **业务监控盲区**：无法直观了解外卖渠道的同步状态和成功率，缺少数据监控和预警机制

从截图可以看到，当前系统已经记录了外卖同步日志（如"从TTPOS推送商品数据到Grab"、"从Grab推送商品数据到TTPOS"等），但这些日志缺少统一的管理界面和查询功能。

### 业务价值

- **提升问题排查效率**：通过可视化日志管理，快速定位外卖同步失败原因，减少 80% 的排查时间
- **增强数据可追溯性**：完整记录外卖订单同步历史，支持业务审计和数据核对
- **降低运维成本**：提供 Web 界面查询日志，无需登录服务器，降低技术支持成本
- **提高业务透明度**：实时监控外卖渠道同步状态，及时发现和处理异常情况
- **优化用户体验**：快速解决外卖订单同步问题，减少商户投诉和用户等待时间

## 💡 解决方案概述

### 方案描述

在云平台（Admin）中新增"日志管理"模块，专门用于管理外卖相关的同步日志。该模块提供以下核心功能：

1. **日志列表展示**：以表格形式展示外卖同步日志，包括类型（TTPOS推送/Grab推送/TTPOS获取）、门店、名称、状态、时间、原因等字段
2. **多维度筛选**：支持按门店、类型、状态进行筛选，快速定位目标日志
3. **状态可视化**：通过进度条和状态标签（成功/失败/进行中）直观展示同步状态
4. **失败原因展示**：对于失败的同步任务，清晰展示失败原因，便于快速定位问题
5. **分页查询**：支持分页加载，避免大量数据影响性能
6. **权限控制**：商户管理员只能查看自己店铺的日志，平台管理员可查看所有日志

### 核心功能点

1. **日志查询接口**：提供 API 接口查询外卖同步日志，支持多维度筛选和分页
2. **日志展示页面**：在云平台前端实现日志管理页面，展示日志列表和详情
3. **筛选和搜索**：支持按门店、类型、状态、时间范围进行筛选
4. **状态可视化**：使用进度条、状态标签等 UI 组件展示同步状态
5. **权限控制**：基于用户角色控制日志查询权限
6. **日志详情**：点击日志条目查看详细信息，包括完整的请求/响应数据（可选）

## 📊 初步评估

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [x] **中**：需要前后端联调，基础业务逻辑
- [ ] **高**：涉及架构调整、第三方集成、复杂算法

**说明**：
- 后端需要设计日志表结构，实现日志查询 API
- 前端需要实现日志管理页面，包括列表展示、筛选、分页等功能
- 需要梳理现有外卖同步逻辑，确保日志记录完整
- 需要考虑日志数据量大的情况，优化查询性能

### 风险识别

**潜在风险**：
1. **日志数据量过大**：随着时间推移，日志数据可能非常庞大，影响查询性能
2. **现有日志不完整**：现有外卖同步逻辑可能没有完整记录日志，需要补充
3. **多租户数据隔离**：需要确保商户只能查看自己的日志，避免数据泄露
4. **外卖平台差异**：不同外卖平台（Grab、LINE MAN）的日志格式可能不同，需要统一处理

**缓解措施**：
1. **日志归档策略**：设计日志归档机制，定期归档历史日志，保留近期数据在主表
2. **索引优化**：在日志表的关键字段（门店ID、类型、状态、时间）上建立索引
3. **权限控制**：在 API 层严格校验用户权限，确保数据隔离
4. **统一日志格式**：设计通用的日志数据结构，适配不同外卖平台

## 📝 附录

### User Story（初稿）

**作为** 商户管理员  
**我想** 在云平台查看我店铺的外卖订单同步日志  
**以便于** 快速了解外卖订单同步状态，及时发现和解决同步问题

**作为** 平台运维人员  
**我想** 查看所有店铺的外卖同步日志，并按门店、类型、状态进行筛选  
**以便于** 监控外卖渠道的整体运行状况，快速定位和解决问题

**作为** 技术支持人员  
**我想** 查看外卖同步失败的详细原因  
**以便于** 快速排查问题并给出解决方案

### AC 验收标准（初稿）

基于 DooTask 任务中的 AC 模板，具体验收标准如下：

**AC1：核心功能验证**
- **Given** 用户已登录云平台且有日志查询权限
- **When** 用户访问"日志管理"页面
- **Then** 系统应展示外卖同步日志列表，包括类型、门店、名称、状态、时间、原因等字段
- **And** 日志列表应按时间倒序排列（最新的在前）

**AC2：筛选功能验证**
- **Given** 用户在日志管理页面
- **When** 用户选择门店、类型、状态等筛选条件并点击"查询"
- **Then** 系统应只展示符合筛选条件的日志
- **And** 筛选条件应支持多选和组合

**AC3：权限控制验证**
- **Given** 用户是商户管理员（非平台管理员）
- **When** 用户访问日志管理页面
- **Then** 系统应只展示该用户所属店铺的日志
- **And** 不应展示其他店铺的日志

**AC4：状态可视化验证**
- **Given** 日志列表中存在不同状态的日志（成功、失败、进行中）
- **When** 用户查看日志列表
- **Then** 系统应通过不同颜色或图标清晰展示各日志的状态
- **And** 对于失败的日志，应在"原因"列展示失败原因

**AC5：分页功能验证**
- **Given** 日志总数超过单页显示数量（如 20 条）
- **When** 用户查看日志列表
- **Then** 系统应展示分页控件，支持翻页查看
- **And** 分页控件应显示当前页码和总页数

**AC6：边界场景处理**
- **Given** 用户筛选的条件没有匹配的日志
- **When** 用户点击"查询"
- **Then** 系统应展示"暂无数据"提示
- **And** 不应报错或显示异常

**AC7：性能验证**
- **Given** 日志表中存在大量数据（如 10 万条）
- **When** 用户进行日志查询
- **Then** 系统应在 3 秒内返回查询结果
- **And** 不应因数据量大而导致超时或崩溃

### 线框图/原型（可选）

根据截图，当前已有的日志展示包括以下字段：
- **类型**：TTPOS推送、Grab推送、TTPOS获取
- **门店**：门店1、门店2、门店3
- **名称**：具体的同步操作描述
- **状态**：成功、失败、进行中（用进度条表示）
- **时间**：同步时间
- **原因**：失败原因（如"这是原因"）

建议的 UI 改进：
1. 在顶部增加筛选区域（门店下拉框、类型下拉框、状态下拉框、查询按钮）
2. 表格增加分页控件
3. 状态列使用更明显的颜色区分（绿色=成功，红色=失败，黄色=进行中）
4. 失败原因支持展开查看详细信息
5. 增加"刷新"按钮，支持手动刷新日志列表
