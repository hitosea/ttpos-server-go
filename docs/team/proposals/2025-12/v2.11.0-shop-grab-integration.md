## 🎯 背景和动机

### 问题描述

当前 TTPOS 系统仅支持店内点餐和简单的外卖功能，缺乏与主流外卖平台（如 Grab）的集成能力。商户需要在多个系统之间切换管理商品、订单，导致：

1. 商品数据需要在多个平台重复维护，效率低下且容易出错
2. 外卖订单无法统一管理，需要人工在不同平台间切换处理
3. 分类和商品信息不同步，导致客户端展示不一致
4. 总部无法统一管理分店的外卖商品和分类

### 业务价值

- **提升运营效率**：商品数据统一维护，一次配置多平台同步
- **降低人工成本**：自动同步订单，减少人工录入和切换操作
- **增强管控能力**：总部可统一下发外卖商品和分类配置到分店
- **提高数据准确性**：避免多平台数据不一致导致的客诉问题
- **扩大营收渠道**：接入 Grab 等主流外卖平台，增加订单来源

### 目标用户

- [x] 商户管理员（配置外卖 API、管理外卖商品）
- [x] 总部运营人员（统一下发外卖商品和分类）
- [x] 分店运营人员（管理本店外卖商品价格和上下架）

## 💡 解决方案概述

### 方案描述

在新管理端（Go Main 模块）中增加 Grab 外卖模块，实现与 Grab 平台的完整集成。功能包括：

1. **外卖 API 配置**：商户可在管理端配置 Grab API 密钥，完成平台对接
2. **商品数据导入**：从 Grab 平台导入商品数据到 TTPOS 系统
3. **分类增强管理**：支持分类在"店内"或"Grab 外卖"渠道的显示控制，分类变更自动同步到 Grab
4. **商品增强管理**：商品配置 Grab 外卖专属信息（价格、库存、上下架状态等），商品变更自动同步到 Grab
5. **总部分店权限**：总部可下发商品和分类到分店，分店对总部来源的商品有价格和上下架权限
6. **订单同步显示**：Grab 订单自动同步到 TTPOS 系统，POS 端可直接处理

### 核心功能点

1. **外卖 API 对接配置页面**：配置 Grab API 密钥、商户信息，测试连接状态
2. **商品数据导入功能**：从 Grab 拉取商品列表并导入到 TTPOS
3. **分类增强管理**：
   - 新增"显示渠道"字段（店内、Grab 外卖）
   - 总部来源的分类被分店选择外卖显示时，需勾选外卖显示
   - 分类变更后自动同步到 Grab 平台
4. **商品增强管理**：
   - 新增 Grab 外卖专属字段（外卖价格、外卖库存、外卖上下架状态等）
   - 外卖商品字段默认继承店内商品，但默认下架
   - 总部可下发外卖商品到分店
   - 分店对总部来源的商品有价格和上下架权限（同步时不受总店影响）
   - 分店自行创建的商品拥有所有外卖更改权限
   - 商品变更后自动同步到 Grab 平台
5. **订单同步功能**：
   - Grab 订单自动同步到 TTPOS
   - POS 端显示外卖订单并支持接单操作
6. **删除保护**：外卖订单未完成时，不允许删除关联的商品或规格

## 📊 初步评估

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [ ] **中**：需要前后端联调，基础业务逻辑
- [x] **高**：涉及架构调整、第三方集成、复杂算法

**复杂度说明**：
- 需要对接 Grab 第三方 API，涉及认证、数据同步、错误处理
- 涉及商品、分类、订单等核心数据模型的扩展
- 需要实现总部分店权限控制逻辑
- 需要实现双向数据同步（TTPOS → Grab、Grab → TTPOS）
- 需要处理数据冲突和同步失败的补偿机制

### 工作量预估

- **预计天数**: 15-20 天
- **预估 SP**: 13-21（待技术评审确认）

**工作量分解**（粗略）：
- Grab API 对接与封装：3-5 天
- 分类增强功能：2-3 天
- 商品增强功能：4-6 天
- 订单同步功能：3-4 天
- 总部分店权限控制：2-3 天
- 测试与联调：3-4 天

### 风险识别

**潜在风险**：
1. **Grab API 稳定性风险**：Grab API 可能存在限流、超时、数据格式变更等问题
2. **数据同步冲突风险**：TTPOS 和 Grab 两边同时修改商品数据可能导致冲突
3. **性能风险**：大量商品同步可能导致接口超时或数据库压力
4. **总部分店权限逻辑复杂**：需要精细控制不同来源商品的权限，逻辑复杂易出错
5. **数据迁移风险**：现有商户如已有 Grab 商品，需要提供数据迁移方案
6. **外卖订单未完成时的删除保护**：需要在多个删除入口（商品、规格）增加检查逻辑

**缓解措施**：
1. **Grab API 风险**：
   - 实现 API 调用重试机制和降级策略
   - 记录详细的 API 调用日志便于排查
   - 提供手动重新同步功能
2. **数据同步冲突**：
   - 明确 TTPOS 为主数据源，Grab 为从数据源
   - 实现冲突检测和提示机制
   - 提供同步历史记录和回滚功能
3. **性能风险**：
   - 商品同步采用异步批量处理
   - 增加同步进度提示
   - 对大商户提供分批同步功能
4. **权限逻辑复杂**：
   - 详细梳理权限矩阵和流程图
   - 编写完整的单元测试覆盖各种权限场景
   - 进行充分的 UAT 测试
5. **数据迁移**：
   - 提供数据导入工具
   - 编写迁移文档和操作手册
   - 对试点商户进行人工协助迁移
6. **删除保护**：
   - 在删除前查询是否存在未完成的外卖订单
   - 提供明确的错误提示："商品或规格处于未完结订单中，暂时无法删除"

## 📝 附录

### User Story（初稿）

**作为** 商户管理员  
**我想** 在管理后台配置 Grab 外卖 API 并管理外卖商品和分类  
**以便于** 实现商品数据统一维护，订单统一处理，提升运营效率

**作为** 总部运营人员  
**我想** 统一下发外卖商品和分类配置到分店  
**以便于** 保证品牌统一性和运营标准化

**作为** 分店运营人员  
**我想** 对总部下发的商品进行价格调整和上下架控制  
**以便于** 根据本店实际情况灵活运营

**作为** 收银员  
**我想** 在 POS 端看到 Grab 外卖订单并进行接单处理  
**以便于** 统一处理所有订单，提高工作效率

### AC 验收标准（初稿）

**AC1: 外卖 API 配置**
- WHEN 商户首次进入外卖管理模块 THEN 系统 SHALL 显示 API 配置页面
- WHEN 商户填写 API 密钥并点击测试连接 THEN 系统 SHALL 验证连接并显示结果
- WHEN API 连接成功后 THEN 系统 SHALL 显示商品数据导入页面

**AC2: 分类增强管理**
- WHEN 商户编辑分类时 THEN 系统 SHALL 提供"显示渠道"选项（店内/Grab 外卖）
- WHEN 分类被设置为 Grab 外卖显示 THEN 系统 SHALL 自动同步到 Grab 平台
- WHEN 分店选择总部来源的分类用于外卖 THEN 系统 SHALL 要求勾选外卖显示

**AC3: 商品增强管理**
- WHEN 商户编辑商品时 THEN 系统 SHALL 提供 Grab 外卖专属字段配置
- WHEN 商品被设置为外卖商品 THEN 系统 SHALL 默认继承店内字段但默认下架
- WHEN 总部下发外卖商品到分店 THEN 分店 SHALL 拥有价格和上下架权限
- WHEN 分店自行创建外卖商品 THEN 分店 SHALL 拥有所有字段的编辑权限
- WHEN 商品信息变更后 THEN 系统 SHALL 自动同步到 Grab 平台

**AC4: 订单同步与处理**
- WHEN Grab 平台有新订单 THEN 系统 SHALL 自动同步到 TTPOS
- WHEN POS 端打开订单列表 THEN 系统 SHALL 显示外卖订单并标识来源
- WHEN 收银员点击接单 THEN 系统 SHALL 更新订单状态并通知 Grab 平台

**AC5: 删除保护**
- WHEN 商品或规格存在未完成的外卖订单 THEN 系统 SHALL 阻止删除操作
- WHEN 删除被阻止时 THEN 系统 SHALL 提示"商品或规格处于未完结订单中，暂时无法删除"
