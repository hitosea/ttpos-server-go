 ## 🎯 背景和动机

 ### 问题描述

 Main 模块需要从外卖聚合侧获取渠道菜单数据，但当前缺少统一的 gRPC 接口，主服务只能通过重复封装 HTTP 或直接访问内部逻辑，存在接口不可复用、错误处理不一致和数据格式漂移风险。需要一个稳定的 gRPC 服务对外暴露，以便主模块按渠道获取菜单原始 JSON。

 ### 业务价值

 - 为主模块提供标准化的渠道菜单获取能力，减少重复开发
 - 确保菜单数据与聚合服务保持一致，降低解析和格式偏差风险
 - 通过 gRPC 统一链路，便于后续治理（限流、熔断、监控）

 ## 💡 解决方案概述

 ### 方案描述

 在 ttpos-takeout 的 gRPC 服务中新增 `GetChannelMenu`，接受 `shop_uuid` 与 `provider_name`，直接调用现有 `service.ChannelMenu().GetChannelMenu` 获取渠道菜单，并将返回的 `rawData` 以 JSON 字符串透传给主模块，不做解析或结构变换，仅补充必要的请求/响应封装与错误码映射。

 ### 核心功能点

 1. 定义 gRPC 接口及 proto：请求包含 `shop_uuid`、`provider_name`，响应包含 `raw_data`（string）和基础状态码/消息
 2. 实现 gRPC Handler：调用 `service.ChannelMenu().GetChannelMenu`，透传渠道返回的菜单 JSON
 3. 增加链路治理：调用超时控制、错误码统一映射、基础日志与指标上报

 ## 📊 初步评估

 ### 技术复杂度

 - [ ] **低**：纯 UI 调整，无业务逻辑变更
 - [x] **中**：需要前后端联调，基础业务逻辑
 - [ ] **高**：涉及架构调整、第三方集成、复杂算法

 ### 工作量预估

 - **预计天数**: 1 天
 - **预估 SP**: 2（待技术评审确认）

 ### 风险识别

 **潜在风险**：
 1. `provider_name` 传值不合法或未被聚合服务支持导致调用失败
 2. 渠道返回的菜单 JSON 体积较大，可能造成 gRPC 响应体过大或超时
 3. 渠道侧偶发错误需要透传，缺少标准化错误码映射

 **缓解措施**：
 1. 在 Handler 中校验 `provider_name` 白名单并返回明确错误码
 2. 设置合理超时与响应大小上限，必要时增加压缩或分页
 3. 补充错误码映射表与观测日志，便于快速定位渠道异常
