## 🎯 背景和动机

### 问题描述

当前 Grab 提交订单的 API 结构存在以下问题：

1. `SubmitOrderReq` 结构体为空，仅包含 Meta 信息，实际的请求数据在 Logic 层直接使用 SDK 的 `grabfood.SubmitOrderRequest` 进行解析
2. API 层和 Logic 层之间的数据流不够清晰，缺少类型化的请求结构体
3. `shopUuid` 的获取逻辑不够优先级化，应该优先从 `SubmitOrderRequest.partnerMerchantID` 获取，而不是依赖配置查询

**示例**：
> 当前实现中，API 层只是定义了一个空的请求结构体，实际的业务逻辑在解析原始 JSON 后直接使用 SDK 类型，导致代码结构不够清晰，类型安全也较差。

### 业务价值

- 提升代码类型安全性，避免运行时类型错误
- 改善 API 层和 Logic 层的职责分离
- 优化 `shopUuid` 获取逻辑，提升配置查询的优先级
- 便于后续维护和扩展 Grab 集成功能

## 💡 解决方案概述

### 方案描述

修改 `SubmitOrderReq` 结构体，使其继承 `*grabfood.SubmitOrderRequest`，并调整 Logic 层的实现逻辑。具体包括：

1. 将 `SubmitOrderReq` 结构体修改为嵌入 `*grabfood.SubmitOrderRequest`
2. 调整 Logic 层，直接使用 API 层的类型化请求对象
3. 优化 `shopUuid` 获取逻辑，优先从 `partnerMerchantID` 字段获取

**示例**：
> API 层定义完整的请求结构体，Logic 层直接使用类型化的请求对象，无需重复解析，提升代码可维护性和类型安全。

### 核心功能点

1. 修改 `SubmitOrderReq` 结构体，嵌入 `*grabfood.SubmitOrderRequest`
2. 调整 Logic 层 `HandleSubmitOrder` 方法，直接使用 API 层传入的类型化对象
3. 优化 `shopUuid` 获取逻辑，优先从请求对象的 `partnerMerchantID` 字段获取
4. 保持向后兼容性，确保现有功能不受影响
