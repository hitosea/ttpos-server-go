## 🎯 背景和动机

### 问题描述

- ERPNext 与 TTPOS 支付方式需要双向同步，但目前缺少标准化的保存接口，命名规则、渠道与支付方式映射不统一，易出现重复或不可读的名称。
- 旧有支付方式数据沿用手工创建，未形成“渠道 + 支付方式 + 序号 + 商户简称”的规范，影响跨系统核对与扩展。

### 业务价值

- 建立统一命名规则，便于 ERP/TTPOS 双向同步与排查。
- 支撑 LianLianPay 等渠道支付方式落地，减少人工维护成本。
- 为后续支付方式扩展（自定义/系统默认）提供稳态编号策略，避免冲突。

## 💡 解决方案概述

### 方案描述

在 `selling.proto` 新增 `SaveModeOfPayment` RPC，接受 `company_abbr`、`branch`、`channel`、`pay_type`，服务端按规则生成支付方式名称：`{channel}-{pay_type}-{4位递增序号} - {company_abbr}`。序号默认从 0000（系统/同步默认）或 0001（自建扩展）起按组合递增，确保同名可区分且跨系统一致。保存后同步回 ERP/TTPOS，对接现有支付方式状态字段。

### 核心功能点

1. `SaveModeOfPayment` 接口：入参 `company_abbr`、`branch`、`channel`、`pay_type`，返回落库的支付方式标识与规范化名称。
2. 命名规则执行：`channel + '-' + pay_type + '-' + 4位序号 + ' - ' + company_abbr`，序号按渠道+支付方式维度递增，预留 0000 给系统/默认，同名自建从 0001 递增。
3. 双向同步钩子：TTPOS 新增/更新后写 ERP；ERP 变更回流 TTPOS，保留旧数据不强制重算名称。
4. 状态与类型映射：`pay_type` 与 TTpos/ERP 状态字段一致，`channel` 为ttpos传入的渠道类型，如`LianlianPay`，其余默认为通用。

### 工作量预估

- **预计天数**: 3 天（接口+序号策略+双向同步联调）
- **预估 SP**: 3（待技术评审确认）

### 风险识别

**潜在风险**：
1. 旧数据命名不符合规则，可能与新规则冲突。
2. 序号生成并发下重复或越权覆盖。
3. ERP/TTPOS 状态或支付类型映射差异导致同步失败。

**缓解措施**：
1. 对存量名称只读，不回填；新建时检测冲突并追加序号。
2. 序号生成加唯一索引/分布式锁，失败时重试并返回明确错误。
3. 建立映射表和校验器，异常时打审计日志并告警。

## 📝 附录

### User Story（初稿）

作为 ERP/TTPOS 集成维护者  
我想 为各渠道支付方式生成统一可读的编号与名称并双向同步  
以便于 消除重名/冲突，确保 ERP 与 TTPOS 支付方式对齐。

### AC 验收标准（初稿）

1. **WHEN** 传入 `channel=LianLianPay, pay_type=Alipay, company_abbr=No.21` **THEN** 系统 **SHALL** 返回名称 `LianLianPay-Alipay-0000 - No.21`（默认序号），并落库/同步成功。
2. **IF** 同一组合再次新增自定义支付方式 **THEN** 系统 **SHALL** 使用序号从 `0001` 起递增，避免与 `0000` 系统默认冲突。
3. **WHEN** TTPOS 添加/更新支付方式 **THEN** **SHALL** 同步至 ERP；ERP 更新 **THEN** **SHALL** 同步至 TTPOS，失败记录审计日志。
4. **IF** 输入缺失 `company_abbr` 或 `pay_type` **THEN** **SHALL** 返回校验错误，不写入。
