## 🎯 背景和动机

### 问题描述

当前支付方式创建时，所有支付方式的序号都是自动递增的（0001, 0002, 0003...），无法区分是由系统自动创建的默认支付方式，还是由用户手动创建的自定义支付方式。

在系统初始化或迁移场景中，需要为每个公司创建一套标准的默认支付方式（如 Cash、Balance、Free Meal 等），这些系统级支付方式应该使用固定的序号（000），以便：
1. 在 ERP 系统中快速识别系统默认支付方式
2. 避免与用户自定义支付方式的序号冲突
3. 保持多公司间系统支付方式命名的一致性

### 业务价值

- **提升系统可维护性**：通过固定序号 000 标识系统默认支付方式，便于运维和故障排查
- **规范数据管理**：区分系统数据和用户数据，避免误删或误操作系统关键配置
- **支持多公司部署**：确保不同公司的系统默认支付方式命名一致，降低集成复杂度
- **简化数据迁移**：在系统升级或数据迁移时，可以快速识别和处理系统级支付方式

## 💡 解决方案概述

### 方案描述

在 `SaveModeOfPaymentReq` 消息中新增一个可选字段 `added_by`（类型：`optional string`），用于标识支付方式的创建来源：
- 当 `added_by = "sys"` 时，表示这是系统自动创建的默认支付方式，序号固定为 `0000`
- 当 `added_by` 为空或其他值时，保持现有逻辑，序号自动递增（0001, 0002, 0003...）

在 `createModeOfPayment` 方法中，根据 `added_by` 字段的值决定序号生成策略：
- 如果 `added_by == "sys"`，跳过 `nextModeOfPaymentSeq` 调用，直接使用序号 `0000`
- 否则，调用 `nextModeOfPaymentSeq` 获取下一个可用序号

### 核心功能点

1. **Protobuf 定义扩展**：在 `SaveModeOfPaymentReq` 中新增 `optional string added_by = 8` 字段
2. **序号生成逻辑调整**：在 `createModeOfPayment` 中增加条件判断，根据 `added_by` 值决定序号
3. **向后兼容**：未传入 `added_by` 时，保持现有行为不变（自动递增序号）
4. **日志记录**：在创建系统支付方式时，记录审计日志，便于追踪

### 风险识别

**潜在风险**：
1. **序号冲突**：如果已存在序号为 000 的支付方式（用户手动创建），可能导致创建失败
2. **向后兼容**：旧版本客户端不传 `added_by` 字段，需确保不影响现有功能

**缓解措施**：
1. 在创建前检查序号 000 是否已被占用，如果已存在则返回错误或使用其他策略
2. 将 `added_by` 设计为 `optional` 字段，未传入时保持现有逻辑不变

## 📝 附录

### User Story（初稿）

**作为** 系统管理员  
**我想** 在创建支付方式时标识其来源（系统自动创建 vs 用户手动创建）  
**以便于** 快速识别系统默认支付方式，避免误操作，简化数据迁移和故障排查

### AC 验收标准（初稿）

1. **WHEN** 调用 `SaveModeOfPayment` 且 `added_by = "sys"` **THEN** 系统 **SHALL** 创建序号为 000 的支付方式
2. **WHEN** 调用 `SaveModeOfPayment` 且 `added_by` 为空或其他值 **THEN** 系统 **SHALL** 使用自动递增序号（0001, 0002...）
3. **IF** 序号 000 已被占用 **THEN** 系统 **SHALL** 返回错误信息，提示序号冲突
4. **WHEN** 创建系统支付方式成功 **THEN** 系统 **SHALL** 记录审计日志，包含 `added_by` 字段值

### 技术实现要点

#### 1. Protobuf 定义修改

```protobuf
// SaveModeOfPaymentReq 保存/同步支付方式请求
message SaveModeOfPaymentReq {
  string company_abbr = 1;
  string branch = 2;
  string channel = 3;
  string pay_type = 4;
  optional bool enabled = 5;
  optional string name = 6;
  string payment_id = 7;
  optional string added_by = 8; // 新增：创建来源标识，"sys" 表示系统创建
}
```

#### 2. 业务逻辑调整

在 `createModeOfPayment` 方法中：

```go
// 判断是否为系统创建
var nextSeq int
var err error

if req.AddedBy != nil && strings.TrimSpace(*req.AddedBy) == "sys" {
    // 系统创建：固定使用序号 0000
    nextSeq = 0
    g.Log().Infof(ctx, "[createModeOfPayment] 系统创建支付方式，使用固定序号 0000")
} else {
    // 用户创建：自动递增序号
    nextSeq, err = s.nextModeOfPaymentSeq(ctx, prefix, companyName)
    if err != nil {
        return nil, err
    }
}

name := fmt.Sprintf("%s%04d - %s", prefix, nextSeq, req.CompanyAbbr)
```

#### 3. 冲突检测（可选增强）

在创建前检查序号 0000 是否已存在：

```go
if nextSeq == 0 {
    // 检查序号 0000 是否已被占用
    existingName := fmt.Sprintf("%s0000 - %s", prefix, req.CompanyAbbr)
    count, err := service.Doctype().Count(ctx, &erp.ErpReq{
        DocType: erp.DocTypeModeOfPayment,
    }, &erp.RequestParams{
        Filters: [][]string{{"name", "=", existingName}},
    })
    if err != nil {
        return nil, gerror.Wrapf(err, "检查支付方式序号冲突失败")
    }
    if count > 0 {
        return nil, gerror.Newf("系统支付方式序号 0000 已被占用: %s", existingName)
    }
}
```
