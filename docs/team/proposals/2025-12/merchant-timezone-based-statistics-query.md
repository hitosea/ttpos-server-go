## 🎯 背景和动机

### 问题描述

当前统计报表等各类数据查询时，可能存在使用设备时区而非商户时区的情况，导致跨时区商户的数据查询不准确。

**具体场景**：
- 商户设置时区为泰国（UTC+7），管理员在北京时区（UTC+8）12点查询"今日0-12点"的数据
- 期望：查询到的是泰国时区的0-12点数据（对应北京时间1-13点）
- 现状：可能查询到的是北京时区的0-12点数据（对应泰国时区23点-11点），导致数据不准确

**业务影响**：
- 跨时区商户（如日本、泰国、土耳其等）的统计数据不准确
- 商户无法正确查看自己的营业数据
- 影响商户对经营状况的判断和决策

### 业务价值

- ✅ **数据准确性**：确保商户查看的是基于自己时区的真实营业数据
- ✅ **用户体验**：无论管理员在哪个时区，都能正确查看商户数据
- ✅ **业务合规**：符合跨时区业务场景的实际需求
- ✅ **减少误解**：避免因时区问题导致的业务决策错误

## 💡 解决方案概述

### 方案描述

**核心原则**：所有统计报表、数据查询、导出功能，统一使用商户设置的时区进行计算和查询，而非设备/浏览器时区。

**实现方式**：
1. 后端 API 统一使用商户时区（从 `company_setting.timezone` 或 `store_setting.time_zone` 获取）
2. 前端传递的时间参数（如"今日"、"本周"等）在后端转换为商户时区的时间范围
3. 所有时间相关的查询、统计、导出都基于商户时区
4. 前端显示时，可显示商户时区的时间，或同时显示本地时区时间作为参考

**示例**：
- 商户设置时区：`Asia/Bangkok` (UTC+7)
- 管理员在北京时区（UTC+8）12:00 查询"今日"数据
- 后端计算：商户时区的"今日" = 泰国时区 00:00:00 - 23:59:59（对应北京时间 01:00:00 - 00:59:59）
- 查询结果：返回商户时区今日的营业数据

### 核心功能点

1. **统一时区获取机制**
   - 所有统计查询接口统一从商户设置获取时区
   - 确保时区信息传递到 Repository 层

2. **时间范围转换**
   - 将前端传递的"今日"、"本周"、"本月"等时间类型转换为商户时区的具体时间戳范围
   - 使用 `utils.SetTimezone(timezone)` 工具类进行时区转换

3. **SQL 查询时区处理**
   - 修复使用 `FROM_UNIXTIME` 的查询，统一使用商户时区
   - 参考已有 Bug 修复方案：`bug-251226-001-statistics-from-unixtime-timezone-statistics-error`

4. **数据导出时区处理**
   - 导出功能同样使用商户时区
   - 导出文件名、数据内容都基于商户时区

5. **前端时区显示**
   - 前端可显示商户时区信息
   - 时间显示可同时显示商户时区和本地时区（可选）

## 📊 初步评估

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [x] **中**：需要前后端联调，基础业务逻辑
- [ ] **高**：涉及架构调整、第三方集成、复杂算法

**说明**：
- 已有部分代码使用商户时区（如 `BusinessDataCountReq.GetParam`）
- 需要统一检查所有统计查询接口
- 需要修复 SQL 查询中的时区问题
- 前端需要适配时区显示

### 工作量预估

[粗略估算，具体 SP 在技术方案评审时确定]

- **预计天数**: 5-7 天
- **预估 SP**: 8-13 SP（待技术评审确认）

**工作量分解**：
- 后端 API 统一时区处理：2-3 天
- SQL 查询时区修复：2-3 天
- 前端时区显示适配：1-2 天
- 测试验证：1 天

### 风险识别

**潜在风险**：
1. **历史数据兼容性**：已存储的数据可能基于不同时区，需要确认是否需要迁移
2. **SQL 查询性能**：时区转换可能影响查询性能，需要优化
3. **前端时区显示**：用户可能混淆商户时区和本地时区
4. **测试覆盖**：跨时区场景测试复杂，需要充分测试

**缓解措施**：
1. **数据兼容性**：确认历史数据存储方式，如使用 UTC 时间戳则无需迁移
2. **性能优化**：使用 MySQL `CONVERT_TZ` 函数或应用层优化，参考已有 Bug 修复方案
3. **用户教育**：前端明确显示商户时区信息，提供时区说明
4. **测试策略**：创建多时区测试用例，覆盖主要时区场景（UTC+7, UTC+8, UTC+9 等）

## 📝 附录

### User Story（初稿）

**作为** 商户管理员  
**我想** 在查看统计报表时，系统使用我设置的商户时区来计算时间范围  
**以便于** 无论我在哪个时区，都能准确查看基于商户时区的营业数据

### AC 验收标准（初稿）

1. **WHEN** 商户设置时区为 `Asia/Bangkok` (UTC+7) **AND** 管理员在北京时区 (UTC+8) 12:00 查询"今日"数据 **THEN** 系统 **SHALL** 返回商户时区今日（00:00:00 - 23:59:59）的营业数据

2. **WHEN** 商户设置时区为 `Asia/Shanghai` (UTC+8) **AND** 管理员在泰国时区 (UTC+7) 查询"今日"数据 **THEN** 系统 **SHALL** 返回商户时区今日的营业数据

3. **WHEN** 导出统计报表 **THEN** 导出的数据 **SHALL** 基于商户时区的时间范围

4. **WHEN** 查询"本周"、"本月"等时间范围 **THEN** 系统 **SHALL** 使用商户时区计算时间范围

5. **WHEN** 前端显示时间信息 **THEN** 系统 **SHALL** 明确标识使用的时区（商户时区）

### 技术实现要点

1. **后端统一时区获取**
   ```go
   // 从商户设置获取时区
   timezone := ctx.GetCompanySetting().Timezone
   // 或从 store_setting 获取
   // timezone := storeSetting.TimeZone
   ```

2. **时间范围转换**
   ```go
   // 使用工具类转换时间范围
   queryStartTime, queryEndTime := utils.SetTimezone(timezone).TodayStartEndUnix()
   ```

3. **SQL 查询时区处理**
   - 参考 `bug-251226-001` 修复方案
   - 使用 `CONVERT_TZ` 或应用层转换
