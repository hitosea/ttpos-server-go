## 🎯 背景和动机

### 问题描述

TTPOS 系统在餐饮高峰期面临极高的并发压力，主要体现在：
1. **数据库压力大**：频繁的商品详情查询、报表统计查询直接冲击 MySQL。
2. **外部集成限流**：ERP 同步、支付接口等外部调用在并发下容易触发频率限制或重复下单风险。
3. **缓存击穿/雪崩**：核心缓存失效时，大量并发请求穿透至数据库，可能导致系统崩溃。
4. **重复计算**：复杂的促销活动、会员权益计算在同一时间内对同一用户多次执行，浪费服务器 CPU。

### 业务价值

- **降低响应延迟**：核心接口响应时间预计降低 50% 以上。
- **保护核心资源**：大幅减少 MySQL 和第三方 API 的无效负载。
- **提升稳定性**：通过请求合并（Singleflight）彻底消除热点 Key 失效带来的缓存击穿风险。
- **降本增效**：减少对高性能数据库实例的依赖，提升单机并发处理能力。

## 💡 解决方案概述

### 方案描述

设计一套集成 **Singleflight (请求合并)** 与 **Layered Cache (多级缓存)** 的统一框架。该框架将作为 Go Main 项目的基础 pkg，封装通用的“查询-缓存-合并”逻辑。
核心思路是：当缓存失效时，利用 Singleflight 确保只有一个协程去执行真实的业务逻辑（查库或调接口），其他并发请求阻塞等待该结果，从而实现“一次执行，多次共享”。

### 核心功能点

1. **Singleflight 请求合并引擎**：集成 `servantgo` 或官方 `x/sync/singleflight`，提供泛型接口 `Run[T Task](t T) T`。
2. **多级缓存策略**：支持 L1 (内存级，如 BigCache) + L2 (分布式，如 Redis) 的透明切换。
3. **Read-Through 自动加载**：封装“先查缓存，不中则 Singleflight 加载，再存缓存”的完整闭环。
4. **防并发穿透保护**：针对高频空查询结果进行缓存，防止针对不存在 Key 的攻击。

## 📊 初步评估

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [ ] **中**：需要前后端联调，基础业务逻辑
- [x] **高**：涉及架构调整、第三方集成、复杂算法

### 工作量预估

- **预计天数**: 7 天
- **预估 SP**: 13（涉及并发安全和核心包重构）

### 风险识别

**潜在风险**：
1. **Singleflight 导致协程堆积**：如果后端业务（如 ERP 接口）响应极慢，所有等待该结果的协程都会阻塞，可能耗尽连接池。
2. **数据一致性**：多级缓存下，Local Cache 与 Redis 之间的数据同步可能存在微小延迟。

**缓解措施**：
1. **超时与降级**：为 Singleflight 任务增加 Context 超时控制，超时后快速失败或返回旧数据。
2. **发布订阅模式**：利用 Redis Pub/Sub 机制，在数据变更时主动失效所有节点的 Local Cache。

## 📝 附录

### User Story（初稿）

**作为** 后端开发人员  
**我想** 使用统一的缓存框架  
**以便于** 在不增加代码复杂度的前提下，轻松处理高并发下的请求合并与多级缓存，保护下游资源。

### AC 验收标准（初稿）

1. **WHEN** 100 个并发请求同一个失效的缓存 Key **THEN** 系统 **SHALL** 仅调用一次业务逻辑函数，且 100 个请求均获得正确结果。
2. **IF** 业务逻辑函数返回 Error **THEN** Singleflight **SHALL** 将该 Error 广播给所有等待者，且不缓存该错误结果（除非显式配置）。
3. **IF** 本地缓存开启 **THEN** 命中本地缓存的请求 **SHALL** 在 1ms 内返回，不请求 Redis。
