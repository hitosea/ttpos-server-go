## 🎯 背景和动机

### 问题描述

当前 Main 模块没有对外暴露可复用的 gRPC 能力来为 GrabFood 渠道创建自助点餐（SelfServeJourney）链接，调用方需要自行拼装 HTTP 请求至 GrabFood API，存在认证、超时和错误映射不统一的问题，无法沉淀监控和重试策略。

### 业务价值

- 提供统一、可监控的 GrabFood CreateSelfServeJourney 服务，降低对接成本
- 支持各终端快速获取自助点餐链接，加快渠道上线和迭代
- 统一鉴权与错误处理，减少集成风险并提升稳定性

## 💡 解决方案概述

### 方案描述

在 Main 模块新增 gRPC 服务 `CreateSelfServeJourney`，由内部调用 `grabfood-api` 的 `CreateSelfServeJourneyAPIService` 完成 GrabFood 自助点餐链接创建，并将生成的链接和元数据返回调用方。环境（沙箱/生产）由 takeout 模块既有渠道配置自动决定，调用方无需传入；服务层统一处理签名、凭证、超时与错误码映射，输出统一的响应结构与日志指标。

### 核心功能点

1. 定义并实现 gRPC 接口 `CreateSelfServeJourney`（请求包含门店/品牌标识、渠道配置、回调参数等；响应返回链接、过期时间、trace_id）。
2. 封装调用 `CreateSelfServeJourneyAPIService` 的适配层，包含凭证管理、签名、环境选择、超时与重试（幂等约束）。
3. 统一错误码与错误信息映射（网络超时、授权失败、Grab API 业务错误），附带 trace_id/请求体用于排查。
4. 监控与日志：记录调用耗时、成功率、错误分布；暴露核心指标供告警。
5. 配置与安全：通过配置中心/环境变量维护 Grab 凭证、host、超时，避免硬编码，支持按渠道/门店隔离。

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [ ] **中**：需要前后端联调，基础业务逻辑
- [x] **高**：涉及架构调整、第三方集成、复杂算法

### 工作量预估

- **预计天数**: 3 天
- **预估 SP**: 5（待技术评审确认）

### 风险识别

**潜在风险**：
1. GrabFood API 不可用或响应异常导致服务不可用。
2. 凭证/签名配置错误导致授权失败。
3. 重试策略不当可能触发非幂等重复创建。

**缓解措施**：
1. 设置合理超时与熔断，提供降级提示并记录 trace_id。
2. 配置校验与启动自检，密钥集中管理，分环境隔离。
3. 仅对超时/可重试错误启用带幂等键的重试；对非幂等错误直接返回。

## 📝 附录

### User Story（初稿）

**作为** 使用 Grab 渠道自助点餐的顾客/运营方  
**我想** 通过系统一键生成 Grab 自助点餐链接  
**以便于** 在扫码端/营销渠道快速分发，减少人工配置

### AC 验收标准（初稿）

1. **WHEN** 提供有效的门店/品牌标识和合法凭证调用 gRPC `CreateSelfServeJourney` **THEN** 系统返回可访问的自助点餐链接及有效期。
2. **IF** GrabFood API 返回错误或超时 **THEN** 系统返回明确的错误码与错误信息（含 trace_id），并记录日志/指标；不产生重复创建。
