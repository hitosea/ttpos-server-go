## 🎯 背景和动机

### 问题描述

当前 `SaleBill` (销售账单) 和 `SaleOrder` (销售订单) 模型承载了过多的业务逻辑，包括但不限于：
1. **会员积分计算** (`CalcMemberPoint` 等方法直接耦合在 Model 中)
2. **ERP 库存与成本计算** (`GetErpProductBomMaterials`, `flavorUseCard` 等)
3. **退款与反结账逻辑** (`NewReturnOrder` 包含复杂的退款分摊逻辑)
4. **打印与设备交互** (部分字段专门服务于打印)

这种“上帝对象”模式导致：
- **维护困难**：修改任何一个业务逻辑都可能影响订单核心稳定性。
- **复用性差**：难以在非餐饮场景（如单纯的零售或商城）复用订单核心能力。
- **测试困难**：单元测试需要模拟大量的业务上下文才能测试基础的订单状态流转。
- **性能隐患**：大对象在内存中占用高，且加载了过多不必要的关联数据。

### 业务价值

- **提升架构可维护性**：将“订单核心状态管理”与“业务规则计算”分离，降低系统耦合度。
- **支持业务快速扩展**：为未来可能的新业务线（如纯外卖、商城、第三方对接）提供干净的订单底座。
- **增强系统稳定性**：核心订单模块变更频率降低，业务层变更不会意外破坏订单数据完整性。
- **无痛迁移**：通过“另起炉灶”的方式，不影响现有业务的稳定性，逐步实现架构演进。

## 💡 解决方案概述

### 方案描述

采用 **绞杀榕模式 (Strangler Fig Pattern)**，在不改动现有 `main/app/model` 业务实现的前提下，另起炉灶新建一个独立的 **Order Core Module**。

该模块将：
1.  **共用数据库表**: 复用现有的 `sale_bill`, `sale_order`, `sale_order_product` 等表结构，但定义全新的、轻量级的 Struct。
2.  **纯净的数据操作**: 新模块仅包含数据的 CRUD 和基础状态流转（如 `Pending -> Paid`），绝不包含“积分计算”、“库存扣减”等业务逻辑。
3.  **共存与渐进**: 旧业务继续使用旧 Model，新业务（或重构后的模块）使用新 Module。未来通过 Facade 层逐步将旧逻辑迁移到新架构上。

### 架构分层

1.  **Legacy Layer (旧业务层)**:
    *   维持现状，使用 `main/app/model/sale_order.go`。
    *   不进行破坏性重构，确保现有业务 0 风险。

2.  **New Order Core Module (新核心层)**:
    *   位置: `modules/order_core/` (建议)
    *   Structs: `CoreSaleOrder`, `CoreSaleBill` (仅包含数据库字段映射，无业务方法)。
    *   Service: 提供纯粹的 `Create`, `UpdateStatus`, `GetDetail` 接口。
    *   Events: 发布 `OrderCreated`, `OrderPaid` 等领域事件。

3.  **New Business Services (新业务适配层)**:
    *   订阅核心层的事件，执行业务逻辑。
    *   示例: `LoyaltyService` 监听 `OrderPaid` 事件 -> 计算积分。

### 核心功能点

1.  **独立模块构建**: 在 `modules/` 下新建 `order_core`，重新定义 PO (Persistent Object)。
2.  **状态机实现**: 在新模块中实现严格的订单状态机，防止非法状态流转。
3.  **事件驱动机制**: 引入 Event Bus，将订单状态变更通知给业务模块。
4.  **双写/读适配 (可选)**: 在过渡期，如果新旧模块同时操作数据，需设计并发锁或版本控制机制（Optimistic Locking）。

## 📊 初步评估

### 技术复杂度

- [ ] **低**：纯 UI 调整，无业务逻辑变更
- [x] **中**：需要新建模块和映射，但无需修改旧逻辑，风险可控
- [ ] **高**：涉及架构调整、第三方集成、复杂算法

### 工作量预估

- **预计天数**: 5 天 (核心模块搭建 + 基础单元测试)
- **预估 SP**: 8 (不含旧业务迁移)

### 风险识别

**潜在风险**：
1.  **数据一致性**: 新旧模块共用数据库表，如果同时操作同一行记录，可能导致数据覆盖。
    *   *缓解*: 引入乐观锁 (`version` 字段)；明确新旧模块的职责边界（例如：旧模块管收银，新模块管外卖，互不干扰）。
2.  **代码冗余**: 短期内会有两套 Order Structs。
    *   *缓解*: 接受短期冗余以换取长期解耦；制定明确的废弃计划。

**缓解措施**：
1.  **领域划分**: 初期仅在新业务（如对接新的第三方外卖平台）中使用新模块。
2.  **只读访问**: 对于旧业务产生的数据，新模块初期可以只提供“只读”能力，用于报表或查询，验证模型正确性。
