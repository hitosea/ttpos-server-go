# TTPOS 后端服务治理方案 - 总览

> **项目背景**：从50商户扩展到500商户，解决耦合、性能、维护问题
> 
> **治理目标**：提升开发效率，支持500商户稳定运行
> 
> **完成时间**：2025-11-XX

---

## 🎯 核心目标

### 开发效率提升
```
当前：新功能开发2-3周，5个后端协作困难
目标：新功能开发3-5天，并行高效协作
提升：2-3倍开发效率
```

### 支持500商户扩展
```
当前：50商户，500商户压测失败
目标：稳定支持500商户并发
扩展：可扩展到1000商户
```

### 运维效率提升
```
当前：故障排查>30分钟
目标：故障定位<5分钟
提升：链路追踪+监控告警
```

---

## 🔴 关键问题（P0必须解决）

### 1. Main服务耦合严重
```
• order.go 14K行，难以维护
• 服务循环依赖（Material ↔ Warehouse）
• 新功能影响全局，开发效率低
```

### 2. 数据库连接数爆炸
```
• 500商户 = 5000连接
• 数据库压力大，扩展受限
```

### 3. 故障排查困难
```
• 无链路追踪系统
• 故障定位>30分钟
• 无法快速定位性能瓶颈
```

### 4. 事件丢失风险
```
• 内存事件总线，进程重启丢失
• 无法支持异步解耦
```

---

## ✅ 治理方案（简洁版）

### 问题1：Main服务模块化重构
```
方案：DDD领域建模
• 拆分订单、商品、会员、库存、支付等域
• 解耦服务依赖
• CQRS模式

预期：开发效率提升2-3倍
```

### 问题2：连接池优化（不改架构）
```
方案：优化连接参数 + 延迟初始化
• MaxOpen: 3-5, MaxIdle: 1-2
• 按需创建连接
• 连接监控

预期：连接数降至2000-2500
保持：独立数据库（便于数据迁移）
```

### 问题3：链路追踪系统
```
方案：OpenTelemetry + Jaeger
• 关键路径埋点
• 全链路可视化

预期：故障定位<5分钟
```

### 问题4：引入RabbitMQ
```
方案：替换内存事件总线
• 事件持久化
• 支持异步消费

预期：事件不丢失
```

### 问题5：监控告警（P1）
```
方案：Prometheus + Grafana
• 关键指标监控
• 自动告警
```

---

## 🚫 明确不做的事

```
✗ BMP-ERP重构
  理由：架构合理，TTPOS定位为"餐饮+ERP一体化"
  
✗ 自建进销存
  理由：有ERPNext提供专业能力
  
✗ 改为共享表+TenantID
  理由：数据迁移复杂度高，保持独立数据库
  
✗ 离线收银能力（暂缓）
  理由：客户暂无痛点，优先级P2
```

---

## ⏰ 实施路线（6个月）

```
第1-2月：基础设施 + 模块化POC（并行）
├─ 链路追踪、RabbitMQ、连接池优化
└─ 订单/商品/会员域POC

第3-4月：Main服务全面模块化重构
└─ 基于POC经验，重构主要业务模块

第5月：监控告警 + 性能优化
└─ Prometheus、N+1优化、缓存

第6月：API网关 + 收尾
└─ 网关部署、文档、培训
```

详见：[07-实施路线图.md](./07-实施路线图.md)
