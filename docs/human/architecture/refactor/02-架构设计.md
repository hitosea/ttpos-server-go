## 二、DDD领域建模

### 2.1 限界上下文识别

**核心域（Core Domain）- 保留在Main**
- 商品域（Product Context）
- 订单域（Order Context）
- 库存域（Inventory Context）
- 收银域（Cashier Context）
- 桌台域（Desk Context）

**支撑域（Supporting Domain）- 保留在Main**
- 会员域（Member Context）
- 支付域（Payment Context）
- 促销域（Marketing Context）

**通用域（Generic Domain）- 微服务化**
- 鉴权服务（Auth Service）
- 消息服务（Message Service）
- 统计服务（Analytics Service）
- 短信服务（SMS Service）
- 外卖服务（Takeout Service）
- ERP服务（ERP Service）
- 结算服务（Settlement Service）

### 2.2 核心域详细设计

#### 商品域（Product Context）

**聚合根：Product**
```
Product（商品）
├── 标识：ProductUuid, CompanyUuid
├── 基本信息：Name, Price, CostPrice
├── 业务属性：Type, Status
├── 规格属性：Specs[], Attributes[]
├── 套餐相关：PackageGroups[]
└── 库存关联：InventoryUuid

实体：
• Category（分类）
• Spec（规格）

值对象：
• Price（价格）
• Attribute（属性）

领域服务：
• IProductDomainService
  - CreateProduct()
  - CalculatePrice()
  - CheckAvailability()

仓储接口：
• IProductRepo
  - Save()
  - FindByUuid()
  - FindByCategoryUuid()
```

#### 订单域（Order Context）

**聚合根：Order**
```
Order（订单）
├── 标识：OrderUuid, SaleBillUuid, CompanyUuid
├── 订单类型：Type, Source
├── 订单项：Items[] (OrderItem实体)
├── 金额信息：Amount (值对象)
├── 状态流转：Status, StatusHistory[]
├── 关联信息：DeskUuid, MemberUuid
└── 业务属性：Population, Remark

实体：
• OrderItem（订单项）

值对象：
• OrderAmount（订单金额）
  - OriginalAmount
  - DiscountAmount
  - ServiceCharge
  - FinalAmount

领域事件：
• OrderCreatedEvent
• OrderPaidEvent
• OrderCancelledEvent

领域服务：
• IOrderDomainService
  - CreateOrder()
  - CalculateAmount()
  - ChangeStatus()
  - CancelOrder()
```

#### 库存域（Inventory Context）

**聚合根：Inventory**
```
Inventory（库存）
├── 标识：InventoryUuid, CompanyUuid
├── 关联：ProductUuid, WarehouseUuid
├── 库存数量：Quantity (值对象)
├── 库存策略：Strategy, AlertThreshold
└── 预占机制：Reservations[]

实体：
• Reservation（预占记录）

值对象：
• InventoryQuantity
  - Available（可用库存）
  - Reserved（预占库存）
  - Total（总库存）

领域服务：
• IInventoryDomainService
  - Reserve()      (预占)
  - Confirm()      (确认扣减)
  - Release()      (释放预占)
  - Rollback()     (回滚)
```

#### 收银域（Cashier Context）

**聚合根：SaleBill**
```
SaleBill（销售账单）
├── 标识：SaleBillUuid, CompanyUuid
├── 账单类型：Type, Source
├── 包含订单：Orders[] (OrderUuid列表)
├── 账单金额：Amount
├── 结账信息：PaymentRecords[] (实体)
├── 状态：Status
├── 关联：DeskUuid, MemberUuid
└── 时间：OpenTime, SettleTime

实体：
• PaymentRecord（支付记录）
  - PaymentUuid
  - PaymentMethod
  - Amount
  - TransactionId

领域服务：
• ICashierDomainService
  - CreateBill()
  - Settle()
  - ReverseSettle()
```

#### 桌台域（Desk Context）

**聚合根：Desk**
```
Desk（桌台）
├── 标识：DeskUuid, CompanyUuid
├── 桌台信息：Name, AreaUuid, Capacity
├── 状态：Status (空闲/占用/清洁/维护)
├── 当前账单：CurrentSaleBillUuid
├── 开台信息：OpenTime, Population
└── 桌台属性：Type, QRCode

领域服务：
• IDeskDomainService
  - OpenDesk()      (开台)
  - ChangeDesk()    (换台)
  - MergeDesks()    (并台)
  - CloseDesk()     (清台)
```

### 2.3 领域间依赖关系

```
依赖规则（单向依赖）：

订单域 → 商品域（查询商品信息）
订单域 → 库存域（扣减库存）
订单域 → 会员域（查询会员折扣）
收银域 → 订单域（聚合订单）
桌台域 → 收银域（创建账单）

禁止：
✗ 商品域 → 订单域（逆向依赖）
✗ 库存域 → 订单域（逆向依赖）
```

### 3.2 依赖注入改造

**Before（问题）：**
```go
type orderSrv struct {
    dbm        *database.DBManager
    memberSrv  *memberSrv         // 直接依赖实现
    productSrv *productSrv        // 直接依赖实现
}
```

**After（正确）：**
```go
type OrderCommandHandler struct {
    // 领域服务（接口依赖）
    orderDomainSrv  domain.IOrderDomainService
    
    // 仓储（接口依赖）
    orderRepo       domain.IOrderRepo
    productRepo     domain.IProductRepo
    
    // 外部服务（接口依赖）
    inventorySrv    domain.IInventoryDomainService
    memberSrv       domain.IMemberDomainService
    
    // 事件发布器
    eventPublisher  event.IEventPublisher
}
```

### 3.3 CQRS模式应用

**命令（Command）- 写操作：**
```go
// 创建订单命令
type CreateOrderCommand struct {
    CompanyUuid  uint64
    ProductItems []OrderItemDTO
    MemberUuid   uint64
    DeskUuid     uint64
}

// 命令处理器
type CreateOrderHandler struct {
    orderDomainSrv domain.IOrderDomainService
    orderRepo      domain.IOrderRepo
    eventPublisher event.IEventPublisher
}

func (h *CreateOrderHandler) Handle(ctx context.Context, cmd CreateOrderCommand) error {
    // 1. 领域验证
    // 2. 创建订单
    // 3. 持久化
    // 4. 发布事件
}
```

**查询（Query）- 读操作：**
```go

type ListOrdersQuery struct {
    CompanyUuid uint64

type ListOrdersHandler struct {
    db    *gorm.DB
    cache cache.Cache
}

func (h *ListOrdersHandler) Handle(ctx context.Context, query ListOrdersQuery) (*OrderListResp, error) {
    // 1. 查询缓存
    // 2. 查询数据库
    // 3. 组装DTO
```

## 四、服务通信设计

### 4.1 通信方式选择

| 场景 | 通信方式 | 理由 |
|------|---------|------|
| **Main内部模块** | 直接函数调用 | 同进程，无网络开销 |
| **Main → 微服务（同步）** | gRPC | 需要立即返回结果 |
| **Main → 微服务（异步）** | RabbitMQ事件 | 解耦、容错、削峰 |
| **微服务 → 微服务** | 事件驱动为主 | 松耦合、可独立部署 |
| **前端 → Main** | HTTP/JSON | 前端统一接口 |

### 4.2 事件驱动架构

**事件定义规范：**
```go
// 事件结构
type DomainEvent struct {
    EventId     string                 // 事件ID
    EventType   string                 // 事件类型：domain.aggregate.action
    Timestamp   int64                  // 时间戳
    Version     string                 // 事件版本
    Payload     interface{}            // 事件数据
    Metadata    map[string]interface{} // 元数据（traceId等）
}

// 事件命名规范
order.created.v1
order.paid.v1
order.cancelled.v1
product.updated.v1
```

**事件发布与订阅：**
```
┌──────────┐                  ┌──────────────┐
│   Main   │──Publish Event──▶│  RabbitMQ    │
└──────────┘                  │  Event Bus   │
                               └──────┬───────┘
                                      │ Subscribe
                        ┌─────────────┼─────────────┐
                        │             │             │
                   ┌────▼───┐    ┌───▼────┐   ┌───▼────┐
                   │Analytics│    │Message │   │Settlement│
                   │ Service │    │Service │   │  Service  │
                   └─────────┘    └────────┘   └──────────┘
```

## 五、关键技术决策

### 5.1 为什么核心业务保持单体？

**优势：**
```
1. 事务一致性
   - 订单+库存+支付 在同一事务
   - ACID保证
   - 无分布式事务复杂性

2. 性能优越
   - 无网络开销
   - 无序列化/反序列化
   - 本地调用<1ms

3. 开发效率高
   - 统一代码库
   - 易于重构
   - 调试方便

4. 部署简单
   - 单进程部署
   - 无服务间依赖
   - 回滚简单
```

**劣势（可控）：**
```
1. 扩展受限
   - 只能垂直扩展（加机器配置）
   - 解决：餐饮业务特点，单体足够（QPS<10000）

2. 技术栈统一
   - 必须使用Go
   - 解决：团队已统一Go，非问题

3. 部署粒度大
   - 修改一个功能需要重启整个服务
   - 解决：灰度发布、蓝绿部署
```

### 5.2 为什么增值服务微服务化？

**适合微服务的特征：**
```
1. 业务边界清晰
   - 鉴权、消息、统计、短信
   - 功能独立，不依赖其他服务

2. 变更频率高
   - 需要独立迭代
   - 不影响核心业务

3. 技术栈差异
   - 统计服务适合Python
   - 报表服务适合Python
   - 核心业务用Go

4. 扩展需求不同
   - 消息服务需要高并发
   - 统计服务需要大数据处理
   - 可独立扩展
```

### 5.3 关于多语言微服务

**允许但需谨慎：**

**✅ 推荐场景：**
- 统计服务：Python（数据分析优势）
- 报表服务：Python（Pandas/NumPy）
- 企业对接：Java（Spring生态）

**⚠️ 必须统一的规范：**
1. 通信协议：gRPC + Protobuf
2. 链路追踪：OpenTelemetry
3. 日志格式：JSON结构化
4. 监控指标：Prometheus
5. 配置管理：Nacos
6. 错误码：统一体系
7. 鉴权：JWT + OAuth2.0

**🎯 实施策略：**
```
阶段1（当前-6个月）：
• 统一Go，建立标准

阶段2（6-12个月）：
• 统计/报表可尝试Python
• 前提：治理规范完善

阶段3（12个月后）：
• 按需选择语言
• 评估维护成本
```
