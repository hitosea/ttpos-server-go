# 03 - 微服务拆分方案

> **目标**：明确微服务拆分策略和服务设计
> 
> **原则**：增值服务微服务化，核心业务保持模块化单体

---

## 一、微服务拆分策略

### 1.1 拆分原则

**适合拆分为微服务的特征：**
```
✓ 业务边界清晰
✓ 功能相对独立
✓ 变更频率高（需要快速迭代）
✓ 技术栈有特殊需求
✓ 扩展需求不同
✓ 团队可以独立负责
```

**不适合拆分的特征：**
```
✗ 强事务依赖
✗ 高频同步调用
✗ 数据高度耦合
✗ 团队无法独立维护
```

### 1.2 拆分决策矩阵

| 服务 | 边界清晰 | 独立性 | 变更频率 | 技术栈 | 扩展需求 | 结论 |
|------|---------|-------|---------|--------|---------|------|
| 商品管理 | ⚠️ | ❌ | 低 | Go | 低 | **保留Main** |
| 订单管理 | ⚠️ | ❌ | 中 | Go | 中 | **保留Main** |
| 库存管理 | ⚠️ | ❌ | 中 | Go | 中 | **保留Main** |
| 鉴权服务 | ✅ | ✅ | 低 | Go | 中 | **微服务** |
| 消息服务 | ✅ | ✅ | 中 | Go | 高 | **微服务** |
| 统计服务 | ✅ | ✅ | 高 | Python | 高 | **微服务** |
| 外卖服务 | ✅ | ✅ | 中 | Go | 中 | **微服务（保留）** |
| 短信服务 | ✅ | ✅ | 低 | Go | 低 | **微服务** |
| 结算服务 | ✅ | ✅ | 中 | Go/Java | 中 | **微服务** |

## 二、微服务详细设计

### 2.1 鉴权服务（Auth Service）

**职责边界：**
```
• JWT生成与验证
• 权限管理（RBAC）
• SSO单点登录
• 密码加密/验证
• Token刷新
• 登录日志
```

**技术选型：**
```
语言：Go
框架：Gin + gRPC
存储：Redis（Token黑名单）+ MySQL（用户权限）
缓存：Redis（权限缓存）
```

**API设计（简化）：**
```protobuf
service AuthService {
    rpc Login(LoginRequest) returns (LoginResponse);
    rpc Logout(LogoutRequest) returns (LogoutResponse);
    rpc ValidateToken(TokenRequest) returns (TokenResponse);
    rpc CheckPermission(PermissionRequest) returns (PermissionResponse);
    rpc RefreshToken(RefreshTokenRequest) returns (RefreshTokenResponse);
}
```

**与Main交互：**
```
Main → Auth Service: 
  - 验证Token（每个请求，通过API网关）
  - 检查权限（关键操作）

Auth Service → Main:
  - 推送权限变更事件（异步）
```

**性能要求：**
```
QPS: >10000
P99延迟: <10ms
可用性: 99.9%
```

### 2.2 消息服务（Message Service）

**职责边界：**
```
• WebSocket消息推送
• 站内消息
• 邮件发送（对接第三方）
• 短信发送（对接第三方）
• 消息模板管理
• 消息历史记录
```

**技术选型：**
```
语言：Go
框架：gRPC + WebSocket
队列：RabbitMQ（保证可靠性）
存储：MongoDB（消息历史）
```

**API设计（简化）：**
```protobuf
service MessageService {
    rpc SendMessage(SendMessageRequest) returns (SendMessageResponse);
    rpc SendBatch(BatchMessageRequest) returns (BatchMessageResponse);
    rpc GetMessageList(GetMessageRequest) returns (MessageListResponse);
    rpc MarkAsRead(MarkAsReadRequest) returns (MarkAsReadResponse);
}
```

**与Main交互：**
```
Main → RabbitMQ → Message Service
（异步解耦，Main不依赖Message Service可用性）

事件：
• order.created → 发送订单创建通知
• order.paid → 发送支付成功通知
• desk.opened → 推送开台消息到厨房端
```

**可靠性保证：**
```
1. 消息持久化（RabbitMQ）
2. 消费失败自动重试（3次）
3. 死信队列处理
4. 消息去重（MessageId）
```

### 2.3 统计服务（Analytics Service）

**职责边界：**
```
• 实时统计（今日销售额、订单量）
• 离线统计（日/周/月报表）
• 数据分析（销售趋势、商品排名）
• 自定义报表
• 数据导出（Excel/CSV）
```

**技术选型：**
```
语言：Python（数据处理优势）或 Go
框架：gRPC
存储：
  - ClickHouse（时序数据、OLAP）
  - Redis（实时统计缓存）
  - MySQL（报表配置）
任务：Celery（Python）/ Go Cron
```

**数据流：**
```
Main → Event Bus → Analytics Service
         ↓
    ClickHouse 存储
         ↓
    定时聚合任务
         ↓
    缓存到 Redis
         ↓
    API 查询返回
```

**API设计（简化）：**
```protobuf
service AnalyticsService {
    rpc GetRealtimeStats(RealtimeStatsRequest) returns (StatsResponse);
    rpc GetHistoricalStats(HistoricalStatsRequest) returns (StatsResponse);
    rpc ExportReport(ExportRequest) returns (ExportResponse);
    rpc CreateCustomReport(CustomReportRequest) returns (ReportResponse);
}
```

**性能优化：**
```
1. 实时统计走Redis缓存（<10ms）
2. 历史统计走ClickHouse预聚合（<100ms）
3. 复杂报表异步生成，轮询查询结果
```

### 2.4 外卖服务（Takeout Service）

**职责边界：**
```
• 对接外卖平台（Skootar、Grab、Lineman）
• 外卖订单同步
• 骑手调度
• 配送状态跟踪
• 配送费计算
```

**现状：**
```
✅ 已在BMP实现（ttpos-takeout）
✅ 功能相对完善
✅ 运行稳定

建议：保持独立，不需要迁移
```

**优化建议：**
```
1. 与Main的交互改为事件驱动
   - Main创建外卖订单 → 发布事件
   - Takeout Service订阅事件 → 调用外卖平台API

2. 增加重试机制和熔断保护
3. 增加外卖平台的适配器模式（易扩展新平台）
```

### 2.5 ERP服务（ERP Service）

**职责边界：**
```
• 对接ERP系统（ERPNext）
• 采购单同步
• 库存同步
• 销售单同步
• 财务对账
```

**现状：**
```
✅ 已在BMP实现（ttpos-erp）
⚠️ Main强依赖（同步调用）

问题：
• Main创建采购单需要同步调用ERP
• 延迟增加80-200ms
• ERP故障影响Main
```

**迁移建议（详见05-BMP迁移.md）：**
```
核心功能（库存同步、采购单）→ 迁移到Main
非核心功能（财务对账）→ 保持微服务

理由：
1. 库存同步是核心流程，需要事务一致性
2. 迁移后延迟降低90%（200ms → 20ms）
3. 减少网络故障风险
```

### 2.6 结算服务（Settlement Service）

**职责边界（新增）：**
```
• 对账管理
• 分账管理（多商户）
• 财务报表生成
• 发票管理
• 资金流水
```

**技术选型：**
```
语言：Go 或 Java（企业级）
框架：gRPC
存储：
  - MySQL（主数据）
  - MongoDB（账单明细）
  - Redis（缓存）
```

**拆分理由：**
```
1. 财务逻辑复杂，需要独立演进
2. 需要高可靠性（金融级事务）
3. 可能需要符合金融合规要求
4. 团队可以独立负责
```

### 2.7 短信服务（SMS Service）

**职责边界：**
```
• 短信发送（对接第三方）
• 验证码管理
• 短信模板管理
• 发送历史记录
• 短信余额管理
```

**技术选型：**
```
语言：Go
框架：gRPC
队列：RabbitMQ
存储：MySQL
缓存：Redis（验证码、频率限制）
```

**可靠性保证：**
```
1. 队列异步发送（不影响主流程）
2. 失败自动重试
3. 多短信平台轮询（容灾）
4. 频率限制（防止滥用）
```

## 三、服务通信模式

### 3.1 同步调用（gRPC）

**适用场景：**
```
• 需要立即返回结果
• 关键业务流程
• 查询操作

示例：
• Main → Auth Service: 验证Token
• Main → Auth Service: 检查权限
```

**最佳实践：**
```go
// 1. 连接池复用
var clientPool *AuthClientPool

func GetAuthClient() AuthServiceClient {
    return clientPool.Get()
}

// 2. 超时控制
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()

// 3. 熔断保护
breaker := gobreaker.NewCircuitBreaker(settings)
result, err := breaker.Execute(func() (interface{}, error) {
    return authClient.ValidateToken(ctx, req)
})

// 4. 降级策略
if err != nil {
    // 降级：使用本地缓存的权限信息
    return cachedPermissions, nil
}
```

### 3.2 异步调用（消息队列）

**适用场景：**
```
• 不需要立即返回结果
• 可容忍延迟
• 需要削峰填谷
• 需要解耦

示例：
• Main → Message Service: 发送通知
• Main → Analytics Service: 统计数据
• Main → Settlement Service: 生成账单
```

**事件驱动模式：**
```
Publisher（Main）
    ↓ Publish Event
RabbitMQ Exchange
    ↓ Route
Queue 1 → Consumer (Message Service)
Queue 2 → Consumer (Analytics Service)
Queue 3 → Consumer (Settlement Service)
```

**事件定义：**
```go
type DomainEvent struct {
    EventId     string      // UUID
    EventType   string      // order.created.v1
    Timestamp   int64       // Unix timestamp
    Version     string      // v1.0
    Payload     interface{} // 事件数据
    Metadata    Metadata    // TraceId, UserId等
}

// 事件命名规范
order.created.v1      (订单创建)
order.paid.v1         (订单支付)
order.cancelled.v1    (订单取消)
product.updated.v1    (商品更新)
inventory.changed.v1  (库存变更)
```

## 四、服务治理

### 4.1 服务注册与发现

**方案：Nacos**
```
优势：
• 已在使用，团队熟悉
• 支持配置管理
• 支持健康检查
• 国内社区活跃

配置：
• 服务自动注册
• 健康检查间隔：5秒
• 实例权重配置（灰度发布）
```

### 4.2 负载均衡

**策略：**
```
1. 客户端负载均衡（gRPC）
   - 轮询（RoundRobin）
   - 加权轮询（Weighted）
   - 一致性哈希（根据CompanyUuid）

2. 服务端负载均衡（HTTP）
   - API网关（APISIX）
   - 支持多种算法
```

### 4.3 熔断与降级

**熔断策略：**
```
开启条件：
• 连续失败3次
• 错误率>50%（10秒内）

熔断后：
• 快速失败（不再请求）
• 定期探测（半开状态）
• 恢复后自动闭合

降级策略：
• 返回默认值
• 返回缓存数据
• 返回友好错误提示
```

### 4.4 限流

**限流维度：**
```
1. 全局限流
   - API网关层
   - 总QPS限制：10000

2. 服务级限流
   - 每个服务设置独立限流
   - Auth Service: 10000 QPS
   - Message Service: 5000 QPS

3. 租户级限流
   - 根据company_uuid限流
   - 防止单个租户占用过多资源

4. 用户级限流
   - 根据user_id限流
   - 防止恶意请求
```

## 五、微服务开发规范

### 5.1 项目结构

```
{service-name}/
├── api/              # API定义（Proto）
│   └── v1/
│       └── service.proto
├── cmd/              # 启动入口
│   └── main.go
├── internal/         # 内部代码
│   ├── handler/      # gRPC Handler
│   ├── service/      # 业务逻辑
│   ├── repository/   # 数据访问
│   └── model/        # 数据模型
├── pkg/              # 可共享的包
│   ├── config/
│   ├── logger/
│   └── tracing/
├── go.mod
└── README.md
```

### 5.2 接口版本管理

**版本策略：**
```
1. URL版本
   /api/v1/auth/login
   /api/v2/auth/login

2. Proto版本
   package auth.v1;
   package auth.v2;

3. 向下兼容原则
   • 新增字段（可选）
   • 不删除字段
   • 不修改字段类型
   • 不修改字段含义

4. 废弃策略
   • 标记Deprecated
   • 保留至少6个月
   • 提前3个月通知
```

### 5.3 错误处理

**统一错误码：**
```go
// 错误码定义
const (
    SUCCESS           = 0
    PARAM_ERROR       = 1001
    AUTH_FAILED       = 1002
    PERMISSION_DENIED = 1003
    NOT_FOUND         = 1004
    INTERNAL_ERROR    = 9999
)

// 错误响应
type ErrorResponse struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Details string `json:"details,omitempty"`
    TraceId string `json:"trace_id"`
}
```

## 六、微服务部署策略

### 6.1 容器化

**Dockerfile示例：**
```dockerfile
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/service ./cmd

FROM alpine:latest
RUN apk --no-cache add ca-certificates
COPY --from=builder /app/service /service
ENTRYPOINT ["/service"]
```

### 6.2 服务编排

**docker-compose.yml（开发环境）：**
```yaml
version: '3.8'
services:
  auth-service:
    build: ./auth-service
    ports:
      - "50051:50051"
    environment:
      - DB_HOST=mysql
      - REDIS_HOST=redis
    depends_on:
      - mysql
      - redis
  
  message-service:
    build: ./message-service
    ports:
      - "50052:50052"
    environment:
      - RABBITMQ_URL=amqp://rabbitmq:5672
    depends_on:
      - rabbitmq
```

### 6.3 灰度发布

**策略：**
```
1. 蓝绿部署
   - 部署新版本（绿）
   - 切换流量到新版本
   - 保留旧版本（蓝）备份

2. 金丝雀发布
   - 10% 流量到新版本
   - 监控关键指标
   - 逐步增加到100%

3. A/B测试
   - 根据用户ID分流
   - 对比新旧版本效果
```
