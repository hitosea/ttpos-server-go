# 需求规格说明书 (SRS)

#### 1. 引言

##### 1.1 文档目的

本文档旨在详细描述 TTPOS 收银系统后端服务的软件需求规格。它将明确系统的功能和非功能需求，作为开发团队、测试团队以及项目相关方之间沟通和理解系统范围与目标的正式基础。本 SRS 将指导系统的设计、开发、测试和部署工作，确保最终产品满足业务需求并符合质量标准。

##### 1.2 范围

本 SRS 涵盖 TTPOS 收银系统后端服务的所有核心功能模块，包括但不限于收银管理、订单管理、商品管理、桌台管理、会员管理、支付处理、事件通知和系统级别的非功能性要求。系统旨在支持餐饮行业的日常运营，提供稳定、高效、安全的后端服务。

##### 1.3 读者对象

本 SRS 的主要读者包括：
*   **项目经理**：用于项目规划、进度跟踪和风险管理。
*   **开发工程师**：用于系统设计、编码和实现。
*   **测试工程师**：用于设计测试用例和执行系统测试。
*   **业务分析师**：用于验证需求与业务目标的一致性。
*   **质量保证人员**：用于确保系统满足质量标准。
*   **系统架构师**：用于指导技术选型和架构决策。

#### 2. 总体描述

##### 2.1 产品视角

TTPOS 收银系统后端服务是一个独立的业务应用，专注于为餐饮行业提供核心的收银和订单管理功能。它将作为一个强大的后端支持，与前端应用（收银端、H5 点餐端、厨房显示系统等）通过 RESTful API 进行交互。本项目不直接涉及用户界面，但其设计将充分考虑前端应用的数据和功能需求。

**系统上下文图**:

```mermaid
graph TD
    A[前端应用<br>(收银端/H5/厨房显示)] <--> B(TTPOS 后端服务)
    B <--> C[数据库<br>(MySQL/SQLite)]
    B <--> D[缓存服务<br>(Redis)]
    B <--> E[外部服务<br>(支付网关/短信服务/ERP/CRM)]
    B <--> F[Nacos<br>(服务发现/配置中心)]
    B <--> G[RocketMQ<br>(消息队列)]
```

*   **TTPOS 后端服务**: 本 SRS 的核心焦点，提供所有业务逻辑和数据处理能力。
*   **前端应用**: 接收用户输入并展示数据。
*   **数据库**: 存储所有业务数据，支持多租户。
*   **缓存服务**: 提高数据访问性能，用于存储临时数据和分布式锁。
*   **外部服务**: 与支付、短信、ERP、CRM 等第三方系统集成，扩展系统功能。
*   **Nacos**: 提供服务注册与发现、动态配置管理。
*   **RocketMQ**: 作为消息队列，支持异步通信和事件驱动架构。

##### 2.2 产品功能概述

TTPOS 后端服务将提供以下主要功能模块：

*   **用户与权限管理**: 提供员工登录、权限控制（基于角色和权限），确保系统操作的安全性。
*   **商品管理**: 支持商品信息的查询、分类管理，为点餐提供数据基础。
*   **桌台管理**: 支持桌台区域和类型管理、桌台状态管理（开台、清台、转台、合并桌台）、桌台订单创建与维护。
*   **点餐与订单管理**:
    *   **购物车操作**: 商品的添加、删除、数量修改、规格属性调整、备注。
    *   **订单创建与修改**: 创建销售账单、销售订单，支持订单商品改价、打折、抹零、赠菜、退菜、转菜、打包。
    *   **必点商品**: 确认必点商品机制。
    *   **订单检查**: 在结账前对订单进行全面检查，如库存、必点商品等。
    *   **订单状态流转**: 跟踪订单从创建到完成的各个阶段。
*   **厨房管理**: 支持商品送厨、分批送厨、菜品制作完成状态更新，与厨房打印和显示系统集成。
*   **会员管理**: 支持会员信息查询、会员优惠应用、会员积分抵扣、会员密码验证。
*   **支付与结账**:
    *   **账单生成**: 根据订单内容生成待支付账单。
    *   **支付方式**: 支持多种支付方式（如二维码支付），与外部支付网关集成。
    *   **优惠管理**: 优惠券、积分抵扣、会员折扣、改价、打折、抹零、免单等多种优惠机制。
    *   **支付单管理**: 创建、撤销支付单。
    *   **订单完结**: 完成支付后更新订单状态，进行后续处理。
*   **打印管理**: 支持小票、发票等各类单据的打印。
*   **日志与异常处理**: 记录系统日志，提供健壮的异常捕获机制，防止程序崩溃。
*   **系统配置**: 支持系统各项参数的配置。
*   **国际化**: 支持多语言显示，提供多语言资源管理。

##### 2.2.1 核心业务流程

TTPOS 系统支持餐饮行业的完整收银业务流程：

**餐厅就餐流程**：
1. **顾客入座**：顾客进入餐厅，选择座位，服务员为桌台开台
2. **点餐服务**：服务员记录顾客点餐需求，添加到桌台购物车
3. **订单确认**：确认购物车内容，生成正式订单并送厨制作
4. **厨房制作**：厨师接收订单，进行菜品制作和状态更新
5. **上菜服务**：服务员根据制作完成情况上菜
6. **结账支付**：顾客用餐完毕，收银员进行结账和收款

**自助点餐流程**：
1. **顾客扫码**：顾客通过手机扫描桌台二维码进入点餐界面
2. **自主点餐**：顾客浏览菜单，选择菜品和规格
3. **提交订单**：确认订单内容，提交到厨房制作
4. **支付结账**：用餐完毕，通过手机完成支付

##### 2.3 用户特征

本系统的主要用户角色及其特征包括：

*   **收银员 (Cashier)**：
    *   **职责**：负责日常的点餐、下单、结账、桌台管理、打印等操作。
    *   **特征**：需要快速、准确地完成操作，界面友好、流程清晰至关重要。需要处理各种异常情况，如退菜、改价、订单修改等。
*   **服务员 (Waiter/Waitress)**：
    *   **职责**：负责引导顾客、记录点餐、送菜、处理顾客需求等。
    *   **特征**：可能通过手持设备进行操作，需要实时查看桌台状态和订单详情。
*   **厨师 (Cook)**：
    *   **职责**：负责根据订单制作菜品。
    *   **特征**：需要接收清晰的送厨信息，更新菜品制作状态。
*   **店长/管理员 (Manager/Administrator)**：
    *   **职责**：负责系统配置、数据报表查看、权限管理、异常处理等。
    *   **特征**：需要系统的稳定性和数据准确性，关注运营数据和管理效率。
*   **顾客 (Customer)**：
    *   **职责**：通过 H5 端点餐、查看订单状态、支付。
    *   **特征**：对操作便捷性、响应速度、支付安全性有较高要求。

##### 2.4 约束

*   **业务约束**: 系统必须支持餐饮行业的标准化收银流程，包括桌台管理、点餐结账、会员管理等核心业务场景。
*   **技术约束**: 系统应采用现代Web技术栈，支持高并发访问和实时数据处理。
*   **数据库约束**: 支持关系型数据库，具备多租户数据隔离能力。
*   **缓存约束**: 提供高性能的缓存机制，支持分布式数据存储和并发控制。
*   **消息队列约束**: 支持异步消息处理和事件驱动架构。
*   **服务发现约束**: 支持微服务架构的服务注册与发现。
*   **性能约束**: 核心业务操作响应时间应控制在合理范围内，确保良好的用户体验。
*   **安全性约束**: 敏感数据必须加密存储和传输，系统应具备完善的权限控制机制。
*   **部署约束**: 支持容器化部署，可扩展至分布式集群环境。
*   **国际化约束**: 支持多语言环境，满足不同地区用户的使用需求。

##### 2.5 假设与依赖

*   **前端应用存在**: 假设存在与后端服务交互的收银端、H5 端和厨房显示系统等前端应用。
*   **外部服务可用**: 假设所集成的外部支付网关、短信服务、ERP/CRM 系统等是稳定可用的。
*   **网络连接**: 假设系统运行环境具备稳定可靠的网络连接。
*   **数据库可用**: 假设数据库服务稳定运行且可访问。
*   **基础设施就绪**: 假设 Docker、Redis、Nacos、RocketMQ 等基础设施已部署并配置正确。

#### 3. 功能需求

本节从业务角度描述 TTPOS 收银系统必须提供的核心功能。这些功能围绕餐饮收银的完整业务流程进行组织，确保系统能够满足餐厅日常运营的所有需求。

##### 3.1 用户认证与权限管理

系统应提供完整的员工身份认证和权限控制功能：

*   **员工登录认证**：员工通过工号和密码登录系统，系统验证身份并分配相应的操作权限。
*   **权限控制**：根据员工角色（收银员、服务员、厨师、管理员）控制其可访问的功能和数据。
*   **会话管理**：支持登录状态保持和安全登出，确保操作安全性。
*   **密码安全**：支持密码加密存储和定期更新要求。

##### 3.2 桌台管理

系统应提供完整的桌台生命周期管理功能：

*   **桌台信息管理**：维护桌台的基本信息，包括区域、类型、容量等。
*   **桌台状态管理**：
    *   空闲桌台可以开台使用
    *   占用桌台可以清台重置
    *   支持桌台转台操作（顾客换座位）
    *   支持桌台合并操作（多个桌台并为一张）
*   **桌台查询**：员工可以快速查询桌台状态和基本信息。

##### 3.3 商品与菜单管理

系统应支持商品信息的维护和查询：

*   **商品信息管理**：维护菜品、饮品等商品的基本信息、价格、分类。
*   **商品查询**：支持按分类、名称等条件查询商品信息。
*   **商品状态管理**：支持商品上架、下架、临时缺货等状态管理。
*   **规格属性管理**：商品可以有不同的规格（如大份、小份）和属性（如辣度、做法）。

##### 3.4 点餐与购物车管理

系统应支持完整的点餐流程：

*   **购物车操作**：
    *   为桌台创建和管理购物车
    *   添加商品到购物车，支持选择规格和数量
    *   修改购物车中的商品数量和规格
    *   从购物车移除商品
    *   添加商品备注和特殊要求
*   **订单预览**：查看购物车内容和总价，支持实时价格计算。

##### 3.5 订单管理

系统应提供完整的订单处理功能：

*   **订单创建**：从购物车生成正式订单，锁定商品和价格。
*   **订单修改**：
    *   添加商品到已有订单
    *   修改订单中商品的数量和规格
    *   删除订单中的商品项
    *   添加或修改订单备注
*   **订单状态管理**：跟踪订单从创建到完成的各个状态。
*   **订单拆分合并**：支持将一个订单拆分为多个，或将多个订单合并。
*   **订单取消**：在一定条件下允许取消订单。

##### 3.6 厨房管理

系统应支持厨房作业流程：

*   **送厨操作**：将订单发送到厨房开始制作。
*   **分批送厨**：支持分批次发送订单商品，便于厨房分阶段制作。
*   **制作状态跟踪**：记录菜品制作进度，通知前台。
*   **退菜处理**：支持退掉已发送到厨房的菜品。
*   **转菜操作**：支持将菜品从一个桌台订单转到另一个。

##### 3.7 结账与支付

系统应提供完整的结账支付功能：

*   **结账准备**：
    *   检查订单是否可以结账（库存、必点商品等）
    *   计算订单总价和各种优惠
    *   生成结账预览信息
*   **优惠应用**：
    *   支持多种优惠方式（打折、减价、抹零）
    *   支持优惠券使用
    *   支持会员积分抵扣
    *   支持整单优惠和单品优惠
*   **支付处理**：
    *   支持多种支付方式（现金、银行卡、移动支付）
    *   生成支付二维码
    *   处理支付结果和回调
    *   支持支付撤销和退款
*   **账单管理**：生成和打印消费账单，支持多种打印格式。

##### 3.8 会员管理

系统应提供会员服务功能：

*   **会员信息管理**：维护会员基本信息、等级、积分等。
*   **会员查询**：通过手机号、会员卡等查询会员信息。
*   **会员优惠**：应用会员专属折扣和积分优惠。
*   **积分管理**：消费时累积积分，结账时使用积分抵扣。
*   **会员验证**：消费时验证会员身份和密码。

##### 3.9 打印管理

系统应支持各类单据打印：

*   **小票打印**：打印消费小票，包含商品明细、总价、支付信息。
*   **发票打印**：支持发票开具和打印。
*   **厨房单打印**：打印送厨单据给厨房制作。
*   **交接班单打印**：打印收银员交接班记录。

##### 3.10 系统配置与管理

系统应提供基础的系统管理功能：

*   **系统设置**：配置餐厅基本信息、营业时间、支付参数等。
*   **员工管理**：管理员可以管理员工信息、角色和权限。
*   **数据统计**：提供基本的销售数据统计和报表。
*   **异常处理**：处理系统异常情况，如打印机故障、网络问题等。

#### 4. 非功能需求

本节描述了 TTPOS 收银系统后端服务必须满足的非功能性要求。这些要求关注系统如何执行其功能，而不是执行什么功能。

##### 4.1 性能需求

*   **NFR-PERF-001: 响应时间**：
    *   **NFR-PERF-001.1**: 大部分（90%）API 接口的本地响应时间应在 200 毫秒以内。
    *   **NFR-PERF-001.2**: 核心业务流程（如点餐、下单、结账）的关键步骤响应时间应更短，以提供流畅的用户体验。
*   **NFR-PERF-002: 并发处理能力**：
    *   **NFR-PERF-002.1**: 系统应能支持高并发请求，具体并发用户数和 TPS（Transactions Per Second）指标待定，需根据实际部署规模和业务峰值确定。
*   **NFR-PERF-003: 资源利用率**：
    *   **NFR-PERF-003.1**: 在正常负载下，CPU 利用率不应超过 70%。
    *   **NFR-PERF-003.2**: 内存利用率应控制在合理范围内，避免内存泄漏。

##### 4.2 安全性需求

*   **NFR-SEC-001: 身份认证与授权**：
    *   **NFR-SEC-001.1**: 所有敏感 API 接口必须进行身份认证，使用 JWT Token 进行鉴权。
    *   **NFR-SEC-001.2**: 系统应实现基于角色的访问控制 (RBAC)，确保用户只能访问其被授权的功能和数据。
    *   **NFR-SEC-001.3**: 提供 Token 刷新机制。
*   **NFR-SEC-002: 数据保护**：
    *   **NFR-SEC-002.1**: 敏感数据（如密码、支付信息）在存储时必须加密，并采用安全的传输协议（如 HTTPS/TLS）。
    *   **NFR-SEC-002.2**: 数据库访问权限应严格控制，遵循最小权限原则。
*   **NFR-SEC-003: 输入验证**：
    *   **NFR-SEC-003.1**: 所有来自用户的输入数据必须进行严格的验证和过滤，以防止 SQL 注入、XSS 等攻击。
*   **NFR-SEC-004: 错误信息处理**：
    *   **NFR-SEC-004.1**: 错误信息不应泄露敏感的系统内部实现细节。
*   **NFR-SEC-005: 防重放攻击**:
    *   **NFR-SEC-005.1**: 对于重要的接口，需要考虑防重放攻击机制。

##### 4.3 可用性需求

*   **NFR-AVAIL-001: 故障恢复**：
    *   **NFR-AVAIL-001.1**: 系统应具备在发生故障时快速恢复的能力。
    *   **NFR-AVAIL-001.2**: 采用异常捕获机制（如 Go 的 `recover`），防止程序因 `panic` 而崩溃掉线，保证服务的连续性。
    *   **NFR-AVAIL-001.3**: 定时任务和独立 Goroutine 应实现 `panic` 捕获，以隔离故障。
*   **NFR-AVAIL-002: 可靠性**：
    *   **NFR-AVAIL-002.1**: 系统应在 7x24 小时内保持稳定运行，SLA（Service Level Agreement）指标待定。
*   **NFR-AVAIL-003: 数据一致性**：
    *   **NFR-AVAIL-003.1**: 在高并发操作中，通过并发锁机制（如 Redsync 分布式锁）保证数据的一致性。

##### 4.4 可维护性需求

*   **NFR-MAINT-001: 代码可读性与规范**：
    *   **NFR-MAINT-001.1**: 代码应遵循 Go 开发规范与最佳实践，包括目录结构、命名规范、接口与实现命名、包导入顺序等。
    *   **NFR-MAINT-001.2**: 关键代码应有清晰的中文注释，解释业务逻辑和设计意图。
*   **NFR-MAINT-002: 模块化**：
    *   **NFR-MAINT-002.1**: 系统应采用模块化设计，降低模块间的耦合度，便于独立开发、测试和维护。
*   **NFR-MAINT-003: 日志记录**：
    *   **NFR-MAINT-003.1**: 系统应提供详细的日志记录功能，包括业务操作日志、错误日志、慢查询日志等，便于问题诊断和系统审计。
    *   **NFR-MAINT-003.2**: 日志级别应可配置。

##### 4.5 兼容性需求

*   **NFR-COMPAT-001: 数据库兼容性**：
    *   **NFR-COMPAT-001.1**: 主要支持 MySQL 数据库。
    *   **NFR-COMPAT-001.2**: 理论上可扩展支持 SQLite 等其他数据库类型（通过 `DBManager` 的设计）。
*   **NFR-COMPAT-002: 操作系统兼容性**：
    *   **NFR-COMPAT-002.1**: 应支持在 Linux 环境下部署运行，并通过 Docker 提供跨平台兼容性。

##### 4.6 国际化与本地化

*   **NFR-I18N-001: 多语言支持**：
    *   **NFR-I18N-001.1**: 系统应支持多语言，所有用户可见的文本信息（包括错误消息、提示信息）应通过国际化机制进行管理。
    *   **NFR-I18N-001.2**: 验证错误信息应支持国际化。

#### 5. 数据模型

本节从业务角度概述 TTPOS 收银系统涉及的核心数据实体及其关系，为系统功能设计提供数据基础。详细的技术实现方案将在数据库设计文档中定义。

##### 5.1 核心业务实体

TTPOS 系统围绕餐饮收银业务流程，包含以下主要业务实体：

*   **商家/公司 (Company)**：独立运营的餐饮企业，每个商家拥有独立的数据空间。
*   **员工 (Staff)**：餐厅工作人员，包括收银员、服务员、厨师、管理员等角色。
*   **商品 (Product)**：餐厅提供的菜品、饮品等可销售物品。
*   **桌台 (Desk)**：餐厅内的物理座位，支持开台、清台、转台等操作。
*   **购物车 (Cart)**：顾客临时选择的商品集合，支持添加、修改、删除操作。
*   **销售订单 (SaleOrder)**：顾客确认的订单记录，包含具体商品和数量。
*   **销售账单 (SaleBill)**：一次完整消费的结算记录，可能包含多个订单。
*   **会员 (Member)**：注册顾客信息，支持积分、优惠等会员服务。
*   **支付记录 (Payment)**：订单支付的详细记录，支持多种支付方式。

##### 5.2 业务关系模型

**核心业务流程关系**：

*   **商家运营关系**：
    *   一个商家拥有多名员工
    *   一个商家提供多种商品
    *   一个商家管理多个桌台

*   **消费流程关系**：
    *   顾客在桌台就餐，通过购物车选择商品
    *   购物车商品确认后形成销售订单
    *   多个销售订单可合并为一张销售账单
    *   销售账单通过支付完成结算

*   **服务关系**：
    *   会员可享受优惠折扣和积分服务
    *   员工负责处理订单和支付流程
    *   厨师接收订单进行菜品制作

##### 5.3 数据完整性要求

*   **多租户隔离**：不同商家的数据必须完全隔离，互不影响。
*   **业务一致性**：订单状态、支付状态、库存数据等关键业务数据必须保持一致性。
*   **审计追溯**：所有重要业务操作应记录操作日志，支持问题追溯和审计。
*   **数据持久性**：关键业务数据应具备完善的备份和恢复机制。

#### 6. 外部接口需求

本节描述了 TTPOS 收银系统后端服务与外部系统或组件之间的接口要求。

##### 6.1 用户界面 (UI)

*   **IRS-UI-001: RESTful API**：
    *   **IRS-UI-001.1**: 后端服务通过提供标准的 RESTful API 与前端应用（如收银端、H5 点餐端、厨房显示系统）进行通信。
    *   **IRS-UI-001.2**: API 遵循 `/api/v1/{module}/{resource}` 的 URL 命名规范（使用 snake_case）。
    *   **IRS-UI-001.3**: API 请求和响应数据格式为 JSON。
    *   **IRS-UI-001.4**: 统一响应格式，包含 `code`, `message`, `data` 字段，其中 `data` 字段不能返回 `null` 或数组。分页信息统一放在 `data.meta` 中。
*   **IRS-UI-002: WebSocket (可选/未来扩展)**：
    *   **IRS-UI-002.1**: 对于需要实时通信的场景（如厨房订单状态更新、呼叫通知），系统应考虑支持 WebSocket 接口。

##### 6.2 软件接口

*   **IRS-SW-001: 支付网关接口**：
    *   **IRS-SW-001.1**: 系统应提供与主流支付网关（如支付宝、微信支付、其他本地支付服务）集成的接口，支持二维码支付、刷卡支付等。
    *   **IRS-SW-001.2**: 支付接口应支持支付单的创建、查询、撤销和回调处理。
*   **IRS-SW-002: 短信服务接口**：
    *   **IRS-SW-002.1**: 系统应提供与短信服务提供商集成的接口，用于发送验证码、订单通知等短信。
*   **IRS-SW-003: ERP/CRM 系统接口**：
    *   **IRS-SW-003.1**: 系统可能需要与外部 ERP (Enterprise Resource Planning) 或 CRM (Customer Relationship Management) 系统集成，例如获取总部物品列表、同步会员信息等。
    *   **IRS-SW-003.2**: 接口的具体协议和数据格式需根据实际集成的外部系统而定。
*   **IRS-SW-004: Nacos 接口**：
    *   **IRS-SW-004.1**: 系统应与 Nacos 服务注册与发现中心集成，进行服务的注册、发现和配置管理。
*   **IRS-SW-005: RocketMQ 接口**：
    *   **IRS-SW-005.1**: 系统应与 RocketMQ 消息队列集成，通过发布和订阅消息实现异步通信和事件驱动架构。
*   **IRS-SW-006: 日志服务接口**：
    *   **IRS-SW-006.1**: 日志应输出到文件，并可配置与外部日志收集服务（如 ELK Stack）集成。

##### 6.3 硬件接口

*   **IRS-HW-001: 打印机接口**：
    *   **IRS-HW-001.1**: 系统应支持与各类热敏打印机、票据打印机集成，用于打印小票、发票、厨房订单等。
    *   **IRS-HW-001.2**: 打印功能应支持多种打印模板和格式。
*   **IRS-HW-002: 扫描枪/POS 机接口 (间接)**：
    *   **IRS-HW-002.1**: 虽然后端不直接与扫描枪等硬件交互，但其 API 设计应支持前端从这些设备获取数据（如商品条码、支付码）并发送给后端。

##### 6.4 通信接口

*   **IRS-COM-001: HTTP/HTTPS**：
    *   **IRS-COM-001.1**: 所有的客户端-服务器通信应通过 HTTP/HTTPS 协议进行，确保数据传输的安全性。
*   **IRS-COM-002: TCP/IP**:
    *   **IRS-COM-002.1**: 数据库连接、缓存服务连接等底层通信基于 TCP/IP 协议。

#### 7. 其他需求

##### 7.1 逆向工程

*   **ORS-RE-001: 防止逆向工程**：
    *   **ORS-RE-001.1**: 系统应采取措施防止或增加逆向工程的难度，特别是对于核心业务逻辑和安全算法。

##### 7.2 可移植性

*   **ORS-PORT-001: 跨平台部署**：
    *   **ORS-PORT-001.1**: 系统应具备良好的可移植性，能够轻松部署到不同的 Linux 环境中。
    *   **ORS-PORT-001.2**: 利用 Docker 技术进行容器化部署，简化环境配置和依赖管理。

##### 7.3 部署

*   **ORS-DEP-001: Docker 化部署**：
    *   **ORS-DEP-001.1**: 系统应提供 Dockerfile，支持基于 Docker 镜像的自动化部署。
    *   **ORS-DEP-001.2**: 部署过程应简化，支持脚本化部署，减少人工干预。
*   **ORS-DEP-002: 集群部署**：
    *   **ORS-DEP-002.1**: 系统应支持高可用的集群部署方案，包括数据库集群、Redis 集群、API 集群等。
    *   **ORS-DEP-002.2**: 具备水平扩展能力，以应对业务量增长。
